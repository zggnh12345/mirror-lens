## 0. 总目标与执行结论

3.5.25 是基于 3.5.24 的**修复版本**，不是新一轮功能扩展，也不是对 3.5.24 的架构重写。

本任务要解决的核心问题：

1. 清除旧 API 参数、旧配置入口、旧环境变量、字段映射、fallback 和其他兼容残留。
2. 将 Host 范围、能力判定和能力持久化收敛为唯一事实源。
3. 取消新增 Source 时不必要的“归属必选”约束，不再把缺失能力推断成支持。
4. 统一地址输入方式，端口直接写在地址栏，正确支持域名、IPv4、IPv6 和自定义端口。
5. 删除失效文案和旧 UI 控件。
6. 删除 `ML_HOSTPROBE_*` 环境变量，将 Host 映射统一纳入正式配置。
7. 完善内置 Host 与 Foreign Host 的自动探测，严格区分 Yes、No、Unknown。
8. 新增、编辑、探测写回分别定义清晰的原子事务边界，禁止双写和半成品状态。
9. 追查 SparkCR、SUNBALCONY 从曾经全绿变成 `TLS 证书校验失败` / `连接异常` 的真实原因，修复 TLS 错误传递和诊断失真。
10. 完成独立复核、全量测试、真实环境验收、性能对照和证据归档。

**本任务不以“代码改完”作为完成标准。** 必须所有门禁通过，才能标记 `RELEASE_READY=true`。

### 0.1 已确认的设计方向

- 3.5.24 是不可回写的修复基线。
- 3.5.25 不保留旧 API 兼容层；测试也统一使用新契约。
- 不保留旧配置双读、旧环境变量 fallback、字段 alias、旧/新执行双轨。
- 单轨、单一事实源、明确事务提交点。
- 不兼容旧 API 不等于删除用户已有数据，不等于允许改数据库 Schema、凭据格式或缓存代际。
- 未经明确授权，不推送、不合并 main、不部署、不发布、不修改生产数据。

### 0.2 证据状态标识

全文使用以下状态，禁止混用：

| 状态 | 含义 |

## 1. 版本与改动边界

### 1.1 版本定义

| 项目 | 冻结要求 |
|---|---|
| 修复版本 | 3.5.25 |
| 基线版本 | 3.5.24 |
| 版本性质 | 修复，不扩展无关功能 |
| 3.5.24 历史 | 保持原样，不 amend、不重写、不移动标签 |
| 实施分支 | 从经核实的 3.5.24 基线创建专用修复分支 |
| 数据库 Schema | 默认不变 |
| 凭据格式 | 不变 |
| AEAD AAD | 不变 |
| Cache Epoch | 不变 |
| 旧 API 兼容 | 不保留 |
| 旧配置迁移兼容 | 不保留运行时兼容层 |
| 旧环境变量入口 | 删除 |
| 双轨执行 | 禁止 |
| 自动推送/合并/部署/发布 | 未授权，禁止 |

### 1.2 不兼容策略

3.5.25 采用单一的新 API 契约：

- 删除旧参数及其别名。
- 删除旧请求字段的读取、转换和默认映射。
- 删除旧响应字段的投影或双字段输出。
- 删除旧配置键的兼容读取、自动迁移和 fallback。
- 删除旧环境变量入口及其优先级覆盖。
- 删除用于承接旧请求的 handler 或 wrapper。
- 删除旧字段到新字段的映射函数。
- 删除仅为旧契约服务的测试 helper、fixture 和文档。
- 不得在新 API 失败时回退旧 API。
- 不得在新配置缺失时读取旧环境变量。
- 不得在新字段为空时用旧字段补齐。

旧客户端应按 3.5.25 新契约升级。服务端不得静默吞掉旧字段并假装请求成功；应按新契约校验并返回清晰错误。

### 1.3 不兼容不等于数据破坏

以下操作不包含在本任务授权内：

- 删除已有 Source 记录；
- 清空 `source_host_caps`；
- 重建数据库；
- 修改既有凭据密文；
- 更换 AEAD AAD；
- 改动 Cache Epoch；
- 通过生产数据清理绕过新契约校验。

如需数据迁移，必须先证明必要性，列出迁移前后数据语义、回滚方式和影响，再停止等待单独裁定。

### 1.4 不兼容升级的实际影响

由于 3.5.25 明确删除旧 API 兼容层，因此不能把它描述为对旧 API 客户端完全无感的升级：

- 所有调用旧 API 参数/字段的外部客户端必须在切换前改用 3.5.25 新契约；未升级客户端会收到明确错误，不会走旧逻辑兜底。
- 使用 `ML_HOSTPROBE_*` 的部署必须在升级前人工核对变量值，并按冻结后的正式配置格式准备配置文件；程序不负责自动迁移旧环境变量。
- 前端和后端必须作为同一版本契约部署，避免旧前端暂时调用新后端或新前端调用旧后端。
- 发布说明必须列出被删除的 API 参数、配置键和环境变量，以及调用方/部署者的必要调整。
- 既有数据库 Source、凭据和其他数据默认保留；本任务不通过清库或重建数据库完成升级。
- 如果当前部署无法在切换前完成客户端、前端/后端和配置的协调，真实发布应判定为 `BLOCKED_UPGRADE_READINESS`，不能以“向后兼容”作为风险缓释。

因此，“不改 Schema、保留已有数据”可以与“API 不兼容”同时成立，但这不等于旧 API 调用方能够无感升级，也不保证零停机切换。本文不授权实际部署或生产切换。

### 2.4 “单轨、单事务”专项普查

必须区分两件事：

- **单轨：** 一个业务语义只有一套生产执行路径和一个权威事实源。
- **单事务：** 一个需要原子性的数据库业务动作只有一个数据库提交点。

禁止把“单轨”理解成所有 HTTP 请求共用一个全局数据库事务，也不得为了口号而把网络请求放进数据库事务。

检查：

1. 新旧 handler 是否并存；
2. 是否存在新逻辑失败后 fallback 到旧逻辑；
3. 是否先写主表、再由另一个流程补写能力表；
4. 是否双写两个字段或两套表；
5. 是否在启动时把旧配置转换成新配置并继续运行；
6. 是否存在后台 goroutine 修补前台请求留下的半状态；
7. 探测结果是否被多个入口以不同规则写入；
8. 并发写入是否有版本条件或防旧覆盖机制；
9. Source 地址改变时，旧 Host 的能力是否可能被错误复用。

产出 `transitional-state-inventory.md` 和 `transaction-boundary-audit.md`。

## 3. F1：取消归属必选与能力强制推断

### 3.1 目标

- UI 删除不必要的归属必选下拉框。
- API 不再因归属字段缺失而返回 400。
- 删除 Store 中将缺失归属或能力强制设为 `CapYes` 的逻辑。
- 不得把 Unknown、未提供、未探测解释为 Yes。
- 新增/编辑和测试全面切换到新请求契约。
- 不保留旧归属字段作为兼容输入或隐式推断来源。

### 3.2 语义规则

| 输入/状态 | 处理 |
|---|---|
| 不提供归属字段 | 按新契约接受，不因该字段缺失拒绝 |
| 无能力探测记录 | Unknown |
| 探测超时 | Unknown |
| DNS/TLS/连接异常 | Unknown |
| 对端明确不支持 | No |
| 完成真实能力验证 | Yes |

取消必选不等于取消地址、Source 身份和其他必要字段的校验。

### 3.3 验收

- 新增 Source 不提供归属字段成功；
- 缺失能力不会被写成 Yes；
- 不兼容的旧字段不会改变新请求行为；
- Store 不再包含强制推断；
- UI/API/Store 三层语义一致；
- 测试不再为旧请求格式保留兼容路径。

## 4. F2：端口写在地址栏

### 4.1 目标

- 彻底删除独立端口输入框及对应状态。
- 地址栏只填写 Host 与可选 Port，不含 Scheme；协议由 HTTP/HTTPS 下拉框单独决定。
- label、placeholder、hint 三处文案统一说明端口写在地址栏。
- IPv6 示例采用 `[fd00::1]:5000`。
- 前端和后端使用统一结构化地址解析结果，不重复拼接端口。

### 4.2 输入规则

覆盖：

| 输入类型 | 示例 | 协议来源 |
|---|---|---|
| 域名默认 HTTPS 端口 | `mirror.example.org` | 下拉框 HTTPS → 443 |
| 域名自定义端口 | `mirror.example.org:5000` | 下拉框 + 地址栏端口 |
| IPv4 | `192.0.2.10:5000` | 下拉框 + 地址栏端口 |
| IPv6 默认端口 | `[fd00::1]` | 下拉框 HTTPS → 443 |
| IPv6 自定义端口 | `[fd00::1]:5000` | 下拉框 + 地址栏端口 |

**协议只由下拉框决定，地址栏禁止出现 Scheme。** 以下输入必须返回 HTTP 400（负向测试）：`https://mirror.example.org`、`http://mirror.example.org:5000`、`https://[fd00::1]:5000`。不自动剥离、不做兼容转换，详见 §11.6 D-F2-ERR。

注意：示例中的 TEST-NET/文档地址仅用于解析单测，不代表可作为生产可访问地址。

### 4.3 校验

- 端口范围必须在合法区间；
- 拒绝空端口、非数字端口和溢出端口；
- 拒绝格式不合法的 IPv6 方括号；
- 拒绝 userinfo；
- scheme 只来自下拉框、address 只来自地址栏，二者不得混用；地址栏含 `http://` 或 `https://` 时返回 400；
- host、effective port 必须有唯一解析规则；
- UI 提交与 API 直调同一输入时，解析结果必须一致；
- 不得由 UI 先拆分端口、再由 API 二次拼接；
- 不得把带端口的 Authority 当作 TLS ServerName；
- 不指定端口时 HTTPS 用 443、HTTP 用 80；指定端口时使用地址栏端口；不合法地址和端口明确报错，不静默修正。

## 6. F4：删除 `ML_HOSTPROBE_*`，Host 映射统一进入配置

### 6.1 目标

F4 的“默认兜底”必须与“不保留旧配置兼容层”拆开定义，防止一边删除环境变量、一边继续用编译默认值静默补齐旧配置。四种机制分别冻结如下：

| 机制 | 是否允许 | 规则 |
|---|---|---|
| 读取 `ML_HOSTPROBE_*` 环境变量 | 禁止 | 删除读取路径；不得作为配置缺失时的 fallback |
| 读取旧 YAML key / 旧字段 alias | 禁止 | 不自动迁移、不双读；旧 key 按严格配置规则拒绝或明确报错 |
| 编译期默认值 `Default()` | 不能模糊处理 | 仅允许用于生成全新、完整的 canonical config；不得在读取已有配置时静默补齐缺失的 Host 映射 |
| 规范 Host 配置字段 | 唯一权威来源 | 加载后规范化一次，运行期只消费该配置对象，不再读取其他来源 |

- 删除所有 `ML_HOSTPROBE_*` 环境变量声明、读取、解析、覆盖和测试。
- Host 映射全量进入正式配置；配置文件是唯一权威配置入口。
- 不保留环境变量 shadow、fallback、旧 YAML 兼容、空字段回退编译列表或优先级覆盖。
- 配置加载、校验和运行时探测使用同一份规范化配置。
- 配置错误必须明确失败，不能静默忽略后使用默认映射。

### 6.2 Host 范围

规划范围：

- 8 个既有 Host：从 3.5.8 §5.5 的实测记录逐项提取；
- `lscr.io`：此前实测出现 HTTP 401，需按探测协议语义确认；
- lscr.io 上 `linuxserver/traefik` 镜像引用对应的 Registry Authority：从本次实测的**完整镜像引用和实际 HTTP 请求**提取真实 Registry Host，不得把 `traefik` 项目名、镜像名或 namespace 当作 Host；此前该端点出现 HTTP 401，401 只证明返回认证挑战，仓库存在性须完成 token challenge、取 token 并查询目标 manifest 后判定；

**禁止猜测那 8 个 Host 的名称。** 实施者必须从 3.5.8 §5.5 的原文和历史实测证据提取，形成逐项来源表。`traefik` 仓库名也不能直接当作 Registry Host；归档须保留完整镜像引用（可脱敏但不删 Registry Authority）、规范化后的 Registry Host、实际请求的 `/v2/` 或 manifest 路径、响应码和认证挑战。此原则同样适用于 lscr.io。

### 6.3 通配规则

`*.pkg.dev` 必须有明确匹配算法和负向测试：

- 匹配真实的受限子域；
- 不匹配根域 `pkg.dev`，除非原始设计明确要求；
- 不匹配相似后缀；
- 不匹配 `a.pkg.dev.attacker.example`；
- 不允许通过简单 `strings.Contains` 或不带边界的 `HasSuffix` 误匹配。

### 6.4 401/403 的含义

HTTP 401/403 本身不能自动证明 Host 不支持能力：

- 401 可能表示认证要求；
- 403 可能表示权限、策略或请求路径限制；
- 429 表示限流；
- 5xx 表示服务端异常；
- 网络超时、DNS、TLS、连接失败均不能判定为 No。

必须根据该 Host 的能力探测协议，对状态码和响应内容作分类。无法证明“不支持”时保持 Unknown。

### 6.5 Host 下线

- 不得因为一次探测失败就下线 Host；
- 下线必须有多次证据、时间窗口和影响范围；
- 必须评估现有 Source 和能力记录；
- 不得静默改变生产配置；
- 生产 config 修改不在本任务自动授权范围内。

## 7. F1b：自动探测完善并统一写回

### 7.1 唯一能力模型

能力只允许三态：

| 值 | 语义 |
|---|---|
| `Yes` | 已由真实内容验证证实支持 |
| `No` | 对端明确回答不支持 |
| `Unknown` | 尚未探测或当前结果不可判定 |

不能以 TCP 建连成功、HTTP 200、401/403、探测超时或数据库缺记录直接推断 Yes/No。

### 7.2 机制 A：内置三类 Host

- 内置三类 Host 走统一探测入口；
- 补齐当前未覆盖的明确不支持结果，写入 `VerdictNo`；
- 暂时性故障写入 `VerdictUnknown`；
- 成功必须完成规定的真实内容验证后才写 Yes；
- 所有探测结果均保留错误类别和足够的诊断证据。

### 7.3 机制 B：Foreign Host

三种 Host 控制机制各司其职、互不替代，必须分别满足：

1. `POST /api/sources/{id}/hosts`：为某个 Source 建立与 Foreign Host 的关联并初始化持久化状态（`source_host_caps` 等）；**不代表自动进入全局准入，也不代表已有探测仓库**。
2. `registry.multi_origin_hosts`：全局准入范围，决定该 Host 能否进入多源探测/调度；API 登记 Host 不会自动把它加入此列表。
3. `probe.host_probe_repos`：为该 Host 提供代表性探测仓库；加入准入列表不表示已配置探测仓库，配置探测仓库也不表示已为所有 Source 建立 Host 关联。

其他规则：

- 未登记 Host 不通过隐式后缀规则自动进入探测；
- `*.pkg.dev` 使用 §11.3 冻结的统一受限匹配器与解析器；
- 401/403 按协议语义判定，不直接写 No；
- 无法验证能力时保留 Unknown。

完整流程：新增 Source（§11.1）→ 独立 Host API 登记（§11.2）→ 确认 `multi_origin_hosts` 准入（§11.3 D-LSCR）→ 确认 `host_probe_repos` 有代表仓库（§11.3）→ 进入调度探测。任一步缺失都不得隐式补齐。

### 7.4 其他 Host 的处理

| Host 状态 | 行为 |
|---|---|
| 已登记且受支持 | 按其规则探测 |
| 未登记 | 不自动探测、不自动纳入多源 |
| 新增登记 | 按 §7.3 分别完成 Host API 关联、全局准入配置、探测仓库配置，三者独立校验并留证 |
| 准备下线 | 先评估现有 Source 和业务影响 |
| 已下线 | 停止新探测；历史数据处置按独立数据策略，不擅自清除 |

### 7.5 `source_host_caps` 写回

- `source_host_caps` 是运行时 Host 能力的唯一持久化事实源；
- 写入键必须由规范化后的 Source 与 Host 组成；
- 只更新本次探测对应的 Source+Host；
- 不得覆盖同一 Source 其他 Host 的能力；
- 探测目标与当前 Source 配置不一致时，结果不得写回；
- 旧探测不得覆盖较新的探测结果；
- Unknown 不得被转换为 Yes/No；
- Store 不得补默认 Yes；
- 不保留旧能力字段双写或投影。

## 8. 单轨与单事务设计

### 8.1 单轨约束

唯一生产路径必须贯穿：

`UI → 新 API Contract → 唯一 Service → 唯一 Store 写入入口 → 规范化状态`

禁止：

- 新旧 handler 并行；
- 双读/双写；
- 旧字段回退；
- 配置双源；
- 旧状态机回退；
- 失败后切换到旧实现；
- 通过异步补偿把两个独立事务伪装成原子操作。

### 8.2 新增 Source 事务

网络探测不应持有数据库事务。Source 新增的数据库操作应在一个短事务中完成：

1. 校验并规范化地址；
2. 创建 Source 主记录；
3. 初始化必要的能力状态为 Unknown（不登记 Foreign Host——按 §11.1/§11.2，Host 由独立的 `/api/sources/{id}/hosts` 接口在第二步登记，Source 创建事务不承担此职责）；
4. 校验唯一约束和外键约束；
5. 一次提交。

任何一步失败，全部回滚。不得留下 Source 已创建但能力状态不完整的半成品。

### 8.3 编辑 Source 事务

一个事务内完成：

1. 锁定目标记录，或使用版本条件更新；
2. 校验并规范化新地址；
3. 更新 Source；
4. 按冻结规则处理受影响的 Host 能力；
5. 写入现有系统要求的变更记录；
6. 一次提交。

地址/Host 改变后，旧 Host 能力不得错误复用。并发编辑不得静默丢失更新。

### 8.4 探测写回事务

探测网络请求在事务外执行。探测完成后，以一个短事务执行：

1. 确认 Source 仍存在；
2. 确认本次探测目标仍匹配当前 Source 配置；
3. 使用版本号、更新时间或等价条件防止旧结果覆盖新结果；
4. 更新唯一的 Source+Host 能力记录；
5. 一次提交。

**不得在网络请求期间持有数据库事务。**

### 8.5 AddSourceHost（Foreign Host 登记）事务

Foreign Host 登记是独立于 Source 新增/编辑/探测写回的第四类事务场景，由 Agent 3 负责（见 §11.4 的竞态修复冻结）。调用链：`POST /api/sources/{id}/hosts` → API 层字段级校验（§11.7）→ Store `AddSourceHost` 单事务。

事务边界（冻结）：

1. `BEGIN IMMEDIATE` 开启事务；
2. **在事务内**读取当前 Source 与 Endpoint（修复现有实现先读 `sources.base_url` 再开事务的竞态）；
3. 依事务内读到的 Endpoint 计算 Realm policy；
4. 写入全部关联记录：`source_host_caps`、`source_realm_policy`、`source_health_scope`（必要时清理）、`registry_host_recovery`、`source_health`（必要时清理）、Source Host 事件记录与探测状态重置；
5. 一次提交；任一步失败全部回滚，不留半成品。

并发要求：`SetBaseURL`/地址变更与 `AddSourceHost` 并发时，不得把旧 Endpoint 对应的 Realm policy 写入新状态；用版本条件或等价校验保证一致。验收必须覆盖每个写入步骤失败后的全量回滚，以及 `SetBaseURL` 与 `AddSourceHost` 的并发竞态，并核对上述各表一致性。

### 8.6 Schema 前置门禁

上述事务必须优先使用现有 Schema 实现。若现有 Schema 无法提供必要的唯一性、版本比较或原子写入：

- 不得自行新增列、索引或表；
- 不得改用双写绕过；
- 输出证据、影响、替代方案；
- 标记 `BLOCKED_SCHEMA_DECISION`；
- 等待单独裁定。

| 错误码 | 条件 |
|---|---|
| `TLS_CERT_UNTRUSTED` | 系统信任链验证失败 |

- `retryable`；
- `tls_applicable`；
- 可用时的 HTTP 状态；
- 规范化 Host/Port；
- 内部日志可追踪的 cause。

### 9.5 技术详情

UI 点击查看技术详情必须能看到与真实错误一致的内容：

- 实际失败阶段；

### 10.1 3.5.24 网络安全语义回归保护

3.5.25 不得借 Host 探测或 TLS 修复改变既有 SafeHTTP / Pin 安全边界。G0 必须从当前 3.5.24 代码与冻结记录复核以下语义，G4 必须保留回归测试：

- `AllowPrivate` 仅放行 RFC1918 与 IPv6 ULA；不能成为“所有非公网地址均可访问”的总开关。
- `AllowLoopback` 与 `AllowPrivate` 相互独立；打开其中一个不代表另一个也打开。
- CGNAT、TEST-NET/文档网段、基准测试网段、链路本地、组播及其他特殊用途地址，不得因为 `AllowPrivate=true` 而被放行。
- FakeIP 字面量地址不得直接放行；DNS 解析得到的 FakeIP 例外仍受原有专门约束。由于 3.5.24 配置模型没有用户已批准的 resolver/Canary 字段，3.5.25 不得擅自新增这些字段或写入固定 resolver/Canary 地址；相关行为若无法按已冻结规则验证，标记 `BLOCKED`，不得猜测环境参数。
- Pin 的创建、拨号及重定向检查维持 public-only；不能继承普通 Guard 的 `AllowPrivate` / `AllowLoopback` 放宽。
- `InsecureSkipVerify` 的允许范围：仅允许存在于**专用 TLS 诊断路径**——先完成握手取得对端证书材料，随后必须立即通过 `verifyChain` 使用系统信任根和正确 Host/IP 身份独立验证。这是“先取证、后手动验证”的两阶段设计，**不等于信任该证书、不等于业务请求可跳过验证、不得据此把 Source 标记为健康**。实际业务 `http.Transport` 必须继续执行标准证书验证。不得为了让探测变绿而跳过 `verifyChain`、忽略其错误，或把握手成功当作 TLS 验证成功。实施 Agent 不得删除诊断路径中的 `InsecureSkipVerify`（否则无法取得无效证书的详细信息）；更不得把它带入业务请求。
- 对应回归测试：自签/未知 CA → 诊断可取证书信息但结果必须为 Verify Failed；Hostname/SAN 错误 → 必须报 Hostname 错误；过期证书 → 必须报证书过期；业务 HTTP 请求仍由标准 Transport 验证；无 Verify 成功证据时不得将 TLSOK 或 Source 健康置为通过。
- 不得因 SparkCR / SUNBALCONY 告警把证书验证降级成只看 TCP/TLS 握手成功。

如果当前 3.5.24 代码与上述冻结语义存在差异，先记录差异并停止相关范围，不得在 3.5.25 中顺手重构 SafeHTTP / Pin。

如取证证明排除项中的某项是修复所必需的，应停止并提交单独裁定，不得顺手扩大任务范围。

## 11. 冻结契约：API / 配置 / 事务 / UI

本章为正式冻结的实施契约（九项冻结决定 + 实施补充与边界条款均已定稿）。所有 Agent 必须以本章为唯一权威来源；未在本章定义的旧字段、旧环境变量、旧兼容行为一律视为已删除。本章只定义目标契约，不表示代码已经实现；实现状态由 G2 实施、G4 测试和 G1 冻结记录共同证明。唯一保留的待取证项是 D-MANIFEST（§11.9 维持 D2），它属于取证状态而非设计待决，故不在此处列为待决。

> 来源说明：本章九项冻结决定（D-API、D-HOST、D-CONFIG-1~4 合并为 D-CONFIG、D-F2、D-F2-ERR、D-PATCH、D-STORE、D-LSCR、D-MANIFEST）来自用户于 design freeze 前作出的正式裁定；三处实施补充（未知字段拒绝范围、primary_realm API 层校验、extra_realms 上限）和两项边界（PATCH 旧字段与未知字段区分、严格校验适用范围）来自对 3.5.24 实际代码（`internal/api/api.go`、`internal/api/hosts.go`、`internal/store/policy.go`、`main.go`、`internal/config/config.go`）的只读核对。源码依据仅为定位参考，实施时仍须按 G0 重新读取当前基线。

### 11.1 D-API：新增 Source 的新请求契约

`POST /api/sources` 的唯一合法请求体：

```json
{
  "name": "My Registry",
  "endpoint": {
    "scheme": "https",
    "address": "mirror.example.org:5000"
  }
}
```

- `name`：字符串，必填，非空。
- `endpoint`：对象，必填；`scheme` 与 `address` 必须同时提供，不允许缺省。`scheme` 只允许 `https` 或 `http`；`address` 为不含 Scheme 的 Host 或 Host:Port，规则见 §11.6 D-F2。
- 旧字段 `url`、`host`、`scheme`（顶层）、`port`（顶层）、`repo_host`、`connect_host` 一律不再作为新增源接口的兼容字段。携带这些字段时按 §11.8 的 POST 旧字段规则明确拒绝（HTTP 400，`legacy_field_not_supported`），不得由 JSON 解码器静默忽略后接受请求。
- 成功响应返回新建 Source 的 ID；Foreign Host 不在本请求中登记，按 §11.2 处理。

### 11.2 D-HOST：Foreign Host 两步登记

新增 Source 不负责登记 Foreign Host。新增 Source 成功后，通过 3.5.24 已存在的独立 Host 管理接口登记：

`POST /api/sources/{id}/hosts`：

```json
{
  "host": "quay.io",
  "primary_realm": "https://quay.io",
  "extra_realms": []
}
```

- `host`：必填、非空。
- `primary_realm`：必填、非空，不能省略或传空字符串；API 层显式校验见 §11.7。Realm 的格式、合法性与规范化仍由现有底层 `normalizeRealm` 负责，Agent 不得自动猜测或代为推导。
- `extra_realms`：数组，最多 3 个，上限依据 `policy.go` 的 `maxPolicyExtraRealms = 3`，验收矩阵见 §11.7。
- 不允许把 Foreign Host 塞回 Source 新增请求体，重新引入归属必选问题。
- Agent 分工：Agent 1 实现新增 Source 新契约；Agent 2 实现 Foreign Host 登记与探测配置；Agent 3 保证 `AddSourceHost` 完整事务；UI 在新增 Source 成功后通过独立 Host 管理界面继续登记。

### 11.3 D-CONFIG：Host 配置字段与默认值

正式配置字段（新增于 `probe` 段）：

```yaml
probe:
  host_probe_repos:
    gcr.io: distroless/static:nonroot
    registry.k8s.io: pause:3.9
    "*.pkg.dev": google-samples/containers/gke/hello-app:1.0
    quay.io: prometheus/busybox:latest
    mcr.microsoft.com: hello-world:latest
    registry.gitlab.com: gitlab-org/cli:latest
    public.ecr.aws: docker/library/alpine:latest
    cgr.dev: chainguard/static:latest
    lscr.io: linuxserver/traefik
  host_probe_interval_sec: 21600
  host_probe_scan_sec: 30
```

对应 Go 配置结构（目标形态，实施以 G0 冻结为准）。**以下为完整合并后的结构：3.5.24 已有的五个字段必须原样保留，新增三个字段是追加而非替换。** 尤其 `host_probe_interval_sec` 是 Host Probe 的全量对账周期，不能取代已有的通用探测周期 `interval_sec`。

```go
type Probe struct {
    // —— 3.5.24 现有字段，必须保留 ——
    AllowPrivate bool `yaml:"allow_private"`
    IntervalSec  int  `yaml:"interval_sec"`
    Concurrency  int  `yaml:"concurrency"`
    TimeoutSec   int  `yaml:"timeout_sec"`
    SampleMiB    int  `yaml:"sample_mib"`
    // —— 3.5.25 新增字段 ——
    HostProbeRepos       map[string]string `yaml:"host_probe_repos"`
    HostProbeIntervalSec int               `yaml:"host_probe_interval_sec"`
    HostProbeScanSec     int               `yaml:"host_probe_scan_sec"`
}
```

冻结规则：

- D-CONFIG-1：`probe.host_probe_repos` 为 Foreign Host 探测仓库映射的唯一正式来源；默认表 9 行来自 3.5.8 §5.5 的 8 个实测 Host（其中 `*.pkg.dev` 是受限通配键，对应 3.5.8 实测的 `us-docker.pkg.dev`）加用户实测的 lscr.io。实施者必须从 3.5.8 §5.5 原文逐项复核，不得只复制映射而丢掉实测依据；映射是开放的 `map[string]string`，这些只是默认预置值，不是白名单。`*.pkg.dev` 是**唯一允许的通配键**，不得出现其他通配表达式或空仓库值，配置加载阶段必须校验拒绝。
- D-CONFIG-2：`host_probe_interval_sec` 默认 21600 秒（6 小时），是全量对账周期；来源为 3.5.24 `hostProbeInterval()` 与 `hostprobe.go` 的 `defaultHostProbeInterval`，属迁移现有运行默认值，不是新设性能参数。
- D-CONFIG-3：`host_probe_scan_sec` 默认 30 秒，是到期任务扫描周期；来源为 3.5.24 `hostProbeScanInterval()` 与 `hostprobe.go` 的 `defaultHostProbeScan`。两个周期语义不同，不得互换。两者都必须大于零并做明确范围校验；范围校验至少保证秒数转换为 `time.Duration` 不溢出（纳秒表示下不越界），超出上限时启动报明确配置错误，不使用编译默认值兜底。
- D-CONFIG-4：全新安装可由 `Default()` 生成完整 canonical 默认配置；已有配置文件缺少这些必需字段时必须启动报错（fail-fast），不得从 `Default()`、旧字段或环境变量静默补齐；显式配置为空 map 表示“没有登记 Foreign Host”，不得回退默认列表；`config.example.yaml` 与 `Default()` 必须保持一致；三个 `ML_HOSTPROBE_*` 环境变量（`ML_HOSTPROBE_REPOS`、`ML_HOSTPROBE_INTERVAL`、`ML_HOSTPROBE_SCAN`）彻底删除；正式运行只从配置对象取参数，Runner 不得形成第二套生产配置来源。
- D-LSCR：`registry.multi_origin_hosts` 默认列表同步加入 `lscr.io`（3.5.24 `config.go` 当前默认 8 个 Host 不含它）。探测映射与准入白名单两处必须同步变更，并验证 lscr.io 能进入调度。现有生产配置不在本任务自动修改授权内，升级说明必须明确要求人工核对。


#### D-RESOLVE：仓库映射统一解析规则（方案 B，冻结）

`probe.host_probe_repos` 同时支持精确 Host 键与唯一的受限通配键 `*.pkg.dev`。**必须实现一个统一的仓库解析函数**，由 HostProbeRunner 的周期性能力对账 `reconcileRepos` 与到期任务构造 `jobs` 两处共同调用，禁止各写一份查找逻辑（否则两处可能对同一 Host 得出不同结论：对账认为无配置而清除已有能力，任务构造却能找到仓库，或相反）。

解析顺序（冻结）：

1. **配置加载时规范化 Map 键**：对所有精确 Host 键调用 `registryhost.Normalize`（小写化、去尾部点、docker.io 别名归一、非法键拒绝）；非法 Host key 启动报配置错误；两个不同原始键规范化后冲突时启动报错，不允许随机覆盖；`*.pkg.dev` 是唯一特殊键，单独识别，不进入普通 Host 规范化；运行期只查规范化后的 Map。实际 Host 同样用 `registryhost.Normalize` 规范化后再查表，二者口径一致。
2. **精确键优先**：先查 `repos[normalizedHost]`，命中即返回，不再看通配键；
3. 精确键不存在时，才检查配置中是否存在 `*.pkg.dev`，并通过 `registryhost.Match` 既有规则判断实际 Host 是否匹配（即 `IsArtifactRegistry` 的严格三段 `<location>-docker.pkg.dev` 语义，不是任意后缀通配）；
4. 命中后返回对应仓库（仓库名用 `probe.NormalizeRepo` 归一后比对）；**无匹配时两处调用方执行不同业务动作**，详见下方“解析结果的两场景处理”；**任何情况都不得退回通用 `library/alpine` 仓库兜底**（3.5.24 中 `ProbeRegistryHost` 的 `library/alpine` 兜底因 runner 提前拦截而不可达，本规则维持该设计）；
5. 配置中的空仓库值、非 `*.pkg.dev` 的通配表达式在配置校验阶段拒绝。

**解析结果的两场景处理（冻结）：** 统一解析函数只负责“解析出仓库或解析失败”，两个调用方对同一解析结果执行各自业务动作，不构成重复解析逻辑。

| 解析结果 | `reconcileRepos`（周期性能力对账） | `jobs`（到期任务构造） |
|---|---|---|
| 精确键命中 | 比对诊断记录中的实际 Repo；一致则保留，不一致则 `ResetHostCaps` 重置为 Unknown | 用精确仓库创建探测任务 |
| 通配键命中 | 同上：比对实际 Repo，一致保留、不一致重置 | 用通配仓库创建探测任务 |
| **无匹配** | **对已有非 Unknown 结论执行 `ResetHostCaps`，把失效结论重置为 Unknown**（映射被修改或删除都属输入变化，旧结论可能属于另一个仓库，不得继续用于选路）；保留诊断与时间，不动凭据代次 | **跳过该任务并记录缺少映射的原因**，不执行网络探测 |
| Source 能力原本为 Unknown | 保持 Unknown | 无仓库时跳过 |
| 任意情况 | 不得使用 `library/alpine` 兜底 | 不得使用 `library/alpine` 兜底 |

依据 3.5.24 现有行为：`reconcileRepos` 在 `ok=false` 或仓库不一致时调用 `ResetHostCaps`；本规则保留该语义，禁止把它简化成 continue。

精确键优先于通配键：即使两者同时存在也使用精确配置，以便未来某个 Location 需要不同探测仓库时可用精确键覆盖通配默认值。

解析结果示例（冻结）：

| 实际 Host | 精确配置 | 通配配置 | 最终结果 |
|---|---|---|---|
| `us-docker.pkg.dev` | 有 | 有 | 使用精确配置 |
| `us-docker.pkg.dev` | 无 | 有 | 使用 `*.pkg.dev` |
| `europe-west1-docker.pkg.dev` | 无 | 有 | 使用 `*.pkg.dev` |
| `foo.pkg.dev` | 无 | 有 | 不匹配 |
| `a.b-docker.pkg.dev` | 无 | 有 | 不匹配 |
| `evil-docker.pkg.dev.attacker.example` | 无 | 有 | 不匹配 |
| `quay.io` | 无 | 无 | 跳过，不兜底 |

三项保护条件（冻结）：

- **精确键优先于通配键**，覆盖规则如上。
- **仓库存在不等于 Host 支持**：3.5.8 实测的 `google-samples/containers/gke/hello-app:1.0` 只证明它在 `us-docker.pkg.dev` 可用，不得声称已证明在所有 Artifact Registry Location 可用；其他 Location 必须通过真实 Manifest/内容验证。仓库或 Tag 不存在时仍遵守 D2，不得将 Manifest 404/410 直接转为 `VerdictNo`。
- **两条调用路径都必须测试**：`reconcileRepos` 与 `jobs` 对同一 Host 必须得到一致解析结果；测试覆盖精确键优先、两个合法 Location 的通配解析、非法 Location 拒绝、未知 Host 无映射。

`registry.multi_origin_hosts` 仍是独立准入条件：仓库映射命中不自动赋予多源资格（见 §7.3）。

补充约束：

- `lscr.io` 的 HTTP 401 只作为认证挑战证据，仓库存在性仍须通过 token challenge 和 manifest 查询确认，不得直接判为 Host 能力 Yes。
- `registry.multi_origin_hosts` 的准入由 `filterAllowed` 控制；配置说明必须写明“加了 Host 还要确认白名单放行”。

### 11.4 D-STORE：AddSourceHost 事务边界与竞态修复

保留 3.5.24 `AddSourceHost()` 已有的 `BEGIN IMMEDIATE` 单事务写入路径，不另造第二套。事务内原子包含：`source_host_caps`、`source_realm_policy`、`source_health_scope`（必要时清理）、`registry_host_recovery`、必要的 `source_health` 清理、Source Host 事件记录与相关探测状态重置。

冻结修复（base_url 竞态）：现有实现先读取 `sources.base_url`（`hostcaps.go:398`），再开启事务（`:403`），而 Realm policy 依赖该值。目标顺序为：

1. 开启 `BEGIN IMMEDIATE` 事务；
2. 在事务内读取当前 Source 及其 Endpoint；
3. 根据事务内读到的当前 Endpoint 计算 Realm policy；
4. 写入所有关联记录；
5. 一次提交。

地址变更与 Host 登记并发时，不得让旧 Endpoint 对应的 Realm policy 被写入新状态。可用版本条件或等价校验保证一致；不得为解决此问题重写整个 Store。

### 11.5 D-PATCH：PATCH /api/sources/{id} 字段矩阵

`PATCH /api/sources/{id}` 是资源的部分更新，但 `endpoint` 子对象采用整体替换语义。字段矩阵为唯一权威口径：

| 字段 | 可单独 PATCH | 出现时的要求 |
|---|---|---|
| `name` | 是 | 独立更新 |
| `note` | 是 | 独立更新 |
| `enabled` | 是 | 独立更新 |
| `preferred` | 是 | 独立更新 |
| `group_id` | 是 | 独立更新 |
| `status` | 是 | 独立更新 |
| `endpoint` | 否，不能部分更新 | 一旦出现，`scheme` 与 `address` 必须同时提供，整体替换 |
| 旧地址字段（`base_url`、`repo_host`、顶层 `scheme`、`port`） | 否 | 明确拒绝，见 §11.8 |

- 允许 metadata 字段（`name`/`note`/`enabled`/`preferred`/`group_id`/`status`）与完整 `endpoint` 同时提交。
- 允许不包含 `endpoint` 的 metadata-only PATCH。
- 禁止只提交 `endpoint.scheme` 或只提交 `endpoint.address`；任一缺失按错误响应处理。
- 本矩阵对应 3.5.24 `api.go:900-913` 的源 PATCH 字段，不覆盖 `groupItem` 的 rank PATCH（`api.go:847`）等其他接口。

### 11.6 D-F2 / D-F3 / D-F2-ERR：地址栏与协议下拉框

- D-F2：保留 HTTP/HTTPS 协议下拉框；删除独立端口框；连接地址输入框包含 Host 与可选 Port，不含 Scheme。协议只由下拉框决定；未指定端口时 HTTPS 用 443、HTTP 用 80；指定端口时用地址栏端口；不合法地址和端口明确报错，不静默修正。
- 合法地址示例：`mirror.example.org`、`mirror.example.org:5000`、`192.0.2.10:5000`、`[fd00::1]`、`[fd00::1]:5000`。示例中的 TEST-NET 地址仅用于解析单测，不代表生产可访问地址。
- D-F2-ERR：地址栏包含 Scheme 时明确返回 HTTP 400，不自动剥离、不做兼容转换。以下输入必须 400：`https://mirror.example.org`、`http://mirror.example.org:5000`。原因是协议已由下拉框决定，自动剥离会引入隐式修正，且与旧 API 不兼容基调一致。
- D-F3：仅删除失效的 `See §2.3 warning` 文案及引用；协议下拉框保留，HTTP 选项文案可改为“HTTP（明文，不推荐）”。不删除协议选择器。
- 校验共性：拒绝 userinfo、`scheme`/`host`/`effective port` 必须有唯一解析规则、UI 提交与 API 直调同一输入解析结果一致、不得由 UI 先拆端口再由 API 二次拼接、不得把带端口的 Authority 当作 TLS ServerName。

### 11.7 实施补充：未知字段、primary_realm 与 extra_realms

**(1) 未知 JSON 字段拒绝——本版本新增 API 行为，不是现有能力。** 仅对以下三个端点明确要求在各自 JSON 解码路径启用严格字段校验，并覆盖嵌套 `endpoint` 对象：

| 端点 | 新增要求 |
|---|---|
| `POST /api/sources` | 拒绝未知字段，包括旧版 `url`、`host`、`scheme`、`port`、`repo_host`、`connect_host` |
| `PATCH /api/sources/{id}` | 拒绝未知字段，包括旧版 `base_url`、顶层 `scheme`、`port`、`repo_host`；旧字段与未知字段区分处理见 §11.8 |
| `POST /api/sources/{id}/hosts` | 拒绝请求体中的未知字段 |

不要求全局 API 解码器统一启用 `DisallowUnknownFields`，避免扩大兼容性影响范围。（3.5.24 全仓仅 `credentials.go` 使用过该选项，源与 Host 接口当前未启用。）

**(2) primary_realm——API 层显式校验，先于 Store 调用。** `POST /api/sources/{id}/hosts` 在调用 `AddSourceHost` 前必须完成字段级校验：

| 字段 | 校验要求 | 失败结果 |
|---|---|---|
| `host` | 必须非空 | HTTP 400 |
| `primary_realm` | 必须非空，不能省略或传空字符串 | HTTP 400 |
| `extra_realms` | 最多 3 个 | HTTP 400 |

`primary_realm` 为空时 API 层直接返回明确字段错误，例如：

```json
{ "error": "primary_realm is required" }
```

不得依赖 `normalizeRealm("")` 产生底层 URL 解析错误再把模糊错误返回客户端。Realm 格式、合法性与规范化仍由底层 `normalizeRealm` 负责，职责不得混淆。

**(3) extra_realms——最多 3 个，依据 `policy.go:24` 的 `maxPolicyExtraRealms = 3`。** 验收矩阵必须包含：

- 0 个：通过；
- 1 个：通过；
- 3 个：通过；
- 4 个：HTTP 400，明确指出超出上限；
- 数组元素格式错误：HTTP 400。

不能只测正常的空数组样例。

### 11.8 边界补充：PATCH 旧字段与未知字段区分、严格校验适用范围

**(1) PATCH 旧字段与未知字段必须区分处理。** 针对 `PATCH /api/sources/{id}`：

| 输入类别 | 字段 | HTTP 状态 | 错误语义 |
|---|---|---|---|
| 已知旧字段 | `base_url`、`repo_host`、`scheme`、`port` | 400 | `legacy_field_not_supported`，明确指出旧字段已废弃 |
| 未知字段 | DTO 未定义的其他字段、拼写错误字段 | 400 | `unknown_field`，明确指出字段未定义 |

实现时必须先识别旧字段，再执行严格 DTO 解码；不能让旧字段仅因 `DisallowUnknownFields` 被归类为普通未知字段。两者都返回 400，但错误类别与字段名必须可区分。验收测试必须分别断言状态码、错误类别和字段名，不能只断言请求失败。

上述区分同样适用于 `POST /api/sources`：旧字段 `url`、`host`、`scheme`（顶层）、`port`（顶层）、`repo_host`、`connect_host` 命中时返回 HTTP 400、`legacy_field_not_supported` 并指出具体旧字段；其他未知字段返回 HTTP 400、`unknown_field`。POST 的拒绝语义以本段为准，§11.1 的交叉引用指向此处。

**(2) 严格字段校验的适用范围。** 仅覆盖 `POST /api/sources`、`PATCH /api/sources/{id}`、`POST /api/sources/{id}/hosts` 三个端点。明确不覆盖：`groups` 及其 `groupItem` rank PATCH（`api.go:847`）、`credentials`、其他未列出的 API。Agent 不得扩大改动面到其他接口。

### 11.9 D-MANIFEST：Manifest 404 语义维持待取证

维持 D2：没有完成真实协议取证之前，不把 manifest 404/410 直接判成 `VerdictNo`。仓库不存在、tag 不存在与 Registry 不支持某种协议不是同一种状态；`/v2/` 层能明确证明协议不支持的情况与某个仓库或 tag 不存在必须区别对待。此项不从已删除的历史草稿恢复成已冻结决定。

## 14. G3：独立复核

独立复核必须由未参与对应代码实施的 Reviewer 执行。复核期间冻结代码，不得一边复核一边修改。

### Reviewer A：API/UI 与兼容清理

检查：

- 旧参数是否完全退出生产路径；
- 新请求/响应契约是否唯一；
- 旧字段是否仍被读取、忽略或映射；
- UI 是否仍显示独立端口或归属必选控件；
- API 是否有新旧 handler 并存；
- 测试是否仍以旧契约为通过依据。

### Reviewer B：Host 能力与事务

检查：

- Host 配置是否唯一；
- `source_host_caps` 是否唯一；
- Yes/No/Unknown 判定是否正确；
- 401/403/404/429/5xx 语义是否合理；
- Unknown 是否被误写成 No 或 Yes；
- 新增/编辑/探测写回是否原子；
- 并发写回是否可能旧覆盖新；
- Source Host 改变后旧能力是否被错误复用；
- 是否存在双写、补偿写或后台修复半状态。

### Reviewer C：TLS、安全与实际调用链

检查：

- TLS 错误是否保真传递到 UI；
- SNI、SAN、EffectivePort 是否正确；
- HTTP Source 是否误执行 TLS；
- DNS/TCP/TLS/HTTP 错误是否区分；
- 是否削弱 Guard、SSRF、Redirect、Pin 等防护；
- SparkCR 与 SUNBALCONY 的错误是否有证据支持最终诊断。

### 14.1 Finding 格式

每条问题必须记录：

- ID；
- 严重级别 P0/P1/P2/P3；
- 文件、函数、行号；
- 实际生产调用路径；
- 复现步骤；
- 证据；
- 影响；
- 修复要求；
- 回归测试。

复核结论只能是 `PASS`、`CHANGES_REQUIRED` 或 `BLOCKED`。

有未关闭 P0/P1 时禁止进入 Release Ready。影响安全或数据一致性的 P2 也必须关闭或单独裁定。

### 15.3 Host 和能力测试

- 精确 Host；
- `*.pkg.dev` 受限通配解析（方案 B，见 §11.3 D-RESOLVE）：精确键优先、两个合法 Location（`us-docker.pkg.dev`、`europe-west1-docker.pkg.dev`）通配解析成功、`foo.pkg.dev`/`a.b-docker.pkg.dev`/`evil-docker.pkg.dev.attacker.example` 拒绝、未知 Host 无映射跳过且不兜底；
- **两条调用路径一致性**：`reconcileRepos` 与 `jobs` 对同一 Host 得到相同解析结果（防止对账清除能力而任务构造仍能找到仓库，或相反）；
- **映射变更/删除后旧结论失效**：删除或改变某 Host 的仓库映射后，`reconcileRepos` 必须对已有非 Unknown 结论调用 `ResetHostCaps` 重置为 Unknown（旧 Yes 不得残留），保留诊断与时间、不动凭据代次；`jobs` 侧则跳过并记录缺映射；
- 配置校验：空仓库值、非 `*.pkg.dev` 通配表达式被拒绝；
- **配置键规范化**：`QUAY.IO` 规范化后能匹配 `quay.io`；带尾部点的合法 Host key 按统一规则处理；`QUAY.IO` 与 `quay.io` 同时存在时启动拒绝冲突；带端口、路径、userinfo 的精确键启动拒绝；运行期只查规范化后的 Map；
- 三机制独立性：API 登记不自动准入、准入不等于有仓库、有仓库不等于已为所有 Source 建立关联；
- 根域负向匹配；
- 相似后缀负向匹配；
- 未登记 Host；
- 已登记 Foreign Host；
- 401、403、404、429、5xx；
- DNS、TLS、TCP、超时；
- 明确不支持的响应；
- 缺失能力记录；
- Unknown 不写为 Yes/No；
- No 不写为 Yes；
- Yes 必须有真实内容验证；
- 一次探测只修改对应 Source+Host；
- 旧探测不能覆盖新探测；
- Source 地址改变后旧 Host 能力不被错误沿用。
