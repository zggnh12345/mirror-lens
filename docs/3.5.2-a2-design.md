# A2 设计草案 v1（Host 探测退避持久化）

> 状态：**设计冻结中，不批准生产代码开工**。本文对应裁定「A2 先做设计、不开工」。
> 范围基线：A2-0 源码审计已完成（本文第 3 节），A2-1 起的接口与字段需在 O1–O4 裁定后冻结。

## 1. 目标与非目标

### 目标

1. 把 Host 探测的失败退避从进程内存持久化到 `registry_host_recovery`。
2. `next_probe_at` 成为唯一调度时间权威，消除内存 `backoff` 与数据库两套时间源。
3. 重启后保留尚未到期的退避状态。
4. 保留 C4、C5、C6 已冻结的调度、Guard 与状态机语义。
5. 增加最小退避观测。

### 非目标

- 不改变 Registry Host 六态派生。
- 不改变候选 SQL 与候选准入规则。
- 不改变探测协议、并发上限、30s 扫描模型。
- 不引入逐 Host Timer。
- 不支持多 Runner / 多实例。
- 不重构 Guard。

## 2. 关键事实：内存退避当前到底在挡什么

`hostprobe.go` 的 `probeState` 有两个职责，必须拆开看：

- `running`：进程内互斥，覆盖 claim→finish 的整个生命周期（`hostprobe.go:93-95`、`:320-323`）。A2 保留，不下沉。
- `backoff` / `next`：仅用于「未成功提交」的连续失败节流（`:352-364`）。

要点：**未提交成功的失败，recovery 行的 `next_probe_at` 根本没被改过，行保持到期。** 也就是说数据库已经在说「该探了」，是内存的 `st.next` 在拦。一旦进程重启，内存清空，下一轮 30s 扫描会立刻重探。

因此 A2 的实质不是「新增调度」，而是把内存里那层节流搬到数据库，让「该不该探」只有一个答案。

### 3.2 `rec_failures` 的写入点

- 唯一自增：`store/commit.go:253`（`Cap=Unknown` 时 `failures++`），随 UPSERT 写入 `:301`。
- 三处清零：`host.go:133`、`host.go:369`、`store.go:790`。
- 参与 `DeriveState`（`commit.go:266`），间接影响 `failed` 判定与 `recoveryBackoff(failures)`。

这正是不能复用的原因：它统计的是「已提交的探测失败」，且已被状态机消费。

### 3.4 Context 取消的实际行为（与设计表不一致，见 O1）

探测用的 ctx 是 `context.WithTimeout(parent)`（`hostprobe.go:391`）。Runner 关闭时 parent 被取消，Probe 返回运输类错误，代码**照常走 CommitHostProbe**（`:420-433`），于是：

- `Cap=Unknown` → `rec_failures++`（`commit.go:253`）；
- `DeriveState` 走 `initial` 分支 → `next_probe_at = now + recoveryBackoff(f)`（`commit.go:284-291`）。

即「关闭」当前会改变持久化状态并累计失败次数。设计表要求「Context 取消/关闭不累计退避」，这需要实现层面的守卫，不能只靠分类。

### 3.5 内存退避的现有参数与重置条件

- 起点 15s（`defaultHostProbeBackoff`），每次 ×2，上限 600s（`maxHostProbeBackoff`），无抖动（`hostprobe.go:352-364`）。
- 凭据快照 gen 或 digest 变化时清零（`noteSnapshot`，`:338-341`）。
- 成功后 `retry=false` 直接删除状态（`:348-351`）。

## 4. A2-1 设计：持久化退避

### 4.1 字段

`registry_host_recovery` 新增：

```sql
retry_failures INTEGER NOT NULL DEFAULT 0
```

- 只统计「可重试、未成功提交」的执行失败；
- 成功提交清零；
- 代次变化清零；
- 不参与 `DeriveState`、不参与候选 SQL、不影响 `rec_failures`。

迁移方式：`PRAGMA table_info` 判断缺列后 `ALTER TABLE ... ADD COLUMN`（`CREATE TABLE IF NOT EXISTS` 对既有表不生效，必须显式迁移；与 C6-E 的 meta DDL 同属基础 schema 迁移段）。

### 4.2 Store 接口（待 O2/O3 冻结后定稿）

```go
type HostProbeRetry struct {
    SourceID   int64
    Host       string
    Gen        int64 // 执行起点快照代次
    At         int64 // 本次失败发生时间
    Failures   int   // 本次执行后的连续失败次数（由 Runner 传入）
}

// ScheduleHostProbeRetry 只更新重试调度字段，不改变状态机结论。
func (s *Store) ScheduleHostProbeRetry(r HostProbeRetry) (bool, error)
```

事务内校验（全部满足才写）：

1. 源存在、`status<>'archived'`、`enabled=1`、`repo_host` 仍等于 `r.Host`；
2. `registry_host_gen.gen = r.Gen`（缺行视为不匹配）；
3. recovery 行存在且 `gen = r.Gen`；
4. `next_probe_at <= r.At`（CAS：期间没有更新的调度写入）；
5. 只 `UPDATE next_probe_at, retry_failures, updated_at`。

返回 `false`（拒绝）的三种情况：代次不匹配、CAS 失败、源不可用。拒绝时**不得解除 Guard**，也不得回写任何字段。

### 4.3 失败分类与写入职责

| 结果 | 是否写 retry | `retry_failures` | 说明 |
| --- | --- | --- | --- |
| CommitHostProbe 成功提交 | 否 | 由 CommitHostProbe 清零 | 时间由状态机决定 |
| 探测失败且成功提交 | 否 | 由 CommitHostProbe 决定 | 同上 |
| `stale_snapshot` | 否 | 不变 | 行保持到期，靠下一轮 30s 扫描重试（见 D2） |
| 临时凭据读取失败 | 是 | +1 | 仅在代次可确认时 |
| 临时本地执行错误 | 是 | +1 | 不伪装成上游探测失败 |
| 本地写库失败 | 是 | +1 | 与 Guard Block 同时发生，写入不得解除屏蔽 |
| Context 取消 / Runner 关闭 | 否 | 不变 | 见 O1，需要守卫 |
| 源已禁用 / 归档 / 换 Host | 否 | 不变 | 由 4.2 的校验兜底 |

### 4.4 算法

`D(n) = min(15s × 2^(n-1), 600s)`，n 为本次失败后的 `retry_failures`。不加抖动，避免同批改动两个变量。

写入值：`next_probe_at = At + D(n)`，`n` 上限按 7 计（600s）。

### 4.5 清零规则

- 成功提交：`CommitHostProbe` 在既有事务内 `retry_failures=0`（新增一列写入，不改其余语义）。
- 代次变化：`ApplyCredChanges`（`host.go:362`）与换 Host（`host.go:127`）的 UPSERT 增加 `retry_failures=0`。
- enabled 0→1（`store.go:826`）拉近 `next_probe_at` 时同时清零。

## 5. A2-2 观测（与现有 metrics 体系对齐，见 D1）

现状：`internal/metrics` 是手写 `atomic.Uint64` + 快照视图（`recovery.go:15-66`），**没有** Prometheus 客户端、没有标签维度、没有 Histogram。

建议实现：

| 指标 | 形式 | 语义 |
| --- | --- | --- |
| `hostprobe_retry_scheduled_total` | Counter | 写入成功次数 |
| `hostprobe_retry_rejected_total` | Counter（按 `reason` 分桶：`gen_mismatch` / `cas_lost` / `source_unavailable`） | 拒绝次数 |
| `hostprobe_retry_pending` | Gauge（快照时 `SELECT COUNT(*)`） | `retry_failures>0 AND next_probe_at>now` 的 Host 数 |
| 退避延迟 | Counter + 固定桶计数（15/30/60/120/240/480/600s）+ 总和 | 代替 Histogram，可算均值与分布 |

标签只用有限枚举，禁止 Host / sourceID 等高基数维度。`pending` 必须来自数据库查询，不能用内存 map 推算。

## 6. A2-3 / A2-4：明确不做

- **逐 Host 定时器**：30s 扫描已给出明确延迟边界；定时器不减少工作量，只增加取消/重启/生命周期复杂度。除非实测证明扫描耗时成为瓶颈。
- **持久化 claim / 多 Runner**：`probeState.running`、Runner token map、Guard failClosed 三者都不是跨进程锁。多实例需要独立设计 DB claim/lease、owner token、续租、fencing token、Guard 一致性与 seed 标记并发安全，不能在 A2 顺手加字段。

## 9. 待裁定（阻塞 A2-1 冻结）

**O1｜Context 取消会写库**
现状：关闭时 Probe 被取消 → 仍提交 `Cap=Unknown` → `rec_failures++`、`next_probe_at=+backoff`。
建议：在 `runOne` 提交前检查 `parent.Err() != nil`，取消则直接返回，不提交、不计数、不写 retry。
影响：属于 C6 写入路径的行为收窄，需要你确认是否纳入 A2-1。

**O2｜`ScheduleHostProbeRetry` 的 CAS 维度**
建议：`gen` + `next_probe_at<=At` + 源可用三项。是否需要额外比对 `state`（例如只允许 `initial`/`failed`/`expired` 接受 retry）？

**O3｜写库失败路径的 Guard 顺序**
现状：先 `blockRoute` 再 retry。A2 需明确：若 retry 写入失败，Guard 是否继续 Block（建议是，直到成功提交）；若 retry 写入成功，Guard 也**不得**解除。

**O4｜探测结果自相矛盾路径**
`hostprobe.go:413-417` 当前不提交、不 Block、不计数。归入「临时本地执行错误」进入退避，还是维持现状（靠行仍到期、30s 后重探）？建议维持现状并加一个计数器。

**D1｜观测形式**
现有 metrics 无标签、无 Histogram。建议按第 5 节降级为计数器 + 固定桶，或者你要求引入 Prometheus 客户端（会新增依赖，属于扩大范围）。

**D2｜`stale_snapshot` 不写退避的后果**
不写 → 行保持到期 → 每 30s 重探一次，直到代次稳定。接受这个频率吗？若不接受，只能在确认代次仍为当前代次时写退避（CAS 会天然拒绝旧代次写入）。
