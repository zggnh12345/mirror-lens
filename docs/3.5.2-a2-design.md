# A2 设计草案 v2（Host 探测退避持久化）

> 状态：**A2-1 已实现（仅文档冻结的 CAS 条件除外，见 §4.6）**。A2-2 未开工。
> v2 依据裁定 O1–O4、D1–D2 修订：新增「原因 → 调度 / Guard / 计数器」完整映射、`finish` 职责重定义、CAS 条件。
> v3 依据 R2 裁定：CAS 增至七项（封死 hard-excluded），R2-2/R2-3 维持原判。
> 与 v1 的差异集中在第 4、5、9 节；第 3 节源码审计结论不变。

## 1. 目标与非目标

### 目标

1. 把 Host 探测的可重试执行失败从进程内存持久化到 `registry_host_recovery`。
2. `next_probe_at` 成为唯一调度时间权威，消除内存 `backoff` 与数据库两套时间源。
3. 重启后保留尚未到期的退避状态。
4. 保留 C4、C5、C6 已冻结的调度、Guard 与状态机语义。
5. 增加最小退避观测。

### 非目标

- 不改变 Registry Host 六态派生。
- 不改变候选 SQL 与候选准入规则。
- 不改变探测协议、并发上限、30s 扫描模型。
- 不引入逐 Host Timer。
- 不支持多 Runner / 多实例。
- 不重构 Guard。

## 2. 关键事实：内存退避当前在挡什么

`probeState` 有两个职责：

- `running`：进程内互斥，覆盖 claim→finish 的整个生命周期（`hostprobe.go:93-95`、`:320-323`）。A2 保留。
- `backoff` / `next`：仅用于「未成功提交」的连续失败节流（`:352-364`）。

**未提交成功的失败，recovery 行的 `next_probe_at` 根本没被改过，行保持到期。** 数据库已经在说「该探了」，是内存 `st.next` 在拦；进程重启即失效。

A2 的实质不是新增调度，而是把这层节流搬进数据库，让「该不该探」只有一个答案。

### 3.4 Context 取消的实际行为

`context.WithTimeout(parent)`（`:391`）。Runner 关闭时 parent 被取消，Probe 返回运输错误，代码照常 `CommitHostProbe`（`:420-433`）→ `Cap=Unknown` → `rec_failures++`（`commit.go:253`）→ `initial` 分支 `next=+backoff`（`commit.go:284-291`）。

即「关闭」当前会改变持久化状态并累计失败次数，需要 O1 的守卫。

### 3.5 内存退避参数

- 起点 15s，每次 ×2，上限 600s，无抖动（`hostprobe.go:344-365`）。
- gen/digest 变化清零（`noteSnapshot`，`:331-342`）。
- 成功删除状态（`:348-351`）。

## 4. A2-1 设计

### 4.1 字段

```sql
retry_failures INTEGER NOT NULL DEFAULT 0
```

单一退避阶梯：统计「Runner 自身可重试的执行失败」，成功提交清零、代次变化清零；不参与 `DeriveState`、不入候选 SQL、不写 `rec_failures`。

**为什么只有一个字段（D3）**：若为「本地执行异常」再开一列，同一 Host 上两套阶梯会各自算出不同的 `next_probe_at`，A2 刚消除的双时间源会以另一种形式回来。故障性质的区别放在指标层（分原因计数器），调度层共用一条阶梯。

迁移：`PRAGMA table_info` 判断缺列 → `ALTER TABLE ... ADD COLUMN`（`CREATE TABLE IF NOT EXISTS` 对既有表不生效），与 C6-E 的 meta DDL 同在基础 schema 段。

### 4.2 原因枚举（取代 retry 布尔）

```go
type retryReason int

const (
	retryNone retryReason = iota
	retryCredentialPending
	retryLocalExecution
	retryCommitFailed
	retryOutcomeInconsistent
	retryStaleSnapshot
	retryCanceled
)
```

`retryStaleSnapshot` 与 `retryCanceled` 保留在枚举中，是为了让映射穷尽、不需要默认分支。

### 4.3 原因 → 调度 / Guard / 计数器 完整映射（本次冻结核心）

| 原因 | 触发 | 写 retry 调度 | `retry_failures` | Guard | 指标 |
| --- | --- | --- | --- | --- | --- |
| `retryNone` | `HostCapsCommitted` | 否，时间由 CommitHostProbe 决定 | 清零（同事务） | `unblockRoute(j)`，按 token 规则 | — |
| `retryCredentialPending` | 凭据变更中 | 是 | +1 | 不动 | `scheduled{credential_pending}` |
| `retryLocalExecution` | 其他凭据读取错误 / 本地执行异常 | 是 | +1 | 不动（无证据否定 Host） | `scheduled{local_execution}` |
| `retryCommitFailed` | CommitHostProbe 返回 error | 是 | +1 | **Block + Invalidate** | `scheduled{commit_failed}` |
| `retryOutcomeInconsistent` | `StoreFields` 不变量被破坏 | 是 | +1 | **Block + Invalidate** | `scheduled{outcome_inconsistent}` |
| `retryStaleSnapshot` | 快照代次已过期 | **否** | 不变 | 不动 | 不计数 |
| `retryCanceled` | `parent.Err() != nil` | **否** | 不变 | 不动 | 不计数 |
| `ErrNotReconciled`（非 retry） | 装配错误 | 否 | 不变 | 不动 | 不计数 |

共享规则：以上四种需要退避的原因共用同一个 `retry_failures` 与同一条时间阶梯；**不同原因之间不重置计数**（O4 紧跟一次凭据失败时是第 2 次失败，而不是重新从 15s 起）。

两条硬规则：

1. **Block 只有一种解除方式**：后续独立探测、使用当前代次、`CommitHostProbe` 提交成功后，按 `unblockRoute` 的 token 规则解除。`ScheduleHostProbeRetry` 成功、数据库重试成功、retry 计数写入，一律不解除。
2. **`retryOutcomeInconsistent` 必须退避**：Block 不阻止 Runner 再取这个 Host；不排重试就会以 30s 节奏无限重探一个本地不变量已损坏的 Host。它与 `retryStaleSnapshot` 的区别在于：stale 靠代次稳定自愈，O4 不会。

### 4.4 `finish` 重定义（数据库唯一权威）

| 组件 | 新职责 |
| --- | --- |
| `next_probe_at` | 唯一调度时间权威（持久化） |
| `claim` | 仅 `running` 互斥；不再判断 `next` |
| `finish` | 仅删除执行状态；不再计算或保存时间 |

- `probeState` 去掉 `backoff` / `next` / `gen` / `digest`，只留 `running`。
- 删除 `noteSnapshot`（gen/digest 变化的重置由 `ApplyCredChanges` 与换 Host 的写入路径负责）。
- `defer r.finish(key, retry)` 改为 `defer r.release(key)`。
- 顺序固定：**先 `ScheduleHostProbeRetry`，后 `release`**，避免释放与下一轮扫描之间出现无保护窗口。

**退化路径**：`ScheduleHostProbeRetry` 返回 error 时（DB 故障等），`release` 照常执行，不保留任何内存时间。后果是该 Host 下一轮 30s 扫描再探——这是可接受的上界，且不会出现「内存与数据库各说一套」。`rejected{reason=db_error}` 与四个 `scheduled{reason=...}` 分开统计，不混入「成功安排重试」的口径。

### 4.5 O1 守卫位置

```go
capv, mode, note, err := out.StoreFields()
if err != nil {
	// O4：Block + Invalidate + retryOutcomeInconsistent
	return
}

// 只判断 Runner / 上层生命周期，不判断 Probe 子 Context。
if parent.Err() != nil {
	return // retryCanceled：不提交、不计数、不调度
}

res, err := r.o.Store.CommitHostProbe(...)
```

- 放在 `StoreFields` 之后、`CommitHostProbe` 之前，覆盖 `StoreFields` 执行期间的取消。
- 禁用 `ctx.Err()`：子 Context 超时是真实探测失败，必须照常提交。
- 明确这不是原子消除：`parent.Err()` 通过后、事务开始前仍可能取消。该检查是**提交边界**，不宣称消除竞态。

### 4.6 `ScheduleHostProbeRetry` 与 CAS 七项

```go
type HostProbeRetry struct {
	SourceID int64
	Host     string
	Gen      int64 // 执行起点快照代次
	At       int64 // Unix 秒
}

// 返回 false 表示拒绝（未写任何字段）。
func (s *Store) ScheduleHostProbeRetry(r HostProbeRetry) (bool, error)
```

失败次数不由 Runner 传入：事务内执行 `SELECT retry_failures`（同一把写锁下），按 `n = min(old+1, 7)` 计算，且 **UPDATE 写入的就是这个 `n`**（不是 `retry_failures+1`）。读取、计算、写入是同一个值，`old=7` 时写入仍为 7，字段自身不会越过上限。

事务（`BEGIN IMMEDIATE`）内必须同时满足：

1. `registry_host_recovery.gen = expectedGen`
2. `registry_host_gen.gen = expectedGen`（代次权威在此表，不只信 recovery 行；缺行视为不匹配）
3. `next_probe_at <= At`（只有仍到期才允许改；已被推进到未来则不覆盖）
4. `sources.enabled = 1`
5. `sources.status <> 'archived'`
6. `sources.repo_host = expectedHost`，且 `source_id / family='registry' / scope` 完整匹配
7. `registry_host_recovery.state <> 'hard-excluded'`

```sql
UPDATE registry_host_recovery
   SET next_probe_at = ?, retry_failures = ?, updated_at = ?
 WHERE source_id = ? AND family = 'registry' AND scope = ?
   AND gen = ?
   AND next_probe_at <= ?
   AND state <> 'hard-excluded'
   AND EXISTS (SELECT 1 FROM registry_host_gen g
                WHERE g.host = ? AND g.gen = ?)
   AND EXISTS (SELECT 1 FROM sources s
                WHERE s.id = ? AND s.enabled = 1
                  AND s.status <> 'archived' AND s.repo_host = ?)
```

- 时间一律 Unix 秒，禁止混入纳秒。
- `RowsAffected()==0` 即拒绝；拒绝时不写任何字段、不改 Guard、不重试。
- 拒绝原因分桶：`gen_mismatch` / `cas_lost` / `source_unavailable` / `db_error`（事务内先做一次分类 `SELECT`，分类只用于指标，不参与判定）。
- 第七项只排除 `hard-excluded`，不是 `state IN (...)` 白名单；其余状态仍由 `next_probe_at` 决定是否到期。`hard-excluded` 的语义是永久退出普通恢复循环，`next_probe_at=0` 是配套状态，不能被执行失败重新推进到未来（R2-1 裁定封死）。
- `registry_host_gen` 缺行按不匹配处理：`EXISTS` 不成立即拒绝。

### 4.7 清零规则

| 时机 | 位置 | 动作 |
| --- | --- | --- |
| 探测结果提交成功（含 `Cap=Unknown` 的失败提交） | `commit.go` UPSERT | `retry_failures=0` |
| 代次递增 | `host.go:363-372` | 0 |
| 换 Host | `host.go:127-134` | 0 |
| enabled 0→1 | `store.go:827` | 0 |
| 种子 | `recovery_seed.go` | 默认 0 |

只有 `retryNone` 且为当前代次的成功提交才清零；`retryStaleSnapshot`、`retryCanceled`、`ScheduleHostProbeRetry` 的 CAS 拒绝（含 `gen_mismatch` / `cas_lost` / `source_unavailable` / `db_error`）**一律不清零**，计数原样保留。

理由：这些清零路径都重新定义了「当前代次的调度起点」，旧阶梯不再适用。

### 4.8 算法

`D(n) = min(15s × 2^(n-1), 600s)`，n=`retry_failures`（按 7 封顶）；`next_probe_at = At + D(n)`；不加抖动。

## 5. A2-2 观测（D1 批准：atomic + snapshot）

| 指标 | 形式 | 语义 |
| --- | --- | --- |
| `hostprobe_retry_scheduled_total` | 按原因分列的独立 Counter（credential_pending / local_execution / commit_failed / outcome_inconsistent） | 调度写入成功次数 |
| `hostprobe_retry_rejected_total` | 按原因分列（gen_mismatch / cas_lost / source_unavailable / db_error） | 拒绝次数 |
| `hostprobe_retry_pending` | Gauge，SQL `COUNT(*) WHERE retry_failures>0 AND next_probe_at>now` | 退避中的 Host 数 |
| 延迟分布 | 固定桶 15/30/60/120/240/480/600s 计数 + 总和 | 代替 Histogram |

约束：不引 Prometheus 客户端、不加动态标签、不用内存 map 推算 pending；指标必须能区分「Runner 执行失败」与「CommitHostProbe 记录的探测失败」（后者仍由 `rec_failures` 与现有 recovery 指标承载）。

## 6. A2-3 / A2-4：明确不做

- **逐 Host 定时器**：30s 扫描的延迟边界已明确；定时器不减少工作量，只增加取消/重启/生命周期复杂度。
- **持久化 claim / 多 Runner**：`probeState.running`、Runner token map、Guard failClosed 都不是跨进程锁。多实例需要 DB claim/lease、owner token、续租、fencing token、Guard 一致性与 seed 并发安全，不能在 A2 顺手加字段。

## 7. A2-6 验收

T1 首次失败 15s；T2 15/30/60/120/240/480/600；T3 封顶 600s；T4 重启保留时间与计数；T5 成功提交清零且时间由 CommitHostProbe 决定；T6 旧代次不写新代次；T7 stale 不覆盖；T8 提交成功后 `release` 不覆盖；T9 parent 取消不计数不调度（并验证子 Context 超时仍提交）；T10 disabled/archived 不写；T11 调度成功不解除 Block；T12 TTL 物化语义不变；T13 候选准入不变。

新增：T14 `retryOutcomeInconsistent` 走 Block + 调度且 `rec_failures` 不变；T15 七项 CAS 逐条破坏后均拒绝；T15b `old=7` 时再失败仍写入 7、延迟仍为 600s（字段不越过上限）；T16 真实 SQLite 端到端（Runner → retry → 重开 Store → `ListDueHostProbes` → Runner）。

门禁：`gofmt -l .`、`go build ./...`、`go vet ./...`、`go test ./... -count=1`、`go test -race ./internal/store ./internal/runner -count=1`。
