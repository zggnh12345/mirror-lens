# 3.5.5 Canonical Schema

状态：P0 / P0.5 / P1 / P2 / P3 已完成，待发布。基线 `3.5.4 @ 3e3813e`。

## 交付顺序与验收

| 阶段 | 内容 | 证据 |
|---|---|---|
| P0 | 冻结 3.4.6 / 3.5.4 真实 Schema、字段映射、空 Host 分布 | `docs/schema-inventory/`、`docs/schema-migration-mapping.md` |
| P0.5 | 单实例锁；恢复与升级 journal 门禁；FIFO 故障注入 | `internal/dblock`、`main.go`、`scripts/restore_test.sh` |
| P1 | Canonical DDL + `schema_meta`；三份库 Schema hash 一致 | `internal/store/schema`、`db-migrate verify` |
| P2 | 离线迁移 + 原子切换 + 回滚副本 | `cmd/db-migrate`、`scripts/upgrade-db.sh`、`scripts/upgrade_test.sh` |
| P3 | 运行时只认 Canonical；历史迁移冻结；同版发布 | `store.Open`、`registry_identity_state` 清退、`internal/version` |

## 不变量

1. Schema 只有一份：`internal/store/schema/canonical.sql`。
2. `repo_host` 是 Host 归属的唯一持久化事实；`''` 永远表示无归属。
3. `docker.io` / `ghcr.io` 必须显式存储，不做空串隐式 Hub。
4. 不持久化 `registry_identity_state`；API 字段由 Host + `github_cap` 派生。
5. 旧库（没有 `schema_meta`）在 `store.Open` 阶段被拒绝，不在启动时补列、
   回填或执行历史迁移。
6. 历史迁移 SQL 与 checksum 常量原样保留，但运行时不可达；历史记录不写入
   新库。
7. 回滚只恢复 `mirror-lens.db.pre-3.5.5`（含 `-wal`/`-shm`）和原
   `secret.key`，不做 DB/key 联合替换。

## 命令

```bash
# 构建离线工具
go build -o db-migrate ./cmd/db-migrate

# 空库 / 3.4.6 / 3.5.4 -> Canonical
./db-migrate init --out fresh.db
./db-migrate migrate --in 3.4.6.db --out 3.4.6-canonical.db --baseline 3.4.6
./db-migrate migrate --in 3.5.4.db --out 3.5.4-canonical.db --baseline 3.5.4

# 校验
./db-migrate verify --db 3.5.4-canonical.db

# 生产离线升级（停服、复制、checkpoint、迁移、原子切换、回滚副本）
# 同时生成 600 的 secret.key.pre-3.5.5 与 DB/key/tool 的 manifest
./scripts/upgrade-db.sh --data /path/to/data --tool ./db-migrate --baseline 3.5.4
./scripts/upgrade-db.sh --recover --data /path/to/data --tool ./db-migrate
```

## 发布门禁

- `go test ./...` 全绿。
- `scripts/restore_test.sh` 全绿（uid 1000 用例在无 CAP_SETUID 的环境跳过）。
- `scripts/upgrade_test.sh` 全绿。
- 三份库 `verify` 的 `schema_hash` 相同。
- 生产升级前完成 DB + key + manifest 备份，并演练恢复。
- 3.5.5 必须与 Canonical Schema 同版发布；旧二进制没有 `schema_meta` 检查，
  发布流程禁止它直接打开新库，回滚必须恢复旧 DB 与 key。
