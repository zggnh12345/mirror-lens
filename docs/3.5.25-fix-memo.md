## 一、背景：为什么要修

3.5.24 的 §2.3 把「未知连接地址」从旧版「静默默认 docker.io」改成「必须显式选归属 Registry（host/repo_host），否则 400」。发布后复核发现：**归属选择既没能可靠决定能力，还会在用户图省事选错时反噬探测。**

代码取证结论（均为 3.5.24 现状）：

1. **`repo_host` 早已不是能力的真实来源。** `store.Source` 注释（`store.go:48-76`）明确：`source_host_caps`（源 × Host 能力矩阵）才是 14c 后的唯一持久化事实；`RepoHost` 只是兼容展示用的主 Host，`RegistryIdentity` 是派生值。`RepoHost` 在 gateway / scheduler / adapter 中零引用，grep 只命中 store 自身。
2. **选 docker.io 会把能力钉成 Yes，架空探测。** `store.go:495-497`：选 docker.io 且 `DockerCap==Unknown` 时强置为 `CapYes`（ghcr.io 同理强置 GhcrCap=Yes、DockerCap=No）。
3. **探测探不出「沉默的不支持」。** `runner.go:361` 中 `CapYes` 的 kind 仍进探测列表；但 `applyInner`（`runner.go:449-455`）只认明确的 `VerdictYes`/`VerdictNo`。一个实际只代 ghcr 的源，其 docker 探测在 `fetchManifest` 取 `library/alpine` 返回 404 时，只在 `docker.go:170` 附近设 `res.Error`，**不设 `Verdict`**（空串），两个 case 都不进 → `capv` 保持 Yes → `SetCapsLive` 继续写 Supported。只有 `/v2/` 返回 404/410 或 HTML 假站点（`docker.go:125/134`）才给 `VerdictNo`。
4. **所以「图省事选 docker.io」会回到旧版的原点**，而且更糟：UI 让用户以为自己确认过归属。

**修复总原则**：归属（逻辑身份，历史遗留字段）与能力（探测结论）解耦。**添加时不要求用户选归属；能力全部由探测写回 `source_host_caps`；foreign host 走「添加 Host」逐个登记。**

## 二、修复项（F1–F4 + 配套 F1b，均标定为 3.5.25）

### F1 去掉「归属 Registry（必选）」选择项

- **现状**：添加/编辑面板各有「归属 Registry（必选）」下拉框（`index.html:266` 新增、`index.html:299` 编辑），选项 docker.io / ghcr.io / quay.io / gcr.io；API `addSource` 对未知域名无 host 返回 400（`api.go` 673-692，`p1_2_uiapi_test.go` 锁定该行为）。
- **修复**：
  1. UI 移除新增/编辑面板的归属下拉框；提示语改为「保存后自动识别它支持 Docker Hub / GitHub / GHCR」。
  2. API `addSource` 不再因未知域名/IP 无 host 而 400；新增源不再强置 `DockerCap=Yes` / `GhcrCap=Yes`（删除 `store.go:495-503` 的强置逻辑），能力保持 `CapUnknown` 交首次探测裁定。
  3. Foreign host（quay.io / gcr.io / registry.k8s.io / mcr.microsoft.com 等）不再由该下拉框登记，改走既有「添加 Host」入口（`store.AddSourceHost`，`hostcaps.go:392`），可加多个；登记后探测自动写回能力、自动补 Realm policy。
  4. 同步更新 `p1_2_uiapi_test.go` / `add_source_test.go` / `web_panel_test.go` 中依赖「无 host 必 400」「RepoHost 默认值」的断言。
- **收益**：消除「用户猜错归属 → 能力被钉死」的路径；归属与能力解耦；与 14c 多 Host 模型一致。
- **风险与边界**：
  - 新源初期面板显示「未知」而非立即「支持」，需等首轮探测（观察池 L1 连续通过 2 次后进 L2，见 `runner.go:observePass`）。
  - **必须配套补 `docker.go`：当 `fetchManifest` 明确 404/410 时设 `Verdict=VerdictNo`**，否则 CapUnknown 也纠不回 No（与 F1 是同一个缺口，缺一不可）。注意区分「源不代 docker」与「该仓库不存在」——两者都可能 404，不能简单把 404 全判 No；可先以 `/v2/` 层结论为准，manifests 404 仅记 Error 不改 Verdict，留作观察项。
  - `addSource` 仍应保留 `registryhost.Check(host)` 对**显式传入** host 的校验，避免非法 Host 入库。

### F2 连接地址输入框包含端口

- **现状**：协议、连接地址、端口是三个独立字段（`index.html:256-264` 新增、`:290-297` 编辑）；连接地址 label 明确写「不含协议和端口」。
- **修复**：合并为单一「连接地址」输入框，**彻底删除独立端口框**。
  - label：`连接地址（域名 / IPv4 / IPv6，可带端口）`
  - placeholder：`docker.1panel.live 或 mirror.example.org:5000 或 [fd00::1]:5000`
  - 下方 hint：`可只填域名（HTTPS 默认 443 / HTTP 默认 80），也可带端口，如 mirror.example.org:5000；IPv6 请用 [地址]:端口。`
  - 保存时从地址栏解析 host / port 再构造 `SourceEndpoint`；不再有独立端口字段。
  - 编辑面板同步（删除 editPort，editHost 带端口）。
- **收益**：少一个字段，符合用户「连接地址最好包含端口」的直觉；IPv6 地址必须带括号+端口才能无歧义表达，合并后反而更清晰。提示写全三种写法，避免用户不知道能不能带端口。
- **风险与边界**：
  - 解析要处理：无端口按协议默认（HTTPS 443 / HTTP 80）、IPv6 字面量 `[...]:port`、非法端口（1–65535）报 400、地址里误带 `https://` 前缀时的兼容提示。
  - API 现有 `connect_host`/`scheme`/`port` 三字段（`api.go:612-627`）保持兼容，不强改协议；UI 合并属前端+一层解析适配。
  - 编辑链路 `TestPatchSourceEndpoint` 需同步调整。

### F3 去掉 HTTP 选项里莫名其妙的「See §2.3 警告」

- **现状**：新增/编辑面板的协议下拉里写死 `<option value="http">HTTP（明文，See §2.3 警告）</option>`（`index.html:260`、`:293`）。「§2.3」是任务书/设计文档的内部章节号，直接暴露给面板用户莫名其妙；且真正的安全提示已经在下方 `addHttpWarn` / `editHttpWarn` 的 `⚠ 已选 HTTP：认证信息与传输内容将以明文传输…` 里完整给出。
- **修复**：下拉文案改为通顺中文，例如 `HTTP（明文，不推荐）` 或 `HTTP（明文）`；删除对内部文档章节号的引用。保留下方红色警示条作为实际说明。
- **收益**：面板文案自洽，不再出现无上下文的内部编号。
- **风险**：纯文案改动，风险极低；注意新增/编辑两处一并改，避免不一致。

### F4 删除 ML_HOSTPROBE_* 环境变量，探测仓库全量收敛到 config

- **现状**：Host 探测仓库映射只读环境变量 `ML_HOSTPROBE_REPOS`（`main.go:154-169` 解析、`main.go:601` 注入 `HostProbeOptions.Repos`）；缺失时仅打日志跳过（`hostprobe.go:319`）——生产实测该变量未设置，等于所有 foreign host 探测 job 全被跳过。而项目设计原则是「只留四个开关，其余参数在配置文件里」（`main.go` 注释）。`config.Probe`（`config.go:357-365`）目前只有 `allow_private`/`interval_sec`/`concurrency`/`timeout_sec`/`sample_mib`。
- **修复**：
  1. `config.Probe` 新增 `host_probe_repos`（map[string]string）；`config.example.yaml` 的 `probe:` 段写入**内置全表**（8 个多源 Host + lscr.io 共 9 个的代表仓库，均取自 3.5.8 设计 §5.5 的真实公开 Host 验收记录，用实测通过且带 digest 的仓库；用户给的四行是其中子集）：
     ```yaml
     probe:
       allow_private: false
       host_probe_repos:
         gcr.io: distroless/static:nonroot
         registry.k8s.io: pause:3.9
         "*.pkg.dev": google-samples/containers/gke/hello-app:1.0
         quay.io: prometheus/busybox:latest
         mcr.microsoft.com: hello-world:latest
         registry.gitlab.com: gitlab-org/cli:latest
         public.ecr.aws: docker/library/alpine:latest
         cgr.dev: chainguard/static:latest
         lscr.io: linuxserver/traefik
     ```
     说明：
     - **range 写法**：`*.pkg.dev` 由 `registryhost.Match` 做模式匹配（`hostprobe.go:334`），默认映射里的 key 也走同一匹配；若 `Repos[host]` 精确查找不认通配，实施时按 `registryhost.Match` 的语义补一次查找（对应真实 host `us-docker.pkg.dev`，3.5.8 实测 `google-samples/containers/gke/hello-app:1.0`）。
     - **lscr.io（用户要求纳入 3.5.25）**：用户已自行实测，要求加入探测映射与 `multi_origin_hosts` 范围。代表仓库用 `linuxserver/traefik`（2026-11-26 实测 `GET https://lscr.io/v2/linuxserver/traefik/manifests/latest` 返回 401=需 token、仓库存在；同站的 nextcloud/plex 也可用）。启用它要同步改 `config.example.yaml` 的 `multi_origin_hosts`（加入 `lscr.io`）并更新那条「暂不启用」注释——这属行为变更，与 F1 一起单独评审。
     - **docker.io / ghcr.io / github 不需要**：这三类走机制 A 的内置探测，不走 `host_probe_repos`。
     - **tag 可省**：`ProbeRegistryHost` 的 `Tag` 默认 latest；3.5.8 表里部分仓库用固定 tag（3.9 / nonroot / 8.0），配置只写 `repo`，tag 由代码默认或另设 per-host tag（实施时定，不阻塞本备忘录）。
     - **仓库可能下线**：3.5.8 §5.3 要求「若仓库下线，替换为同 Host 稳定公开仓库并重新记录 digest」——这些映射不是一劳永逸，需纳入定期复核。
  2. **`main.go` 彻底删除三个环境变量**——`ML_HOSTPROBE_REPOS`（`main.go:154-169`/`:601`）、`ML_HOSTPROBE_INTERVAL`（`main.go:144-152`）、`ML_HOSTPROBE_SCAN`（`main.go:130-140`）——全部改为只读 `cfg.Probe.HostProbeRepos` 及新增的 config 字段（`host_probe_interval_sec` / `host_probe_scan_sec`）。**不保留环境变量覆盖**：生产实测 `docker inspect mirror-lens` 的 Env 只有 `DATA_DIR`/`PATH`/`TZ`，这三个变量从未被使用，属于历史遗留；项目设计原则是「只留四个开关，其余参数在配置文件里」（`main.go` 注释），保留兼容只会制造"到底哪个生效"的歧义。临时调试可直接改 config 或用新开关。
  3. 生产 `config.yaml` 同步写入该段（属生产配置变更，须单独授权，不在本备忘录的自动实施范围内）；生产容器 Env 无需改动（三个 `ML_HOSTPROBE_*` 本来就没设）。
- **收益**：配置项集中收敛到 `config.yaml`，与其余参数一致；新部署默认带上 9 个内置多源 Host 的探测仓库，避免 Host 探测因缺配置长期跳过；消灭三个从未被使用的历史环境变量，消除"config 与环境变量谁生效"的歧义。
- **风险与边界**：
  - 新增 config 字段需有默认值兜底，旧配置文件不含该字段时不得破坏启动（`Default()` 补默认 map，含 9 个 host 的映射与 interval/scan 默认值）。
  - 删除环境变量是行为变更：若有用户正在用 `ML_HOSTPROBE_*` 临时覆盖（生产实测没有，但不能排除其他部署），升级后这些设置会失效——需在发布说明中明确告知，给出 config 迁移写法。
  - 生产 `config.yaml` 的改动须单独授权、先备份，不能随代码一起静默生效。

### F1b 自动探测完善（F1 的配套，缺一不可）

去掉归属选择后，能力必须完全靠探测得出。现行探测是**两套机制**，完善要分别做：

**机制 A：内置三类协议探测（runner.Engine，已有，需修纠 No 缺口）**
- 探什么：docker.io / ghcr.io / github 三类固定 kind（`runner.go:allKinds`），由 `kindsFor`（`runner.go:351`）决定每个源探哪些；`CapYes`/`CapUnknown`/`CapNo` 都会入列（`CapYes` 也探，用于健康管理）。
- 怎么完善：
  1. **补沉默不支持的判定**：`docker.go` 的 `fetchManifest` 明确 404/410 时设 `Verdict=VerdictNo`（现在只在 `/v2/` 404/410 或 HTML 假站点时设，见 `docker.go:125/134/170`）；这样 `applyInner` 的纠 No 分支（`runner.go:454`，要求 `capv==CapUnknown`）才有机会生效。
  2. **去掉强置 Yes 后保持 CapUnknown 到首次探测**：确认 `observed`（`runner.go:390`）的观察池只拦 `CapUnknown && pending`，新源会先 L1 连过 2 次（`observePass`）再进 L2 完整探测——这个路径对「不预置能力」的新源是通的，不需要额外改。
  3. 注意区分「仓库不存在」与「源不代此协议」：两者都可能 manifest 404，不能一律判 No；先以 `/v2/` 层结论为准，manifests 404 仅记 Error 不改 Verdict 的保守做法列入观察项，实施时按实测定。

**机制 B：Foreign Host 探测（runner.HostProbeRunner，需把 F4 配置接上）**
- 探什么：每个 `(源, Host)` 一行，来自 `registry_host_recovery`（`ListDueHostProbes`），由 `store.AddSourceHost` 登记 Host 时建行/建 caps/建 policy（`hostcaps.go:392`）——这就是 F1 里「foreign host 走添加 Host 入口」能自动探的原因。
- **瓶颈在探测仓库映射**：`hostprobe.go:301` 对每个 Host 必须查到该 Host 上真实存在的代表性仓库（`Repos[host]`），查不到就跳过并告警（`hostprobe.go:319`）。不同 Registry 没有通用仓库，猜一个只会 404 判错。
- 怎么完善：
  1. F4 把 3.5.8 §5.5 实测过的 8 个多源 Host + 用户实测的 lscr.io 共 9 个的仓库映射写进 `probe.host_probe_repos`（详见 F4 全表），启动时由 `main.go` 注入 `HostProbeOptions.Repos`，新部署默认就能探这些 Host。
  2. `reconcileRepos`（`hostprobe.go:235`）会在仓库映射变化时重置结论——config 改动后能力会自动重测，不用手动干预。
  3. 新 Host 未在映射表中时，面板给出明确提示「该 Host 尚无探测仓库配置，请先在 config 的 probe.host_probe_repos 添加 host=repo」，替代现在仅打日志的静默跳过。
  4. `filterAllowed`（`hostprobe.go:325`）按 `registry.multi_origin_hosts` 白名单过滤，关闭的 Host 不探——配置说明里要写明「加了 Host 还要确认白名单放行」。

**其他 Host 怎么办（重要边界）**：`probe.host_probe_repos` 是开放的 `map[string]string`，上面 9 行只是**默认预置值，不是白名单**。
- 现状：未在 map 中的 Host，`hostprobe.go:301` 会把它的 job 直接跳过、不入队，只集中告警一次（`hostprobe.go:319`）——该 Host 的能力永远停在 Unknown，面板无标签、调度不采用。
- 探测层其实有兜底：`ProbeRegistryHost` 在 `p.Repo==""` 时用 `library/alpine`（`registryhost.go:174-175`）。但 runner 在生成 job 时就已经拦掉了，**兜底永远触发不到**。这是刻意设计：`library/alpine` 只在 docker.io 存在，拿到 quay.io / gcr.io 上探必然 404，会把一个可用的源误判成未知（注释 `hostprobe.go:34-37` 明说「猜一个只会制造 404」）。
- 所以其他 Host 的解法按成本排序：
  1. **在 config 里加一行 `host=repo`**（无需改代码，最简）。 selectivity 由配置承担：每个 Host 填一个它上面真实存在的代表性仓库。
  2. 面板「添加 Host」时提供「探测仓库」可选字段，随 Host 一起登记（需新设计，把仓库映射从 config 下沉到 per-host 数据；避免每次加新 Host 都要改 config 重启）。
  3. **不建议**取消 runner 的映射拦截直接吃 `library/alpine` 兜底——会把非 docker.io 的可用源误判为不支持。
- 待确认：其他 Host 长期靠配置手工登记是否可接受；若不可接受，采用解法 2 并把探测仓库纳入 Host 管理 UI。

**探测结果写回**：两机制最终都汇入 `source_host_caps`（机制 A 经 `SetCapsLive`，机制 B 经 `CommitHostProbe`），面板 HUB/GHCR/GCR/PKG 标签由该表派生——去掉归属选择后，这些标签就是用户判断「它支持什么」的唯一依据，因此 F1/F1b/F4 必须一起上线。
