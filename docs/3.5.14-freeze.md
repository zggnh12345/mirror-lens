## 0. 版本结构

3.5.14 拆成三个内部里程碑，最终只发布一个 `v3.5.14`：

| 阶段 | 交付 | Schema | 回滚 |
|---|---|---|---|
| 3.5.14a | 新表、确定性回填、Realm 完整性、运行时新写路径 | S14a | 恢复迁移前数据库 + 3.5.12 镜像 |

`3.5.14a/b/c` 是内部阶段名，不是 SemVer 发布标签。最终发布标签为 `v3.5.14`；`3.5.15` 的 CredStore 依赖 3.5.14c，不依赖 3.5.14b。

Schema 标签冻结：

- 14a / 14b：`schema.Version = "3.5.14a"`，Canonical Hash 记为 `H14a`。
- 14c / 最终发布：`schema.Version = "3.5.14"`，Canonical Hash 记为 `H14c`。

## 1. 数据模型

```sql
CREATE TABLE source_host_caps (
    source_id           INTEGER NOT NULL,
    host                TEXT NOT NULL,
    enabled             INTEGER NOT NULL DEFAULT 1
                        CHECK (enabled IN (0, 1)),
    last_verdict        TEXT NOT NULL
                        CHECK (last_verdict IN
                          ('Supported','Unsupported','Inconclusive','Mismatch')),
    effective_status    TEXT NOT NULL
                        CHECK (effective_status IN
                          ('Unknown','Supported','Unsupported','Mismatch')),
    registry_path_mode  TEXT NOT NULL DEFAULT ''
                        CHECK (registry_path_mode IN ('', 'native', 'host_prefix')),
    registry_prefix     INTEGER NOT NULL DEFAULT 0
                        CHECK (registry_prefix IN (0, 1)),
    PRIMARY KEY (source_id, host),
    FOREIGN KEY (source_id) REFERENCES sources(id) ON DELETE CASCADE,
    CHECK (effective_status <> 'Supported'
           OR registry_path_mode IN ('native', 'host_prefix'))
);

CREATE INDEX idx_source_host_caps_host
ON source_host_caps(host, effective_status, enabled);
```

约束：

- 新表不存 `registry_cap`。`registry_cap` 只是 14a/14b 的旧字段投影，由 `effective_status` 派生。
- 新表不存 `last_supported_at`、`registry_probe_at`、`registry_probe_error`。Foreign Host 的探测事实和成功时间以 `registry_host_recovery` 为唯一来源；旧 `sources` 字段只做投影。
- `host` 写入前必须经 `registryhost.Check` 规范化；禁止大小写、尾点、空白差异产生重复行。
- `effective_status='Supported'` 时 `registry_path_mode` 必须是 `native` 或 `host_prefix`；其他状态允许空字符串。
- `registry_prefix` 只对 `ghcr.io` 有意义，但所有行都可存 0/1。

## 2. 状态模型

`last_verdict` 是最近一次探测观察；`effective_status` 是当前有效能力结论。

| 最近探测 | last_verdict | effective_status |
|---|---|---|
| 首次成功 | Supported | Supported |
| 首次确认不支持 | Unsupported | Unsupported |
| 首次网络/认证/仓库状态不确定 | Inconclusive | Unknown |
| 已 Supported 后 Inconclusive | Inconclusive | 保持 Supported |
| 已 Unsupported 后 Inconclusive | Inconclusive | 保持 Unsupported |
| 已 Supported 后确认内容不一致 | Mismatch | Mismatch |

规则：

- `Inconclusive` 不得抹掉已有的 `Supported` / `Unsupported` 结论。
- `Mismatch` 是一次完整验证后的硬排除：相同仓库、相同引用、Manifest 内容与官方 Digest 确实不一致；排除认证失败、网络失败和格式协商差异。
- `Mismatch` 不进入普通 Unsupported 的六小时重试；只能由管理员显式重置为 `Unknown`，再重新探测。
- 真实健康失败、冷却和熔断仍可临时阻止调度；“保留 Supported”不等于无视运行时健康。

候选准入：

```text
source 未归档
AND sources.enabled = 1
AND source_host_caps.enabled = 1
AND effective_status = 'Supported'
AND registry_path_mode IS NOT EMPTY
AND Host 全局准入允许
AND health / recovery 允许
AND policy_exists(source_id, host)
AND（Foreign Host）成功结论未过期
```

`policy_exists` 对 Docker / GHCR 同样适用：六个双用途 Source 的 `ghcr.io` 策略必须在 14a 补齐；补不齐则 caps 行 `enabled=0`，14b 不得把它们放进候选。

Docker Hub / GHCR 保持现有行为：能力由用户配置/`SetCapsLive` 写入，不套用 Foreign Host 的 `registry_host_recovery` TTL；`effective_status=Supported` 即可，不因缺少 recovery 行被排除。Foreign Host 的 TTL 只认 `registry_host_recovery.last_success_at`。

`multi_origin_hosts` 只约束 Foreign Host；Docker Hub / GHCR 是核心协议路径，不因该白名单未列出而被排除。14a/14b 必须回归这条既有行为。

## 3. 14a 旧字段投影

### 3.1 投影表

| 新表 Host | 旧字段投影 |
|---|---|
| `docker.io` | `docker_cap` |
| `ghcr.io` | `ghcr_cap`、`ghcr_prefix` |
| 原 `repo_host` 且是 Foreign Host | `registry_cap`、`registry_path_mode`、`registry_probe_at`、`registry_probe_error` |
| 其他新增 Foreign Host | 不投影 |
| 无 Registry Host 的 Source | 不创建 caps 行，不投影 |

如果原 `repo_host` 是 `docker.io` 或 `ghcr.io`，它只走对应协议槽位，不再投影到 `registry_cap` / `registry_path_mode`。

`github_cap` 不属于 Registry Host 能力：14a/14b 继续只写旧字段，不建 `github.com` caps 行；14c 不删除 `github_cap`、`git_cap`、`range_cap`。

### 3.2 投影值

- `effective_status=Supported` → `registry_cap=1`
- `Unsupported` → `0`
- `Unknown` → `-1`
- `Mismatch` → `2`

投影取 `effective_status`，不取 `last_verdict`。`last_verdict=Inconclusive` 且 `effective_status=Supported` 时，旧投影仍为 1。

14a 的投影**不读取 `enabled`**：回填时即使某行因 `policy_gaps` 被置 `enabled=0`，旧字段仍按 `effective_status` 投影，保证 14a 旧读路径不变。14b 建立 `SetSourceHostEnabled` 后，用户停用某 Host 时同步把对应旧投影写成 0（`enabled ? cap : 0`），保证回滚到 14a 时停用意图仍生效；策略缺口造成的 `enabled=0` 属于迁移差异，必须在 14b 候选中显式记录，不能静默改变旧路径。

### 3.3 写入口所有权

- `SetCapsLive`：只写 `docker.io` / `ghcr.io` caps 行，以及 `docker_cap`、`ghcr_cap`、`ghcr_prefix`；`github_cap` 继续只写旧字段。
- `CommitHostProbe`：只写 Foreign Host caps 行，以及原 `repo_host` 的 `registry_cap`、`registry_path_mode`、`registry_probe_at`、`registry_probe_error`。
- 两个入口都必须在自己的 `BEGIN IMMEDIATE` 事务内完成 caps + 投影；不能顺手改对方的投影字段。
- 新增 Foreign Host 探测成功时，绝不能修改 `repo_host`，也不能修改旧 Foreign 投影。

### 3.4 不变量

```text
新表可以有多个 Host
旧 Foreign 投影最多对应原 repo_host
repo_host 不因新增 Host 改变
新增 Foreign Host 不覆盖旧字段
所有必要投影与权威表写入同一事务
```

14a 验收比较的是“旧查询在 14a 前后一致”，不是“旧查询 == 新查询”。14a 的新查询只做 shadow，允许出现新增 Host 的预期差异；到 14b 才做逐 Host 的 old/new 对比，新增 Host 属于预期新增，必须显式列出。

`SetRepoHost` 在 14a 期间保持 Store 方法，不新增 API；若调用，必须在同一事务内迁移原 Foreign 投影、策略、健康和恢复状态。若无法保证，14a 明确冻结该入口。

## 4. 回填规则

对每个现有 Source：

1. `repo_host` 非空且不是 `docker.io` / `ghcr.io`：写 `(source_id, repo_host)`，`effective_status` 由旧 `registry_cap` 映射。
2. `docker_cap` 为 1/0/-1：写或合并 `(source_id, docker.io)`，`effective_status` 由 `docker_cap` 映射；`registry_path_mode='native'`。
3. `ghcr_cap` 为 1/0/-1：写或合并 `(source_id, ghcr.io)`，`effective_status` 由 `ghcr_cap` 映射；`registry_path_mode='native'`，`registry_prefix=ghcr_prefix`。
4. `repo_host=''`：不创建 Foreign caps 行；不从 `base_url` 推断 Host；不把空字符串映射为 `docker.io`。
5. 同一 `(source_id, host)` 只能一行；冲突按以下优先级消解，不能静默覆盖：
   - `docker.io`：`docker_cap` 优先，`registry_cap` 只在 `docker_cap=-1` 时参考。
   - `ghcr.io`：`ghcr_cap` 优先，`registry_cap` 只在 `ghcr_cap=-1` 时参考。
   - 其他 Host：`registry_cap` 优先。
   - 两个已知值冲突且无法消解：迁移 fail closed，输出 `source_id` / `host` / 两个值，人工处理。
6. 旧字段不删除；回填与投影在同一事务内完成。
7. 回填时 `enabled=1`（保留旧用户许可），Source 级 `sources.enabled` / 归档仍由上层门禁控制；只有 4.1 的 `policy_gaps` 可以把对应行置 `enabled=0`。

旧能力值到新状态的映射必须同时写 `last_verdict` 和 `effective_status`：

| 旧值 | last_verdict | effective_status |
|---|---|---|
| 1 | Supported | Supported |
| 0 | Unsupported | Unsupported |
| -1 | Inconclusive | Unknown |
| 2 | Mismatch | Mismatch |

Docker / GHCR 的 `docker_cap` / `ghcr_cap` 只允许 1/0/-1；出现 2 视为数据异常，迁移 fail closed。

### 4.1 双用途 Source 的 Realm 缺口

生产已确认 6 个双用途 Source：54、69、71、86、88、638。它们有 `docker_cap=1` 和 `ghcr_cap=1`，但只有 `(source_id, docker.io)` 策略，没有 `(source_id, ghcr.io)` 策略。

14a 必须：

- 按 `policySeedForSource` 规则，用实际 BaseURL 和 GHCR 官方 Realm 生成 `(source_id, ghcr.io)` 策略。
- 校验生成的策略合法；不能安全生成时进入 `policy_gaps`，并把该 `ghcr.io` caps 行 `enabled=0`。
- 不允许出现“caps 行 enabled=1、policy 缺失、14b 直接 fail closed”的第三种状态。
- 14a 的旧字段投影不因 `enabled=0` 改变（见 3.2），所以旧 GHCR 路径仍按原 `ghcr_cap` 工作；14b 才按新门禁排除该行。
- 如果某行被置 `enabled=0`，14b 的 GHCR 候选会比 14a 少；必须在 14b 验收中作为显式差异记录，不能声称全量 diff 为空。

### 4.2 行数与候选基线

生产 2026-11-17 只读盘点（95 个 Source）：

- Foreign `repo_host`（非空、非 `docker.io`/`ghcr.io`）：4 行
- `docker_cap in (-1,0,1)`：95 行（1=34、0=14、-1=47）
- `ghcr_cap in (-1,0,1)`：95 行（1=8、0=15、-1=72）
- 预期 `source_host_caps` 行数：194（4 + 95 + 95，无重叠）
- 双用途 `docker_cap=1` + `ghcr_cap=1`：6 个（54、69、71、86、88、638）

194 是 2026-11-17 基线，不是固定值；迁移切点必须按实际 DB 重算并解释差异。

迁移报告必须给出：每个 Host 的 caps 行数、`enabled=1` 行数、`effective_status` 分布、`policy_gaps` 列表；实际行数与 194 不一致时必须解释，不能静默继续。

- 14a 前后旧候选查询必须一致；新 shadow 查询的差异必须逐条归因。
- 无 Registry Host 事实的 Source 不创建 Foreign caps 行，不参与 Registry 候选。

## 5. 运行时事务

总则：任何一次运行时写入，只要影响多张表，就必须在同一个 `BEGIN IMMEDIATE` 内完成；不允许一张表成功、另一张表延后。Token Cache 和离线迁移是例外。

### 5.1 SetCapsLive

- 当前是单条 UPDATE；14a 改为 `BEGIN IMMEDIATE`。
- 写 `source_host_caps` 的 `docker.io` / `ghcr.io` 行。
- 同一事务生成 `docker_cap`、`ghcr_cap`、`ghcr_prefix` 投影。
- 保留 `status<>'archived'` 条件和 `RowsAffected` 语义。
- 失败整体回滚。

### 5.2 CommitHostProbe

- 已是 `BEGIN IMMEDIATE`。
- 继续只处理 Foreign Host，继续拒绝 `ghcr.io`；错误文案改为“Docker/GHCR 由 SetCapsLive 写入”，不能再写成旧字段唯一入口。
- 扩展为同时写 caps 行、原 `repo_host` 投影、health/recovery。
- 新增 Host 探测成功不修改 `repo_host` 和旧 Foreign 投影。
- 失败整体回滚。

### 5.3 禁止

- 先写权威表、后写投影，或反过来。
- Docker/GHCR 走无事务 UPDATE，Foreign 走事务。
- 14a 引入旧读路径的 dual-read 开关。
- 新查询结果影响真实请求，或新查询失败时自动回退旧查询。

## 6. 迁移

### 6.1 迁移链

```text
3.5.7 → 3.5.11 → 3.5.14a
         Realm 表    Host 能力表
```

生产 3.5.12 的程序版本是 3.5.12，但 Schema 仍是 3.5.11；不存在“3.5.12 Schema”输入指纹。

现有 `db-migrate` 已支持 3.5.7 输入，并已有 `backfillPolicies` / `policy_gaps`；缺的是 `3.5.11 → 3.5.14a` 这一段，不是缺 Realm 回填本身。

### 6.2 两段职责

1. `3.5.7 → 3.5.11`：复制旧表、建 `source_realm_policy`、按 `repo_host` 种子化、输出缺失策略报告、校验 Canonical。
2. `3.5.11 → 3.5.14a`：校验真实输入 `schema_version=3.5.11` / hash `e39e1197…`，建 `source_host_caps`，执行 `backfillHostCaps` 和双用途策略补齐。

`3.5.11 → 3.5.14a` 的顺序固定为：

```text
1. 打开输入库只读，校验 schema_meta / fingerprint
2. 目标临时库执行 Canonical DDL（含 source_host_caps）
3. copyAll 复制旧表；source_host_caps 是新增表，不在复制清单，复制后保持空表
4. backfillPolicies（3.5.7 路径已在上一段完成；3.5.11 路径保留/补齐）
5. backfillHostCaps
6. rebuildSequences
7. foreign_key_check / integrity_check
8. VerifyTx / 结构 Hash / metadata
9. 提交事务，关闭临时库，清理 sidecar
10. publishNoClobber 原子发布（独立步骤）
```

`copyAll` 不能把 `source_host_caps` 当作旧表复制；漏掉 `backfillHostCaps` 会让 14b 候选为空。

每一步都更新输入指纹；`cmd/db-migrate/main_test.go` 的“只允许三个输入指纹”断言必须同步更新。

### 6.3 事务与发布边界

当前 `db-migrate` 是 `EnsureFresh` / `copyAll` / `finalizeTargetMeta` 多阶段提交；14a 要满足“staging 单事务”，必须把它重构成：

- 目标临时库 `BEGIN IMMEDIATE`。
- DDL、复制、Realm 回填、`backfillHostCaps`、metadata、结构 Hash 验证、外键/完整性检查都在同一事务。
- `schema.Verify` 当前只接受 `*sql.DB`；必须新增 `VerifyTx(*sql.Tx)` 或等价的 tx 查询接口，不能在事务未提交时换另一个连接验证。
- 提交事务后关闭临时库、清理 `-wal` / `-shm`。
- 文件发布独立执行 `publishNoClobber`。

如果 14a 不重构为 staging 单事务，就只能宣称“离线迁移 + 原子发布”，不能宣称“单事务迁移”；这是两条不同的验收口径，不能混写。

### 6.4 失败边界与 14a 回滚 RPO

- 任一步失败：删除临时库和 sidecar，不发布目标文件，不保留半迁移数据。
- 备份库和旧 `secret.key` 只作灾难恢复，不作常规回滚路径。
- 14a 回滚：停服 → 恢复迁移前 DB / `secret.key` / 配置 → 部署 3.5.12 镜像。

14a 的 RPO 必须写清：

| 时间区间 | 回滚方式 | RPO |
|---|---|---|
| 迁移、隔离验收、开放流量前 | 恢复 14a 前 DB + 3.5.12 镜像 | 0 |
| 14a 已开放流量后 | 恢复 14a 前 DB 会丢失迁移后的探测/策略/源写入 | 不承诺 0 |

3.5.12 二进制不能直接读 14a 的 Schema（`3.5.14a`），所以 14a 之后不能只换镜像回滚。若要求开放流量后仍 RPO=0，必须实现并实测 14a→3.5.11 反向迁移；不能用“有备份”代替证明。

14a 执行纪律：停写/停服 → WAL checkpoint → FD 扫描 → flock 独占 → 备份 DB/`secret.key`/配置 → 临时库迁移 → 隔离容器验收 → 生产替换 → 入口关闭、后台探测暂停 → 只读健康检查 → 开放流量。开放流量前不产生新写入，RPO 才能为 0。

## 7. 3.5.14b 读路径切换

### 7.1 权威关系

| 数据 | 14b 之后职责 |
|---|---|
| `source_host_caps` | 所有 Registry Host 的能力权威 |
| `sources.repo_host` | 旧版本兼容投影，14c 删除 |
| `sources.registry_cap` / `registry_path_mode` | 原 `repo_host` 的旧版投影，14c 删除 |
| `sources.docker_cap` / `ghcr_cap` / `ghcr_prefix` | 协议兼容投影，14c 删除 |
| `registry_host_recovery` | Source + Host 恢复状态与 Foreign TTL |
| `source_health_scope` | Source + Host 健康证据 |
| `registry_host_gen` | Host 级凭据代次 |

### 7.2 候选准入

```text
source.enabled
AND source_host_caps.enabled
AND effective_status = 'Supported'
AND registry_path_mode IS NOT EMPTY
AND Host 全局准入允许
AND health / recovery 允许
AND policy_exists(source_id, host)
AND（Foreign Host）成功结论未过期
```

`policy_exists` 对所有 Host 生效；Docker/GHCR 的 policy 在 14a 回填时补齐。`multi_origin_hosts` 只约束 Foreign Host，Docker/GHCR 不因未列入该白名单被排除。

Docker/GHCR 不要求 recovery 行；Foreign Host 的 TTL 只认 `registry_host_recovery.last_success_at`。

### 7.3 必须修改的读路径

- `SourceCandidates("registry:<host>")`、`registryCandidatesRaw()`
- `ScopedHealthOf()`：不能再用 `JOIN sources src ON src.repo_host = g.host`，改为按 `z.scope` 关联 `registry_host_gen`
- Docker / GHCR 候选查询：读 caps 的 `docker.io` / `ghcr.io` 行
- `SourceStat.RegistryPath`、Gateway、Scheduler、Probe、UI
- GHCR 路径改写读 `source_host_caps.registry_prefix`，不再读 `sources.ghcr_prefix`
- 策略 API：`internal/api/policy.go` 不能再用 `src.RepoHost == host` 校验；改为检查 `(source_id, host)` 是否存在
- `ListRealmPolicies` / `ListPolicyHosts` 不再通过 `sources.repo_host` 取 Host，改为按 `source_host_caps` 的 Host 集合
- `SourceStat` / 首页标签按 caps 的 `effective_status` 生成，不再按 `repo_host` 推断

### 7.4 切换与回滚

- 14b 不改表、不改 `schema_meta`，与 14a 使用同一 Schema 版本。
- 14b 二进制只含新读路径，不含旧读路径、dual-read 开关或 feature flag。
- 回滚：停 14b → 部署 14a 镜像 → 14a 使用旧读路径和旧投影；caps 保留不删。
- 切换验收：逐 Host 比较 old/new 候选；新增 Host 是预期新增，必须显式列出；旧 Host 不得有非预期差异。

### 7.5 Host 管理 API / UI（14b 必须交付）

14b 不能只切读路径；Source-Beta多 Host、per-host 启停和策略编辑都依赖 Host 管理写路径。以下操作在 14b 建立，14c 只删除旧字段，不把 API 留到 14c：

```text
AddSourceHost(source_id, host, policy)
SetSourceHostEnabled(source_id, host, enabled)
RemoveSourceHost(source_id, host)
ResetSourceHostVerdict(source_id, host)
```

- `AddSourceHost`：caps + `source_realm_policy` + health/recovery 初始化 + 审计，同一事务；policy 非法或缺失则整体失败；Source 已归档则拒绝。
- `SetSourceHostEnabled`：caps.enabled + 对应旧投影（`enabled ? cap : 0`；仅 `docker.io`、`ghcr.io` 和原 `repo_host` 有旧投影）+ 审计 + 调度缓存失效，同一事务；Source 已归档则拒绝。
- `RemoveSourceHost`：14b 期间**不允许删除 `host == repo_host` 的行**；原主 Host 的移除必须走 `SetRepoHost` 迁移或等 14c。其他 Host 可删除 caps/policy/health/recovery；`registry_host_gen` 是 Host 级全局代次，保留不动。
- `ResetSourceHostVerdict`：仅管理员；`effective_status=Unknown`，保留 `last_verdict` 作为历史，清 blocked/hard-excluded，recovery 置待探测，写审计。

API：

```text
GET    /api/sources/{id}/hosts
POST   /api/sources/{id}/hosts
PUT    /api/sources/{id}/hosts/{host}/enabled
DELETE /api/sources/{id}/hosts/{host}
POST   /api/sources/{id}/hosts/{host}/reset
```

UI 必须显示 `enabled`（可编辑）、`effective`（只读）、`last_verdict`、`blocked_reason`；不能只显示一个“已启用”标签。14b-F 的“关闭Source-Beta K8S 能力不影响 Docker/GHCR”必须通过这个 API 验收，不能靠改配置文件。

## 8. 3.5.14c 旧结构清理

### 8.1 删除范围

- `sources.repo_host`
- `sources.registry_cap`
- `sources.registry_path_mode`
- `sources.registry_probe_at`
- `sources.registry_probe_error`
- `sources.docker_cap`
- `sources.ghcr_cap`
- `sources.ghcr_prefix`
- 旧投影写入和旧读兼容代码

保留 `github_cap`、`git_cap`、`range_cap`：它们代表 GitHub RAW / Release、Git smart HTTP、Range 分片，不是 Registry Host 能力。3.5.14 的目标是“Registry Host 能力旧模型清理”，不是删除所有协议能力。

### 8.2 repo_host 删除后的语义

14c 不保留“主 Host”字段。Source 的 Host 集合完全由 `source_host_caps` 表达；UI/API 改为 Source × Host 管理。

`AddSourceHost` / `SetSourceHostEnabled` / `RemoveSourceHost` / `ResetSourceHostVerdict` 已在 14b 建立（见 7.5），14c 只做：

- 删除 `repo_host` 后，`RemoveSourceHost` 不再有“不能删原主 Host”的限制，任何 Host 都可移除。
- `SetRepoHost` 及依赖 `repo_host` 的旧 API 一并删除。
- 旧字段的 JSON/API 投影删除；UI 完全改为 Source × Host。

事务语义沿用 7.5，不因 14c 改变：caps + policy + health/recovery + 审计必须同事务；`registry_host_gen` 是 Host 级全局代次，不随单 Source 的 Host 删除而删除。

### 8.3 SQLite 表重建

14c 删列不能只改 Canonical DDL，必须按 SQLite 安全重建流程：

1. 保存 `sources` 相关索引、触发器、视图定义。
2. 按最终 Canonical 建新表。
3. 复制保留列。
4. 检查 `AUTOINCREMENT` / `sqlite_sequence`。
5. 删旧表，重命名新表。
6. 恢复索引、触发器、视图。
7. 确认 `source_host_caps` 的外键仍指向重建后的 `sources`，必要时重建该外键。
8. `PRAGMA foreign_key_check`。
9. `PRAGMA integrity_check`。
10. 校验最终 Canonical Hash。

`PRAGMA foreign_keys` 必须在事务开始前按迁移流程设置；不能指望在事务中修改立即生效。

### 8.4 回滚与 RPO

| 时间区间 | 回滚方式 | RPO |
|---|---|---|
| 停服、迁移、隔离验收期间 | 恢复 14c 前 DB + 14b 镜像 | 0 |
| 开放生产流量之后 | 不能直接恢复旧快照并宣称无损 | 需反向迁移或接受明确数据丢失窗口 |

RPO=0 只承诺到开放生产流量之前。开放后若要求 RPO=0，必须实现并实测 14c→14b 反向迁移；不能用“有备份”代替证明。

执行纪律：停写 → WAL checkpoint → FD 扫描 → flock 独占 → 备份 DB/`secret.key`/配置/manifest/14b digest → 临时库迁移 → 隔离容器业务验收 → 生产替换 → 入口关闭、后台探测暂停 → 只读健康检查 → 开放流量。

## 9. API / UI

- `GET /api/sources/{id}/hosts`：返回每个 Host 的 `enabled`、`effective_status`、`last_verdict`、`registry_path_mode`、`blocked_reason`。
- `PUT /api/sources/{id}/hosts/{host}/enabled`：只改管理开关；需要 CSRF、鉴权和审计。
- `POST /api/sources/{id}/hosts`：新增 Host，必须同时提供合法 policy。
- `DELETE /api/sources/{id}/hosts/{host}`：删除 Host 关系；14b 禁止删除原 `repo_host`，14c 取消该限制。
- `POST /api/sources/{id}/hosts/{host}/reset`：管理员重置 Mismatch/Unknown；写审计。
- UI 必须同时显示原始 `enabled` 和计算后的 `effective`，不能只显示一个“已启用”标签。
- `blocked_reason` 至少区分：Source 停用、Host 白名单不允许、caps 停用、探测未知/不支持、Mismatch、健康/恢复阻止、策略缺失。
- 审计事件至少包括：`source_host_added`、`source_host_enabled`、`source_host_disabled`、`source_host_removed`、`source_host_verdict_reset`；事件只写 Source ID / Host / 操作者 / 时间 / 结果，不写凭据或 Realm Token。

## 10. 3.5.12 基线修正

3.5.12 的 Host 状态不能再用单一 `BLOCKED_EXTERNAL_SOURCE` 混写。每条记录拆成：

- `candidate_status`：`CANDIDATE_OBSERVED` / `NONE_OBSERVED` / `UNKNOWN`
- `product_status`：`NOT_EXECUTED` / `REAL_PASS` / `FAILED`

已实测：

| Host | host-prefix 尝试 | 结果 | 当前记录 |
|---|---|---|---|
| `registry.gitlab.com` | `m.daocloud.io/v2/registry.gitlab.com/...` | 产品级 ProbeRegistryHost + HostProbeRunner + 应用 `/v2/` 回源 200，Digest `sha256:ffe21f02…` 一致 | `REAL_PASS` |
| `public.ecr.aws` | `m.daocloud.io/v2/public.ecr.aws/...` | 产品级 ProbeRegistryHost + HostProbeRunner + 应用 `/v2/` 回源 200，Digest `sha256:f59abe65…` 一致 | `REAL_PASS` |
| `cgr.dev` | host-prefix 403；per-host 另测 | 不能据此判定整个 Host 无公共源 | `NOT_EXECUTED`，保留两种路径证据 |
| `asia-east1-docker.pkg.dev` | host-prefix 403；per-host 另测 | 同上 | `NOT_EXECUTED`，保留两种路径证据 |

规则：

- HTTP 200 和 Digest Header 不等于产品级 `REAL_PASS`；必须经 Mirror Lens 的 HostProbe、候选选择、Manifest 回源和 Digest 对照。
- GitLab / ECR 已在隔离环境完成产品级探测、实际 HostProbe 调度和真实 `/v2/` 回源；证据 `docs/evidence/3.5.14-live-hostprobe-20261116.json` / `.md`。
- 14a 的候选基线以修正后的 3.5.12 记录为准；不能继续用错误的 `BLOCKED` 结论作为“无候选”依据。

## 11. 验收门禁

### 11.1 14a

- 迁移报告：caps 行数、enabled 行数、状态分布、`policy_gaps`、双用途 6 个 Source 明细。
- 旧查询在 14a 前后逐 Host 一致；新 shadow 差异逐条归因。
- 双用途 Source 的 `ghcr.io` policy 要么成功生成，要么明确 `enabled=0` 并记录 14b 预期差异。
- `SetCapsLive` / `CommitHostProbe` 失败时 caps 与投影都不落库。
- 新增 Foreign Host 探测不改变 `repo_host` / 旧 Foreign 投影。
- 迁移 staging 事务、`VerifyTx`、外键/完整性检查通过；文件发布独立验收。
- 3.5.7 输入和 3.5.11 输入各跑一遍真实副本。
- shadow 查询只观察、不参与决策；默认采样，不能对每个请求都执行第二套查询。
- shadow 指标至少：`source_host_caps_shadow_total`、`source_host_caps_shadow_mismatch_total`、`source_host_caps_shadow_error_total`。

### 11.2 14b

- 所有 Registry Host 读路径只读 caps；旧字段不再独立决定候选。
- 逐 Host old/new 候选对比；旧 Host 无非预期差异；新增 Host 显式列出。
- Docker / GHCR / 双用途 / 空 repo_host / Mismatch / 过期成功记录全部覆盖。
- 回滚演练：14b → 14a 镜像，旧读路径可用。
- 策略 API 对第二 Host 可写；`ScopedHealthOf` 不再依赖 `repo_host`。
- `AddSourceHost` / `SetSourceHostEnabled` / `RemoveSourceHost` / `ResetSourceHostVerdict` 的 API、审计、事务和缓存失效全部覆盖。
- Source-Beta多 Host 验收：Docker/GHCR/K8S/GCR 标签与实际回源一致；关闭 K8S 不影响 Docker/GHCR。
- 14b 期间删除原 `repo_host` 必须被拒绝，返回明确错误。

### 11.3 14c

- `repo_host` 和旧 Registry 字段删除；`github_cap` / `git_cap` / `range_cap` 保留。
- Source × Host API/UI 可用；per-host 启停生效且不影响其他 Host。
- 表重建后 `foreign_key_check` / `integrity_check` / Canonical Hash 通过。
- 停服期间回滚 RPO=0 演练通过；开放流量后的数据丢失窗口有书面确认。
- 反向迁移若未实现，文档明确写“不承诺开放后 RPO=0”。

### 11.4 性能与观测门禁

相对 14a 基线，候选查询最大允许退化：

| 指标 | 阈值 |
|---|---|
| 候选查询 P50 | +5% |
| 候选查询 P95 | +10% |
| 候选查询 P99 | +15% |
| 吞吐量 | 下降不超过 5% |
| 错误率 | 增加不超过 0.1 个百分点 |
| SQL 查询次数 | 每次调用最多增加 1 条固定查询 |

禁止随候选数量增长的 N+1 查询。测量方法：同环境预热后 10 轮，每轮至少 10,000 次候选查询，使用同一数据库快照和相同 Host 分布，分别计算 P50/P95/P99。阈值是冻结门槛，不是已经达成的结果。
