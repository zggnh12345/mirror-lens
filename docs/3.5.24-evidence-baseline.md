## G0-1 UI/API 持久化能否表达 Scheme/Port —— **PASS**

结论：自定义 Registry 节点的连接地址（Scheme + Host + Port）由**现有 `sources.base_url` 字段**无损承载，无需新增列/表、无需改 Schema、无需把端口写进 Host 身份字段。

**两种身份必须分清**（G0-1 成立的核心前提）：
- `sources.base_url`：保存**自定义节点自身的连接地址**（含 scheme/port）。
- `repo_host`、`source_host_caps.host`、`source_realm_policy.host`、`registry_host_gen.host` 等：仍保存**逻辑 Registry Host**（客户端请求指向的逻辑仓库，不含端口）。

本次功能是**扩展节点连接地址支持**，不改变客户端请求所指的逻辑 Registry；因此载体判断成立，不需要把 Scheme/Port 写入任何 Host 身份字段。

证据链：

1. **UI 有新增源入口**：`internal/api/web/index.html:1416` 表单 POST `/api/sources`，字段 `url`（及显式 `host`）。
2. **handler**：`internal/api/api.go:608` `base, err := normalizeURL(in.URL)`；`RepoHost` 来自 `in.Host` 或已知域名派生（`:627-645`）；`registryhost.Check(host)` 只校验逻辑身份 Host（`:646-651`）；`:652-658` `store.Source{BaseURL: base, RepoHost: host, ...}`。
3. **normalizeURL**（`api.go:677-700`）：无 `://` 时补 `https://`；校验 scheme 仅 http/https；`hostPart := ...; if hostPart == "" || !strings.Contains(hostPart, ".")`（`:694`）；**`return v, nil` 原样返回**（`:700`）——scheme 与端口均原样保留。
   - IPv4 `http://203.0.113.10:5000`：含点 → 通过，端口/scheme 原样保留。
   - 域名 `https://registry.example.com:5443`：含点 → 通过。
   - **IPv6 字面量 `[2001:db8::10]`：无点 → 被 `:694` 拒绝**（实现阶段须修的校验缺陷，非载体缺失）。
4. **DB Schema**：`internal/store/schema/canonical.sql:32-60` `sources` 表：`base_url TEXT NOT NULL` + `UNIQUE(base_url)`，`repo_host` 等列；`base_url` 存完整 URL。无新增列/表。
5. **读回无损**：`ListSources` 直接 `rows.Scan(&it.BaseURL, ...)`（`internal/store/policy.go:451`），BaseURL 原样读回，无重编码。
6. **逻辑 Host 派生去端口**：`hostFromBaseURL` = `registryhost.Normalize(u.Hostname())`（`internal/store/policy.go:327-337`）；`AddSource` 内 `registryhost.Check(x.RepoHost)`（`store.go:490`，另有 `:482-488` 默认归属逻辑）。
7. **旧域名节点兼容**：`base_url` 既有值原样读回；缺省 scheme 由 normalizeURL 补 `https://`；不改变既有数据语义。

阻断条件核对（任务书 1.4 G0-1）：不需新增 DB 列/表、不改 Schema、不把端口拼进 Host 身份字段、不需歧义字符串编码——**均未触发**。

> 备注（实现阶段待处理，不影响 G0-1 判定）：`api.go:646-651` 与 `store.go:490` 对显式 Host 的 `registryhost.Check` 会拒 IP/带端口身份（`registryhost.go:54-65` `checkHost`：`:58` 拒端口、`:65` 拒 IP；`:156 Allowed` 第二道门 defaultHosts + artifact-registry）。这是 3.5.24 要改的**身份准入逻辑**，但"节点连接地址"的持久化载体已存在，故 G0-1 PASS。
>
> **禁止**（设计冻结硬约束）：不得把 `Allowed()` 改成 `if net.ParseIP(host) != nil { return nil }` 式全局放行。

## G0-2 Token Realm 与普通 Redirect 机制边界 —— **PASS（安全设计可行，但确认必须拆分）**

决定性发现：**`identity.go` 的 HTTPS-only 限制是位于 `switch kind` 之前的共用前置门，Token 跳转与 CDN/普通 Redirect 三类全部经过它。当前实现无法安全支持"HTTP Registry + 同 Host HTTP Realm Token 端点"——会被该门直接拒绝。**

**必须先分清两套独立判断**（本次审查纠正：早期把二者混为一谈）：
- **Realm 授权**（Challenge 的 Realm 是否属于该 Host 允许列表）= `PolicySnapshot.Allows`（`internal/v2auth/policy.go:73-97`）。它用 `realm.Scheme://realm.Host` 比对策略自身的 `p.Scheme`/`p.Realms`（`:80/:86/:90-95`），**不读取最初 Registry 请求的 scheme**。`OfficialPolicy` 甚至硬编码 `Scheme:"https"`（`policy.go:64`）。调用链：`auth.go:214` / `registryprivate.go:208`。
- **Token 跳转**（Token 服务返回 3xx 后能否跳到下一 URL）= `RedirectPolicy`（`identity.go:221-265`）的 `sameOrigin`/`:254`，属 `http.Client.CheckRedirect`。**不能用它推导 Realm 授权结论。**

证据链（Token 跳转侧）：

1. **唯一裁决入口**：`v2auth.RedirectPolicy`（`internal/v2auth/identity.go:221`）。
2. **共用 HTTPS-only 前置门**：`identity.go:242` `if !strings.EqualFold(to.Scheme, "https") { ... }`，位于 `switch kind`（`:252`）**之前**，对 `RedirectToken` / `RedirectCDN` / `default` 三种 kind **一视同仁生效**。
   - `:245-247` `from` 非 HTTPS 仅有注释分支，不拒绝。
   - `:248` `from` 为 https 而 `to` 非 https → 拒"HTTPS 降级重定向"；**但该判断当前不可达**（`:242` 已拦掉所有非 https 的 `to`），是被前置门遮蔽的死代码。实现窄范围 HTTP 例外时**必须重构判断顺序**，让"HTTPS→HTTP 降级拒绝"重新成为有效门禁（不是简单删 `:248`）。
   - `:251` `sameOrigin = EqualFold(Scheme) && EqualFold(from.Host, to.Host)`（`.Host` **含端口**）。
   - `:254` `RedirectToken`：`!sameOrigin` → 拒"Token 端点只允许同源重定向"；否则 `{StripAuth:false, RecheckPolicy:false}`。
   - `:262` `RedirectCDN`：method 非 GET/HEAD 拒；恒 `{StripAuth:true, RecheckPolicy:false}`。
   - `:264` `default`：`{StripAuth:!sameOrigin, RecheckPolicy:true}`。
3. **Token 调用链**：`internal/gateway/registryauth.go:193 fetchToken` → `http.Client.CheckRedirect`（`:236-248`）→ `:240 RedirectPolicy(v2auth.RedirectToken, GET, from, r.URL, len(via))`。Basic 仅在同源时保留（`:244-247` 显式二次清除 Authorization）。
4. **普通 Redirect 调用链**：`internal/gateway/gateway.go:685 applyRedirectPolicy` → `:694 RedirectPolicy(kind, method, from, to, hops)`；`:698 if d.StripAuth` 清认证头；`:704-705 recheckRedirectPolicy`。**注意现状差异**：`recheckRedirectPolicy`（`:715`）在 Scheme 或 Host 改变时直接 `return nil`（`:719`），**不重新解析目标策略**；仅同 Host/Scheme 才完整重解析。G1 目标要求"每跳重查"，属实现阶段变更点，不能写成现状已保证。
5. **Realm 写入层强制 HTTPS**：`internal/store/policy.go:387` `normalizeRealm`：`u.Scheme != "https" || u.Host=="" || u.User!=nil || u.RawQuery!="" || u.Fragment!=""` → 拒；返回 `\"https://\"+host`（**去端口**，`:393/:400`）。即 HTTP Realm 在策略写入阶段已被挡。
6. **DefaultRealmsFor(IP) = nil**：`internal/v2auth/auth.go:170-175`，不动。

2.5 矩阵（**按机制边界重写**：Realm 授权 = `Allows`；Token 跳转 = `RedirectPolicy`）：

| 场景 | 判断机制 | 当前行为 | 目标（冻结） |
|---|---|---|---|
| HTTP Registry + 同 Host HTTPS Realm | Realm 授权 `Allows` | **允许**（前提：HTTPS Realm 在允许列表内；`p.Scheme` 默认 https，与普通 Registry 请求 scheme 无关） | 保留此安全升级路径 |
| HTTP Registry + 同 Host HTTP Realm | Realm 写入 `normalizeRealm` | 拒绝（写入层只收 https Realm） | 新增窄例外：仅"明确配置 HTTP 的 Registry + 同 CanonicalHost 的 HTTP Realm"允许 |
| HTTPS Registry + 同 Host HTTP Realm | Realm 授权/写入 | 拒绝 | **保持拒绝**（绝不 HTTP Token Realm） |
| 跨 Host Realm | Realm 授权 `Allows` | 拒绝 | 保持拒绝 |
| HTTPS Registry + HTTP Realm 的 Token 跳转 | Token 跳转 `RedirectPolicy` | `:242` 拒绝 | 保持拒绝；重构顺序使降级门禁有效 |
| 普通 Redirect HTTPS→HTTP | Token/普通跳转 `RedirectPolicy` | `:242` 拒绝（`:248` 不可达） | 保持拒绝（不放宽） |
| 普通 Redirect HTTP→HTTP 跨 Host | `RedirectPolicy` default + Recheck | `:242` 要求 https，拒 | 按完整 Origin 独立判断，跨 Host 拒；每跳 Policy/safehttp 重查（现状不满足，见证据 4） |

判据（任务书 1.4 G0-2）：
- Token 跳转与 Realm 授权是两套机制；HTTPS-only 前置门位于 Token 跳转侧，必须拆调用上下文——**确认必须改**。
- 不得通过全局放宽 HTTPS-only 绕过——冻结硬约束。
- HTTP Realm 例外严格限于"明确配置 HTTP 的 Registry + 同 CanonicalHost 的 HTTP Realm"；HTTPS Registry 不得使用 HTTP Realm。
- 允许 HTTP Realm 不得放宽普通 HTTPS→HTTP Redirect、不得跨 Origin 泄漏 Authorization、不得跳过每跳 Policy/safehttp——由"拆上下文 + 独立测试锁定"保证（实现阶段 RED-GREEN）。

## G0-4 Manifest Key 变更与性能基线口径 —— **PASS（基线口径已冻结，含对任务书预设格式的实测修订）**

决定性实测修正：`origin` 变量 = `parsed.Host`（`registry.go:302/306` `origin := host`，host 来自 `parsed.Host`），是**裸 Host，不含 scheme、不含端口**。因此当前真实 Key 与任务书 1.4 G0-4 预设的 `https://host:443/...` 不同，按任务书"如代码事实不同，必须按实测修订说明"修订。

证据链：

1. **键构造位置**：`internal/adapter/registryadapter/registry.go:343`（manifest）与 `:376`（blob），经 `store.RegistryCacheKey(epoch, kind, rest)`。
2. **RegistryCacheKey**（`internal/store/epoch.go:109-118`）：`epoch<=0` 走 `docker:<kind>:<rest>`（3.5.14c 兼容）；`epoch>0` 才产生 `docker:m|b:<epoch>:<rest>`。
3. **格式演进（纠正早期错误：不存在 `docker:m:0:` 键）**：
   - 旧（epoch=0，3.5.14c 兼容）：`docker:manifest:<裸host>/<name>:<ref>|accept=…`（`credwrite_test.go:156` 锚定：`RegistryCacheKey(0,"manifest","quay.io/x:1") == "docker:manifest:quay.io/x:1"`）
   - 当前（epoch>0，3.5.15+）：`docker:m:<epoch>:<裸host>/<name>:<ref>|accept=…`
   - 3.5.24 拟引入：`docker:m:<epoch>:<scheme://CanonicalHost:EffectivePort>/<name>:<ref>|accept=…`
   - 当前代码不可能产生含 IP:Port 的键：`origin` 为裸 host 身份，`checkHost:58/65` 拒端口与 IP、`Allowed:156` 第二道门；故**不列虚构的 IP:Port 键样例**。
4. **任务书预设 vs 实测**：
   - 预设旧 `docker:m:0:registry.example.com/...`：`docker:m:0:` 前缀代码不会产生（epoch=0 走 `docker:manifest:`；`docker:m:` 要求 epoch>0）——属任务书措辞偏差，按实测修订。
   - 预设新 `docker:m:0:https://registry.example.com:443/...`：`https://:443` 当前代码中不存在（origin 无 scheme/port）；3.5.24 把 scheme+有效端口引入键后才近似该预设。
   - **缓存读取兼容性：未验证**。已确认 `CacheKey` 由 `PlanParsed` 单一构造（`registry.go:343/376`）、`RegistryCacheKind`/`RegistryCacheKeyEpoch`（`epoch.go:122/137`）仅用于 GC/审计前缀解析；但**未逐行核实缓存 Get 实现**，不能断言"读路径无旧 Key 兼容查找"。
5. **生产 Cache Epoch：未验证**。本轮未读取生产 `cache_epoch` 实际值，故不推断生产当前用 `docker:manifest:` 还是 `docker:m:N:` 前缀；仅确认代码层两种格式的存在条件。
6. **升级影响**：所有既有域名 Registry 的旧格式 manifest 缓存无法命中新格式 Key；每个尚未重建的新 Manifest Key 升级后首次请求回源 Miss 并重建该 Key 记录（按 Key 计数，非"每 Registry 一次"）。旧记录不主动清空，按 TTL/GC 回收（`gc.go:73-75` CacheExpired；`epoch.go:187/223` CacheEpochSweep 为独立审计/回收入口）。
7. **Blob 不变**：`docker:b:<epoch>:sha256:…`（`registry.go:376`），内容寻址，跨仓库复用，不受本次 manifest 键变更影响；**Cache Epoch 不变**（`epoch.go:21 CacheEpoch` 读现有值，不 bump）。
8. **性能基线方法（冻结）**：3.5.23 与 3.5.24 两版本各自先完成自己的 Manifest 缓存预热，再测热缓存；3.5.24 升级后首次回源/重建单独记为 `manifest_key_rebuild_first_miss`（一次性重建成本，须披露回源次数与耗时），不混入热缓存命中样本。

## G0 结论汇总与进入 G1 的条件

| 门禁 | 最终状态 | 结论 |
|---|---|---|
| G0-1 持久化 | **PASS** | 载体 = 现有 `sources.base_url`（连接地址）与 `repo_host` 等（逻辑 Host）分离；无需改 Schema；端到端无损往返（IPv6 校验缺陷属实现待修） |
| G0-2 安全机制可拆分 | **PASS** | HTTPS-only 前置门为 Token 跳转共用，必须拆调用上下文 + 独立测试；区分 Realm 授权（Allows）与 Token 跳转（RedirectPolicy）；禁止全局放宽 |
| G0-3 真实环境 | **分层：宿主 IPv4/IPv6 PASS；生产容器 BLOCKED** | 宿主具备真实公网 IPv4/IPv6 出站；但生产 bridge 容器无公网 IPv6、无 IP SAN 证书、无后端 IP:Port 直连 → 对应真实验收项 BLOCKED |
| G0-4 Key 规则 | **PASS** | origin 为裸 host；格式按 epoch 条件修订（无 `docker:m:0:`）；首次回源重建与热缓存样本分离 |
| G0-4 生产 Epoch / 实际缓存读取路径 | **NOT_RUN（未验证）** | 未读生产 cache_epoch、未逐行核实缓存 Get 兼容性，不推断 |

**是否满足进入 G1 设计冻结的条件：是。** G0-1（功能可行性先决条件）PASS；无"必须新增 Schema/改 Host 身份字段"的阻断；G0-2 存在清晰安全拆分路径；G0-3 缺口按场景分层标注、不阻断代码层设计；G0-4 Key 规则可复现（生产 Epoch/读取路径标未验证）。
