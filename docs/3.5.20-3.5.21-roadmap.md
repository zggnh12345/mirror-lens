## 三、3.5.21：换源链优化

### 3.1 背景与根因（实测结论）

现象：慢速下载（约 100KB/s）持续数分钟不切换源。

根因（已用生产数据 + 隔离环境端到端实测确认）：

- 换源资格门槛 `switch_min_mbps=8`，即候选星标源近 5 条速度样本中位数须 ≥ 8192KB/s。
- 生产仅 2 个星标源：凤凰城（近期有效样本 <3 条，直接不合格）、春川（实测 0.4~6.8MB/s，多数 1~2MB/s）。
- 无任何候选能过 8MB/s，换源链实际 100% 不触发；日志表现为
  `换源跳过 xxx：样本不足/偏慢 ... 门限=8192KB/s` → `单流判慢：没有可换的星标源`。

已排除项（不需要改）：
- 10 秒判慢机制正常。
- HTTP/1.1 下 midFill（中途并行）接管正常，实测可交付完整文件并通过校验。
- 生产链路中 mirror-lens 侧为 HTTP/1.1（Traefik 终止客户端侧 HTTP/2 后以 HTTP/1.1 回源），`http.Hijacker` 可用，midFill 不受 HTTP/2 影响。

### 3.2 设计基线（冻结）

#### 换源资格公式

```
T_i = max( F,  P_i / 1.3,  C × 1.2 )
候选通过条件： S_i >= T_i
```

| 符号 | 含义 |
|------|------|
| `S_i` | 候选源 i 近 5 条真实速度样本的中位数 |
| `P_i` | 排除当前供数源与候选 i 自身后，其他合格候选源中位数的中位数 |
| `C` | 当前供数源实时速度（`sw.sample()`） |
| `F` | 绝对速度下限，默认 1 MiB/s |

规则：
- 每个候选至少 3 条样本才参与判断（沿用现状）。
- `P_i` 无有效同伴时取 0，门槛退化为 `max(F, C×1.2)`——这是允许的降级。
- 使用中位数，不使用最大值（生产样本 CV>1.4，峰值不可靠）。
- 必须是 `P_i / 1.3`，不能是 `P_i × 1.3`（后者会让候选被自己所在群体的中位数淘汰）。

#### 换源进度闸门

```
允许换源的条件：
  total >= 30 MiB
  sent  <= min( 150 MiB, 0.8 × total )
```

- 80% 限制剩余收益（避免接近完成时折腾）。
- 150 MiB 限制最大已发送前缀（避免大文件无限制回放）。
- 两者取 min，缺一不可。

#### 新源响应处理

| 响应 | 处理 |
|------|------|
| HTTP 206 | 校验 Content-Range / 版本后按偏移直接接续 |
| HTTP 200 | 计算前缀回放成本；超过独立回放预算则拒绝该候选 |

- 首字节预算（现有 `switchFirstByteBudget=3s`）只覆盖等待首字节，不覆盖 `discardN` 回放。
- 回放预算必须独立设定，且回放过程本身要可取消（不能只靠历史速度估算）。
- 具体回放预算数值需通过真实环境测试确定，不直接继承首字节预算。

#### 配置语义迁移

| 配置键 | 3.5.19 语义 | 3.5.21 语义 |
|--------|-------------|-------------|
| `switch_min_mbps` | 固定准入门槛（默认 8） | 绝对速度下限 F（默认 1） |
| `switch_min_file_mib` | 固定最小文件（60） | 30 |
| `switch_max_sent_mib` | 固定已发上限（48） | 由 `min(150, 0.8×total)` 取代，配置项保留为绝对上限 |

注意：
- 生产配置中已存在 `switch_min_mbps=8`，**改代码默认值不会覆盖已有配置**；升级时必须显式把生产配置改为 1。
- 配置不热生效：`main.go` 启动时把配置复制进 `Gateway.ParOptions`，Web 保存只改 API 侧副本，必须重启服务。

### 3.3 已核实的代码事实（实施时以此为准）

- `internal/gateway/watch.go`
  - `switchSpeedOK`（约 :204）：`len(sp)<3` 直接 false；`medianInt64(sp) >= minKBps`。
  - `trySwitch`（约 :296）：13 处 `continue`（312~456）覆盖速度不合格、名额不足、请求失败、非 200/206、版本验证失败、首字节超时，全部汇到末尾统一返回 `没有可换的星标源`——存在诊断盲区。
  - 成功时打日志：`单流换源：%s 已接手（已发 %d MB，验证器=%v）`（约 :477）。
  - `switchFirstByteBudget = 3 * time.Second`（约 :491），仅首字节。
  - `discardN`（约 :482）用于 HTTP 200 丢弃已发前缀，无独立时间边界。
  - `streamWatch.slow()`：`giveUp` / `maxSwitch` / `total < minFile` / `sent <= 0` / `sent > maxSent` / `switch_gap` / 窗口满 / 均速低于 `limitKB`。
  - `limitKB = WatchMBps × 1024`；`sw.sample()` 的 `rateKB` 用 ÷1024。
- `internal/store/sources.go`
  - `RecentProxySpeeds` 返回 `bytes/ms`（数值≈十进制 KB/s），与 `rateKB` 的 ÷1024 存在单位错位，实施时统一为 KiB/s（内部建议 B/s）。
  - `minProxySpeedBytes = 16 MiB`；样本寿命 `proxySpeedMaxAgeSec = 7 天`。
- `internal/scheduler/scheduler.go`
  - `Candidates` 默认 `MaxCandidates=3`，可配 1~10；动态基线必须基于当前请求实际取得的候选集，不能声称统计全库星标源。
- `internal/gateway/stream.go`
  - `onSlow`（约 :681）：先 `trySwitch`，失败后 `setGiveUp()` 并尝试 `midFill`。
  - `setGiveUp` 全代码仅一处（:689）；`slow()` 开头检查 `giveUp`，故首次判慢失败后本次请求不再换源。

### 3.4 实施顺序

**第一阶段：受控实验（不碰生产）**
- 用真实 HTTP/1.1 端到端脚手架验证两件事：
  1. 当前源 100KB/s、候选 1.7MB/s、门槛 1 → 是否触发 `单流换源：xxx 已接手`。
  2. 当前源 2.5MB/s、候选 1.7MB/s、门槛 1 → 是否误换更慢源（验证 `C×1.2` 的必要性）。
- 目的：先确认"降门槛能解决"与"裸降会误换"两个判断，再决定是否动生产。

**第二阶段：生产配置验证（仅一个变量）**
- 只改 `switch_min_mbps: 8 → 1`，其余保持 60/48/3/10/2/30。
- 前置条件：
  - 目标候选至少 3 条有效样本（春川满足，凤凰城不满足）。
  - 测试请求满足原 60/48 限制（文件 ≥60MiB，判慢时已发 ≤48MiB）。
  - 优先用新请求，避免续传前缀干扰。
  - 确认当前源确实处于约 100KB/s，而非仅低于 3MiB/s（否则 2.5→1.7 会变慢）。
- 判定成功：出现 `单流换源：xxx 已接手`，而不是只看 `换源跳过` 消失。
- 该配置只作为诊断实验，不作为长期全局配置。

**第三阶段：代码实现**
- 动态门槛（`T_i`）、单位统一、当前速度接入。
- 进度闸门 `30 + min(150, 0.8×total)`。
- HTTP 200 独立可取消回放预算。
- 结构化失败日志（`speed_rejected / lease_rejected / request_failed / verifier_rejected / first_byte_timeout / switch_success`）。
- 80% 计算用安全整数运算，避免 `total × 8` 溢出。

**第四阶段：真实验收**
- 同一下载目标、相同网络、相同源配置做前后对照。
- 记录：原始速度、当前源 10 秒实时速度、候选样本与中位数、`P_i`、`T_i`、换源前后吞吐、206/200 比例、换源空档时间。
- 不以单次峰值认定成功。

### 3.5 验收测试清单

| 场景 | 预期 |
|------|------|
| 单候选 1.7MB/s，当前 100KB/s | 允许换源 |
| 候选 <1MB/s | 拒绝 |

### 3.6 明确不动的部分

- 10 秒判慢机制（`watch_mbps=3`、`watch_sec=10`）。
- 首次换源失败后的 `giveUp` 语义（保留，不改为无限重试）。
- 换源间隔 30 秒、每请求最多 2 次。
- `Preferred` 星标资格、每源至少 3 条样本、取近 5 条中位数。
- 调度器候选顺序与 `MaxCandidates` 默认值。
- midFill 接管、HTTP/1.1 Hijack、Range + ETag/摘要版本验证。
- 数据库 Schema、独立测速系统。

### 3.7 风险与未验证项

- 未验证：降门槛后生产环境的 HTTP 接管（206/200、版本验证、lease）是否必然成功。第一阶段受控实验用于消除此不确定性。
- 未验证：`C×1.2` 对抖动的抑制效果，需真实环境对照。
- 效果天花板：参数优化只能在现有源池内择优，不能创造快源。当前仅 2 个星标源且其一无有效样本，动态基线实际退化为 `max(F, C×1.2)`。
- 预期收益：100KB/s 场景下，60MiB 文件由约 10 分钟降至约 50 秒量级；前提是换源后能维持候选历史中位速度。

## 三·八、第一阶段受控实验结论（2026-11-23，已完成）

实验代码：`internal/gateway/exp_switch_gate_test.go`（纯测试文件，未改产品代码）。
方法：httptest 限速源 + 注入候选样本（`speedProbe`）+ 固定候选列表（`parTargets`），
观测 `plan.Upstream` 是否切到候选源；每场景重复 5 次，结果稳定一致。
门槛 F=1MB/s，`SwitchMinMBps=1`；判慢线按场景设；样本单位 KB/s。

| 场景 | 当前源 | 候选样本 | 判慢线 | 结果（5/5） | 判定 |
|------|--------|----------|--------|-------------|------|
| 实验1 | 100KB/s | 1700KB/s | 3MB/s（兜底） | 换源=true | 降门槛确实能解决慢速不换源 |
| 实验2 | 2.5MB/s | 1700KB/s | 3MB/s | 换源=true | **裸降会误换更慢源**（2.5→1.7），`C×1.2` 必要 |
| 实验3 | 100KB/s | 900KB/s | 3MB/s（兜底） | 换源=false | 低于绝对下限 F 被正确拒绝 |

**结论**：文档 §3.1 的两个判断均被实测证实——
1. 单纯把 `switch_min_mbps` 从 8 降到 1 能让慢源场景触发换源；
2. 但裸降会让 2.5MB/s 的当前源换到 1.7MB/s 的候选（变慢），
   必须实现动态门槛里的 `C×1.2` 项来抑制。

**因此不采用第二阶段的"裸降配置"作为长期方案**（它只能做短时诊断）；
直接进入第三阶段实现完整动态门槛 `T_i = max(F, P_i/1.3, C×1.2)`。

实验脚手架注意点（供第三阶段参考）：
- 候选样本单位是 KB/s（不是 B/s）：`speedProbe` 返回 `[]int64{1700,1700,1700}` 即 1.7MB/s。
- `WatchMBps=0` 会被 `newStreamWatch` 兜底为 3MB/s，不是"恒判慢"。
- 当前源速率必须让判慢窗口覆盖满 1 秒（`slow()` 要求 `dur>=window` 且 `sent>0`），
  否则文件传完都没进入换源评估——实验2 因此用 16MiB 文件。
- 本实验只观测"是否换源"，不校验内容完整性（限速时钟抖动会让边界差几个 chunk，
  与换源资格判定无关）。

## 三·十一、离线反事实分析（2026-11-24，零构建）

方法：从生产库只读副本取 `proxy_speed`（真实下载 bytes/ms），按 `RecentProxySpeeds` 语义
（每源近 5 条取中位数，KB/s）得到候选历史速度 P，再把 P 与不同当前源速度 C 代入
`T=max(1024, P_peer/1.3, C×1.2)`，与旧门槛 8192 KB/s 对比。**这是判定逻辑的反事实复算，
不是运行时回放**；库中没有"某次下载当时的 C 与已发字节"，故无法重建完整判定序列。

真实样本（近 5 条中位数）：
- 凤凰城(88) docker = 783 KB/s；ghcr = 3867 KB/s
- 春川(638) docker = 6517 KB/s；ghcr = 12914 KB/s

结论：
1. **核心收益成立**：638 docker 的 6517 KB/s 低于旧门槛 8192，旧规则**拒绝**（差 1.7MB/s 够不着）；
   新规则在 C<5.1MB/s 时由 F=1024 或 C×1.2 主导，**接受**。这正是慢源场景换不到该源的直接证据。
2. **不误选慢源**：88 docker 仅 783 KB/s，低于 F=1MB/s，新旧门槛都拒绝；且 peer=638(6517) 使
   `P/1.3=5013`，88 远不够。降门槛没有变成"无脑换"。
3. **C×1.2 有真实边界体现**：638 docker 在 C=10240 KB/s 时 T=12288 > 6517 → 拒绝，
   即当前源已 10MB/s 时不会换到 6.5MB/s 的候选。
4. **`P/1.3` 的副作用需注意**：两星标源同时可用时，88 ghcr(3867) 因同伴 638(12914) 太快而被拒
   （T=9934）；若 638 不可用则 peer=0，88 在 C<3.2MB/s 时会被接受。相对择优是否过严，需真实环境确认。

局限：验不了接管成功率（HTTP 206/200、版本校验、lease），这仍是 p4 唯一必须跑新二进制的部分；
样本偏少且含缓存命中极值（638 最高 107MB/s），中位数已部分缓解；88 docker 近期确实慢，
意味着 docker 维度实际只有 638 一个可用候选。
