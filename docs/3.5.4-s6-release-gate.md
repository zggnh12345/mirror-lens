状态：S6 准备中。未打 tag、未推镜像、未做生产迁移。

## 一、进入发布的硬条件

1. 备份与恢复的代码路径验证必须使用 1f2cb55 起的正式实现（`janitor.BackupNow`），
   不接受手工组装的等价目录作为证据。
2. `restore.sh` 的故障注入、幂等、WAL/SHM 隔离用例全过。
3. 启动门禁用例全过：已有库缺 key 拒绝、恢复日志优先拦截、正常启动、首次安装。
4. 全量测试与 race 门禁绿。
5. 发布窗口检查（下一节）全部打勾。

## 二、升级窗口检查顺序

发布前：

1. 确认旧平铺备份（`backup/mirror-lens-YYYYMMDD.db` + 对应 `secret.key`）
   至少保留一份可恢复副本，并在发布记录里写下文件名与 SHA-256。
2. 不假设生产已经产生新格式备份——新格式只在升级后的服务运行过备份周期后才有。
3. 记录当前生产库与 key 的 SHA-256，作为回退比对基线。

升级后首次启动：

4. 确认服务正常启动且日志没有 `secret.key 缺失` 或 `未完成的恢复切换`。
5. 等待或触发一次备份，确认生成 `backup/units/mirror-lens-YYYYMMDD/`，
   且 `manifest.json` 中 DB/key 的 SHA-256 与文件实际值一致。
6. 用该单元执行一次真实恢复演练（停服务 → `restore.sh` → 启动），
   确认恢复后可正常服务、候选集与升级前基线一致。
7. 用 3.5.3 二进制打开同一份数据库副本，确认仍能读取（新列不阻塞旧代码）。
8. 确认旧备份恢复流程仍可用，且旧平铺目录不会被 `restore.sh` 当成新单元
   （应报「缺少 manifest.json」而拒绝）。

回退：

9. 若新版本不可用，回退到 3.5.3 二进制 + 发布前记录的旧库/key 备份；
   新库在旧代码下可读，但新格式备份单元只能由新版本使用。

## 三、启动门禁的固定语义

| 数据库 | secret.key | 行为 |
| --- | --- | --- |
| 不存在 | 不存在 | 首次安装，生成密钥并初始化 |
| 存在 | 存在 | 正常启动 |
| 存在 | 不存在 | 拒绝启动，不生成密钥、不改库 |
| 恢复完成 | 配对存在 | 正常启动 |

补充约束：

- `.restore-journal.json` 存在时，先于密钥检查拦截启动；只能由
  `restore.sh --recover` 清除。
- journal 状态无法确认（权限、I/O、路径不是目录等）同样拒绝启动；
  只有明确的 `ENOENT` 才放行。
- journal 只在 DB/key 成对校验通过后删除；校验失败保留现场并回滚。
- 回滚不得先删除当前配对：旧配对必须哈希有记录、文件齐全、内容匹配，
  并在数据目录外的副本上复核通过后才切换；不满足时正式目录与现场原样保留。
- 已完成的恢复重复执行 `--recover` 是无操作，不改变结果。
- 恢复切换前旧 WAL/SHM 随旧配对移入现场目录；正式目录残留 WAL/SHM 时
  拒绝清除切换日志。
