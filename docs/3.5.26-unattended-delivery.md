## F8：Host Probe 缺失策略快照 CAS 修复

【补充 R2/R3】优先级：P2

文件：

- internal/runner/hostprobe.go
- internal/store/commit.go

问题：

基准 I-03 写"策略不存在时新发起探测 PolicyGen=0、HasPolicyGen=false"，而 `ListDueHostProbes` 用 `COALESCE(p.policy_gen,0)`，`hostprobe.go:519` 当前 `HasPolicyGen: j.PolicyGen > 0`。当探测发起时无策略（PolicyGen=0），`HasPolicyGen=false` 会让 `CommitHostProbe` 整个跳过策略代次 CAS；若探测期间用户重新配置策略（`SetRealmPolicy` 建代次 1 并把 recovery 设为立即探测），旧任务可能把 Unknown/Inconclusive 与旧 recovery 退避状态写回，覆盖刚设置的立即探测安排。

冻结修复：

```go
type HostProbeJob struct {
    // ... 原有字段 ...
    PolicyGen    int64
    HasPolicyGen bool
}
```

- 生产调度构造：`HasPolicyGen: true, PolicyGen: x.PolicyGen`（代次 0 也明确表示"已取得快照"）。
- `runOne` 提交：`HasPolicyGen: j.HasPolicyGen`。
- `CommitHostProbe` 在 `HasPolicyGen` 为真时始终比较"当前 policy_gen == 探测开始时 policy_gen"，缺行按 0 处理；不等则 `HostCapsStaleSnapshot`，整笔拒绝写入。
- 不得无条件对测试 fixture 写 `HasPolicyGen: true`：部分 fixture 的策略行 `policy_gen=1` 但 `HostProbeJob.PolicyGen` 默认 0，会导致意外的 `HostCapsStaleSnapshot`；应显式设置该字段。

效果：
- 无策略时启动、期间无变化：0==0，可提交 Unknown/Inconclusive。
- 无策略时启动、期间重配策略：0!=1，整笔拒绝。
- stale snapshot 时 cap、health、recovery 均无任何写入副作用。

### F9 内存状态优先级（applyInner，使用已重新加载的 s.Hosts）

| 优先级 | 条件 | 本轮有效能力 | 目的 |
| --- | --- | --- | --- |
| 0 | Enabled == false | CapNo | 遵守 derivedCap 的既有禁用语义；禁用 Host 不得因探测成功变可用 |
| 1 | PolicyGen == 0 | CapUnknown | 无策略时进入 pending，即使 DB 保留 Mismatch |
| 2 | PolicyGen > 0 && EffectiveStatus == 'Mismatch' | CapMismatch | 保留真实 Mismatch 排除语义 |
| 3 | PolicyGen > 0 && RecoveryState == 'hard-excluded' | CapUnknown | 主动取消过期 CapYes，避免误判 usable |
| 4 | 其余正常状态 | 原探测结果 | 保持现有行为 |

前四种保护状态下，GHCR 本轮有效 `ghcrPrefix=false`。

【补充 R10｜优先级 0 的根因与覆盖面（冻结）】
这不是改变禁用语义，而是让 applyInner 遵守 Store 原有语义：`derivedCap` 已规定 disabled → CapNo（hostcaps.go:172-177），基线 `applyInner` 却在探测成功时无条件 `capv=CapYes`（runner.go:449-450）。
根因比 disabled 更普遍：**SetCapsLive 内部任何一次 `continue`（caps 行不存在、enabled=0、policy_gen 不匹配、Mismatch、hard-excluded）都不改变返回值**——`ok=true` 只表示事务已提交，不表示 per-host 是否实际写入（store.go:757-797）。因此 applyInner 在 `ok=true` 后无条件写回 `s.DockerCap/GhcrCap/GhcrPrefix`（runner.go:481-482）会因任一 skip 而污染内存。
结论：Layer1 归一化（现冻结为方案 A）必须**统一覆盖上述 5 类 skip**，不得只针对 disabled 或只针对 Mismatch/hard-excluded 补单点判断。单独增加一行 `Enabled==false → CapNo` 不足以关闭此问题。

必须区分：CapUnknown 是本轮内存中的有效能力，不是把 DB 中的 Mismatch 改成 Unknown；F7 与 SetCapsLive 的 DB 守卫仍负责保留原始 Mismatch 行。

hard-excluded 冻结规则：
- 不得以现有 Supported 参与 Source 可用性聚合；
- 本轮有效能力降为 CapUnknown；
- 不修改 DB caps verdict，不修改 recovery 状态；
- Mismatch 与 hard-excluded 同时存在时：有策略时 Mismatch 优先；无策略时 PolicyGen==0 优先。

### F9 DB 写入守卫（R10 修订：退回只 UPDATE，不建行）

【补充 R10｜撤销原 UPSERT 冻结结构（冻结）】
原"INSERT ... SELECT ... WHERE NOT EXISTS + ON CONFLICT DO UPDATE WHERE"结构**作废**，不再作为 F9 实现口径。理由：
1. 基线 `SetCapsLive` 的契约就是**只更新已存在且 enabled=1 的 caps 行，不建行**（store.go:753-755 注释明确；14c 的 AddSource/迁移才建行）。`RemoveSourceHost` 会同时删除 caps、policy、健康记录和 recovery（hostcaps.go:485-555），原 UPSERT 在"无 caps 行且无 hard-excluded recovery"时会 INSERT，从而**复活管理员已删除的 Host 关系**。
2. 原 UPSERT 的 INSERT 与 UPDATE 分支都只守卫 Mismatch/hard-excluded，遗漏了基线的另三项守卫：行必须存在、enabled=1、policy_gen 快照匹配（store.go:757-779）。UPDATE 分支缺 enabled=1 会覆盖用户手动禁用 Host 后保留的诊断状态。
3. 在"不建行"的调用点引入 INSERT 分支是纯多余副作用面。与其逐条证明两条路径守卫齐全，不如删除 INSERT 分支，改为**带全部守卫的单条 UPDATE**，一举消解复活问题。

冻结结构（只 UPDATE；列清单与字段按 `upsertHostCapsConn` 真实写入字段对齐）：

```sql
UPDATE source_host_caps
SET last_verdict=?, effective_status=?, registry_path_mode=?, registry_prefix=?
WHERE source_id=? AND host=?
  AND enabled=1
  AND effective_status <> 'Mismatch'
  AND NOT EXISTS (
      SELECT 1 FROM registry_host_recovery r
      WHERE r.source_id = source_host_caps.source_id
        AND r.family = 'registry'
        AND r.scope = source_host_caps.host
        AND r.state = 'hard-excluded'
  )
  -- policy_gen 快照匹配：gens 中存在该 host 且其值与当前 policy_gen 相等
  AND COALESCE((SELECT policy_gen FROM source_realm_policy p
                WHERE p.source_id=source_host_caps.source_id
                  AND p.host=source_host_caps.host), 0) = ?;
```

守卫清单（5 项，全部必须）：① caps 行存在（UPDATE 影响行数=0 即视为 skip）；② enabled=1；③ effective_status<>'Mismatch'；④ 无 hard-excluded recovery；⑤ policy_gen 快照匹配（无策略行按 0 处理，与基线 `COALESCE(policy_gen,0)` 一致）。Recovery 关联键严格为 `r.source_id=... AND r.family='registry' AND r.scope=...`，不能用 `r.host`。

`UPDATE ... WHERE` 的影响行数即 per-host 写回结果：0 表示 skip，须交由 Layer1 归一化处理；>0 表示实际写入。该结果必须能被 applyInner 取得（见方案 A）。

写入路径：新增 `upsertHostCapsGuardedConn`，只用于 `SetCapsLive` 的 docker/ghcr；不改通用 `upsertHostCapsConn`（`CommitHostProbe` 仍用），不动 `upsertHostCapsTx`（AddSource/RemoveSourceHost 建行路径）。

【G0 重取证项】原"SQLite 3.53.1 双分支 UPSERT 实测"随结构作废而整体失效，支线内亦无该实测的命令/SQL/结果证据文件。G0 必须：①核实实际运行的 SQLite 版本；②对新的"带 5 守卫 UPDATE"重做语义实测，至少覆盖 caps 行不存在、enabled=0、Mismatch、hard-excluded、policy_gen 不匹配、正常 Supported 六类，记录命令、SQL 与结果；③将该证据文件纳入证据包。不得再把"已实测"当作既成事实引用。

### F9 跨层竞态与 RecoveryState 读取

Layer2 skip 后 Layer1 处理（【补充 R11】已冻结为方案 A，见 §RunSource 单事务提交边界）：SQL 语句级 skip 时事务仍 COMMIT，`applyInner` 当前仍会写回 `s.DockerCap/GhcrCap/GhcrPrefix`。报守卫跳过写入时，Source 可用性判定不得继续使用未经重新验证的旧能力快照。【补充 R11】方案 A 冻结：单一 Store 提交入口返回 per-host 实际写回处置（由 UPDATE 影响行数得出），applyInner 据此在同一事务内归一化内存并计算最终 Source status。方案 B（事务外重新读取权威状态）作废——它制造新的 TOCTOU 与"先提交、再重读、再修正"中间态。

【补充 R10｜skip 覆盖面（冻结）】无论最终选 A 还是 B，方案必须统一覆盖 SetCapsLive 的全部 5 类 skip：caps 行不存在、enabled=0、policy_gen 不匹配、Mismatch、hard-excluded。不得只覆盖后两种保护状态。验收时须逐类给出断言，缺一类即不通过 G1。

`SourceHost.RecoveryState` 必须在 `attachSourceCaps`、`GetSourceHosts`、`GetSourceHost` 三个读取路径统一填充 `COALESCE(r.state,'') AS recovery_state`（关联键同上），字段 `json:"recovery_state,omitempty"`。该字段不需要 Schema 变更。否则保护逻辑会依赖数据从哪个入口加载，形成路径不一致。

### F9 pending 状态边界

接受：无 Realm policy 时 Source 保持 pending；Docker/GHCR 失败在认证策略解析阶段 fail-closed；不自动创建 Realm policy；GitHub 继续原逻辑探测；不引入 needs-policy 新状态或额外降频。T5 的 Host Probe 退避与 Source 级 RunSource 复测周期须分开验收。pending 是稳定的 fail-closed 业务状态，不是待消除的运行时过渡态。

### 【补充 R11】RunSource 写回：单事务提交边界与三类持久化

依据：基线 applyInner 把能力（SetCapsLive）、协议健康（NoteProbe）、Source 状态（SetStatusLive）及历史证据（ConsecutiveClean/ConsecutiveFailures/LastCheck）分散在多个 Store 方法与多次独立提交中，RunSource 另有 AddCheck（3 条 INSERT）和 TouchProbe。这会产生"caps 已写、health 未写""status 判定时读到半成品证据""中途失败无法整笔回滚"的中间态。

冻结原则（用户裁定）：网络探测与数据库提交分离。每次 RunSource 的探测结果先形成完整候选状态，再由唯一 Store 提交入口在单一 SQLite 写事务内完成能力、健康、Source 状态的校验与写入；任一环节失败整笔回滚；COMMIT 前不向任何调用方发布本轮计算结果；不允许后续任务或下一轮探测补齐部分提交。G0/G1/G2 是审批门禁，不是产品运行时过渡态；可分阶段审批，但产品数据操作不得拆成多次提交。

持久化分三类，边界不得混淆：

**A. 观测与调度记录（事务外，独立写入）**
- AddCheck（checks 表 INSERT）：保持独立观测写入，不进入核心状态事务。但它是 `ConsecutiveClean`/`ConsecutiveFailures`/`ObserveStreak`/`LastCheck` 的**状态判定输入**，不是普通日志：
  - 必须在本轮状态计算**之前**执行并提交，保证状态事务能读到已持久化的观测；
  - 核心状态事务内读取连续成功/失败等历史数据，禁止在事务外算好再带旧结果进事务；
  - AddCheck 写入失败不得回滚已成功的能力/健康/状态提交，但必须有保守处理：不得把未持久化的本轮成功样本当作已满足连续两次干净探测（blocked 恢复条件）；必须记录错误，禁止静默忽略；
  - 测试须覆盖观测写入失败时的状态判定（T17/T18 扩展）。
- TouchProbe（sources.probe_at=now）：语义是"不论成败记录一次探测尝试"，供 dead/blocked 低频恢复调度（probeDue）使用。独立于核心状态事务；状态事务失败、因归档/守卫拒绝写入都不得反向抹掉真实的探测记录；TouchProbe 失败不回滚能力/健康/状态，但必须记录错误。须验证：时间戳写失败后不出现意外高频探测，时间戳更新后不造成不合理恢复延迟。与 F1 的 probe_at=0（立即重新识别）方向相反，二者不得互相覆盖：F1 属端点变更事务，RunSource 完成后的 TouchProbe 属本次探测记录，时序上先后分明。
- source_events：不因"审计"之名自动加入核心状态事务。项目既有约定是 source_events 记录探测统计（见 starrace.go:143），本版不新增状态转换事件写入路径；如确需审计，须先证明其为该状态转换的必要审计并单独冻结语义。

**B. 核心业务状态提交（唯一入口，单一 BEGIN IMMEDIATE 事务）**
唯一 Store 提交入口内顺序：BEGIN IMMEDIATE → 同一连接内重新读取 Source 与 Host 权威状态 → 校验 Source 存在且非 archived → 校验 Host 存在、enabled、PolicyGen → 校验 Mismatch/hard-excluded → 计算最终有效能力 → 更新允许写入的 caps → 更新 source_health → 事务内读取必要历史证据并计算最终 Source status → 更新 Source status → COMMIT。SetCapsLive、NoteProbe、SetStatusLive 不得再作为三个独立提交依次调用，其写入语义收敛到该入口。任一步失败整笔 ROLLBACK。COMMIT 前不得发布本轮最终状态。
- 历史证据读取必须在事务内，否则回到 TOCTOU；网络请求必须在事务外，否则长时间持锁。
- 【补充 R12】同秒多样本排序确定性：仅 `ConsecutiveClean`（store.go:892-895）与 `ConsecutiveFailures`（store.go:1087-1089）补齐 `ORDER BY ts DESC, id DESC`；`LastCheck`（store.go:1068-1070）已含 id DESC、`ObserveStreak`（store.go:1110-1118）已用自增 id DESC，均保持不变。不得把修订扩大为所有查询。

**C. 【补充 R12】per-Source 运行槽位与结果失效（整体替换 R11 §3.C "后来者直接丢弃"，旧口径废止，不得保留为备用路径）**

G1 取证确认（基于 850b610）：Engine.mu/inflight/queued 只串行化 `Run(tier)`（runner.go:58-71、99-121），`RunSource(id)` 绕开该协调（runner.go:291-335），同一 Source 可被 tier 轮次与多个 RunSource 同时处理；代码无 per-Source 槽位、待重跑标记或运行代次。R11 §3.C 的"后来者直接丢弃"与现行 tier 冲突裁定冲突，整体废止。

**C1. 运行槽位（进程内、按 SourceID 粒度）**
- 槽位粒度是 SourceID，**不是 (SourceID, Kind)**。一个槽位覆盖该 Source 本轮全部协议（docker/ghcr/github）的网络探测、观测写入、TouchProbe 与核心状态提交；不得让三种协议各自获得不同代次而拼出互相不一致的状态。
- 每个槽位至少包含：当前运行状态、进程内单调递增的运行代次（整数，仅内存，不落库）、一个合并的待重跑标记、当前任务的取消上下文（context.CancelFunc）、槽位互斥锁（见 C8）。
- 代次是 Engine 内存整数，进程重启后新进程从初值开始；旧探测 goroutine 随旧进程消失，故不需要持久化到 sources 表、不增加字段、不改 Schema。这纠正了 R11 裁定索引中"代次 CAS 因禁改 Schema 被否"的过时结论：内存代次不要求 Schema 变更。禁止用秒级 probe_at/status_at 冒充单调代次（同秒碰撞会误拒）。
- 【补充 R13｜P0-1】**BaseURL 快照捕获**：探测任务启动时捕获该 Source 的 `base_url`（连同运行代次）作为本次任务的身份快照，随结果对象一路传递到所有写入点（consensus、AddCheck、TouchProbe、核心事务、Tampered）。禁止在写入时"现读当前 base_url"来充当快照——旧任务会用新 Endpoint 的 base_url 通过校验。快照是 P0-1 核心事务守卫的输入。

**C2. 入口协调（全局 inflight 与 per-Source 槽位分层）**
- 全局 `inflight/queued` 保留原有职责（一次只跑一轮 tier、记录最高待跑 tier），不为实现 per-Source 单飞而重写调度器。
- per-Source 槽位接入 `Run(tier)` 与 `RunSource(id)` 两条入口，二者共用同一套代次与提交保护。Run(tier) 一轮内每个 Source 只出现一次（jobs 按 source 聚合，runner.go:157-169），故真正的并发冲突来自 RunSource↔Run、RunSource↔RunSource。
- 新请求到达时：无在途任务→启动新任务（代次+1）；有在途任务→按 C3 决定是否使旧任务失效；多次新请求→合并为一个待重跑标记，不无限排队。当前任务结束后，若待重跑标记置位，**重新读取最新 Source 状态**再执行一次完整探测，不复用旧结果。
- pending 合并优先级（【补充 R13｜P1-1】）：多个请求同时进入同一个 pending 槽位时，按"配置变更 > tier3 > tier2 > tier1 > 普通 RunSource"取最高优先级作为待重跑的触发原因；待重跑只执行一次完整探测，执行时读取最新配置，不为每个被合并的请求单独执行。pending 中只要含一次配置变更，重跑就必须对新 Endpoint 完整探测。

**C3. tier 冲突优先级（冻结，【补充 R13｜P1-1】补全反向场景）**
当前任务与新请求的完整矩阵（两个方向都冻结）：

| 当前任务 | 新请求 | 行为 |
| --- | --- | --- |
| tier1/2 执行中 | RunSource | 使旧任务失效（取消上下文+代次+1），合并一次待重跑 |
| tier3 执行中 | 普通 RunSource | 不抢占当前轮次，合并一次待重跑（tier3 轮次完整性优先于普通立即探测） |
| tier3 执行中 | Source BaseURL 被修改 | 旧 Endpoint 结果立即失效，不得参与 consensus（配置正确性优先于 tier3 轮次完整性） |
| 同一 Source 连续多个 RunSource | — | 合并为一次待重跑，执行时读取最新配置 |
| tier3 有效票不足严格多数 | — | 本轮 consensus 为空，不更新预期摘要 |
| RunSource 执行中 | tier1 | 取消当前 RunSource（代次+1），该 Source 纳入本轮 tier1 任务；不单独保留 RunSource 的待重跑（tier1 已覆盖该 Source） |
| RunSource 执行中 | tier2 | 同 tier1：取消当前 RunSource，纳入本轮 tier2；不重复探测 |
| RunSource 执行中 | tier3 | 等待当前 RunSource 完成后再执行该 Source 在本轮 tier3 的探测；该 Source 成为本轮 tier3 有效参与者，不跳过也不复用 tier2 结果参与 consensus |

请求不仅要带 pending 标记，还要带入口类型、tier 与所属轮次标识，不能只有单一布尔。被失效的旧任务二级后果统一按 C4 的写入准入规则处理。

**C4. 五个结果失效检查点 + 写入线性化（冻结，缺一不可；【补充 R13｜P0-2/P1-4/P1-5】）**
五个检查点：1. consensus 计算前（tier3）；2. AddCheck 写入前；3. TouchProbe 写入前；4. 核心状态事务提交前；5. Tampered→blocked 写入前。
- 第 5 点的 `runner.go:495-502`（写点 500）**只是引用旧代码的独立写点位置**；现行设计中 Tampered→blocked 是 C7 核心事务内的一个逻辑分支，不是第二条独立持久化路径。不得按"两个写点"实现。

**写入线性化机制（P0-2，冻结的可证明规则）**：
- 每个写操作（AddCheck、TouchProbe、核心事务、Tampered）的"代次有效性检查"与"实际写入"必须在**持有同一 per-Source 槽位锁的临界区内连续完成**，中间不得释放锁。这是线性化点：检查通过即在同一临界区内写完；失效操作也必须在持有同一槽位锁时递增代次。二者互斥排序，因此只存在两种结果——写入在失效前完成（获准完成的写入保留，见下）或失效先发生（代次不等，写入整体拒绝）。不存在"检查通过后、写入开始前又被取代"的窗口。
- context.CancelFunc **只用于取消网络探测阶段以减少无效工作，不作为写入准入机制**：Go 的 context 不能保证已进入执行路径的 DB 操作自动停止。禁止把"检查一次 generation"当作跨临界区的有效性证明。
- 失效后已获准完成的写入不回滚：AddCheck 已成功提交的历史观测、TouchProbe 已记录的真实尝试，均保留（它们是真实发生的事实）；失效后**不得再开始**任何新的观测/调度/状态写入。T21 按此分时点断言（见测试矩阵）。
- 核心事务从最终准入到 COMMIT 全程持有槽位锁；COMMIT 完成后才释放。网络请求不得在槽位锁或 SQLite 写事务内执行。

**AddCheck/TouchProbe 的 BaseURL 条件写入与失败语义（P1-4，两类记录严格分开）**：
- AddCheck：`INSERT INTO checks (...) SELECT ... WHERE EXISTS (SELECT 1 FROM sources WHERE id=? AND base_url=?)`，`RowsAffected()==0` 表示 Endpoint 已变，旧观测不写入（checks 表不加列、不改 Schema）。TouchProbe：`UPDATE sources SET probe_at=? WHERE id=? AND base_url=?`。二者防 Endpoint 变化；内存代次防同 BaseURL 下旧任务被取代，并列不可互替。**禁止用 `probe_at<=old_value` 充当 CAS 代次**（秒级、非单调）。
- **AddCheck 失败**：对应协议本轮样本不得作为"已持久化证据"参与状态判定；其余成功持久化的协议样本仍按既定规则处理（不因一个协议失败而丢弃整个 Source 的结果）。必须记录错误，禁止静默忽略。Run(tier) 与 RunSource 两条入口遵循同一语义（现行差异：Run(tier) 失败 `continue` 跳过该结果 runner.go:253-260；RunSource `_ =` 忽略并仍交 apply runner.go:324-333——统一为前者）。
- **TouchProbe 失败**：只记录错误，**不因此否定已完成的网络探测结果、不阻断核心状态提交**（R11 已冻结 TouchProbe 属"记录探测尝试"，与协议证据不同）。两入口统一此语义。

**C5. tier3 consensus 与 baseline 缓存（冻结，【补充 R13｜P1-2/P1-3/P1-7】）**
**两条路径显式判定**：
- 路径 A（baseline 命中）：`expected` = 全局官方缓存 digest，**consensus 不执行**；每个 Source 的 `DigestOK` = (自身 docker digest == expected)；过期 Source 只从 DigestOK 比对集合剔除，不重算多数。
- 路径 B（baseline 未命中且 tier>=3）：`expected` = consensus 结果；按下列固定分母规则过滤与重算。现行代码 `consensus()`（runner.go:580-600）以有效票数 `valid` 作分母，过滤掉失效票会同步降低多数阈值——这是安全缺陷，必须改为固定分母。

**严格多数分母冻结（P1-2）**：候选投票集合在轮次开始时确定（本轮参与 tier3 docker 探测的 Source ID 集合），阈值 = `floor(集合大小/2)+1`，**按固定集合计算，结果失效只减少有效票、不缩小分母**。有效票 < 阈值 → consensus 为空，本轮不写预期摘要、不得拿旧结果冒充。不得因剔除一个 Source 而作废其他 Source 已完成的有效结果。

**consensus 形成后的失效语义冻结（P1-2，去掉条件性措辞）**：
- consensus 对象绑定轮次标识（Engine 内存 roundID）与参与者代次集合（不改 Schema）。
- 触发失效的事件明确为：任一参与投票的 Source 发生 BaseURL 变更或其任务代次失效 → 该共识整体失效（因为 expected 可能已被污染）。
- 已消费该共识完成 DigestOK、但尚未提交核心事务的 Source：其 DigestOK 不得作为最终状态依据，核心事务整笔拒绝（由 C1 快照守卫 + 轮次标识校验共同保证），该 Source 进入待重跑。
- 【补充 R14】已合法提交（在失效屏障之前获准并完成 COMMIT）的 DigestOK 结果是当时的有效历史事实，保留为历史证据，不追溯回滚、不事后废除；失效屏障之后任何未获准的旧共识结果一律不得写入。不引入第二套持久化标记来区分历史样本。相关 Source 的待重跑仅针对尚未提交的在途任务。

**baseline() 缓存冻结（P1-3）**：`baseline()`（runner.go:604-624）是独立的全局权威基准缓存，6 小时语义不变，不随任何单个 Source 的 BaseURL 变化清空。采用**单一 in-flight refresh**：缓存未命中时同一刷新期只允许一个官方请求在途，并发调用共享该请求结果；网络请求在缓存互斥锁之外执行；请求完成后只由持有 in-flight 句柄者发布结果，不允许其他并发刷新覆盖（后来者发现已有 in-flight 则等待并共享，不发起新请求）。此方案同时消除重复请求与"较早发起较晚完成覆盖较新值"，不引入第二套缓存路径。

**【补充 R14｜P0-3】Round 有效性屏障与跨 Source 失效原子性**：
- 每个 Engine 最多存在一个活动 tier3 Round。生命周期：Run(tier3) 启动时创建 Round → 先冻结本轮候选 Source ID 集合及各 member 的 BaseURL/运行代次快照 → 再启动网络探测 → Round 持续有效直至本轮所有结果处理完毕（提交/拒绝/进入待重跑）且所有共享许可释放 → 关闭 Round 并清理活动引用 → 下一轮 tier3 才能创建新 Round。现有 Engine 全局 inflight/queued 保持一次一轮 Run(tier) 的职责，不新增第二套全局调度器。
- 屏障同步对象与"活动 Round 元数据/引用"分离：屏障对象不因一轮结束而被并发释放或替换；Engine.mu 只保护活动 Round 引用和元数据，不得持有它等待屏障锁或 Store。失效方只取得 Round 独占许可，不遍历参与者的 Source 槽位锁（成员映射 O(1)）。
- 许可规则：tier3 路径 B（使用非空 consensus 结果计算 DigestOK）的消费者持自身 Source 槽位锁 + Round 共享许可；共享许可从最后一次 Round 有效性检查开始，覆盖携带共识结果的 AddCheck 写入及核心状态事务，直到 COMMIT。路径 A（baseline 命中）、RunSource(tier2)、Run(tier1/2) 不消费 consensus，**不获取 Round 共享许可**（不因统一代码路径而给所有写入无条件加锁）；TouchProbe 只记录探测尝试，按自身 Source 槽位准入规则处理，不单独取 Round 许可。
- 提交许可时序：B 先持共享许可并完成 COMMIT，则 A 才能取独占许可开始配置事务；A 先取独占许可，则 B 无法取共享许可，A 完成 Endpoint 变更与 Round 失效后，B 必须拒绝旧轮次结果。已合法 COMMIT 的 B 不回滚；未取得有效提交许可的消费者不得提交。
- 锁顺序与无环论证见 C8。

  - `roundLifecycleGate` 属于 Engine、长期存在，不随某轮结束销毁或替换；activeRound 是当前活动 Round 引用（最多一个）；Round 自身有独立有效性屏障。不得把生命周期准入对象放进 Round 结构体，否则结束与下一轮创建之间仍有同步对象替换窗口。
  - 创建方只在发布阶段持有准入：获准入 → 确认无活动 Round → 创建 Round 与不可变轮次元数据 → 发布 activeRound → 释放准入 → 开始网络探测。网络请求、等待结果、consensus 计算均不得持有生命周期准入（否则 F1 在整个探测期被阻塞，5 秒 deadline 变成必然超时）。
  - 销毁方经准入：探测与消费者全部结束 → 获准入 → 确认 activeRound 仍指向自己 → 清活动引用 → 释放准入 → 释放 Round 资源。不得先清引用再异步清理屏障。
  - Engine.mu 不得在等待生命周期锁、Round 屏障或 Store 时持有；Round 创建/销毁不得取参与者 Source 槽位锁（避免反向锁依赖）。
  - 失效方只取 Round 独占许可，不遍历参与者 Source 槽位锁，因此不存在"B 持 B 槽位等 Round、A 持 Round 等 B 槽位"的环。数据库写入在持有必要 Source/Round 许可时进行但不在 Engine.mu 内；网络请求不持有 Source 槽位锁、生命周期准入、Round 锁或 SQLite 写事务。
  - per-Source 槽位锁、Engine.mu、Store 单连接池的既有约束不变（store.go:198-203 单连接、busy_timeout=5000）。
- **AddSourceHost 纳入同一 Source 槽位协调（P1-12，理由修正）**：AddSourceHost 已通过 `beginImmediate` 与事务内读取 status/base_url（hostcaps.go:398-410）保证单次事务的 BaseURL 快照一致性——不得再把它描述成"事务外读取 base_url"的旧缺陷（那是 3.5.24 已修复的 D-TX 竞态）。纳入槽位锁的理由是**跨操作互斥与定序**：它与 F1 之间缺少统一 Source 级操作顺序，无法把 DB 变更、运行代次失效、Round 屏障纳入同一逻辑序列。冻结：所有生产调用经统一 Engine 协调入口取 Source 槽位锁 → 持锁调用 Store.AddSourceHost（Store 保留现有 BEGIN IMMEDIATE 与事务内读取）→ 事务提交或回滚后释放；不取 Round 共享许可；不得留绕过锁的第二条生产路径。两种先后均安全：AddSourceHost 先持锁则基于旧 BaseURL 完成、随后 F1 清理旧 policy 与旧 checks；F1 先持锁则 AddSourceHost 重新读取新 BaseURL 后再写。AddSourceHost 取 Source 锁同样遵循 5 秒总 deadline（C6-5），超时不写入、不使用旧快照继续。
- G4 只负责**验证**此顺序无死锁、无无限等待、无不必要全局阻塞（进程内长事务阻塞面板/API/其他探测；跨进程写锁等待可能超过 5 秒，busy_timeout 非保证），**不临时决定锁顺序**。
- 单实例部署假设：内存代次只保证单进程内顺序，不支持多进程共享库时的分布式互斥；未来多实例再设计持久化代次/分布式协调，不得在本版偷加 Schema。

**C9. 待重跑持久化事实、调度唤醒与统一去重状态机（【补充 R15｜P1-13；补充 R16｜R16-7】）**

- **持久化事实负责正确性**：`status='pending'` 证明存在待探测业务事实（持久化）；`probe_at=0` 表示探测时间状态（持久化）；运行代次拒绝旧任务结果（内存）；槽位 inflight 是单 Source 当前执行准入（内存）；槽位 queued/rerun 合并待执行请求（内存）；wake 信号仅减少等待下一轮定时扫描的延迟（内存）。内存 rerun=true 不得作为唯一任务存在性证明。
- **所有入口统一进入同一 per-Source 槽位**：Run(tier)、RunSource(id)、Engine API 唤醒、启动扫描、运行期定时重新发现全部经同一登记与准入逻辑。只有槽位空闲时才启动一个任务；已有任务时不得创建第二个并发任务，新请求只合并为至多一个待执行请求；合并优先级按 C2/C3 双向矩阵，不覆盖更高优先级请求；真正启动任务前重新读库中的 Source 状态与 BaseURL，不用扫描时的陈旧对象；旧 generation 结果不得提交；成功任务最终状态只由唯一 Store 核心提交入口决定。
- **唤醒所有权**：Engine 协调入口在登记持久化事实成功后触发统一调度器唤醒；PATCH 在请求租约释放后可提供一次及时唤醒，但不是唯一恢复来源。唤醒失败、被跳过或崩溃由 C9 崩溃恢复路径兜底。
- **扫描规则**：启动扫描扫描符合待探测条件的 pending Source 并只提供 Source ID 候选、不直接起 goroutine；运行期由既有 `Run(tier)` 定时循环重新发现，受 `l1_minutes`/`l2_minutes`/`l3_minutes` 与 `Interval` 节流（`runner.go:636-657`）；扫描、API 唤醒、Run(tier) 同时命中同一 Source 只能形成一个运行任务和一个合并待执行请求；`probe_at=0` 不能单独作为无限重复唤醒条件；pending 未完成时失败重试受既有 tier 与 Interval 节流，不得 tight-loop；blocked 不进入"pending 持久化恢复扫描"，正常 blocked 探测仍按既有 `probeDue`（`runner.go:272-277`）及两次连续 clean 规则运行。重新发现以数据库权威状态为依据，不依赖上次进程内存状态。

**C10. 人工状态转换分流（【补充 R15｜P1-14；补充 R16｜R16-1/R16-2/R16-4】pending/blocked/archive/restore 不同模板）**

Store 不自行获取 Engine 槽位锁；唯一入口是 Engine 协调方法 `ChangeEndpoint`、`SetSourcePending`、`ArchiveSource`、`RestoreSource`、`DeleteSource`、`SetSourceEnabled`（名称冻结；禁止 API handler 直接调用 Store 绕过 Engine 的生产写入路径）。`SetSourceBlocked` 不再作为管理入口——`status=blocked` 专用于 Runner 探测信任隔离，由核心提交事务产生，不在 Engine 管理 API 中提供人工写 blocked 的入口。各入口语义独立，不为减少函数数量强行合并。
【补充 R17｜R17-2 统一提交后失效顺序】所有入口统一为：取得全部必要锁 → 执行 Store 原子事务 → **COMMIT 成功** → 递增运行代次 → 取消旧任务 → 标记整个活动 Round 失效 → 释放 Round 屏障 → 释放 lifecycle gate → 释放 Source 槽位锁 → 合并唤醒。**事务失败时，generation 不变、在途任务不取消、Round 不失效、pending 内存登记与 wake 信号全部保持原样。**Archive、Restore、Delete、ArchiveStale、CleanupArchived、enabled 禁用全部使用同一提交后失效原则；禁止在任何分支中先失效再写事务。成员判定与 Round 屏障遵循 C6-1/C8 的统一准入区间规则。

**【补充 R17｜R17-13；补充 R18｜4.2 条件 UPDATE 落点】管理员路径仅限 dead/usable → pending，且受 enabled=true 限制；blocked → pending 被拒绝（不得绕过两次 clean 恢复机制），archived → pending 必须走 RestoreSource。管理员 pending 转换必须使用带状态条件的受控 UPDATE：`UPDATE sources SET status='pending', status_at=?, status_reason=? WHERE id=? AND enabled=1 AND status IN ('pending','usable','dead')`；影响行数为 0 即拒绝，不得用通用 `SetStatusWhy`（store.go:824-876，读 old 后无条件 UPDATE）绕过该限制。blocked 的信任隔离恢复只能由核心提交事务在满足连续两次 clean 后、作为事务内逻辑分支完成，不走管理员 pending 路径。该禁止规则在持久化状态转换边界保证，不能只在 API 层读取当前状态后判断，以消除检查与写入之间的竞态。**
- **blocked（探测信任隔离，【补充 R17｜R17-5/R17-12/R17-13】语义重写）**：管理员硬禁用不是 `Source.status` 状态转换，而是通过 `sources.enabled=false` 实现；`status=blocked` 专用于探测信任隔离（如 Tampered），由 Runner 核心提交事务产生，按连续两次 clean 自动恢复。**管理员不得通过 API 或 Web 直接将 blocked 清除为 pending**；外部 PATCH 设置 `status=blocked` 或把当前 blocked 改为 pending 都返回参数错误，blocked → pending/usable/dead 只能由 Runner 在连续两次 clean 条件满足后完成；`enabled=false/true` 不改变原 status。
  blocked 转换流程：Runner 核心提交事务在 COMMIT 成功（且代次/BaseURL/Round 有效性校验通过）后，递增代次并取消旧任务；Tampered 分支按 R14 C7 在**同一次核心事务内**完成——Runner 核心事务已持 Round 共享许可，不得再次取独占屏障造成锁升级死锁，保持事务内逻辑分支。F1 遇到当前 blocked：仍完成 base_url 更新、probe_at=0、checks/policy/F7/审计原子提交，但 `status` 保持 blocked、不登记立即重跑；blocked 恢复仍须新 Endpoint 两次连续 clean，F1 不得绕过门槛。blocked 可显示状态、原因与相关信息，但不提供人工清除或立即复检入口；普通调度仍可在 probeDue 到期时探测以完成两次 clean 恢复。**【补充 R17｜R17-9】`internal/api/web/index.html` 中针对 `status==='blocked'` 显示的 `<button data-life="pending">解除封禁并复检</button>` 必须删除，不改名、不保留为其他形式的人工解除操作；三个概念严格分离：管理员硬禁用 = `sources.enabled=false`（独立启用/禁用开关）、探测信任隔离 = `status=blocked`（只读展示）、信任隔离恢复 = 连续两次 clean（Runner 自动恢复）。重新启用一个 blocked Source 后它仍是 blocked，等待正常调度恢复。**
- **archived（归档）**：采用当前 `store.go:844-874` 的实际语义——进入 archived 只执行 `status='archived'`、status_at/reason、`policy_gen+1`、`recordPolicyChangeTx`；**不得清理 caps/health/health_scope/recovery**。取槽位锁 → lifecycle gate → 成员判定/必要时 Round 独占屏障 → Store 归档事务 → 成功后代次失效/取消任务/Round 失效 → 不登记重跑。归档影响 tier3 成员资格时使该 Source 票据失效，旧票据不得参与 consensus。
- **RestoreSource（显式重新接纳）**：仅限 `archived → pending`，不是任意目标状态的通用恢复接口，普通 dead/blocked/usable → pending 由 SetSourcePending 处理。原子事务内容：校验当前确为 archived → `status='pending'`、`probe_at=0`、status_at/reason → `policy_gen+1` → `source_host_caps` 已有行 UPDATE `effective_status='Unknown'`、`registry_path_mode=''`（**不删除行、不清 registry_prefix、不改 enabled/last_verdict/diagnostics**）→ `DELETE source_health_scope` → `DELETE source_health` → `registry_host_recovery` UPDATE `state='initial', next_probe_at=now, rec_failures=0, retry_failures=0, last_error=''` → `recordPolicyChangeTx` → COMMIT。成功后代次失效并触发合并调度。Schema 不记录归档前完整业务状态，Restore 不承诺还原历史 usable/blocked，靠新探测重建当前状态。当前 API 的 `SetStatusWhy → TouchProbe0 → RunSource` 三段式旧路径作废，统一为上述单事务。
- **Mismatch / hard-excluded 例外**：现有 Restore SQL 会把已有 caps 行重置 Unknown、recovery 重置 initial，与 §0.2"不得自动解除 Mismatch 或 hard-excluded"存在张力。冻结例外：**只有用户显式触发 RestoreSource 才允许执行归档恢复所需的 Host 能力与 recovery 重新初始化**；普通 Endpoint 修改、后台探测、自动调度均不得借此解除 Mismatch 或 hard-excluded。Restore 后 Host 能力必须由合法新探测决定，Realm policy 不得自动伪造或恢复已不存在的授权，Recovery 必须沿用 `SetRealmPolicy` 等合法初始化路径，不得绕过其策略规则。
- **F9 前置守卫精度（消解措辞失真）**：`SetCapsLive` 不是"单条 guarded UPDATE、无 INSERT 分支"。实际是同一 BEGIN IMMEDIATE 事务内先查 Source 状态拒 archived（`store.go:735-743`）、查 caps 行 enabled（L757）、行不存在则 continue（L758-760）、enabled=0 则 continue（L763），通过守卫后才调用底层 `upsertHostCapsConn`（INSERT ON CONFLICT DO UPDATE，L704/L785）。安全边界是该前置存在性与 enabled 守卫：已删除或停用的 caps 行不会进入 UPSERT。不得删除、移出事务或弱化该守卫。

**C11. Round 投票结果绑定成员快照（【补充 R15｜第六节】不增加 Schema）**

Round 发布时固定不可变轮次身份（Round 票据）：Round ID、本轮候选 Source 集合、每个参与 Source 的 BaseURL 快照与运行代次、consensus 规则版本/固定配置快照。结果提交时除"当前 BaseURL 与结果 BaseURL 相同"外，还必须校验：Source 属于本 Round 成员集合、结果来自本 Round、结果对应本 Round 运行代次、该 Source 未被人工状态转换/Endpoint 变更/归档失效、Round 仍有效。Round 票据是不可变内存身份信息，不得依赖全局可变 roundID 字段代替。Round 失效后标记为失效、丢弃其未提交共识结果，由后续新 Round 重新采集；**已提交的历史结果不追溯删除**。所有校验在共享许可保护下、检查至 COMMIT 之间不释放许可。【补充 R16】人工状态转换与删除入口必须经 C6-1/C8 的统一准入区间，使整个活动 Round 的未提交共识失效；非成员、旧代次、BaseURL 不匹配、人工失效、失效 Round 的票据一律拒绝提交（T42）。

**C12. Source 生命周期全部生产入口统一协调（【补充 R16｜R16-8】）**

当前代码存在绕过 Engine 协调的生产路径，必须统一纳入 C6-1/C8 协议，不改 Schema、不改业务规则：
- **ArchiveStale（后台自动归档）**：`runner.go:676` 的 `maintain()` 直接调用 `Store.ArchiveStale`（`store.go:917-969`，单事务批量 UPDATE + 逐条 bump/审计），无槽位/gate/Round 屏障/代次失效/任务取消。修订：新增 Engine 级 ArchiveStale 协调入口；Store 只负责查询到期候选 ID，不得批量改状态；Engine 对每个 Source 单独调用统一 ArchiveSource 流程；Store 事务内重新校验 enabled=1、状态仍为 dead/blocked、status_at 仍达标；只有事务实际完成状态转换后才递增代次、取消旧任务、使活动 Round 失效；每个 Source 单独协调，不得一次持有多个 Source 槽位锁；归档只做 status→archived、policy_gen bump、审计，不清理 caps/health/recovery。
- **DeleteSource（API）**：`api.go:998-1004` 直接 `DeleteSource → Forget → Changed()`，`store.go:1021-1031` 独立事务。修订：DeleteSource 走 Source 槽位锁 → lifecycle gate → 成员判定 → 必要时 Round 独占屏障 → Store 删除事务 → 代次失效/取消/失效 → 调度器 Forget；不允许 API 保留直接 Store 删除的生产路径。
- **CleanupArchived（后台清理）**：`runner.go:682` 直接调用，`store.go:973-1019` 批选 ID 后逐条事务内复核 status=='archived'（L1001-1008，已有部分防护但不在 Engine 协调层）。修订：逐 Source 经统一删除协调入口处理，事务内重新确认仍为 archived，防止误删已恢复 Source；不得与 Restore 的 Engine 租约交错。**【补充 R17｜R17-4】候选 ID 可在事务外查询，但真正删除前必须在同一 BEGIN IMMEDIATE 事务内复核：`SELECT status, status_at FROM sources WHERE id=?`，仅当 `status='archived' AND status_at>0 AND status_at<=?`（before 为本轮清理的归档保留期限截止时间）才允许 `deleteSourceRows` 与 COMMIT；任一条件不满足必须跳过，不得删除附属记录。SQL 条件复核是 Engine 并发协调的必要补充，不替代 Source 槽位/lifecycle gate/成员判定/Round 独占屏障（C12 统一协议仍完整适用）。竞争场景必须覆盖：过期候选 → Restore 为 pending → 再次归档更新 status_at → 旧 CleanupArchived 处理候选时因新 status_at>before 跳过。**
- **统一结果**：人工 ArchiveSource、后台 ArchiveStale、RestoreSource、API DeleteSource、后台 CleanupArchived 五个入口全部遵循同一协议；API 与 Runner maintenance 不得保留任何直连 Store 的生命周期写入路径（T43/T44）。

**C13. PATCH 最终状态准入矩阵与统一网络入口检查（【补充 R17｜R17-6/R17-13】）**

PATCH 的全部字段事务完成、Source 请求租约释放前，不允许网络任务启动；请求结束后调度器必须重新读取最终数据库状态，不得依据 Endpoint 变更时的中间状态派发。矩阵（enabled 不是 status 值，是独立字段）：

| PATCH 最终数据库状态 | 立即唤醒能否启动探测 | 后续调度 |
| --- | --- | --- |
| archived | 否 | 不调度，归档状态保持 |
| enabled=false | 否 | 不调度，保留原业务状态 |
| enabled=true, status=pending | 是 | 经统一槽位去重后立即探测 |
| enabled=true, status=blocked | 否 | 仅按正常 probeDue 定时探测，两次连续 clean 后恢复 |
| enabled=true, status=dead | 否 | 按原有 dead 恢复周期 |
| enabled=true, status=usable | 否 | 按原有 tier 调度 |

**blocked → 拒绝**（不得绕过两次 clean）；archived → 拒绝，必须 RestoreSource。**【补充 R18】管理员 pending 写入必须用 `WHERE id=? AND enabled=1 AND status IN ('pending','usable','dead')` 的条件 UPDATE，blocked→pending 无法通过管理员路径；blocked 只能由核心事务连续两次 clean 恢复；通用 `SetStatusWhy` 不得绕过该边界。**禁止规则在持久化状态转换边界保证，不只靠 API 层读取判断。

**enabled=false 时，无论数据库 status 为 pending/usable/dead/blocked，都不得启动探测、不得提交旧探测结果、不得通过自动状态转换重新启用。**

【补充 R18｜选择 A：blocked Endpoint 变更的 probe_at 时序】**blocked Source 的 Endpoint 变更不在 PATCH 请求内直接启动探测，但 F1 将 probe_at 清零。该 Source 在下一个正常 `Run(tier)` 调度周期即可满足 probeDue，进入统一调度准入流程。后续仍须满足连续两次 clean 才能解除 blocked。此行为是设计预期，不要求等待原有 RecoveryEvery 间隔。**依据：`probeDue`（runner.go:272-277）对 blocked 用 `probe_at==0 || now-probe_at>=gap`，probe_at=0 使下个周期到期；PATCH 本身不绕过统一调度器直接启动网络任务。§8.2 第 2 步保留 `probe_at=0` 并与本段统一。

# 4. 关键不变量

以下不变量是整个版本的验收基础。

## I-01：地址更新原子性

base_url、probe_at、Realm policy 删除、Host 能力状态重置、审计事件必须在同一事务内完成。

任意 SQL 失败：

- 地址不变。
- probe_at 不变。
- Realm policy 完整保留。
- Host 能力状态完整保留。
- 不留下部分审计副作用。

## I-02：策略删除即 fail-closed

地址修改成功后，该 Source 的 source_realm_policy 行数为 0。

对该 Source 的所有 Registry Host：

Resolve() 返回 ErrPolicyMissing。

不允许使用旧 Realm、旧 Host 或旧 Origin fallback。

## I-03：旧探测快照失效

策略存在时：

- PolicyGen >= 1
- HasPolicyGen = true

策略删除后：

- 当前策略代次为 0。
- 旧探测快照不得提交旧 Supported 结论。

【补充 R10｜I-03 HasPolicyGen 口径统一（冻结）】原"策略不存在时新发起探测 PolicyGen=0、HasPolicyGen=false"与 F8 最终实现冲突，作废。统一口径：

| 情况 | PolicyGen | HasPolicyGen |
| --- | --- | --- |
| 生产调度器启动探测，当前有策略 | >0 | true |
| 生产调度器启动探测，当前无策略 | 0 | true |
| 调用者没有提供策略代次快照 | 不作保证 | false |

冻结：`ListDueHostProbes` 生成的**生产任务无论策略是否存在都必须 HasPolicyGen=true**（代次 0 也明确表示"已取得有效快照"）。无策略探测本身不能通过缺失策略认证，必须得到 Unknown/Inconclusive 结果，不得沿用旧 Supported。`HasPolicyGen=false` 仅表示调用者未提供快照，不是生产探测的正常情况。
