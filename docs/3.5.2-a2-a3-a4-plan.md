## 1. A2-2 最小观测

### 要求

1. 四类指标，标签值全部是封闭集合，类型上不可能塞入 Host / URL / 源名：
   - `hostprobe_retry_scheduled_total{reason}`：`credential_pending` /
     `local_execution` / `commit_failed` / `outcome_inconsistent`
   - `hostprobe_retry_rejected_total{reason}`：`gen_mismatch` / `cas_lost` /
     `source_unavailable` / `db_error`
   - `hostprobe_retry_pending`：Gauge，必须由 SQL 统计，不得用内存 map 推算
   - `hostprobe_retry_delay_seconds`：固定桶 15/30/60/120/240/480/600s + 总和
2. 不引 Prometheus 客户端，沿用 `internal/metrics` 的 atomic + snapshot 模式。
3. 指标必须能区分「Runner 执行失败」（本组指标）与「CommitHostProbe 记录的探测
   失败」（仍由 `rec_failures` 与既有 recovery 指标承载）。
4. 拒绝原因在 `ScheduleHostProbeRetry` 的同一事务内分类；分类只用于指标，
   不参与 CAS 判定，不改变任何写入行为。

### 内容

- `internal/metrics/metrics.go`：新增三组计数/gauges 与固定桶 histogram；
  文本格式渲染；未知标签值折叠为 `other`（防御，不新开维度）。
- `internal/store/probe_retry.go`：`ScheduleHostProbeRetryClassified` 返回
  `(reject, delay, err)`；原 `ScheduleHostProbeRetry` 保留为薄包装（测试与旧调用
  零改动）。拒绝分类 SELECT 在同一 `BEGIN IMMEDIATE` 事务内执行。
- `internal/store/probe_retry.go`：`CountRetryPending(now)`，SQL：
  `COUNT(*) WHERE family='registry' AND retry_failures>0 AND next_probe_at>?`。
- `internal/runner/hostprobe.go`：`scheduleRetry` 按结果记 scheduled/rejected/
  delay；`Once` 每轮扫描后用 SQL 结果刷新 pending gauge。
- 测试：metrics 文本输出（含分桶边界 14.9/15/600/601s）、拒绝分类四类、
  pending 只统计未来到期行、Runner 成功/被拒路径计数。

### 验收

| 编号 | 判据 |
| --- | --- |
| A2-2-1 | 四类 reason 各记一次，文本输出行数与值正确 |
| A2-2-2 | 延迟 15/30/60/120/240/480/600 落在对应桶，601s 落 +Inf |
| A2-2-3 | pending 只计 `retry_failures>0 AND next_probe_at>now`，到期的行不计 |
| A2-2-4 | CAS 拒绝不改变任何数据库字段（既有测试仍绿） |
| A2-2-5 | 拒绝分类与真实拒绝原因一致（gen 不符 / 未到期 / 禁用或换 Host / 缺行） |

## 3. A3 真实链路端到端验收

### 要求

用真实组件跑完整链路，不允许 mock 掉被测环节：

- 真实 `httptest` Registry（真 HTTP、Bearer token 挑战、manifest 摘要）
- 真实 `probe.ProbeRegistryHost`（不注入假 Probe）
- 真实 SQLite（临时库，走完整迁移）
- 真实 `HostProbeRunner.Once`、真实 `RecoveryGuard`
- 真实候选 SQL（`RegistryCandidatesRaw`）

覆盖五个场景：跨 Host、陈旧快照、凭据变更、hard-excluded 不重验、
候选 SQL 与 Runner 联合行为。

### 内容

`internal/runner/a3_e2e_test.go`：

1. **跨 Host**：Host A 探测失败写入 A 的恢复行；Host B 的 state / gen /
   next_probe_at 完全不变。
2. **陈旧快照**：探测进行中代次递增 → `CommitHostProbe` 返回 stale，
   不写恢复状态、不写调度、不清退避。
3. **凭据变更**：快照代次落后于库 → 同上，且不 Block 路由缓存。
4. **hard-excluded**：`ListDueHostProbes` 不产出该 Host；Runner 不探测。
5. **候选联合**：cap=1 成功 + gen=当前代次 + 未过期 → 出现在候选；
   失败或过期 → 不出现。

### 验收

| 编号 | 判据 |
| --- | --- |
| A3-1 | 五个场景全部 PASS，且断言直接读数据库，不读内存计数 |
| A3-2 | 陈旧/凭据变更场景下 `rec_failures`、`retry_failures`、`state` 零变化 |
| A3-3 | hard-excluded 的 `next_probe_at` 始终为 0，不被推到未来 |
| A3-4 | 候选结果与 Runner 写入一致（同一事务提交后可见） |

### 实施记录与偏差

- 场景数从 5 增到 6：「凭据变更」单独成一个子测试（真实 `ApplyCredChanges`），
  「候选联合」合并进场景 1 与 6 的断言。
- 假 Registry 未实现 Bearer token 挑战：本批次验证的是无凭据探测路径
  （`/v2/` 直接 200）。带挑战的 token 流程由 `internal/v2auth` 既有测试覆盖，
  不在 A3 重复。
- SSRF 防护默认拒绝回环地址，测试进程内 `probe.Configure(true)` 放开，
  `defer probe.Configure(false)` 恢复；生产默认不变。
