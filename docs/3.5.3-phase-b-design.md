# 3.5.3 Phase B：legacy Registry 数据退出（设计 v2）

> 状态：**已实施**（`feat/3.5.3-phase-b`）。3.5.2 发布范围已冻结为 A1+A2，本阶段代码不进入 3.5.2。
> v2 变更：入口定为启动时自动一次；补迁移标记表 `schema_migrations`；记录 un-archive 与重启的交互语义。
> 依据：`docs/3.5.2-phase-a1-design.md` §11（605-607）、`docs/3.5.2-roadmap.md`。

## 0. 背景与边界

A1 已经删掉 legacy 对候选资格的否决权：`registryCandidatesRaw` 只读
`registry_host_recovery` + `source_health_scope`，不再引用 `source_health`。
`NoteProbeScoped` 对 `family='registry'` 直接返回错误，因此 3.5.2 没有任何
路径再写入 legacy registry 行——它们已经是纯历史数据。

Phase B 的唯一目标：**把这份历史数据移出运行表，并保留可回滚的副本**。
不改候选算法、不改六态、不改 Guard、不引入新依赖。

范围之外（保持现状）：

- `source_health` 表本身不删，其他 family（docker/ghcr/git/…）照常使用；
- `source_health_scope`（含 3.5.1 迁移来的 `gen=0` 行）不属于本阶段，
  A1 的代次规则已经让它们失效但不删除，是否清理另立事项；
- 不做自动回滚，un-archive 只作为发布事故的人工回退手段。

## 1. 覆盖集合

```sql
SELECT source_id, family, fails, ok_at, last_at
FROM source_health
WHERE family = 'registry'
```

**不按 `status` / `enabled` 过滤。** 与 A1 种子、Runner 维护集合的口径一致
（`status<>'archived' AND repo_host<>'' AND repo_host<>'ghcr.io'` 只管是否
参与探测，不决定历史数据去留）。理由：archived 源被重新启用时，遗留的
`fails` 不能在无人察觉的情况下重新具备否决权；A1 虽然已经不看它，但把
死数据留在运行表里会给后续读路径留下复发空间。

## 2. 归档表

```sql
CREATE TABLE IF NOT EXISTS source_health_archive (
  source_id  INTEGER NOT NULL,
  family     TEXT    NOT NULL,
  fails      INTEGER NOT NULL,
  ok_at      INTEGER NOT NULL,
  last_at    INTEGER NOT NULL,
  archived_at INTEGER NOT NULL,
  batch      TEXT    NOT NULL,
  PRIMARY KEY (source_id, family, batch)
);
CREATE INDEX IF NOT EXISTS idx_sha_batch ON source_health_archive(batch);
```

- **不加外键**：`sources` 行可能先被删除，归档记录必须能独立存活，否则
  归档表会随源删除而失去审计价值。
- `batch` = 固定批次 `b1`（`legacyArchiveBatch`），全部历史行同批归档；
  同批次可整体回滚，重复执行幂等。改成时间戳批次会让「重跑」变成新批次，
  失去 dup 判定的基础。
- 不保留 `gen`：legacy 表没有该列，代次语义只属于 scoped 表。

## 3. 迁移事务

```sql
BEGIN IMMEDIATE;

INSERT INTO source_health_archive
  (source_id, family, fails, ok_at, last_at, archived_at, batch)
SELECT source_id, family, fails, ok_at, last_at, :now, :batch
FROM source_health
WHERE family = 'registry'
  AND NOT EXISTS (
    SELECT 1 FROM source_health_archive a
    WHERE a.source_id = source_health.source_id
      AND a.family = source_health.family
      AND a.batch = :batch);

-- 断言：归档行数 == 待删除行数（不一致则 ROLLBACK）
DELETE FROM source_health WHERE family = 'registry';

COMMIT;
```

事务结束由单次 `done(commit)` 负责：

- `COMMIT` 成功 → 关闭专用连接；
- `COMMIT` 失败 → 在**同一连接**上 `ROLLBACK`（`context.Background()`，不受 ctx 取消影响）
  再关闭；提交错误与回滚错误一并返回，不静默吞掉；
- 之后外层 `defer` 再调用是空操作（`errTxFinished`），不会对已关闭的连接二次操作。

判定顺序（`candidates`、`marked` 都是事务内读到的值）：

| 标记 | 剩余行 | 行为 |
| --- | --- | --- |
| 无 | 0 | 写标记，`already_done=false` |
| 无 | >0 | 归档 + 删除 + 写标记 |
| 有 | 0 | `already_done=true`，**不**改写 `applied_at` |
| 有 | >0 | 返回错误、拒绝启动；三方数据原样保留 |

约束：

0. 迁移标记写在同库的 `schema_migrations(name, applied_at)`，与归档、删除同一事务；
   `name = b1-archive-legacy-registry`。标记只表示「该批次执行过」。
1. **同一事务**内完成归档与删除，不允许先删后写；
2. 行数校验在 `COMMIT` 之前，任一不符整体回滚；
3. 幂等：同 `batch` 重跑时 `INSERT` 命中 0 行、`DELETE` 命中 0 行，退出码 0；
4. 失败即中止启动迁移并保持旧数据原样，不允许「部分归档」；
5. 不做 `VACUUM`（大库启动期代价不可控），空间回收交给运维。

## 4. un-archive

```sql
INSERT INTO source_health (source_id, family, fails, ok_at, last_at)
SELECT source_id, family, fails, ok_at, last_at
FROM source_health_archive
WHERE batch = :batch
  AND NOT EXISTS (
    SELECT 1 FROM source_health h
    WHERE h.source_id = source_health_archive.source_id
      AND h.family = source_health_archive.family);
```

- **冲突策略：跳过并报告**。目标 `(source_id, family)` 已存在行时不覆盖，
  返回 `restored / skipped` 两个计数，调用方必须把 `skipped>0` 当作需要人工
  核对的信号。
- 不删除归档行：un-archive 是可重复执行的补救动作，不是「撤销归档」的状态机。
- **回滚语义（方案 A，已实施）**：`UnarchiveLegacyRegistry` 在同一事务内恢复数据并
  删除 `schema_migrations` 中的 `b1-archive-legacy-registry` 标记。理由：标记表示
  「已迁移完成」，数据被搬回运行表而标记仍在，就成了既不在归档态、也不会被再次
  处理的悬空状态；下次启动若认为已完成，这批行会永久停在运行表里。
  撤销标记后重跑是安全的：归档表已有同批次行，`dup` 计数会把它算进 `removed`，
  `archived=0 / removed=N` 是正确结果，事务内自校验 `removed == archived + dup` 通过。
- un-archive 之后如果你想停留在「旧数据已恢复」的状态，不要再启动 3.5.3+：
  任何一次启动都会重新执行迁移。需要长期保留就先导出，不要依赖运行表。
- 迁移在启动时自动执行，不需要管理操作触发；`Unarchive` 不暴露到 HTTP，
  只能由持有库文件的运维直接调用（当前形态：一次性 Go 工具/测试入口）。
- 标记存在但运行表又有 legacy 行（迁移后被人为写回）时**拒绝启动**并报出
  `left` 行数：不静默删除人工恢复的数据，也不改写标记。

## 5. 待裁定（实施前必须回答）

| 编号 | 决策 | 选项 | 建议 |
| --- | --- | --- | --- |
| D-B1 | 归档表保留期 | 永久 / 固定 90 天 / 手动清理 | **永久**：行数等于源数（每源 1 行），不构成增长压力 |
| D-B2 | un-archive 冲突 | 跳过+报告 / 覆盖现行行 | **跳过+报告**：运行表数据永远优先于历史副本 |
| D-B3 | 迁移入口 | 启动时自动一次 / 管理 API 手动 | **已裁定：启动时自动一次** |
| D-B4 | archived 源是否归档 | 是 / 否 | **是**：覆盖集合按 family 全量，避免重新启用时复活否决权 |
| D-B5 | un-archive 与迁移标记 | 撤销标记（方案 A）/ 保留标记（方案 B） | **已裁定：方案 A**，同事务撤销，回滚后可安全重跑 |

## 6. 验收判据

| 编号 | 判据 | 方式 |
| --- | --- | --- |
| B-1 | 归档行数与删除行数一致 | 迁移前后 `COUNT(*)` 对比，事务内断言 |
| B-2 | 原子性 | 注入 DELETE 失败，验证归档同时回滚、运行表零变化 |
| B-3 | 幂等 | 同 batch 连续执行两次，第二次 0 写 0 删 |
| B-4 | 候选零变化 | 迁移前后 `RegistryCandidatesRaw` 结果集合完全一致（同一份 DB 快照） |
| B-5 | 其他 family 不受影响 | docker/ghcr/git 行迁移前后逐行一致 |
| B-6 | un-archive 往返 | 归档 → 删除 → un-archive → 行内容逐字段相等 |
| B-7 | un-archive 冲突 | 目标行已存在时不覆盖，`skipped` 计数正确 |
| B-8 | archived 源覆盖 | archived 源的 legacy 行同样被归档 |
| B-9 | 门禁 | gofmt/vet/build/全量 test/race 全绿，无新依赖 |
| B-10 | 迁移标记 | 失败回滚后无标记；成功后有且仅有一条；重跑不改写归档 |

## 7. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 启动迁移拖慢启动 | 大库 `INSERT...SELECT` + `DELETE` 在同一事务 | 只处理 `family='registry'` 的源级行（行数≈源数），非逐请求路径 |
| 并行实例重复执行 | 两个进程同时迁移 | `BEGIN IMMEDIATE` 串行化；同 batch 幂等；多实例前仍需重做 Guard（既有边界） |
| 误 un-archive | 历史失败计数回到运行表 | 仅管理入口可触发；冲突跳过；操作记审计日志 |
| 归档表被误删 | 失去回滚副本 | 与主库同生命周期，纳入备份；不提供自动清理 |
