## 一、口径核对（阻断项结论）

此前基线中的 `6 / 11 / 72` 不是 `docker_cap` 分布，而是 **`ghcr_cap`** 分布：

```sql
SELECT ghcr_cap, COUNT(*) FROM sources WHERE repo_host='' GROUP BY 1;
-- -1: 72, 0: 11, 1: 6
```

同一库上 `docker_cap` 分布为 `34 / 10 / 45`：

```sql
SELECT docker_cap, COUNT(*) FROM sources WHERE repo_host='' GROUP BY 1;
-- -1: 45, 0: 10, 1: 34
```

交叉表验证两者是同一批 89 条，不是两次不同的数据：

| docker_cap | ghcr_cap | 条数 |
| --- | --- | --- |
| -1 | -1 | 45 |
| 0 | 0 | 10 |
| 1 | -1 | 27 |
| 1 | 0 | 1 |
| 1 | 1 | 6 |

结论：**不存在数据漂移，是字段名误标**。旧基线 6/11/72 应更正为 ghcr_cap 分布；
docker_cap 以 34/10/45 为准。

## 二、分类草案（保守口径）

规则不再以 `docker_cap` 单独推断身份：

| 规则 | 条数 | 目标身份 | 证据 |
| --- | --- | --- | --- |
| `docker_cap=1` | 34 | `identified` + `docker.io` | 具备 Docker 能力，空 Host 历史上即 Hub |
| `docker_cap<>1 AND github_cap=1` | 9 | `not_applicable` | `github_cap=1` 是来源类型证据（id 16–24） |
| 其余（`docker_cap` 为 0 或 -1，无 GitHub 证据） | 46 | `unclassified` + `''` | 身份无法确认 |

关键事实：`docker_cap=-1` **不能**作为 Git 源证据。

- 45 条中仅 8 条 `github_cap=1`；
- 36 条 base_url 为 docker/hub/registry 类主机（如 `docker-registry.nmqu.com`、`docker.1panel.live`）；
- `git_cap` 全为 0（未知），不能反证。

因此原先“45 条 Git 源 → not_applicable”的写法作废。

### 语义冻结

- `unclassified`：身份未确认，**不等于** Docker Hub；不进 Hub 专属探测，不进 foreign 候选，不得由默认值或启动期 backfill 自动转正。
- `not_applicable`：必须有来源类型证据（当前仅 `github_cap=1`）；不得仅凭 `docker_cap=-1` 判定。
- `identified`：仅 `docker_cap=1`（Hub 语义）或有明确 foreign Host 的记录。

## 三、46 条保留策略（冻结）

本次对 46 条 `unclassified` 只做一件事：保留原字段，不推断、不归类。

- 不修改 `docker_cap`、`ghcr_cap`、`github_cap`、`git_cap`。
- 不因 `docker_cap=-1` 推断 Git、Hub 或其他来源类型。
- 不因主机名像 Docker Registry 就自动归类。
- 不写入 `docker.io` 或其他猜测 Host。
- 不进入 foreign Registry Probe，不进入 `registry:<host>` 候选集。
- 不影响原有 Docker/GHCR 候选池（老池查询本就不读 `repo_host`）。

`unclassified` 不是永久归档，也不表示来源不可用；只是当前证据不足。
后续转 `identified` 必须走独立、可审计的身份确认流程，并按新 Host 初始化
`registry_host_recovery` / `source_health_scope`，不能只改 `registry_identity_state`。
