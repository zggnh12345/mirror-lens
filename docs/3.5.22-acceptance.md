## 一、需求

慢源场景下（当前源约 100KB/s），单流换源门槛 `switch_min_mbps=8` 过高，候选源够不着，
只能在慢源上耗完整个文件。目标：降门槛让慢源能被换掉，同时不引入"换到更慢源"的误换。

### 3.3 离线反事实分析（生产真实样本，零构建）

方法：只读副本取 `proxy_speed`，按 `RecentProxySpeeds` 语义（每源近 5 条中位数，KB/s），
代入新门槛与旧门槛 8192 对比。**是判定逻辑复算，不是运行时回放。**

真实中位数：
- Source-Alpha(88) docker 783 KB/s；ghcr 3867 KB/s
- Source-Beta(638) docker 6517 KB/s；ghcr 12914 KB/s

结论：
1. 638 docker 6517 < 旧门槛 8192 → 旧规则拒绝；新规则在 C<5.1MB/s 时接受。**核心收益成立。**
2. 88 docker 783 < F=1024 → 新旧均拒绝；降门槛未变成无脑换。
3. 638 docker 在 C=10MB/s 时 T=12288 > 6517 → 拒绝，`C×1.2` 有真实边界体现。
4. `P/1.3` 副作用：两源同时可用时 88 ghcr(3867) 因同伴 638(12914) 被拒（T=9934）；
   638 不可用时 peer=0，88 在 C<3.2MB/s 时会被接受。
   **列为观察项**：相对择优是否过严尚未在真实环境确认，需在后续真实换源中持续观察；
   本轮与 3.5.23 均不为此调整门槛系数。

详见 roadmap §3.11。

### 4.2 受控接管说明（必须披露）

生产配置下 docker 维度没有第二个可换星标源，无法自然触发成功接管。
为验证成功路径，**只在副本**做了三处临时改动（生产未改）：

- 副本配置 `parallel.enabled=false`，隔离单流路径；
- 副本库把 `registry-upstream-a.example.net` 临时标为星标（后续用户已在生产勾选；见 §4.6）；
- 副本库按刚才并行实测的 2.6MB/s 写入 3 条 sparkcr 样本，使候选达到“≥3 样本”门槛。

因此 4.1 的 92MB 接管是**真实源、真实字节、真实 SHA**，但候选资格是受控构造的；
不能表述为“生产配置已能自然换源”。

### 4.4 为什么 95 个源仍选不出候选

> 以下为部署前（2026-11-24 早些时候）的快照。部署后生产星标已增至 3 个、sparkcr 已有 3 条新鲜样本；当前状态见 §4.6。

生产库 `sources` 共 95 个，`preferred=1` 只有 2 个；docker 维度历史样本 ≥3 条的只有 4 个：

| 源 | 历史 docker 样本 | 是否星标 | 换源时可用性 |
|---|---:|---|---|
| Source-Beta(638) | 127 | 是 | 当前源 |
| Source-Alpha(88) | 24 | 是 | 782 KB/s，低于 F=1 MiB/s |
| registry-upstream-a.example.net(54) | 9 | 否 | 9 条均为 14 天前，超过 7 天有效期 → `n=0` |
| registry-upstream-c.example.net(2) | 7 | 否 | 约 0.1 MB/s，低于门槛 |

其余 91 个源没有 docker 单流样本。`RecentProxySpeeds` 同时要求
`ts >= now-7d`、`bytes >= 16MiB`、`ms > 0`，所以“历史上有 9 条”不等于“现在可用”。

为验证 sparkcr 是否真的能当候选，本轮用真实下载补了 3 条新鲜样本：
92,325,002 B / 15.7s、92,378,832 B / 15.7s、92,230,915 B / 17.9s，
约 5.1–5.9 MB/s，`proxy_speed` 中 sparkcr 的新鲜可用样本变为 3 条。

随后尝试自然慢源接管：638 这次跑到约 5 MB/s，未触发判慢；换 88 当当前源时，
88 对该 blob 返回 HTTP 500，请求直接故障转移，没有形成“慢当前源 + 快候选”的稳定窗口。
因此**受控接管成功仍然成立，但生产配置下的自然接管尚未复现**；这不是“源不够多”，
而是“星标 + 新鲜样本 + 当前源确实慢”三个条件同时满足的概率很低。

### 4.8 200-only 候选失败路径（638 Source-Beta）

**结论：有影响，且是客户端可见的下载失败，不是只慢一点；建议在 3.5.23 处理，
不需要紧急回滚。当前生产顺序下短期不会复现，但代码没有硬保证。**

失败链：
1. 638 凭历史约 7.8MB/s 样本通过 `replayCostOK`，并抬高候选组中位速度；
2. 当前源 sparkcr（54，206、约 5MB/s）被 `speed_rejected`；
3. 638（HTTP 200、`range_cap=0`、不支持 Range）被选中；
4. 5s 回放只拿到约 3.7MB，触发“长度不符，丢弃：期望 64396988 实得 3714854”；
5. 客户端下载失败。

根因：
- 候选速度取最近 5 条历史中位数，可能严重偏离当前实际；638 的高样本同时
  让自身通过门槛、把正常 54 挤掉（`internal/gateway/watch.go:400-413`）。
- `replayCostOK` 用 `sent / sBps` 估算 200 回放成本，估算 ≤5s 就放行
  （`watch.go:522-529`、`watch.go:655-669`）；实际 638 约 0.74MB/s，
  10MB 前缀需约 14.5s，5s 内只回放 3.7MB。
- 旧源在回放前已关闭（`internal/gateway/stream.go:716`）；回放超时分支
  只 `savePartial(); finished=true; return`（`stream.go:748-752`），没有回退。
- 并行路径已有 `rangeKnownOff` 排除不支持 Range 的源（`parallel.go:793-799`），
  单流换源路径缺少等价的 `range_cap` 过滤。

当前生产暴露面：
- `sources.range_cap`：54=1，88=0，638=0。
- `sched_order`：docker `[54,88]`，github `[638,88]`；638 不在 docker 候选。
- 88 虽是 200-only，但最近 5 条 docker 样本中位约 0.75MB/s；10MB 前缀回放
  估算约 13s > 5s，会被 `replay_over_budget` 拒绝。
- 因此正常流量短期低风险；但一旦把 638 加进 docker 顺序，或 88 出现高样本、
  实际速度骤降，失败路径仍可触发。
- **操作约束（本轮裁定）**：在 3.5.23 方案 A 落地前，docker 顺序维持 `[54,88]`，
  不要把 638 加入 docker 候选；88/638 保持 `range_cap=0` 现状即可。该约束属于可能影响
  下载业务的生产配置变更，须单独授权，不在 3.5.23 无人值守实施范围内。

建议方案 A（推荐，最小改动）：换源候选只保留 `range_cap=1`，并在计算候选组
中位速度之前过滤；`switchAcceptable` 再拒绝 HTTP 200 作为兜底。200-only 源
仍可做初始源/回退源，只是不参与中途接管。收益是彻底移除“200 回放超时且
无回退”的失败路径，且 200-only 不再污染 `peerMedianBps`；代价是 88/638
不再参与接管，54 仍可，没有 206 候选时继续当前源。
方案 B（保留 200-only 接管）需要把回放移到关闭旧源之前，失败可回退，
改动核心 stream 路径，风险和测试量大，不建议现在做。
不建议只调大 5s 预算：历史样本可能任意偏离，旧源又已关闭，实际更慢时仍会失败。

详见 `docs/evidence/3.5.22/perf-200only-failure.md`。3.5.22 未改代码；
该失败路径不影响 §4.7 的五轮对照结论（对照使用 206 候选）。

## 五、未验证项与风险

- **生产自然接管只做了一次受控实测**：通过临时调整 `sched_order` 和 638 星标，
  在 88（200-only、慢）→54（206、快）方向上成功接管并完整校验 SHA；
  测试条件不是自然状态，且只做 1 次，不能据此宣称长期稳定。
  自然状态下 638 的历史高速度样本仍可能把 54 判为 `speed_rejected`，
  或把 200-only 的 638 选为候选后回放失败；该失败路径见 §4.8。
- **200-only 候选失败路径未修复**：638 作为 200-only 候选时，历史 7.8MB/s 样本
  让 5s 回放预算误判，旧源已关闭且回放超时无回退，客户端下载失败。
  当前生产 docker 顺序不含 638，88 的近期样本也会被回放预算拒绝，短期低风险；
  但这不是代码硬保证。建议 3.5.23 按 §4.8 方案 A 处理，本轮不改代码。
- **5 次冷缓存性能对照已完成**：S1 中位 615.104s → 45.048s（-92.68%），
  S2 双方 0 次误换，S3 双方 5/5 接管，30/30 SHA 一致；详见 §4.7。
  该结果是本机限速假源的工程验收，5 次样本不宣称公网长期可靠性。
- **`C×1.2` 真实抖动**：只有一次真实接管（c_bps=339,968、threshold=1,451,538），
  样本不足，未证明长期稳定性。
- **206 chunked/无 CL 的 Body 路径**：单测覆盖；真实 sparkcr 本次为有 CL 的 206，
  未遇到 chunked 尾部 EOF 场景。
- **GitHub 代码未推送**：本地 `feat/3.5.18` 代码提交到 `c47c12a`，远端仍为 `039dd15`；
  生产已用本地构建镜像部署，未推送到 GHCR/GitHub。本轮按用户要求只提交文档。

## 六、结论

判定逻辑、本地门禁、真实下载/缓存/SHA、受控条件下的真实 206 接管，
以及冻结判据要求的 5 次冷缓存对照均通过；生产已部署 3.5.22，
配置自动迁移、外部入口、真实 manifest 回源与一次受控换源实测均已通过。
按 §12.9 冻结判据，本轮隔离环境对照达到性能阈值：
S1 中位降幅 92.68%，S2 5/5 不误换，S3 5/5 接管，SHA 30/30 一致。
但**自然状态下的长期换源行为未验证**，5 次样本不能宣称公网长期可靠性；
**200-only 候选失败路径未在 3.5.22 修复**，属于已知客户端失败风险，
建议 3.5.23 按 §4.8 方案 A 处理。代码已在本地 `feat/3.5.18` 提交并部署，
GitHub 代码尚未推送；本轮只提交文档。
