## 2. 结论摘要

| 级别 | 数量 | 摘要 |

| **P0** | **2** | ① 跨 Host 重定向后重新认证，官方 Basic/Token 可被送到任意 HTTPS Host；② 私有认证响应不设 `no-store`，反而把上游 `public, max-age=31536000, immutable` 透传给下游共享缓存/CDN |

## 4. Findings（按严重级别）

### P0-1 跨 Host 重定向后重新认证，官方凭据被发往任意 HTTPS Host

- **位置**：`internal/gateway/registryprivate.go:157-170`（`RoundTrip` 无 host 绑定）、`:540-571`（`directBasic` 无 host 校验）、`internal/gateway/gateway.go:229-244`（`CheckRedirect` 只删 `Authorization`）
- **问题**：`registryAuthTransport.RoundTrip` 决定"用哪份凭据"时只看 context 里的 `PolicySnapshot`，**从不校验 `req.URL.Host` 是否等于 `policy.LogicalHost`**。`http.Client` 跟随 3xx 时会用新 URL 再次调用同一个 `RoundTrip`，而 context（策略、身份）原样传递。`CheckRedirect` 只是把 `Authorization` 删掉，随后 transport 又对新 Host 重新执行"匿名 → 401 → 用凭据"流程。于是：

  - 直接 Basic：上游返回 307 到 `evil.example`，`evil.example` 回 `WWW-Authenticate: Basic`，`directBasic` 把 `robot:s3cret` 以 `SetBasicAuth` 发出去（`:560`）。`AuthorizeCredential` 校验的是"快照 Host == 策略 Host == 身份 Host"，三者都还是原 Host，所以门禁全部通过。
  - Bearer：`evil.example` 只要把 Realm 写成 `https://<官方host>/token`（`policy.Allows` 只校验 Realm，不校验目标），网关就会去官方端点换一个真 Token，再把 `Bearer <token>` 发给 `evil.example`（`:310-315`）。

  这直接违反 1.6 的 C.3"跨 Host 不重新认证"、不变量 3"`Authorization` 不跨 Host"、S07/S08。

- **复现**（真实输出，`ml8-probe/internal/gateway/probe_redirect_reauth_test.go`，用与 `gateway.New` 完全一致的 `CheckRedirect` 构造 client）：

  ```
  $ go test ./internal/gateway/ -run TestProbeCrossHostRedirectReauth -v
  === RUN   TestProbeCrossHostRedirectReauth
      probe_redirect_reauth_test.go:111: a.example 收到 Authorization=""
      probe_redirect_reauth_test.go:112: b.example 收到 Authorization="Basic cm9ib3Q6czNjcmV0"
      probe_redirect_reauth_test.go:114: 跨 Host 重定向后，凭据被重新发送到 b.example: "Basic cm9ib3Q6czNjcmV0"
  --- FAIL
  ```

  `cm9ib3Q6czNjcmV0` 即 `robot:s3cret`。攻击前提很低：`quay.io`/`gcr.io` 或任何中间代理返回一个 307，或客户端请求的 tag 被上游重定向到外部存储（Blob 的 CDN 重定向本来就是跨 Host 的）。

- **修复建议**：
  1. `RoundTrip` 入口加硬绑定：`if !strings.EqualFold(req.URL.Host, policy.LogicalHost) || !strings.EqualFold(req.URL.Scheme, policy.Scheme) { return t.base.RoundTrip(req) }`（不认证、直接透传）；`directBasic` 内同样再校验一次（纵深防御）。
  2. 更彻底：`CheckRedirect` 里对 `StripAuth` 的跳转在 context 上打 `noReauth` 标记，transport 见到标记只发匿名请求。
  3. Registry 侧建议直接拒绝跨 Host 跳转（`RedirectPolicy` 对 `RedirectRegistry` 返回错误），只有 `RedirectCDN` 允许跨 Host 且强制无认证。这样能同时消灭 Bearer 变体。
  4. 补测试：跨 Host 307 + 目标返回 Basic/Bearer Challenge，断言目标收不到任何 `Authorization`。

### P0-2 私有认证响应不设 `no-store`，把上游 `public, immutable` 透传给下游共享缓存

- **位置**：`internal/gateway/stream.go:1076-1101`（`passThrough` 复制上游 `Cache-Control`；`plan.NoStore` 只用于打 `X-ML-Cache: BYPASS` 标签）；`internal/gateway/registry.go:190-195`
- **问题**：私有 Host 的请求确实在缓存查询前就分流（`registry.go:131,255`），网关自己的 `cache_entries` 也不会写入（`privateauth_test.go:221` 已验证）。但 `passThrough` 把上游的 `Cache-Control` **原样**写给客户端，且没有任何 `no-store`。真实 registry 的 blob/manifest 响应通常带 `Cache-Control: public, max-age=31536000, immutable`（代码自己在 `cdn.go:38-45` 就是这么假设的）。结果是：**网关一边"绕过自己的缓存"，一边明确告诉所有下游（CDN、反代、浏览器、公司级代理）"这是公共内容，可以缓存一年"**。本项目还主动输出 `Cache-Tag`/`Surrogate-Key`（`cdn.go:73-80`），等于给 CDN 打了可清理标签，私有内容会被正常写入边缘缓存，之后匿名客户端可直接命中。

  这违反不变量 3（"私有/认证响应不得进入共享缓存"）、S13 的实质语义，以及 B.2 的"不能只在认证成功后设置 no-store"（现在的实现连认证成功后都没设）。

- **复现**（真实输出，`ml8-probe/internal/gateway/probe_private_cc_test.go`，上游故意返回真实 registry 的 blob 头）：

  ```
  $ go test ./internal/gateway/ -run TestProbePrivateResponseCacheControl -v
  === RUN   TestProbePrivateResponseCacheControl
      probe_private_cc_test.go:76: status=200 X-ML-Cache="BYPASS" Cache-Control="public, max-age=31536000, immutable"
      probe_private_cc_test.go:78: 私有认证响应未标 no-store，实际 Cache-Control="public, max-age=31536000, immutable"
  --- FAIL
  ```

- **修复建议**：
  1. `passThrough` 在 `plan.NoStore` 为真时：`w.Header().Set("Cache-Control", "no-store")`，并**删除**从上游复制的 `Cache-Control`（现在 `copyHeader` 会把它带过来），同时补 `Vary: Authorization`。
  2. 对私有 Host 的所有响应（含 401/403）统一走一个 `privateNoStore(h)` helper，避免以后新增分支漏掉。
  3. 补测试：断言私有响应 `Cache-Control` 含 `no-store` 且不含 `public`；匿名 Host 的缓存头不变（P05 回归）。

### P1-1 凭据变更/删除不清负缓存与 Token，改对密码后仍 401 最长 5 分钟

- **位置**：`internal/gateway/registryprivate.go:126-138`（`clearHost`）、`internal/gateway/registryauth.go:162-186`（`invalidateHost`、`clear`）——**三者全仓无生产调用点**；`registryprivate.go:236-241` 是唯一的负缓存读点
- **问题**：1.6 B.5 明确要求"凭据变更立即清除"负缓存，A.2 要求"凭据变更的失效范围只限该 Host：清该 Host 的 Token、负缓存和认证健康"。实现里这些函数写好了但没接线：`store` 层没有任何回调通知 `gateway`，`api/credentials.go` 写完凭据后也不做失效。负缓存 key 是 `host|mode`，**不含 gen**，所以 gen+1 不会自然绕过它。

  实际后果：管理员把密码改对（gen 1→2），请求仍然 401 `auth_backoff`，直到 30s（连续失败后 5 分钟）退避结束。运维会以为"新密码也没用"，从而反复改凭据——这正是 S24 想避免的账号锁定路径的反面。

- **复现**（真实输出，`ml8-probe/internal/gateway/probe_negcache_test.go`）：

  ```
  $ go test ./internal/gateway/ -run TestProbeNegCacheNotCleared -v
  === RUN   TestProbeNegCacheNotClearedOnCredentialChange
      probe_negcache_test.go:87: 第一次(错密码): status=401 X-ML-Auth-Error="auth_failed" upstreamHits=2
      probe_negcache_test.go:98: 第二次(已改对): status=401 X-ML-Auth-Error="auth_backoff" upstreamHits=3
      probe_negcache_test.go:102: 凭据已修正但仍被负缓存拦截
  --- FAIL
  ```

- **修复建议**：在 `main.go` 装配处给 `secret.Store` 注册一个 `OnCredentialChanged(host, gen)` 回调，由 `gateway` 实现：`privNeg.clearHost(host)` + `tokens.invalidateHost(host)`；`PutCredential`/`DeleteCredential` 成功（含 Pending 提交成功）后调用。负缓存 key 建议也带上 gen，作为第二道保险。

### P1-2 `Pending` 状态没有后台重试，状态机不能自愈

- **位置**：`internal/secret/credstate.go:238-242`（注释写"后台 ReconcileHost 补写"）、`:428-489`；全仓 `ReconcileHost` 调用点只有 `internal/api/credentials.go:108`
- **问题**：1.6 A.2 状态表把 `Pending` 的恢复方式定义为"后台 `ReconcileHost` 重试；成功后转 Ready/Absent"，A.4 再要求"`Pending` 状态由后台重试处理；重试只针对该 Host"。实现里没有任何后台 goroutine 或定时任务：`Pending` 只会停留在 `Pending`，直到管理员打开面板点"对账"。S21 的失败判定是"必须重启或永久 pending"，当前实现属于后者（只是把"重启"换成了"人工点击"）。

  另外 `PutCredential` 在 DB 失败时返回 `Pending` + error，API 层把它映射成 **500**（`credentials.go:206-208`），"已写入文件、等对账"这个语义对调用方不可见（202 分支 `:210-213` 不可达，见 P3-1）。

- **修复建议**：加一个低频（如 30s）的 `PendingReconciler`，扫描 `HostCredStates` 中 digest 与文件不一致的 Host，逐个 `ReconcileHost`；限流 + 失败退避 + 写 `credential_reconcile` 审计。API 对 `State==Pending` 返回 202（先判 state，再判 err）。

### P1-3 epoch 物理清理未接线，且旧 epoch 的 blob 前缀永远清不掉

- **位置**：`internal/store/epoch.go:157-168`（`CacheKeyPrefixesBefore`）、`:171-176`（`RegistryCacheKeyPrefix` 只返回 `docker:m:<e>:`）、`:183-208`（`CacheEpochSweep`，**无调用方**）
- **问题**：两个独立缺陷叠加。
  1. `CacheEpochSweep` 全仓无调用点，janitor 也没接。1.6 D-15-12 要求"物理清理由 Gateway 缓存管理模块负责，限速、进度、失败重试、审计"——一项都没有。
  2. `CacheKeyPrefixesBefore(epoch)` 对 `1..epoch-1` 只展开 `docker:m:<e>:`（manifest），**漏了 `docker:b:<e>:`（blob）**。即使接上 janitor，旧 epoch 的 blob 索引也永远删不掉，对应文件永远不会变成孤儿，磁盘永远不回收。

- **复现**（真实输出，`ml8-probe/internal/store/probe_sweep_test.go`）：

  ```
  $ go test ./internal/store/ -run TestProbeSweepCoversBlob -v
      probe_sweep_test.go:25: swept=3
      probe_sweep_test.go:28: after sweep: docker:m:1:a/x:1             present=false
      probe_sweep_test.go:28: after sweep: docker:b:1:sha256:aaa        present=true   <-- 未清理
      probe_sweep_test.go:28: after sweep: docker:manifest:old/x:1      present=false
      probe_sweep_test.go:28: after sweep: docker:blob:sha256:bbb       present=false
      probe_sweep_test.go:28: after sweep: docker:m:2:a/x:1             present=true
      probe_sweep_test.go:28: after sweep: docker:b:2:sha256:ccc        present=true
      probe_sweep_test.go:31: 旧 epoch 的 blob 键没有被清理
  --- FAIL
  ```

  注意现有测试 `credwrite_test.go:172` 只放了 `docker:m:1:` 的旧键，所以这个缺口没被发现。

- **修复建议**：`RegistryCacheKeyPrefix` 返回两个前缀（`docker:m:<e>:`、`docker:b:<e>:`）或改签名返回切片；把 `CacheEpochSweep` 接进 janitor 循环（每轮限量、失败重试、进度落 `meta`、完成后写审计），并把 `CacheEpochStats` 暴露给面板。

### P1-4 新增私有认证 Host 不递增 epoch；epoch 切换无审计

- **位置**：`main.go:326-338`（只在首次启动 `InitCacheEpoch` 0→1）、`:376-390`（`EnsureCacheEpoch(1)` 只保底）；`epoch.go:37-41 BumpCacheEpoch`、`:253-263 AuditCacheEpoch`、`:216 CacheEpochStats` **均无调用方**
- **问题**：1.6 B.3 要求"每次新增私有认证 Host 时递增一次（全局失效，接受一次性成本）"，D-15-12/D-17 要求 epoch 切换有审计。实现只在 3.5.15 首次启动切一次，之后 `private_auth_hosts` 从 `[quay.io]` 扩到 `[quay.io, gcr.io]` 不会再切。`BumpCacheEpoch`/`AuditCacheEpoch` 是死代码，`CacheEpochStats` 也没有面板入口，运维无法确认"旧 epoch 已不可达"。

  影响相对可控（私有 Host 本来就不读缓存，所以不会读到自己的旧条目），但"新启用私有认证的 Host 在启用前被匿名缓存过的内容"这条论证链在文档里成立、在代码里没有对应动作；同时 D-15-12 要求的"清理失败阻断回滚/重开"没有审计依据。

- **修复建议**：启动时把 `private_auth_hosts` 的集合指纹（排序后 hash）存进 `meta`，与上次不同则 `BumpCacheEpoch` + `AuditCacheEpoch`；面板展示 `CacheEpochStats`。

### P1-5 `secret.key` 缺失时自动生成新密钥，违反 R04

- **位置**：`main.go:110-117`（`mustSecretKey`）→ `internal/secret`（`LoadOrCreateKey`，文件不存在时 `O_EXCL` 新建随机密钥）
- **问题**：1.6 R04 与 D.3 都明确写"`secret.key` 缺失时 fail closed，不自动生成新密钥"。当前实现：备份恢复只还原了 `mirror-lens.db` + `registry_creds.enc` 而漏了 `secret.key` 时，进程照常启动，**静默生成一把新钥匙**，随后每条凭据记录 AEAD 失败 → 所有 Host `Quarantined`（`creds.go:321-325`）。表面上"fail closed"了，但：
  - 掩盖了备份单元不完整的运维错误（R06 的核心诉求）；
  - 新密钥会写到 `secret.key` 路径，覆盖"该位置本该有的正确密钥"这一事实，事后排查更容易误判；
  - 面板 Access Token 也同时失效（同一把密钥）。

- **修复建议**：`mustSecretKey` 在 `registry_creds.enc` 已存在而 `secret.key` 不存在时直接 `log.Fatalf`，提示"备份单元缺失，请恢复 secret.key"；只有在两者都不存在（全新部署）时才允许生成。

### P2-1 `VerifyCredential` 绕过 `private_auth_enabled` / `RequireToken` / allowlist

- **位置**：`registryprivate.go:324-337`（`verifyCtxKey` 分支只跳过 allowlist 与 `RequireToken`）、`:471-514`
- **问题**：`verify` 分支跳过 `hostEnabled`（含 `Enabled`）和 `RequireToken`，只保留身份/gen 门禁。于是：`private_auth_enabled=false`（UI 明确写着"凭据可保存但不生效，回源仍为匿名"）时，管理员点"验证"仍会让网关带着存储的凭据真实访问 `quay.io`/`gcr.io`；`POST /api/credentials/{host}/verify` 也不校验 `CredentialHostAllowed`，对 3.5.14 遗留的非 allowlist 记录同样生效。
- **修复建议**：`Enabled=false` 时 verify 直接返回 `verify_disabled`；verify 入口复用 `credentialWriteHost` 的 allowlist 校验；把"跳过 allowlist"收窄成"跳过 `Hosts` 成员检查但保留 `Enabled`"。

### P2-2 重定向的 `RecheckPolicy` 从未被消费，`RedirectCDN` 无生产调用点

- **位置**：`v2auth/identity.go:211-212, 264`（产出 `RecheckPolicy`）、`gateway.go:229-244`（只读 `StripAuth`）；`RedirectCDN` 仅出现在 `identity.go` 与 `identity_test.go`
- **问题**：1.6 C.3 要求 Registry 重定向"同 Host 也重新校验策略"。`RedirectDecision.RecheckPolicy` 被算出来但没人用；Blob CDN 重定向实际走的是 `RedirectRegistry` 规则（`gateway.go:231` 固定传 `RedirectRegistry`），`RedirectCDN` 的"只允许 GET/HEAD"约束在生产路径上不生效（当前 Blob 只有 GET/HEAD，所以暂时无实际危害）。
- **修复建议**：`CheckRedirect` 里对 `RecheckPolicy` 重新 `policy.Allows(r.URL)`（至少校验 scheme/host 属于当前策略）；按请求类型选择 `RedirectKind`（Blob 走 CDN 规则），把 `RedirectKind` 放进 context 而不是在 `CheckRedirect` 里写死。

### P2-3 凭据侧错误统一映射为 503 `auth_stale`

- **位置**：`registryprivate.go:207-211`
- **问题**：`credential()` 返回的任何错误（`ErrNotReconciled`、`ErrCredentialPending`、记录级 `ErrCorrupt`、DB 错误、`ErrCredentialUnavailable`）都被写成 `503 auth_stale`。1.6 B.5 要求区分 `auth_stale` / `auth_unavailable` / `auth_realm_denied`，运维无法从错误码区分"凭据正在变更"与"凭据文件损坏"。
- **修复建议**：按 `errors.Is` 映射：`ErrCredentialPending`→`auth_stale`，`ErrNotReconciled`/`ErrCorrupt`→`auth_unavailable`，DB 错误→`auth_unavailable`，`ErrCredentialUnavailable`→`auth_unavailable`。

### P2-4 候选探测快照并非"空"，删除标记被当成"有凭据"

- **位置**：`internal/runner/hostprobe.go:434-458`（`HasCredential: digest != ""`）
- **问题**：1.6 C.2 要求候选 Source 探测"`CredentialSnapshot` 为空"。现在 `Credentials` 是空的（不会发凭据，`creds_consistency_test.go:534` 已证明），但 `HasCredential` 由 `digest != ""` 推出：**显式删除后的 `emptyDigest(host)` 是非空 64 位十六进制**，于是"已删除凭据"的 Host 在快照里表现为 `HasCredential=true` 且凭据为空。当前只影响 `CommitHostProbe` 的 CAS 分支（`store/commit.go:175`，只在缺行时用到），不会误发凭据，但语义错误，且让"快照为空"这条验收项无法字面成立。
- **修复建议**：`HasCredential` 恒为 `false`（探测全程匿名），`Digest`/`Gen` 只作为 CAS 元数据；或显式 `digest != "" && digest != emptyDigest(host)` 并导出 `emptyDigest` 的判定函数。

### P2-5 审计双写：事务内那条没有操作者/IP

- **位置**：`credwrite.go:101-118`（`CredWrite.Audit` 未带 `User`/`IP`）、`api/credentials.go:197-198`（事务外的 `auditAs` 才带 `User`/`IP`）
- **问题**：1.6 A.3 要求审计"记录 host、mode、gen、结果、操作者/IP"，D-15-9 要求"与 gen 更新同事务或同步写"。实现满足"同事务"，但事务内那条的 `user`/`ip` 为空；带操作者的那条走 `s.st.Audit`（另一条路径）。两者不一致时（例如进程在两条之间崩溃），耐久的那条没有操作者。
- **修复建议**：把 `User`/`IP` 从 API 层传进 `CredWrite.Audit`，事务内一次写全；事务外那条改为只记"结果"或直接去掉，避免重复行。

## 5. 与 1.6 的偏差与建议

### 5.1 与"已知设计取舍"的裁定

| 1. 文件与 DB 无法原子提交：先写文件再 CAS，DB 失败 ⇒ Pending | **不冲突**（1.6 A.2 第 4/5/7 条、不变量 7 明确接受"不承诺原子提交，只承诺可检测 Pending"） | 机制成立（`credstate.go:222-243`），但"后台重试"缺失（P1-2），所以 1.6 承诺的"可恢复"只兑现了一半 |
| 2. epoch 只在首次启动递增一次 | **冲突**（1.6 B.3："每次新增私有认证 Host 时递增一次"；D-15-12） | 见 P1-4。另：1.6 要求"epoch 切换失败不得以旧 epoch 继续服务私有认证"，`main.go:380-386` 是 `log.Fatalf`，这点是对的 |
| 3. 候选探测完全匿名，旧一致性测试被重写 | **不冲突**，且比 1.6 更严（1.6 C.2 原文就是"不读取、不传递官方凭据"） | 方向正确；`creds_consistency_test.go:534` 保留了"候选不得携带任何凭据"的断言，没有削弱。唯一瑕疵是快照仍带 `HasCredential`（P2-4） |
| 4. VerifyCredential 复用同一 transport，跳过 allowlist 但不放宽身份/gen | **部分冲突**（1.6 B.1 的前置条件里 allowlist 是"允许使用凭据"的必要条件，没有 verify 例外） | 复用同一 transport 是对的（避免第二条认证实现）；但连 `Enabled`/`RequireToken` 一起跳过超出授权范围（P2-1）。建议只跳过 `Hosts` 成员检查，保留 `Enabled` 与 allowlist 校验 |

### 5.2 与 1.6 的其它偏差

1. **"同 Host 也重新校验策略"未实现**（P2-2）——1.6 C.3 表格逐字要求。
2. **`RedirectCDN` 规则未接入**（P2-2）——1.6 C.3 表格第三行。
3. **"物理清理由缓存管理模块负责，限速、进度、重试、审计"未实现**（P1-3）——D-15-12、B.3、S14。
4. **`secret.key` 缺失自动生成**（P1-5）——R04、D.3 逐字禁止。
5. **`Pending` 无后台重试**（P1-2）——A.2 状态表、A.4。
6. **认证执行前"重新解析一次"未实现**（`registryprivate.go:207-246`）：现在是"快照 gen（实时读）!= 策略 gen（plan 时读）→ 直接 503"。方向是 fail closed，比 1.6 更保守，不会造成安全问题，但与 A.2"重解析一次，仍不一致才 fail closed"不同；`auth_stale` 会更容易出现（每次凭据变更后，在途请求全部 503 而不是重试一次）。建议至少把"重解析一次"补上，减少凭据轮换时的 503 毛刺。
7. **`AuthorizeCredential` 只在最终执行处校验一次**（设计要求"凭据读取处和最终认证执行处各校验一次"）。当前 `credential()` 读、调用方紧接着校验，语义上等价，但没有"两处"的结构性保证。
8. **性能验收 P01–P05 全部缺失**（P2-6）——D.4 发布门禁。

### 5.3 发布建议

**不建议在修复 P0-1、P0-2 之前开启 `registry.private_auth_enabled`。** 这两条都不是"实现不完整"，而是"实现完成后仍然会泄密"：

- P0-1 让任何能影响上游重定向的一方（第三方镜像、被劫持的 CDN、返回 307 的 registry）拿到 Host 级凭据；Host 级 blast radius 在 1.6 D-15-8 里已经被承认为"该凭据可访问的所有私有仓库"。
- P0-2 让私有内容进入任何下游共享缓存，与"共享缓存 = 公共资源"的不变量直接冲突；本项目还主动输出 CDN 缓存标签，放大了这个风险。

修复顺序建议：

1. **P0-1**（host 绑定 + 拒绝跨 Host 重认证）→ 补 S07/S08 测试；
2. **P0-2**（`no-store` + 删上游缓存头）→ 补 S13 测试；
3. **P1-1 / P1-2**（失效钩子 + 后台对账）→ 这两条决定"运维能不能用"；
4. **P1-3 / P1-4**（sweep 接线 + 前缀修正 + bump 审计）→ 决定 S14 能否通过；
5. **P1-5**（密钥缺失 fail closed）→ 决定 R04/R06 能否通过；
6. P2 批量清理，最后补 P01–P05 实测报告。

在此之前，3.5.15 的可宣称状态应保持：**"机制通过受控 fixture（`SIMULATED_PASS`）；真实私有 Host 未验证（`BLOCKED_EXTERNAL_SOURCE`）；不得宣称私有 Registry 已支持"**（与 1.6 D-15-10/D.4 一致）。
