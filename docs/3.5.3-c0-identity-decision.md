# 3.5.3 Phase C · C0 缓存身份决策材料

> 状态：**只做决策，不写实现**。C0 三项未裁定前，缓存身份模型不进入编码。
> 事实依据均来自当前 HEAD（`feat/3.5.3-phase-b`），行号以本文件写作时的代码为准。

## 0. 现状（先看事实，再看选项）

| 事实 | 证据 |
| --- | --- |
| manifest 缓存键只含 origin/仓库/引用/Accept，**不含任何客户端身份** | `internal/adapter/registryadapter/registry.go:234` |
| blob 键是 `docker:blob:<digest>`，按内容寻址、跨仓库共享 | `internal/adapter/registryadapter/registry.go:261` |
| 只有 `plan.NoStore=true` 才绕过缓存直通，registry 适配器从不设置它 | `internal/gateway/gateway.go:358`；`NoStore` 仅声明于 `internal/adapter/adapter.go:79` |
| 入口把客户端 `Authorization` 只当作**网关 Access Token**，验过后立即删除 | `internal/gateway/gateway.go:1271-1276` |
| 上游 token 申请**不带任何凭据**（匿名 GET realm），私有仓库只会把 401 原样返回 | `internal/gateway/registryauth.go:62-100`、`174` |

推论：**今天不存在「私有内容被跨用户命中」的实际泄漏路径**，因为私有仓库根本取不到内容。
Phase C 的风险只有在引入「上游凭据」之后才成立——这正是必须先做 C0、不能先写 HMAC 的原因。

## 1. Q1：缓存身份模型采用什么方案？

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A. 按客户端身份分键 | 身份指纹（HMAC）拼进 manifest/blob 键，blob 也分租户目录 | 多租户下真正隔离 | 缓存命中率按用户数骤降；blob 无法跨仓库复用；需要密钥管理；磁盘占用成倍 |
| B. 带凭据一律直通 | 客户端携带 registry 凭据时 `NoStore`，只缓存匿名内容 | 实现最小，语义最保守，与现有 `NoStore` 路径一致 | 私有镜像完全没有加速，只有代理/审计价值 |
| C. 单租户信任域 | 网关整体视为一个租户；缓存共享，但入口必须持有 Access Token | 零新增组件，命中率最高，符合单机/单团队部署 | 任何持有 Access Token 的人可读所有已缓存内容；不能对外多租户开放 |

**建议：C，并把「单租户」写进发布说明与配置校验。**
理由：这是家用/单团队自建镜像加速的主流形态（registry 的 pull-through cache 也是
单实例单身份）；A 的代价（命中率、密钥、磁盘）与当前需求不匹配，B 会让 Phase C
变成「加一个永远不命中的分支」，收益最低。

如果以后要开放给多人/多团队，再上 A，而不是现在预防性实现。

## 2. Q2：入口是否解析客户端 Registry 认证？

| 选项 | 含义 | 影响 |
| --- | --- | --- |
| 不解析（维持现状） | 客户端 `Authorization` 只用于网关鉴权，验后删除；上游一律匿名 | 私有仓库 401 直通；无泄漏面；改动为零 |
| 解析但不存储 | 识别 `Bearer`/`Basic` 形态，用于决定直通/缓存，不落库 | 可实现方案 B；需要区分「网关 token」与「registry token」两种 Bearer |
| 解析并用于上游鉴权 | 把客户端凭据转发给上游换取 token | 凭据进入进程内存与上游日志，泄漏面最大，不推荐在单租户下做 |

**建议：不解析。** 与 Q1 的 C 一致：既然只有一个信任域，就没有「按客户端身份分流」
的对象；强行解析只会制造两套 Bearer 语义。若未来选 A/B，再引入解析，并且必须
先解决「网关 token 与 registry token 同形」的判别问题。

## 3. Q3：HMAC 的密钥来源、身份边界与隔离策略

若 Q1=C、Q2=不解析，则**本阶段不引入 HMAC**，Q3 的答案是「不适用」。这是推荐路径。

若将来选 A，需先钉死三项，缺一不可：

1. **密钥来源**：从既有 settings secret 用 HKDF 派生（不新增配置项、不落明文），
   轮换时旧缓存整体失效，必须接受一次全量回源。
2. **身份边界**：以「客户端 Access Token 的哈希」为身份（不存原文），不按源、
   不按 IP；同一 token 多设备视为同一身份。
3. **隔离策略**：manifest 键加身份前缀；blob 因内容寻址无法安全共享，必须
   落到 `blobs/<identity>/<digest>` 独立目录，否则 digest 命中即跨租户泄漏。

**建议：不在 3.5.3 实现 HMAC。** 引入密钥派生与 blob 目录分裂，是为了解决一个
当前部署形态下不存在的问题；等 Q1 真的改成多租户再做。

裁定后 Phase C 的落地形态只有一件事：在配置校验与发布说明里声明单租户边界，

上游凭据，共享缓存就会真的把私有内容暴露给所有 Access Token 持有者。

## 5. 若选 C 之后的实施清单（供评估，不含代码）

1. 目前代码里**没有**上游 registry 凭据配置项（`grep RegistryUser/RegistryPass`
   无结果），所以这一条是前置保护：将来若新增该配置，启动校验必须直接拒绝，
   或要求显式 `allow_shared_private_cache=true` 才能启动（默认拒绝）。
2. 发布说明增加「单租户信任域」章节，明确 Access Token 等价于缓存读取权。
3. 面板提示：已缓存内容对全部令牌持有者可见。
4. 不加 HMAC、不改缓存键、不拆 blob 目录——零迁移。

以上 1-4 的工作量约一个提交，风险集中在「拒绝启动」的兼容性：已有部署若配了
上游凭据会被拦下，需要在升级说明里提前写清。

## 6. 裁定（2026-11-12，已归档）

- C0-1 = C（单租户共享缓存）、C0-2 = 不解析客户端 registry 认证、C0-3 = 不引入 HMAC。
- 信任边界：**持有网关 Access Token 的任意用户属于同一缓存信任域**，可读取该域内
  共享的全部缓存内容。发布说明必须写明这一点。
- 不写启动校验代码：当前没有上游 registry 凭据配置项，写一条检查不存在的配置
  只会制造虚假安全感。将来新增 `registry_user`/`registry_pass` 一类配置时，
  默认拒绝启动或要求显式 `allow_shared_private_cache=true`，随该功能一起提交。
- 不借 C0 扩大范围：不改缓存键、不拆 blob 目录、不做多租户隔离。
