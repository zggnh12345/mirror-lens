## 公共 Source 真实进程

使用实际二进制，Source 为 `https://gcr.procoding.cn`，Host 为 `gcr.io`：

- 探活提交 `registry_cap=1`、`registry_path_mode=native`、`registry_host_recovery.state=ok`
- Source 状态 `usable`
- 请求 `gcr.io/distroless/static` 的 Blob `sha256:2cc7ee...f79fa8`
- HTTP 200，124525 字节
- 响应正文 SHA-256 与请求 Digest 完全一致
- `X-ML-Source: procoding-gcr`
- 第一次 `X-ML-Cache: MISS`
- 第二次同 Digest 请求 `X-ML-Cache: HIT`

这证明至少一个公共第三方 Source 能通过 Mirror Lens 的探活、候选、Blob 和缓存链路，不是只验证了 `/v2/`。

`registry-upstream-b.example.net` 也完成了实际二进制 Source 验收：

- 探活提交 `registry_cap=1`、`registry_path_mode=host_prefix`
- Source 状态 `usable`
- 请求 gcr.io/distroless/static 的 Blob `sha256:d6b1...536f28`
- HTTP 200，32093 字节
- 正文 SHA-256 与请求 Digest 一致
- `X-ML-Source: gp-suwa`
- 第一次 `X-ML-Cache: MISS`
- 第二次 `X-ML-Cache: HIT`

`gp.suwa` 只覆盖 gcr.io、registry.k8s.io、quay.io，不覆盖其余五个 Host；它适合作为公共源，但不是天然的故障源。

## 回退实测状态

- 受控 Source 401 → 官方 `gcr.io` 200：已完成（F3）。
- 官方 401 挑战透传：已完成。
- 公共 Source 的 404 → 官方回退：已完成（gcr.io）：`gcr.linkos.org` 的 kaniko-project/executor Blob 返回 404，Gateway 日志出现 `源未命中，换下一个 ... source=linkos-gcr status=404`，随后官方返回 200、16855189 字节、Digest 一致，缓存 MISS → HIT。
- 故障边 + 公共上游：registry.k8s.io、quay.io、mcr.microsoft.com 已用 Source 故障边注入 Blob 404，Gateway 分别回退官方并返回 200、Digest 一致、缓存 MISS；日志中的 `source=edge-k8s/edge-quay/edge-mcr status=404` 为实际回退证据。
- 其余四项：`registry.gitlab.com`、`public.ecr.aws`、`us-docker.pkg.dev`、`cgr.dev` 未完成。GitLab/CGR 的官方匿名拉取返回 401；ECR 的 `m.daocloud.io` Source 因 Realm 白名单失败；PKG 没有同 Host 公共源。不能用关闭 Realm 校验或伪造 200 来补齐。
- `registry-upstream-b.example.net` 不适合作为故障源：Manifest/Blob 均正常；把 BaseURL 改成无效域名后探活会清除候选，不能算回退通过。

## 覆盖结论

1. `gcr.io`、`registry.k8s.io`、`quay.io`、`mcr.microsoft.com` 有多个公共提供方可选。
2. `registry.gitlab.com`、`public.ecr.aws` 目前只有 DaoCloud path 覆盖。
3. `us-docker.pkg.dev`、`cgr.dev` 没有找到可用公共源，保持“未覆盖”。
4. 公共源普遍使用自己的 Realm；`m.daocloud.io` 和 `gcr.mirrors.wusiyu.me` 作为 Source 探活时均因 Realm 不在官方 Host 白名单而失败。该问题留给 3.5.10 的 Source 自有 Realm 设计，不通过关闭校验绕过。
