## 门禁 1：Store 事务原子性

### 结论：**通过**，但有三条实施约束

现有写事务的统一形态（`CommitHostProbe`、`recovery_seed`、`migrate_recovery`、`Run` 的 Ready 检查）：

```go
conn, _ := s.db.Conn(ctx); defer conn.Close()
conn.ExecContext(ctx, "BEGIN IMMEDIATE")
committed := false
defer func(){ if !committed { conn.ExecContext(context.Background(), "ROLLBACK") } }()
... // 全部写入用同一个 conn
conn.ExecContext(ctx, "COMMIT"); committed = true
```

证据：

- `store.go:188`：DSN 带 `busy_timeout(5000)`、`journal_mode(WAL)`、`foreign_keys(1)`、`synchronous(NORMAL)`。
- `store.go:192`：`SetMaxOpenConns(1)` —— 进程内只有一条连接。
- `commit.go:98-112`、`recovery_seed.go:47-60`、`migrate_recovery.go:88-99`：均为手动 `BEGIN IMMEDIATE` + `committed` 标志 + 背景 ctx 回滚。
- `commit.go:91`：`CommitHostProbe` 使用 **`context.Background()`**（`recovery_seed.go:29`、`recovery_expire.go:68` 相同），不是调用方 ctx。事务一旦开始，Runner 关闭不会把它打断（这也是 O1 守卫必须放在提交之前的直接原因）。

原子性论证：`ScheduleHostProbeRetry` 只需要一条 `UPDATE`，单语句本身即原子；外层 `BEGIN IMMEDIATE` 保证「读 `retry_failures` → 算 `n` → 写回」不被其它写者插入。失败时 `ROLLBACK` 不留下任何部分写入。`busy_timeout=5000` 覆盖锁等待，超时则整笔失败、返回 error。

实施约束：

1. 新方法必须复用同一形态（`s.db.Conn` + 手动 `BEGIN IMMEDIATE` + 背景 ctx 回滚），不得改用 `db.BeginTx`（后者是 deferred BEGIN，语义不同）。
2. 事务内不得调用任何其它 Store 方法 —— 单连接下会自我死锁。
3. 回滚与提交都必须用 `context.Background()`。

## 门禁 2：8 个 `next_probe_at` 写入者的并发关系

### 结论：**通过**，附带两条残留风险（均不改设计）

| # | 写入者 | 事务形态 | 键约束 |
| --- | --- | --- | --- |
| 1 | `commit.go:294-303` CommitHostProbe | 手动 `BEGIN IMMEDIATE`，独占连接 | 事务内校验 source/host/gen/digest（`commit.go:118-155`） |
| 2 | `host.go:127-134` 换 Host | `withSourceLive` → `db.Begin()`（deferred） | `id` + 新 host |
| 3 | `host.go:363-372` ApplyCredChanges | `db.Begin()`（deferred） | `repo_host` 批量 |
| 4 | `store.go:785-790` AddSource | `db.Begin()` | 新行 |
| 5 | `store.go:827-828` enabled 0→1 | 单语句自动提交 | `id` |
| 6 | `recovery_expire.go:27-31` TTL 物化 | 手动 `BEGIN IMMEDIATE` | `state='ok' AND last_success_at=? AND gen=?` |
| 7 | `recovery_seed.go:102-110` 种子 | 手动 `BEGIN IMMEDIATE` | `ON CONFLICT DO NOTHING` |
| 8 | **A2 新增** `ScheduleHostProbeRetry` | 手动 `BEGIN IMMEDIATE` | 六项 CAS |

关键事实：`SetMaxOpenConns(1)` 让**进程内所有写事务串行**。2/3/4 虽用 deferred BEGIN，也不存在锁升级竞争——它们从拿到连接起就独占，其它写者只能在池上排队。因此「交错执行」在本进程内不可能发生，剩下的风险只是**跨事务的陈旧读**（TOCTOU），由 CAS 消除。

逐序验证（A2 retry 记为 R，其它写入记 W）：

| 序 | 结果 | 依据 |
| --- | --- | --- |
| R(t1) → W1 commit(t2>t1) | commit 覆盖调度，`retry_failures=0` | commit 的 UPSERT 无条件写 `next_probe_at`，成功提交是更新的权威 |
| W1 commit(t1) → R(t2>t1) | R 被拒（`next_probe_at>At`） | CAS 第三项；commit 写入的 `next` 恒 ≥ t1+15s |
| W3 gen++(t1) → R(t2) | R 被拒 | `registry_host_gen.gen != expectedGen`，CAS 第二项 |
| W2 换 Host(t1) → R(t2) | R 被拒 | `repo_host != expectedHost`，CAS 第六项 |
| W5 disable(t1) → R(t2) | R 被拒 | `enabled=1` 不成立，CAS 第四项 |
| W6 物化 expired(t1) → R(t2) | R 通过，`next` 被推后 ≤600s，`state` 不变 | CAS 只校验 `next<=At` |
| W1 commit 后 R(t2) 试图复活 | 不可能 | R 由未提交失败触发；同一 key 的执行被 `claim` 串行化 |

残留风险：

- **R2-1（低）**：`hard-excluded` 行 `next_probe_at=0`，若真有 retry 落到它身上，CAS 第三项会通过并把 `next` 推到未来，破坏「不进普通恢复循环」。可达性：`ListDueHostProbes` 已排除 `hard-excluded`（`host.go:472-474`），且本进程内唯一能把该行置为 `hard-excluded` 的是它自己的 commit（本路径不提交）。**单 Runner 下不可达**。若未来要绝对封死，需给 CAS 加第七项 `state<>'hard-excluded'`，这超出已冻结的六项，需你单独批准。
- **R2-2（低）**：TTL 物化把 `next` 置为 now 后，retry 可把它推后至多 600s，`state` 仍是 `expired`。语义未变（T12 只要求 `expired` 语义不变），但「已过期待重探」的源最坏晚 10 分钟恢复。建议接受；若不接受，只能给 CAS 加 `state` 条件，同样属于第七项。
- **R2-3（记录）**：commit 用探测起点 `p.At` 计算 `next`，长探测会得到偏早的 `next`，可能在提交后立刻再次到期。这是 3.5.1 既有行为，A2 不引入也不修复。

## 门禁 3：Guard 的 Generation + Seq 完整链路

### 结论：**通过**。旧代次、旧 token、DB 重试成功均无法解除新屏蔽

完整链路（全部有代码证据）：

1. **Block**（`store/guard.go:51-62`）：`g.mu` 内分配 `seq := g.seq.Add(1)`、写入 `{gen, seq}`、`epoch++`，返回 `GuardToken{gen, seq}`。seq 分配与 map 写入同一临界区，后到的 Block 覆盖旧条目。
2. **Token 记录**（`runner/hostprobe.go:467-481`）：`blockRoute` 把 token 存进 `r.guardTok[GuardKey]`，键是 `(sourceID, "registry", host)`（`:462-465`）。
3. **Invalidate**（`runner/hostprobe.go:504-508` → `scheduler/scheduler.go:303-310`）：清空 `lists` 与 `sticky`；`main.go:356` 注入。Block 路径与成功路径都会调用（`:439`、`:446`）。
4. **Snapshot → Filter → Verify**（`store/guard.go:111-131`）：一次 `RLock` 取整表快照与 epoch，过滤后 `verify(epoch)`；不一致整体重试，三次耗尽返回空集（fail-closed），绝不退化为未过滤列表。三个入口全部走它：`scheduler.go:582`、`scheduler.go:600`、`store/sources.go:355`。
5. **Unblock**（`store/guard.go:64-75`）：`entry.gen == tok.Gen && entry.seq == tok.Seq` 才删除并 `epoch++`，否则返回 false。
6. **唯一调用点**：`unblockRoute` 只在 `hostprobe.go:448`（`HostCapsCommitted` 分支）调用，全文件无第二处。

由此得到三条保证：

- 旧代次的成功提交 → `CommitHostProbe` 在事务内返回 `HostCapsStaleSnapshot`（`commit.go:150`、`:161`），进不了成功分支，不会调用 `unblockRoute`。
- 旧 token → `UnblockIfMatch` 的 seq 比对失败（`guard_test.go:62`、`:38` 已覆盖）。
- 数据库重试成功 → 当前代码**不存在「同一结果二次提交」的路径**；A2 的 retry 是新一次探测，不是重放旧结果。因此「DB 重试成功不解除」在结构上成立。

对 A2 的硬约束（必须写进实施）：

1. `ScheduleHostProbeRetry` 不得触碰 `RecoveryGuard`；不得在失败分支之后调用 `unblockRoute`。
2. 若将来引入「同一结果重试提交」，必须在 `HostCapsCommitted` 分支区分「本次独立探测」与「旧结果重放」，否则会绕过 C5 隔离。A2 明确不做重放。
3. T11 需断言：四种 retry 原因执行后 `Guard.Blocked(key)` 仍为 true（对 Block 类原因），且 `guardTok` 未被清除。
