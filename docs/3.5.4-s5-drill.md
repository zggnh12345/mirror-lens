### restore.sh 故障注入结果

正常恢复、manifest 缺失、DB 篡改、key 篡改、DB 截断、manifest 哈希错误、
旧 WAL/SHM 隔离、重复 `--recover` 幂等、无可恢复材料时保留 journal、
旧配对缺 DB / 缺 key / 哈希错误时拒绝回滚且不破坏正式目录、
补完失败后回滚并留档新配对 → 21/21 通过。
切换点 `after_journal` / `after_stage` / `after_save` / `after_db` / `after_key` / `after_verify`
逐一 SIGKILL，`--recover` 后全部收敛到「完整旧配对」或「完整新配对」，没有混合状态。
以 uid 1000 实际执行恢复通过（DB/key 均为 0600，内容正确）。

回滚规则（P1）：回滚前先证明旧配对完整——哈希有记录、DB/key 都在、内容匹配；
通过后在数据目录外复制并复核，才把正式文件移入 `.restore-failed-<tx>`（不删除），
再从副本落回旧配对并复核。旧配对不完整或哈希为空时，正式目录与现场原样保留、
journal 保留、返回失败；不再出现「先删当前配对、再发现旧配对不可用」。

启动门禁（真实二进制）：已有库缺 key、journal 优先于密钥检查、配对完好启动、
journal 状态不可判定（ENOTDIR/权限等）拒绝启动、全新安装 → 5/5 通过；
缺 key 用例确认不生成 `secret.key`、不改动库文件。

### 从备份恢复后双版本启动

用生产备份（2026-11-10，18,649,088 B）的副本，经 `tools/mkunit`（内部调用
`janitor.BackupNow`，即正式备份实现）生成单元：

- 单元 `backup/units/mirror-lens-20261113/`：`manifest.json` + `mirror-lens.db` + `secret.key`
- manifest：schema=1、`db.sha256=08635bcf…a9ac`、`key.sha256=7217bd06…5956`
- `restore.sh` 校验并恢复 → 落盘 SHA-256 与 manifest 完全一致
- 新版本迁移：93 源、docker 19、ghcr 8、identity 36/9/48、`registry:docker.io` 候选 0
- 3.5.3 旧代码打开同一库：`SOURCES=93 DOCKER=19 GHCR=8`，无 SQL 错误
- 旧平铺目录（只有 `.db`）交给 `restore.sh`：报「备份单元缺少 manifest.json」并拒绝

这一步同时暴露并修掉一个真实缺陷：manifest 是缩进 JSON，早期脚本按行 grep
嵌套对象会读到空的 `db.sha256`。现在先压平 JSON 再解析，测试夹具也改成缩进格式。
