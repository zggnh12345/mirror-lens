## 1. 五个核心概念（冻结，不得混同）

审查指出早期稿件把“实际连接地址”和 Manifest CacheKey 身份都叫 Endpoint，是当前最重要的语义冲突。3.5.24 必须把下面五个概念分开；底层可复用同一个不可变的规范化端点**值结构**（Scheme + CanonicalHost + EffectivePort），但它们承载**不同业务语义，不得当成同一个对象**。

> 身份命名与任务书 §2.1 对齐：任务书原四概念 `Endpoint`（实际连接）对应下表 `SourceEndpoint`，任务书 `Authority`（CanonicalHost+EffectivePort）对应下表 Origin 去掉 Scheme 的序列化形式；语义不变，仅在此统一命名。

| 概念 | 业务用途 | 关键语义 | 典型值 |
|---|---|---|---|
| `RegistryIdentity` | 逻辑 Registry 身份：repo_host、策略 Host、凭据 Host、状态关联 | 纯 Host，不含 Scheme/Port | `ghcr.io`、`quay.io`、`registry.example.com` |
| `RegistryEndpoint` | 请求规划期的逻辑 Registry 目标；用于 Manifest CacheKey（ManifestEndpointKey） | Scheme + CanonicalHost + EffectivePort | `https://registry.example.com:443` |
| `SourceEndpoint` | 实际镜像节点连接地址：`sources.base_url` 对应、调度选中的回源目标 | Scheme + 域名/IP + EffectivePort | `https://mirror.example.com:5443`、`http://<IP>:5000` |
| `Origin` | 实际请求及重定向的来源身份：凭据转发与同源安全判断 | Scheme + CanonicalHost + EffectivePort | `https://registry.example.com:443` |
| `Authority` | 地址序列化组成部分，不是独立业务身份 | CanonicalHost + EffectivePort（含必要 IPv6 方括号） | `registry.example.com:443`、`[2001:db8::10]:5000` |

约束：
- `RegistryIdentity` **不含 IP 字面量示例**。当前 `registryhost.checkHost`（`registryhost.go:54-75`）明确拒绝带端口 Host 与 IP 字面量；repo_host / 策略 Host / 凭据 Host 都依赖逻辑 Registry 身份模型。IP 属于 `SourceEndpoint`，**不得**因 SourceEndpoint 是 IP 就写进 repo_host 或凭据身份字段，**不得**用 `net.ParseIP(host) != nil` 直接放行 `Allowed()`。用户添加的是 IP 镜像节点，不是把逻辑 Registry 身份改成 IP。
- `SourceEndpoint` 是 `sources.base_url` 的规范化连接地址（含 Scheme、域名或 IP、EffectivePort）。它**不是** RegistryIdentity，也不是客户端请求的逻辑 Registry。
- `Origin` 是凭据安全判断的 Scheme+CanonicalHost+EffectivePort 三元组；凭据转发必须调用完整 Origin 比较，**不得**降级为 Host 比较。
- IPv6 规范化与 safehttp `Unmap()` / IPv4-mapped 保持一致；默认端口 80/443。

**裁定 ①（复现值结构，但业务语义分离）**：
- 组成字段相同的部分（Scheme + CanonicalHost + EffectivePort）用一个不可变、规范化强类型端点值结构表达，不维护多套等价结构。
- 但 `RegistryIdentity`（逻辑、去端口）、`RegistryEndpoint`（规划期逻辑目标）、`SourceEndpoint`（实际连接目标）、`Origin`（凭据安全来源）是不同的业务概念与不同的比较函数，禁止互换或降级比较；`Authority` 只是地址序列化的组成部分，不是独立业务身份。
- `RegistryEndpoint` 与 `Origin` 可复用相同的字段结构与规范化算法，但**不得混用业务来源、比较语义和构造入口**：Manifest CacheKey 只能由规划期 `RegistryEndpoint` 构造，不得把 `Origin` 业务对象或同源比较函数当作 CacheKey 构造依据；`P0-3` 来源链（§5.6）已裁定为 `ParsePath → parseRepo → ParsedPath.Host → registryhost.Normalize → CanonicalHost`，Scheme 取 `Adapter.Scheme`、EffectivePort 按 Scheme 推导，CacheKey 阶段不得再独立读取 `Adapter.Upstream`。
- 凭据转发用完整 `Origin` 比较（Scheme+Host+Port 三项）；Host 级 Realm Policy 单独用 `CanonicalHost` 比较（去端口），不走 Origin。

## 2. 两个"同 Host"语义（写死，不得混用）

- **Realm/Policy 判定** → 去端口的 CanonicalHost（`registryhost.Normalize(u.Hostname())`）。
- **凭据转发同源判定** → 完整 Origin（Scheme+CanonicalHost+EffectivePort，即含端口的 `.Host` + scheme）。
- 现状混用点（须修正）：`identity.go:251`、`gateway.go`（applyRedirect/recheck）、`registryauth.go:244`、`csrf.go:59`（csrf 已正确比较 scheme+host+port 三项）。
- **A3 机制边界（本轮纠正）**：Realm 授权（`PolicySnapshot.Allows`，`policy.go:73-97`）与 Token 跳转（`RedirectPolicy`，`identity.go:221-265`）是**两套独立判断**。前者比 Challenge Realm 与策略自身 `p.Scheme`/`p.Realms`，不读原始 Registry 请求 scheme；后者的 sameOrigin/`:254` 只管 Token 服务的 3xx 跳转。不得用后者推导前者的结论。

## 4. 凭据/Realm 裁定（冻结）

Realm 授权（Challenge Realm 是否被策略允许）与 Token 3xx 重定向（来源变化后是否继续携带认证头）是**两套独立判断**，前文 §2 已明确区分此机制边界。本轮收窄复审归因：**问题不是“未区分机制”，而是本表格原“跨 Host Realm：拒绝”一行与前文保留白名单的要求自相矛盾**。现已统一如下。

- 实现位置：`PolicySnapshot.Allows`（`internal/v2auth/policy.go:73-97`，其中 `p.Realms` 白名单比较在 `:90-95`；注意不是 `store/policy.go`，后者是策略播种逻辑 `policySeedForSource`，约 `:241-260`）。Token 重定向判断在 `internal/v2auth/identity.go:221-265`。
- HTTP Endpoint 显式配置 = 授权该 Endpoint 明文凭据（含 Basic）。
- **明文凭据安全警告（需实现 UI 提示）**：允许显式配置 HTTP Endpoint 时，Token Realm 即使是 HTTPS，也**不能保护随后发往 HTTP Registry 的 Authorization**——Basic 凭据 / Bearer Token 到 HTTP Registry 仍可能被链路窃听。UI 必须明示该风险，不得把“Token Realm 是 HTTPS”展示成整条认证链已安全。
- **Realm 授权矩阵（按机制边界，保留既有白名单兼容）**：
  - HTTP Registry + 同 Host HTTP Realm：**需实现目标**——实施后仅当该 Endpoint 被显式配置为 HTTP 且 Challenge Realm 与该 SourceEndpoint 的**完整 Origin（Scheme / CanonicalHost / EffectivePort）完全一致**时允许；不同端口不得自动获得 HTTP Realm 授权。该授权条件尚需实现，现有 `PolicySnapshot`（`policy.go:20-32`）**无 `AllowPlainHTTP` 字段**，`Allows`（`:73-97`）实际只检查 `AllowSameHost`/`Scheme`/`Realms`。此条件必须是针对该 Endpoint 的窄授权，不得扩展为全局放宽 HTTPS-only、不得绕过 P0-3、不得新增 DB 字段——**保留窄路径目标，不得改为一律拒绝，也不得表述为现状已支持**。
  - HTTP Registry + 同 Host HTTPS Realm：**允许**安全升级（`Allows` 比的是 Realm 自身 scheme 与 `p.Scheme`，与 Registry 请求 scheme 无关）——**保留此路径，不得改为一律拒绝**。
  - HTTPS Registry + 同 Host HTTPS Realm：允许，按 `CanonicalHost`（去端口）匹配。
  - HTTPS Registry + 同 Host HTTP Realm：**拒绝**（绝不 HTTP Token Realm，禁止降级）。
  - **显式配置的 HTTPS 跨 Host Realm：允许（保留既有白名单能力）**——`lscr.io → https://ghcr.io`、`gcr.io → https://storage.googleapis.com`、`registry.gitlab.com → https://gitlab.com`（`auth.go:151-165` 的 `DefaultRealms()`，并有 `auth_test.go:35-75`、`registryauth_test.go:56-99` 测试锁定）。不得把白名单允许扩展为任意跨 Host。
  - **未配置的跨 Host Realm：拒绝。**
  - 新增的"HTTP Registry + 同 Host HTTP Realm"例外属**需实现**目标：当前写入层 `normalizeRealm`（`store/policy.go:387-400`）拒绝 HTTP Realm 持久化，需实现窄例外（显式配置 HTTP + Challenge Realm 与 SourceEndpoint 完整 Origin 完全一致）后才生效；不得因此放宽 HTTPS Registry 路径。
- Realm 授权按 `CanonicalHost` 比较（去端口），与 Host 级策略/凭据绑定一致；**但 HTTP Realm 例外不得仅凭去端口 Host 放行，必须叠加完整 Origin 比较**（见下文 AllowPlainHTTP 契约）。当前 `Allows` 用 `realm.Host`（含端口，`policy.go:80/:86`）而 `normalizeRealm` 去端口（`store/policy.go:387-400`），存在语义差异——必须实现后才有“忽略端口”行为。实际发起 Token 请求时 Challenge URL 端口原样保留，由 safehttp 检查实际连接目标。
- 跨 Origin 不自动复制认证头（Token 3xx 重定向仍独立执行完整 Origin 限制，不因 Challenge Realm 跨 Host 白名单而放宽）。
- Host 级凭据映射跨端口共享 = 已接受限制，须写兼容说明。
- `DefaultRealmsFor(IP) = nil` 不动；不扩 `hostProfiles`（gcr.io/quay.io）。
- fail-closed 保留：`AuthorizeCredential` 五条件门禁不削弱。

**HTTP Realm 窄授权与 `AllowPlainHTTP` 运行时契约（冻结，收紧 HTTP 例外）**：
- `PolicySnapshot.AllowPlainHTTP` 是**运行时字段**（非 DB 字段），默认 `false`。当前代码无此字段；实施时新增于运行时策略快照，**不得新增 DB 字段、不得改变凭据格式**。
- 派生来源唯一：只能由对应 Source 的显式 HTTP 配置（即该 Source 的 `sources.base_url` Scheme 为 `http`）派生；不得从凭据 Map 或逻辑 `RegistryIdentity` 推断。
- HTTP Realm 例外必须比较 Challenge Realm 与该 SourceEndpoint 的**完整 Origin**：`Scheme`、`CanonicalHost`、`EffectivePort` 三者全部一致才放行；仅去端口 Host 相同或仅逻辑身份相同**不足以**授权。不同端口（如 Source `:5000`、Realm `:8080`）不得自动获得 HTTP Realm 授权。
- 允许以增加运行时 Source Origin 上下文（或等价机制）承载该完整 Origin 比较，但**不得新增 DB 字段**。
- 本契约**只收紧 HTTP Realm 例外路径**；普通 Redirect 的完整 Origin 检查与 HTTPS→HTTP 降级拒绝保持不变，不因本例外放宽。
- 本契约**不改变**既有 Host 级凭据映射跨端口共享的兼容边界（该边界为已接受限制，另作兼容说明），仅约束 HTTP Realm 放行判定。
- 上述为需实现目标，落地后 `normalizeRealm` 的 HTTP 拒绝须同步提供窄例外；在实现前 HTTP Realm 持久化仍被拒绝，不得表述为现状已支持。

## 5. Manifest 缓存（冻结 Key 前缀与格式；RegistryEndpoint 来源链已裁定）

- **隔离身份 = 请求规划期确定的完整 `RegistryEndpoint`**：Manifest CacheKey 按请求的逻辑 Registry Endpoint（Scheme + CanonicalHost + EffectivePort，即 `scheme://host:port`）构造。该值在请求规划期确定，**不是调度选中的 `SourceEndpoint` 镜像节点地址**，因此同一 Registry/Repo/Ref 不随后端镜像节点漂移；不同 Host、不同 Scheme、不同非默认端口必须隔离；显式默认端口与省略默认端口等价；IPv6 序列化带方括号。此口径以最终版任务书 §0.2、§1 为准；覆盖早期“按逻辑 RegistryIdentity（裸 host）建键”的口径。
- **不得**把调度选中的 `SourceEndpoint`（`sources.base_url` 指向的实际回源节点）写进 Manifest CacheKey：节点地址在规划期尚未选出，纳入后同一请求在不同节点下产生不同键，破坏跨节点共享缓存，并可能把内网 IP 泄漏进缓存键。规划期 `RegistryEndpoint` 与调度期 `SourceEndpoint` 两者必须分开。

**Key 前缀与格式（冻结，沿用现有解析体系，不新增 `docker:m|manifest:`）**：

| 条件 | 3.5.24 目标格式 |
|---|---|
| `epoch <= 0` | `docker:manifest:<RegistryEndpoint>/<repo>:<ref>\|accept=...` |
| `epoch > 0` | `docker:m:<epoch>:<RegistryEndpoint>/<repo>:<ref>\|accept=...` |

示例（Epoch=1）：

- `docker:m:1:https://registry.example.com:443/library/alpine:latest|accept=...`
- `docker:m:1:https://[2001:db8::10]:443/library/alpine:latest|accept=...`

理由：`RegistryCacheKeyEpoch` 用固定字段 `docker:m:<epoch>:` 解析 Epoch，`RegistryCacheKind` 用 `docker:manifest:` / `docker:m:` 识别 Manifest（`store/epoch.go:104-165`，锚定 `credwrite_test.go:156`）。延续现有前缀、只改变 Rest 部分，避免无必要改动键类型识别、Epoch 解析和清理逻辑。**`docker:m|manifest:<epoch>:` 已删除；任务书的 `docker:m:0:` 已删除**——Epoch=0 时真实格式是 `docker:manifest:`，不是 `docker:m:0:`。

**Key 格式演进（按实测）**：

- 旧（epoch=0）：`docker:manifest:<裸host>/<name>:<ref>|accept=…`。
- 当前（epoch>0）：`docker:m:<epoch>:…`（Rest 仍为裸 host）。
- 3.5.24 目标：上表格式，Rest 由裸 host 升级为完整 `RegistryEndpoint`（scheme://host:port）。

- **升级影响（已验证 + 冻结口径）**：因 Key 由裸 host 变为完整 Endpoint，所有既有域名 Registry 的旧格式 Manifest 缓存**必然无法命中**新格式 Key（`CacheGet` 精确键查询、无旧 Key 回退，见 G0-4）。每个尚未重建的新 Key 在升级后**第一次请求各自回源 Miss 并重建该 Key**——按 Key 计数，**不得**写成“每个 Registry 只回源一次”。旧记录不主动清空，按原 TTL/GC 自然回收。Blob Digest Key 与 `CacheEpoch` 不变，Blob 热缓存仍可复用；私有认证请求在共享缓存查询前 bypass，不计入此项。不得用 epoch bump 触发重建。
- 热缓存性能对照：两版本各自先完成自己的 Manifest 缓存预热，再测热缓存；3.5.24 升级后的首次回源/重建请求记为 `manifest_key_rebuild_first_miss`，作为一次性缓存重建成本单独披露（回源次数与耗时），不混入热缓存命中样本。
- **未验证项（单独保留）**：生产 `cache_epoch` 实际值——未读取，不推断生产当前前缀。（读路径“无旧 Key 兼容查找”已由 `CacheGet` 精确查询验证，不再列为未验证。）

**5.6 RegistryEndpoint 规划期来源链（P0-3，设计裁定已明确，六项证据已归档）**：RegistryEndpoint 在请求规划期根据唯一、明确的来源链构造，不得从入站地址或实际镜像节点推导。三种可能不同的协议必须区分：①入站协议（Docker 客户端访问 Mirror Lens 的 HTTP/HTTPS）；②Registry 上游协议（RegistryAdapter 规划上游请求的 Scheme，取自 `Adapter.Scheme`）；③SourceEndpoint 协议（`sources.base_url` 自身的 Scheme）。三者不得互相替代补位。

**Scheme 来源**

- 当前生产装配创建 Registry Adapter 时调用 `registryadapter.New()`（`internal/adapter/registryadapter/registry.go:138-143`），其 `Adapter.Scheme` 初始化为 `https`。
- 当前生产代码不存在其他对 `Adapter.Scheme` 的赋值路径。
- 因此当前生产请求的 RegistryEndpoint Scheme 为 HTTPS。
- 不得使用入站 `r.TLS`、`r.Host` 或 SourceEndpoint Scheme 替代。

**CanonicalHost 来源**

唯一来源链：

```text
请求路径 → ParsePath → parseRepo → ParsedPath.Host → registryhost.Normalize → RegistryEndpoint.CanonicalHost
```

- `ParsedPath.Host` 是 Endpoint 构造时唯一接收的逻辑 Host 输入。
- 对显式 Host 前缀请求，Host 来自路径解析。
同时更新接口边界：当前 `registryhost.Check()`（`registryhost.go:168-178`）= `Normalize()` + `Allowed()` 白名单，既校验语法又校验 Registry 白名单。UI 的 `RegistryIdentity` 输入应明确限定为受支持的逻辑 Registry 身份选择（如 `docker.io`、`ghcr.io`、`quay.io`），不得让用户误以为任意自定义域名都可作为逻辑身份；自定义域名与 IP 是 `SourceEndpoint`（`sources.base_url`）的能力，不等于自动开放任意 `RegistryIdentity`。Docker Hub 兼容识别只允许精确匹配既有入口 `docker.io`、`registry-1.docker.io`、`index.docker.io`；`hub.docker.com` 作为独立历史兼容项按精确匹配处理：`hub.docker.com` → 映射为 `docker.io`，但**不属于** `registryhost.Normalize()` 的 Docker Hub 正式别名集合（正式别名仅 `docker.io`/`registry-1.docker.io`/`index.docker.io`）；不得把历史兼容映射写成取消映射，也不得混入正式别名集合；不笼统描述为 Registry V2 端点。禁止后缀匹配、模糊匹配与 DNS 解析结果推断身份。GitHub / GHCR 的既有专用识别逻辑保留，不与 Docker Hub 默认逻辑混在一起。其他未知域名、IPv4、IPv6 在没有显式 `host`（RegistryIdentity）时必须拒绝新增，不得继续回退到 `docker.io`。

- 对裸仓库名请求，`parseRepo` 按现有规则使用 `Adapter.Upstream` 作为默认 Host，形成 `ParsedPath.Host`。

**EffectivePort 来源**

- 当前逻辑 Registry 请求模型没有独立端口输入。
- `config.Registry.Upstream`（`internal/config/config.go:95`）采用严格纯主机名契约：仅接受符合 `registryhost.Normalize()` 语法规则的主机名，不包含 Scheme、显式端口或 IP 字面量。当前 `Config.Validate`（`config.go:634-642`）仅拒空值与 `://`、`/`，尚未拒绝端口/IP/Scheme，该缺口属实施必修项；不得因 UI 提示（当前 `internal/api/config.go:149-150` 仅 `TrimSpace` + Hint）而视为已校验。
- `sources.base_url` 的端口属于 SourceEndpoint，不属于 RegistryEndpoint。
- 当前生产 Scheme 为 HTTPS，因此 EffectivePort 为 443。
- 通用规范化规则为 HTTPS 默认 443、HTTP 默认 80；但这不代表当前产品已经提供逻辑 Registry 的 HTTP 或自定义端口配置能力。
- 当前没有用户可配置的逻辑 Registry 非默认端口能力。P0-3 关闭仅证明现有受支持请求模型中的来源链完整，不授予新增逻辑 Registry Scheme/Port 输入能力，不得据此扩大产品承诺。
- 任务书中的非默认端口 Key 隔离测试仅作为 Endpoint 值及 Key Builder 的语义测试保留，不得据此宣称现有 `/v2/` 请求入口已支持用户配置任意逻辑端口。

**构造时机与缓存关系**

- RegistryEndpoint 必须在 `rememberedHost()` 替换实际回源 Host、Fallback 和 Source 调度之前构造（`registry.go:176-177` 的 Fallback 与 `OnFallback=rememberHost`）。
- Manifest CacheKey 只能使用规范化后的 RegistryEndpoint、Repo、Ref 和既定 Accept 归一结果（`registry.go:343` 为唯一生产构造点）。
- `rememberedHost`、Fallback、SourceEndpoint 的选择或切换不得改变 RegistryEndpoint 和 CacheKey。
- Upstream 继续保持现有 `rememberedHost`/Fallback 实际回源行为；不得强行改为 RegistryEndpoint.URL 并破坏 GHCR fallback。
- Origin 仍用于凭据及重定向安全判断，不得复用为 Manifest CacheKey 身份。

**能力边界**

IPv6 Endpoint/Authority 的方括号序列化及 Manifest Key 格式测试继续保留。该值结构的序列化能力不代表当前 `/v2/` 路径支持 IP 字面量作为 RegistryIdentity；不得由序列化测试推导新的 IP 身份准入能力。

以上结论证明当前请求模型的 RegistryEndpoint Scheme、CanonicalHost、EffectivePort 来源链完整且唯一，不包含逻辑 Registry 显式非默认端口输入功能。六项为设计证据门禁，不要求实施 API、UI、持久化或重启恢复；六项证据已于 2026-11-25 归档（见 evidence-baseline §P0-3 六项证据归档），P0-3 来源链据此闭合；G1 已于 2026-11-26 经独立冻结授权转为 `DESIGN_FROZEN`（本条为 2026-11-26 状态更新，原「须保持 DRAFT_NOT_FROZEN」的历史表述不再适用）。

**三个 Scheme 的协议隔离（P1-2 补充裁定）**：RegistryEndpoint.Scheme（`Adapter.Scheme`，规划期逻辑身份，默认 HTTPS）、SourceEndpoint.Scheme（`sources.base_url`，用户可配 HTTP/HTTPS，实际节点连接）、Origin.Scheme（实际请求及重定向来源身份）三者职责分离、互不补位。用户把 SourceEndpoint 从 HTTPS 切到 HTTP 只改变实际连接协议与节点地址，不改变 `Adapter.Scheme`、RegistryEndpoint 逻辑身份或 Manifest CacheKey；Origin 变化时清除旧 Origin 的 Authorization，但不等于禁止按目标节点明确授权重新查找并附加该节点自己的凭据；两套判断职责分离——Realm 授权走 Realm Policy（逻辑 Host、Realm Scheme、明确授权列表），普通 3xx 重定向走完整 Origin（Scheme+Host+Port）比较，不得混称为「都是完整 Origin 校验」；HTTP/HTTPS 切换不得导致 Authorization 跨 Origin 泄漏。

**5.7 registry.upstream 严格纯主机名输入契约（P0-3-3 关联裁定，2026-11-25 DECISION_ACCEPTED）**

**输入契约（冻结）**：`registry.upstream` 只允许符合 `registryhost.Normalize()` 现有语法规则的纯主机名；禁止显式端口、IPv4、IPv6 字面量、完整 URL 与路径。不另实现一套 Host 语法，以 `Normalize()` 实际规则为准。

| 允许 | 禁止 |
|---|---|
| `registry-1.docker.io`、`registry.example.com` | 显式端口 `registry.example.com:5000` |
| 大写（由 `Normalize()` 规范化） | IPv4 字面量 `203.0.113.10` |
| 尾点（由 `Normalize()` 去尾点） | IPv6 字面量 `[2001:db8::10]:5000`、完整 URL `https://…`、路径 `/v2` |

**CanonicalHost 与路由分离（冻结）**：CanonicalHost 仅作逻辑身份（缓存键维度），不得覆盖 `Adapter.Upstream` 的实际回源路由；不得把 `RegistryEndpoint.CanonicalHost` 直接覆盖到 `Plan.LogicalHost`。`Normalize()` 在此仅用于校验输入与生成 CanonicalHost，**不得把返回值写回配置或 `Adapter.Upstream`**：`registry-1.docker.io` 经 `Normalize()` 得逻辑身份 `docker.io`，但配置与 `Adapter.Upstream` 必须继续保留原始 `registry-1.docker.io`。`parseRepo()` 以 `Adapter.Upstream` 作为裸仓库名请求的默认 Host，`PlanParsed()` 据此判断默认 Registry，`addGhcrFallback()` 仅在默认上游仍为 `registry-1.docker.io` 时添加 GHCR fallback；写回身份值会改变默认上游判断与 fallback 条件。Docker Hub 身份 `docker.io` 与实际回源 `registry-1.docker.io` 各司其职，语义不变。

**实施必修项（实施阶段，非 G1 冻结前置）**：
- `Config.Validate`（`config.go:634-642`）在 registry 启用时须拒绝：空值、Scheme/路径/查询/Fragment/Userinfo、显式端口、IP 字面量，并经 `registryhost.Normalize()` 验证；非法配置必须明确报错，不得静默退回 Docker Hub、不得截掉端口后继续使用、不得因单个配置非法就自动改成默认上游。
- 必须保留实际路由所需的原始 Host 别名，不得把返回的 CanonicalHost 写回 `Adapter.Upstream`；`Normalize()` 只产生 CanonicalHost 与缓存身份，不写回配置与实际路由 Host，确保 `registry-1.docker.io` 的默认上游判断与 GHCR fallback 语义不变（见任务书 §4 专用测试）。
- 四入口统一：YAML 加载、Web Setter、写入+读回验证、Validate 失败不得覆盖原配置文件；不能仅靠 UI 提示。
- 校验只作用于 `registry.upstream`，不得扩展为全局 URL/Host 限制；不得收紧 `sources.base_url` 原有的 HTTP/HTTPS、IP、非默认端口能力（`sources.base_url` 经 `addSource()` 与 `api.go:677-700 normalizeURL` 解析，scheme+端口原样保留）。为支持 IPv6 SourceEndpoint，允许独立修正 `normalizeURL()` 的 IPv6 方括号与端口解析逻辑，但不得套用 registry 纯域名 `Normalize()` 规则，也不得因此把校验扩展到全局 URL/Host。
- 用 `Normalize()` 而非 `Check()`（`registryhost.go:169-176` 的 `Check()` = `Normalize()` + `Allowed()` 白名单；误用 `Check()` 会把 `registry.example.com` 这类非预置白名单的合法自定义上游以 `UnsupportedError` 拒绝，使纯主机名契约退化为仅预置域名）。
- RED 测试覆盖端口/IPv4/IPv6/协议/路径/错误端口 × 配置加载与 Web 保存路径。
- 配置兼容性：纳管生产实例 `upstream: registry-1.docker.io` 为纯域名，严格契约无兼容破坏；其他历史配置实例升级前需逐实例核验，无需 Schema 迁移。

**三项保护条件（冻结）**：
1. rememberedHost：CacheKey 用原始请求身份；不得以 CanonicalHost 覆盖 `Plan.LogicalHost`。
2. IPv6：保留方括号序列化测试，不开放 IPv6 RegistryIdentity/upstream 输入；IPv6 SourceEndpoint（`sources.base_url`）支持是独立实现项，允许独立修正 `normalizeURL()` 解析以覆盖 IPv6 方括号、IPv6 非默认端口与非法 IPv6 URL，但不得套用 registry 纯域名校验规则。
3. SourceEndpoint：`sources.base_url` 当前支持 HTTP/HTTPS/域名/IPv4/非默认端口（既有能力），**IPv6 是 3.5.24 待实现的目标能力**（`api.go:677-700 normalizeURL()` 现以点号判断拒绝 IPv6，允许独立修正其 URL 解析以覆盖 IPv6 方括号、非默认端口与非法 IPv6 URL，但不得套用 registry 纯域名校验规则）；均不受本节契约限制，不得因本契约而收紧上述既有能力，也不得提前宣称 IPv6 已支持。

**能力边界（冻结）**：自定义域名/IPv4/IPv6/HTTP/HTTPS/非默认端口镜像节点不与本节冲突，须走 `sources.base_url`；禁止把 `http://192.0.2.10:8080` 写入 `registry.upstream`、把 IP 写入 `repo_host`、或以此构造逻辑 Registry CacheKey。3.5.24 须核实链路：UI 添加→API 保存→探测器→TLS SAN（不固定 443）→Gateway 拨号→Redirect/认证/SSRF/IP 访问控制→编辑/删除/重启恢复一致。SourceEndpoint 支持 IP 不等于绕过安全策略。SourceEndpoint 的 HTTP/HTTPS 切换只影响实际连接协议，不改变 RegistryEndpoint Scheme 与 Manifest CacheKey 逻辑身份，也不得导致 Authorization 跨 Origin 泄漏；Realm 授权走 Realm Policy（逻辑 Host、Realm Scheme、明确授权列表）、普通 Redirect 走完整 Origin（Scheme+Host+Port）比较，两套机制独立有效、不得混称（见任务书 §2.5、§4）。

**阶段边界**：本节是架构与输入契约裁定，不是文档修改或代码实施授权；G1 关闭前不要求先提交 Go 代码（避免 B2 流程死锁）。

## 6. 准入与安全底线（冻结）

- 三分准入：产品准入 / safehttp / 凭据提供者资格；不扩 hostProfiles。
- 不改 DB Schema/索引/约束/Schema Version；不迁移或重加密凭据；不改 AEAD AAD 格式。
- 不把端口并入 Registry Host 身份；不扩 hostProfiles 名单；不递增 Cache Epoch、不清 Blob。
- 不加 HTTPS 降级；不默认放行私网/回环/链路本地/组播/保留地址。
- safehttp 完整保留不旁路，每跳重定向重查目标 IP。
- `Allowed()` 禁止 `if net.ParseIP(host) != nil { return nil }` 式裸放行。
- **tlsInfo 拆分（需实现，验收项）· 根因纠正**：`hostOf(base)`（`probe.go:181-188`）去掉的是 Scheme 与路径，返回的是**完整 URL Authority**，因此会保留显式端口与 IPv6 方括号，并**没有丢失端口**。真正缺陷是：`tlsInfo()`（`probe.go:129-164`）接收语义不明确的裸 `host` 字符串，将这个完整 Authority 当作纯 Host，再次执行 `net.JoinHostPort(host, "443")`，造成端口与方括号二次拼接。当前错误矩阵（均源于把 Authority 误当 Host）：

  | SourceEndpoint | 当前传给 tlsInfo 的值 | 当前拼接结果的问题 |
  | --- | --- | --- |
  | `https://host` | `host` | 默认 443，正常 |
  | `https://host:5443` | `host:5443` | 再拼 443，形成非法地址 |
  | `https://[2001:db8::1]` | `[2001:db8::1]` | 再拼端口可能形成重复方括号 |
  | `https://[2001:db8::1]:5443` | `[2001:db8::1]:5443` | Authority 与端口再次拼接，地址非法 |

  **冻结的实施契约（修正方向）**：
  - `tlsInfo` 接收完整 `SourceEndpoint` URL 或结构化 Endpoint，不再接收语义不明确的 `host` 字符串。
  - 用 URL 解析分别取得 `Hostname()`、显式端口与 Scheme；无显式端口时才按 Scheme 选默认端口（HTTPS→443）；`net.JoinHostPort()` 只负责最后一次拼接，不得传入已含端口或方括号的 Authority。
  - **三个值必须分开（冻结契约）**：①DNS 解析用 `URL.Hostname()`（不含端口、不含方括号）；②TLS ServerName 与 `verifyChain(cs, ...)` 的 `x509.VerifyOptions.DNSName` 用实际 SourceEndpoint 的域名或不带方括号的 IP，不得带端口或方括号；③Dial Target = 解析所得 IP + SourceEndpoint 的真实 EffectivePort。不得把 RegistryEndpoint 的逻辑 `CanonicalHost` 用作镜像节点证书身份。`net.JoinHostPort()` 只负责最后一次拼接，不得传入已含端口或方括号的 Authority。
  - HTTP `SourceEndpoint` 不执行 TLS 探测，不得错误连接同主机 443。
  - IPv4 / IPv6 / 域名均有测试；IPv6 方括号不得重复处理；HTTPS 默认端口与非默认端口分别测试；证书校验错误与网络不可达分开报告。
  - 该缺陷影响 TLS 诊断与非默认端口证书检查路径，不等于下载请求必然失败（实际探测请求用完整 BaseURL）。

- **TLS 探测路径 ≠ 真实请求 Transport 的 TLS 握手（边界冻结）**：当前 `tlsInfo()`（`probe.go:112-166`）设 `InsecureSkipVerify: true`，并设 `ServerName: host`；握手后仍执行 `verifyChain(cs, host)`（`probe.go:168`，系统信任根 + `x509.VerifyOptions{DNSName: host}`）手工验证证书链与身份。纠正此前"只读证书元数据、不验证身份"的不完整判断，准确边界为：
  - `InsecureSkipVerify: true` 只绕过 **TLS 握手阶段的自动验证**。
  - 握手完成后，`verifyChain()` **仍执行**证书链及 DNS/IP 身份验证；证书错误不会在握手阶段中止，而体现在 `tlsInfo()` 返回的 `ok=false`。
  - 该 `verifyChain` 同样使用被污染的 `host`（见上方三值契约），因此 `host:5443`、`[2001:db8::1]` 会污染 ServerName 与 `VerifyOptions.DNSName`，出现"自定义端口拨号成功但证书身份验证仍失败"。
  - 这条探测路径验证通过，**仍不能替代**真正 HTTP 请求 Transport 的 TLS 握手失败行为测试；`tlsInfo()` 的地址/验证名修复属"探测正确性"，不得作为 TLS SAN 验收通过的证据。

## 7. 五条底线（冻结）

数据库不变；单轨升级；单事务原子性（"本次没有数据库迁移事务""数据库升级事务数量为零"）；Blob 不变（Digest Key/Epoch 不变）；旧功能不退化（旧 Key 首次回源属已披露影响，新 Key 预热后热缓存性能须过对照阈值）。

## 10. IP 认证边界（冻结）

- 匿名 IP SourceEndpoint：支持范围限于“源即目标、无认证需求”的回源场景，且须经管理员显式登记（`sources.base_url`）；不得因 IP 解析成功自动放行；请求目标仍须匹配已授权的 Registry Endpoint/Policy。
- 逻辑 Registry 凭据复用条件：仅当请求身份为显式配置的逻辑 `RegistryIdentity`（非 IP 字面量）且目标匹配其已授权 Endpoint/Policy 时方可复用；IP 字面量身份不得自动继承逻辑 Registry 的凭据，同一 IP 不同端口不获得端口级凭据隔离。
- IP 字面量 Token Realm：不支持自动推导默认 Realm；`DefaultRealmsFor(IP)` 保持空结果（`internal/v2auth/auth.go:170-175`）；专用云凭据 `hostProfiles` 名单不因支持 IP 而扩展。
- 不得自动扩展 IP 的默认 Realm 信任或专用云凭据资格（与任务书 §0.3/§2.7 一致）。
