## 1. R 预算（单请求累计 Attempt 上限，第11章已冻结）

### 1.1 已冻结推导（保持，不重算既有裁定）

| 模式 | 推导 | 上限 |
|---|---|---|
| 默认顺序 | `M(A+1)+R_fb+R_authority = 4×(2+1)+3+1` | 16 |
| 跨站竞速 | `C×A + (M−C)(A+1) + R_fb + R_authority = 4+6+3+1` | 14 |
| 全模式硬上限 | `max(16,14)` | 16 |

前提：A 全程开启（每站 ≤2 Source Attempt）；fb 未被静态抑制（最多 3）；M=4 全参与；每顺序 Registry 最多一次额外重试；首轮竞速不重试；Authority 独立一次。

### 1.2 逻辑 Attempt vs 物理 HTTP 请求（必须分开）

| 类别 | 现状代码证据 | 是否计入原 R=16 推导 |
|---|---|---|
| 逻辑 Attempt（main/A/B/fb/Authority 主请求） | gateway.go:1531 `g.cli.Do`；每链一次 Dispatched | 是（原公式覆盖） |
| B16 重试 Attempt | 3.5.17 新建 per-Registry 令牌 | 是（已含在 `(A+1)`） |
| Authority Attempt | 新建，唯一一次 | 是（`R_authority=1`） |
| Hedge 额外请求 | gateway.go:1080/1147/1162/1168 已确认真实并发请求 | **否（原公式未含）** |
| Midfill 换源请求 | rangeReq→cli.Do（parallel.go:671/213/894/1001），探活 N 台 + 首段 + 分片 M 段 | **否（原公式未含）** |
| Midfill 探活请求 | probeTarget（parallel.go:664/671） | 否 |
| 私有/重定向附加请求 | withRegistryPolicy/RedirectPolicy | 需单独归类 |

### 1.3 统一预算模型（本审计提出，供 17a 冻结）

原则：**每个真实上游 HTTP 请求 = 一个独立 Attempt（Dispatched 即消耗 R）**。这是 Hedge 无法在逻辑 Attempt 内偷发额外物理请求的唯一可证明口径。

- `AttemptBudget` 为 RequestScope 级单一累计计数器，所有路径共享，无第二套预算。
- 两阶段：`ReserveR`（Prepared 原子预留，可释放）/ `CommitR`（Dispatched 正式消耗，不返还）。`g.cli.Do` 前必须完成 Dispatched 提交。
- Hedge：第二路对冲请求 = 独立 Attempt，预留并提交 R；未胜出取消不返还（已 Dispatched）。
- Midfill：探活请求不计入主 R（属能力探测，建议独立 `R_probe` 配额，MaxPerSource 之外的 preflight_concurrency 语义）；首段+分片请求每一个是独立 Attempt，计入同一 RequestScope 的 R。
- 结论：若采纳「每个物理请求一个 Attempt」，则 **R=16 必须扩展为覆盖 Hedge+Midfill**，否则 R=16 只是「主逻辑 Attempt 上限」，不能声称是物理请求上限。

### 1.4 扩展上界推导（待用户裁定是否纳入冻结）

保守最坏路径（默认顺序模式 + A 全开 + Hedge 每链触发 + Midfill 满分片）：
- 主逻辑 Attempt ≤16（原公式）。
- Hedge 额外：默认顺序主链 A≤2 Source，Hedge 条件 `!raceFormed && !plan.Sequential`——顺序模式下 `plan.Sequential=true`，Hedge 不触发；仅竞速链/非顺序链触发。故 Hedge 主要影响竞速模式，最多 +1 路/链。
- Midfill 换源：Body 阶段，最多 `(par.Workers)` 段 + 探活（独立配额）；`parallel.workers` 默认 4、上限 16。
- 若将 Hedge/Midfill 全部计入同一 R：需为 Hedge 预留 +1，为 Midfill 预留 `workers` 段，则上限从 16 上升，**原 R=16 不再是物理请求上界**。

**审计结论（P0）**：R=16 作为「逻辑 Attempt 累计上限」成立且已冻结；作为「物理 HTTP 请求硬上限」不成立，需用户裁定采用哪种口径。本审计不自行裁定，列入 open-decisions。

### 2.2 单请求峰值（第11章已冻结）

`G_race,request = C×A + F = 2×2 + 1 = 5`（竞速模式单请求瞬时峰值；不是全服务 G）。

### 2.3 全服务 G 推导（本审计提出，供冻结）

G 定义为整个服务同时 Dispatched 的物理 Attempt 总数硬上限。推导：

```
G = ceil(全局并发逻辑请求数 N × 单请求峰值 Attempt 数) + 探活并发
  = N × G_request_max + G_preflight
```

其中：
- `G_request_max`：单请求最多同时 Dispatched 的 Attempt。竞速模式 = C×A+F=5；Midfill 阶段可到 `workers` 段（默认 4）；保守取 `max(5, workers)`。
- `N`：全局并发请求数，需配置（现状无全局请求闸门，需新建）。
- `G_preflight`：探活并发，复用 `preflight_concurrency=4` 语义，不进 R 但进 G（物理连接）。

**冻结缺口**：`N` 未定义、G 具体数值未冻结。第11章 3103 明确此为本任务门禁。本审计给出推导公式与参数依赖，但**不擅自填数值**——需用户裁定 N 与容量目标后代入。列入 open-decisions。

### 2.4 G Lease 与 Source Lease 层级关系（设计）

- 层级：G Lease（全服务）在上，Source Scheduler Lease（单源）在下。申请顺序：**先 G，后 Source**；释放逆序。
- 部分失败回滚：G 成功但 Source 失败 → 释放 G；G 失败 → 不申请 Source。
- 取消发生在两者之间 → 释放已获 G。
- 幂等释放：Body 结束/换源/取消均通过 leaseBody/wrapLease 的 retire 回调，只递减一次。
- Hedge/Midfill 双重计数防护：每个 Attempt 申请一次 G，Dispatched 期间持有，Completed/Aborted 释放；同一物理请求不得申请两次 G。
- 禁止把 Source Lease 改名为 Global Lease（层级不同）。
