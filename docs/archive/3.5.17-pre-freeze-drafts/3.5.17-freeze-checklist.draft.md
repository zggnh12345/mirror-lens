## 3. G3：动态排序（已冻结）

- 名称统一为 **有效映射回源样本**（废止易歧义的"有效回退样本"）。
- **每条映射独立计数**：不得跨映射合并样本；映射身份或可信关系变化时旧窗口清零。
- **统计窗口（W1，已冻结）**：每条可信映射独立维护**最近 50 个有效映射回源样本**；不足 50 用固定排序，达到 50 用动态排序；新样本进入、最旧移出；不使用 200 或无限累计。
- **有效样本定义（F03，已冻结）**：
  - 对某条映射的每一次真实回源尝试最多计一个样本；首站直接命中也计入（不要求先跨站跳转）。
  - 缓存命中且未回源不计入。
  - 成功样本须通过 Manifest 身份验证；真实回源失败计入失败样本。
  - **排除**：用户取消、客户端断开、策略拒绝、认证拒绝、本地准入失败、尚未实际发出的尝试、因其他候选胜出而取消的尝试。
  - 同一请求经过多条映射时，每条实际参与的映射分别最多计一次。
- **评分公式（F02，已冻结）**：
  - `Score = 0.6 × SuccessRate + 0.4 × LatencyScore`
  - `SuccessRate = 成功样本数 / 有效样本总数`
  - `LatencyScore = 1 / (1 + P50(TTFB) / 800ms)`
  - 维度权重：成功率 60%、响应延迟 40%、调用频率 **0%**（仅用于样本积累，不参与评分，避免高频映射形成反馈循环）。
  - 不额外做时间衰减（50 样本滚动淘汰已实现自然老化）；TTFB 只统计真实回源阶段；**只有可测量 TTFB 参与中位数，无可测量 TTFB 时 LatencyScore=0**；成功率与延迟须用同一映射样本；并列按可信映射配置固定顺序兜底，不允许随机打破并列。
- 动态排序不改变可信映射关系，不自动开启跨站竞速；保留固定顺序作为失效兜底。

## 4. 预算模型（G / R / C / F / BSequential）

### 4.1 两级预算与维度分离（已冻结）

| 项目 | G：全局预算 | R：请求级预算 |
|---|---|---|
| 作用范围 | 全服务 | 单个逻辑请求 |
| 限制对象 | 同时占用的上游尝试资源 | 单请求累计发出的上游尝试次数 |
| 生命周期 | 并发占用期间 | 整个请求生命周期 |
| 控制机制 | 全局并发 Lease | 请求级 AttemptBudget |

- **正式删除 `R ≤ G`**：二者分别衡量并发占用与累计消耗，无大小关系。
- G 由全局并发 Lease 控制；R 由请求级 AttemptBudget 控制。B 顺序回退、跨站竞速、A 站内竞速及 fb 均受二者限制。
- 每个逻辑请求只创建**一个共享 AttemptBudget**；B 跨站尝试、A 站内竞速、fb 尝试共用该实例；每次真实上游请求发出前必须取得额度；额度消耗后不返还；并发 Lease 在请求结束/取消/超时/失败后必须释放；嵌套、重试、切换 Registry 不得绕过预算。

### 4.2 C 的唯一含义（F04，已冻结）

- `C = 跨站竞速单轮同时参与的 Registry 候选数上限，固定为 2`。C 只约束跨站竞速，**不约束顺序回退**，不再表示跨站候选总数、顺序回退候选数或总尝试次数。

| 行为 | 是否受 C 限制 | 是否消耗 R |
|---|---|---|
| 跨站竞速单轮候选 | 是，最多 2 个 | 是 |
| 顺序回退后续 Registry | 否 | 是 |
| 权威 Registry 兜底 | 否 | 是 |
| A 站内 Source 竞速 | 不直接受 C 限制 | 是 |
| A 内部 fb | 不直接受 C 限制 | 是 |

### 4.3 main 链 / fb 链 / F 的独立维度（已冻结）

fb 链是**既有链级 fallback**（`addGhcrFallback` / `fetchRace`），与 A 的 `star_race` 开关**相互独立**，不受其控制。

- **A（main 链并发路数）**：A 开启时单站最多 2 路星标 Source；A 关闭时为 1 路串行 main Source。公式中 A 关闭时**取 1，不取 0**。
- **F 的最终定义**：当前逻辑请求中，所有符合既有 fallback 资格、**已经实际启动且尚未退出**的 fb 链所占用的并发资源总和。
  - 每条启动且未退出的 fb 链最多贡献 **1 路**并发 Lease（依据：`fetchRace` 中 fb 链 `pc.RaceReady=false`、不叠加 Hedge、`fetchSeq` 严格顺序执行）。
  - F **不是**每个站固定一条，不按 fb target 数累计，也不按 main Source 数乘算。
  - 未触发 fb、`prev != nil` 不进 `fetchRace`、fb 已取消并确认退出、与 B 的 GHCR 候选去重后——均不计入（F=0）。
  - 现有代码下，**只有符合条件的 docker.io 默认上游请求**可能贡献 F；ghcr/quay/gcr/mcr 等站无 fb 链。
  - G 必须基于**实际 Lease 集合**计算，不能仅根据候选数量乘法推算。

### 4.4 BSequential 的定义（已冻结）

BSequential = 顺序回退路径在**任一时刻**实际占用的 **main 链**并发资源，**不是**顺序回退候选总数，也**不是**累计尝试次数。

| 场景 | BSequential |
|---|---|
| 顺序回退，每次只回源一个 Source | 1 |
| 顺序回退，单站 A 开启同时运行两个 Source | 2 |
| 依次访问 5 个 Registry，每次只回源一个 Source | 1（不是 5） |

> 上表数值仅为定义示例（A 站内上限为 2，遵循 1.6 第 1946 行），**不是冻结的 A、G 或 R 数值**。顺序回退候选数量不进入 G 的乘法项，只受 R 限制。

### 4.5 预算公式按模式分支（原三项恒相加公式已废止）

废止 `GlobalUsage = BSequential + (C×A) + F`。改为按 B 模式分别计算（`GlobalUsage` 为 main 链与 fb 链实际并发 Lease 总和，每份 Lease 只计一次）：

| 模式 | A 开关 | main 链资源 | fb 链资源 | GlobalUsage |
|---|---|---|---|---|
| 顺序回退 | 关闭 | BSequential=1（单站串行） | F | `BSequential + F` |
| 顺序回退 | 开启 | BSequential（单站最多 2） | F | `BSequential + F` |
| 跨站竞速 | 关闭 | C×1 | F | `(C×1) + F` |
| 跨站竞速 | 开启 | C×2 | F | `(C×2) + F` |

- 两种模式是**分支关系，不是恒定叠加关系**。竞速失败后进入顺序补位，必须按实际运行状态重新计算，不能把竞速阶段预算与顺序补位预算永久相加。
- F 统计实际占用：A 关闭时 F 仍按实际 fb 并发计数，不清零（跨站竞速、A 关闭、两站 fb 都实际运行时 `GlobalUsage = 2×1 + 2 = 4`）。
- 竞速转顺序补位：决定进入补位前，必须**先取消竞速候选 → 关闭未选中 Body → 确认执行路径退出 → 释放全部竞速 Lease → 再按 BSequential 重新申请**。超时不等于路径已退出；若超时后旧路径仍可能占资源，必须中止模式转换并返回受控失败，不得伪造 Lease 已释放。使用同一 RequestScope 与 AttemptBudget，不重置 R。

### 4.6 R 的最坏累计路径推导（规则冻结，数值未冻结）

- R 不从 G 或并发峰值倒推，按单个逻辑请求可能经历的**最坏累计路径**推导：

```
R_required = R_race + R_fallback + R_authority
```

  - `R_race`：跨站竞速阶段所有实际可能发出的 main 和 fb 请求。
  - `R_fallback`：竞速结束后顺序补位阶段所有实际可能发出的 main 和 fb 请求。
  - `R_authority`：权威站兜底实际发出的请求。
  - 每项均按**累计真实 Attempt 数**计算，不得用 G 的并发资源数代替。
- 必须考虑：最多 C=2 个候选同时失败；顺序补位可能经过多条映射；每站 A 最多 2 个 Source；fb 链的真实请求也计入；权威站兜底必须保留额度；失败/超时/取消已发出的额度不返还，未实际发出的不消耗。
- R 冻结值 = 所有允许配置组合下 `R_required` 的最大值。**身份等价抑制只减少特定组合的实际消耗，不作为 R 上限的取值依据**（上限至少按 fb 实际启动的组合推导，如 docker+quay）。
- `R_race` 按候选站类型求和，废止通用乘法 `C×(2+1)`：

```
R_race = Σ_i (R_main,i + R_fb,i)
```

  - `R_main,i`：该候选 main 链真实请求数（A 开最多 2、关最多 1）。
  - `R_fb,i`：该候选既有 fb 链真实请求数，不具备 fb 资格时为 0。

| B 候选 | 映射 / A | main 最大 | fb 最大 | 合计 |
|---|---|---|---|---|
| quay + gcr | A 开 | 4 | 0 | 4 |
| docker + quay | A 开 | 4 | 1 | 5 |
| docker + ghcr | 同名 repo 且 ManifestIdentity 等价 | 4 | 0 | 4 |
| docker + quay | A 关 | 2 | 1 | 3 |

> 表中数字为"每 main Source 最多一次、docker fb 最多一次"的结构上限示例，**不是 R 的冻结值**；实际推导还须核对重试、取消、真实发出条件与 fb 多 target（见 F19）。

### 4.7 模式转换与 Lease 生命周期（17a 出口门禁）

- 顺序回退进入下一 Registry 前，前一尝试的并发 Lease 必须已释放才重新申请。
- 跨站竞速启动最多申请 C=2 个候选并发资源；候选胜出后取消其他候选、关闭未选中 Body、释放对应 Lease。
- 竞速全部失败进入顺序补位：先释放全部竞速 Lease，再按新状态申请。
- 预算额度 R 不因失败/取消/超时返还；已释放 Lease 可被后续尝试复用，但不返还累计额度；A 的 fb 与 B 的回退共享同一 AttemptBudget。
- 17a 出口须提交：两种 B 模式的**预算状态转换图**、**Lease 生命周期**、**竞速失败后顺序补位的测试设计**。

## 6. F18：顺序回退映射数量上限与截断规则（17a 提案审查冻结）

> F18 不只是性能容量参数，它还决定 F19 静态抑制范围，因此 **F18（含 M 具体数值）必须先于 F19 最终冻结**。

- **M = 单个逻辑请求允许参与顺序回退的可信副本候选总数上限**，包含首轮 C=2 竞速候选；首轮竞速候选从这 M 个中选取，剩余按顺序补位。M **不表示**首轮之外的额外数量。

```
B_replica = B_truncated(M)，|B_replica| ≤ M，B_race ⊆ B_replica
```

- **权威站兜底独立于 M**：权威站属正确性保障，不受 M 截断影响，保留兜底机会（避免所有可信副本失败时权威站也被截断）。但"独立于 M"仅指不受 M 截断，**不等于**可排除出 F19 快照（见 F19-14）。
- 17a 必须明确：M 的具体数值；映射超过 M 时的确定性选择规则；截断后如何保留权威站兜底机会；映射配置变化是否影响既有排序窗口及在途请求的 MappingGen；达到上限后是否仍为权威站预留 R 额度。
- 不能只冻结"最多 M 个映射"而不说明权威站是否占名额、是否另留兜底名额；不能让 R 随映射数量无限增长，也不能静默截断后声称兜底保证成立。

## 7. F19：GHCR fallback 联动、身份去重与链级 Claim（审查基线候选，未冻结）

> F19 解决的是 fb 适用范围、跨入口去重与请求级资源协调。它保证跨链不重复发起，但**不取代**链内 `tried` 去重、AttemptBudget、A 竞速资格与重试限制。

### 7.1 fb 适用范围与互斥边界（已冻结语义）

- fb 适用范围**保持现有代码语义，不扩展**为通用 Registry fallback（否则会把 3.5.17 从架构协调升级为新功能开发）。
- `addGhcrFallback` 挂 fb 链的全部条件：默认上游 `registry-1.docker.io` + 非 `library/xxx` + 请求未被 `rememberedHost` 改写为其他 host；目标 ghcr.io，路径取 `p.Upstream.Path`（同名 repo）。
- **适用边界（重要）**：当前代码下"权威站是 GHCR"与"docker fb 链存在"**互斥**——fb 存在时权威站恒为 docker.io、fb 目标为 ghcr.io；权威站变 ghcr 时 `host != def` 或默认上游已非 docker.io，fb 不挂载。17a 不得为这个当前不存在的状态增加运行时分支。
- fb 链独立于 `star_race`；fb 不占 B 的 C 名额；fb 实际并发计入 G，真实 Attempt 计入 R；`prev != nil` 不进 `fetchRace` 时 F=0。
- **fb 链多 target**：F 最多贡献 1 路并发（`R_fb` 与 F 分离）；`R_fb` 按该 fb 链实际可能发出的全部 target 请求数累计（`N_fbTargets` = 加速源候选 + 官方站），未发出的不耗 R、已发出的不返还。示例表 fb=1 仅为单 target 简化，不代表生命周期只消耗一次 R。

### 7.2 Identity 定义（已冻结语义）

```
Identity = (Registry, Repository, ManifestIdentity)
ClaimKey = (RequestScope, Identity)   // 不含 ChainID
```

- **Registry 分量取规范化逻辑 Registry（origin），不取物理加速站 host**——与 `logicalHostFor` / CacheKey 既有口径一致（代码里 `host` 会被 `rememberedHost` 改写，origin 不会）。
- **ManifestIdentity**：静态抑制阶段以**规范化后的请求引用及内容协商语义**判断（tag 或 digest 字符串 + Accept 一致）；解析后的 digest 只用于响应正文身份验证与提交校验，不参与静态抑制。静态去重是**请求身份等价，不是最终内容等价**；tag 与 digest 不因最终解析到相同内容而等价；同一 tag 但内容协商语义不同也不等价。
- **认证上下文不参与身份等价判断**，只决定由哪条路径发起、使用哪套凭据；身份等价不代表认证可互换、不代表可信关系可互换。

### 7.3 静态抑制（F19-14，已冻结语义）

- 静态抑制快照取 **F18 截断后的完整 B 候选集合**（不是配置全集，不是运行时实际发出集合）：

```
B_snapshot = B_truncated(M) ∪ B_authority   // 按 Identity 去重
Suppress(fb) = ∃ b ∈ B_snapshot : Identity(b) = Identity(fb)
```

  - `B_authority` = 本请求符合权威站兜底资格的候选，不占 M 名额；与可信副本 Identity 相同时只保留一个有效候选身份，不重复计数或发起。
  - 权威站进入快照是**候选集合定义的一致性规则**，不是因为当前 Docker fb 会与 GHCR 权威站冲突（该状态互斥，见 7.1）。
  - 首轮竞速候选与顺序补位候选构成**同一个完整快照**；GHCR 即使不在首轮，只要进入截断后的补位集合，等价 fb 仍被抑制。
- **静态抑制优先于 Claim 可用性**：请求开始时按快照静态确定被抑制的链；被抑制链全程不参与 Claim 竞争；Claim 后续释放不改变抑制结果；只有未被抑制的链才有资格在 Claim Released 后重竞争。快照用请求开始时固定的候选集，不因排序变化、候选跳过、请求失败或 Claim 释放重算。
- F18 截断掉的映射视为"B 未纳入"，不参与静态抑制，docker fb 保留既有资格。

### 7.4 链级 Claim 与三层状态（已冻结语义）

- **Claim 状态（链级）**：`Reserved`（某 Chain 取得 Identity 所有权，尚无 Attempt 越过发送边界）/ `Dispatched`（该 Chain 至少一个 Attempt 已越过发送边界，不再允许其他 Chain 接管）/ `Released`（无任何 Attempt 越过边界而彻底放弃，可释放）。
- **Attempt 状态（单次物理请求级）**：`Prepared` / `Dispatched`（已越过发送提交边界，R 正式消耗）/ `Aborted`（提交前取消或失败，不耗 R）。
- **Chain 生命周期**：`Open`（允许注册新 Attempt）/ `Closing`（不再接受新注册，等待已注册退出）/ `Closed`（所有已注册 Attempt 结束）。
- 同链（同 `OwnerChainID`）多个合法 Attempt 共享一个 Claim、允许并发 → **保住 3.5.16 A 站内多 Source 并发能力**；不同 Chain 对同一 Identity 原子竞争同一 Claim（只一个取得发起权）。不同 Identity 独立竞争，不全局串行。
- Claim 记录持有者 `OwnerChainID`（ChainID 不进 ClaimKey）。`fetchRace` 的 `atomic.Bool` 仅作语义参考，**不指定数据结构复用**；是否可复用由 17a 代码审查决定。

### 7.5 发送门控、取消仲裁与 R 两阶段（已冻结语义）

- **发送界标**：`Reserved → Dispatched` 在调用 `g.cli.Do(req)` **之前**的发送门控临界区完成。`Dispatched` 表示请求已越过**本地发送提交边界、进入 HTTP Client 执行阶段**——不等于网络字节已到达上游。此刻起 R 正式消耗、Claim 不可回滚、其他 Chain 不能再取得该 Identity 的 Claim；此后即使 `Do` 返回 `context canceled`、网络错误等均不返还 R。
- **取消仲裁（统一线性化点）**：
  - 本地主动取消：先经过发送门控并在门控内标记取消，再调用 CancelFunc；与 Attempt 的 Dispatched 提交在同一同步机制下竞争。
  - 外部 Context（如客户端断开）：不经过本地状态机；在门控内 `cli.Do(req)` 前检查 `ctx.Err()`，**以该检查结果为仲裁点**——观察到取消则取消胜出（Attempt Aborted、无已提交 Attempt 时 Claim 才释放）；未观察到则发送提交胜出；检查之后发生的取消不回滚提交。不得虚构锁与 Context 之间的同步关系。
  - 禁止出现"Claim 已 Released 但请求仍进入 `Do`"。
- **R 两阶段**：`ReserveR`（原子预留，参与并发预算控制，**不算正式消耗**）→ 门控内取消则**释放预留**（撤销占位，不是返还）→ 未取消则 `CommitR`（与 Attempt Dispatched 一起完成，**正式消耗**）→ `cli.Do` 后无论结果不返还。`ReserveR` 成功不等于已消耗；只有 `CommitR` 才是消耗、才不可返还。

### 7.6 Claim 释放与 Attempt 计数（已冻结语义）

- Chain 关闭后**禁止注册新 Attempt**。以下操作受同一同步门控保护：注册 Attempt（须 Open，活跃计数+1）、Attempt 提交 Dispatched（检查取消，更新 Attempt/Claim，提交 R）、提交前 Aborted（活跃计数-1）、Chain 开始关闭（Open→Closing）、Claim 释放判定。

```
ReleaseClaim = ChainClosed ∧ ActiveAttempts=0 ∧ ¬AnyAttemptDispatched
```

  - `AnyAttemptDispatched` 是整条 Chain 生命周期内的**历史事实**，不因已提交 Attempt 完成/失败/取消而清零。
  - 所有 Attempt 都在提交前退出 → Claim 可释放；任一 Attempt 已提交 → Claim 不释放给其他 Chain；Attempt 1 正提交、Attempt 2 正清理时须由同一门控确定先后。
- **Attempt 结束幂等、只递减一次**（EOF、主动 Close、ctx 取消、错误返回可能多路径触发清理）。Dispatched Attempt 持续计数直到响应体读取结束、被关闭或传输路径确认退出；`cli.Do` 返回响应头**不递减**；Body 结束/路径退出才递减。无论最终成功、失败或取消，Claim 保持 Dispatched 不释放。
