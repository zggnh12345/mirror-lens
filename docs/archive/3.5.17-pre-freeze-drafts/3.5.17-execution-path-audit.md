## 0. 重大发现：Midfill 实际 fetch 调用链已定位（推翻历史假设）

历史底稿记「Midfill 实际请求发出点尚未定位、是否产生额外物理请求待核」。本次追踪**已定位并闭环**：

```
stream.go:672  onSlow（Body 读循环判慢）
   ├─ trySwitch(...)            watch.go:284  换源分支（判慢先试换源）
   └─ trySwitch 失败 → midFill  midparallel.go:37
        ├─ parPreflight(...)     parallel.go:587  探活每台源
        │    └─ probeTarget()    parallel.go:664
        │         └─ rangeReq()  parallel.go:671
        ├─ rangeReq(...)         midparallel.go:141  第 0 段
        └─ parChunk(...)         midparallel.go:239  其余段
             └─ rangeReq()       parallel.go:894
所有 rangeReq → g.cli.Do(req)   parallel.go:1001  ← 真实物理 HTTP 请求发出点
```

- `rangeReq`（parallel.go:984-1003）构造带 `Range: bytes=N-M` 的 GET，`withRegistryPolicy` 带认证策略，`g.cli.Do(req)` 实际发出。
- 结论：Midfill **确实发起额外物理 HTTP 请求**（Range 分片），有独立 `taskCtx=context.WithCancel(requestCtx)`（midparallel.go:178）、Source Lease 申请/转移/释放（134/154/165/309）、整份 SHA 校验（319-338）、CachePut（362）。
- 影响：Midfill 不能再记「请求点未定位」；它必须作为独立真实请求路径纳入统一 Attempt/R/G Lease/生命周期设计。其预算关系见 `3.5.17-budget-audit.md`。

同时澄清历史术语混淆：
- `midparallel.go:373 switch` 是 Go `switch` 语句（按 fail/ok 统计 reportSource），**不是换源判定**。
- `midparallel.go:331 failSrc` 是整份 SHA 校验失败后的归因记录（单源可归因，多源不猜），**不是触发换源的逻辑**。
- 真正的换源判定是 `trySwitch`（watch.go:284），它与 midFill 是并列分支：判慢先试换源，换源失败才走中途并行。
