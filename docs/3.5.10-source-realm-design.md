# 3.5.10 Source 自有 Realm 与认证隔离设计

**状态：** Draft，未冻结。本文只冻结问题边界和方案选择，不包含实现变更。
**基线：** 3.5.9 代码 `0d7708a`，验收文档 `1cdf6df`。
**目标读者：** 3.5.10 实现者、独立审查者、发布负责人。

## 1. 要解决的问题

3.5.9 已经证明：

- 官方 Host 可以完成多源候选、失败回退和缓存；
- 公共第三方 Source 能作为候选，但它的认证 Realm 不一定属于被代理的官方 Host；
- 典型失败是：

```text
public.ecr.aws 的 Source 探活失败：
认证 Realm 不在该 Host 的白名单内：
public.ecr.aws 的 Realm https://m.daocloud.io
```

这不是“公共源 Manifest 不可达”，而是当前 Realm 模型只按 `repo_host` 查全局白名单。`m.daocloud.io` 作为 `public.ecr.aws` 的 Source 时，Challenge 指向 Source 自己的认证端点，而 `public.ecr.aws` 的内置白名单没有它。

同一问题影响：

- `registry.gitlab.com` 的 DaoCloud 类 Source；
- 其他使用自有认证端点的公共镜像站；
- 将来接入的私有 Registry 镜像。

3.5.9 不应通过关闭 Realm 校验、放宽全局白名单或把 `m.daocloud.io` 写进所有 Host 的默认表来解决。那会把“某个 Source 的认证端点”变成“所有 Source 都可信的 Realm”，扩大凭据泄露面。

## 2. 现有代码事实

以下结论均来自当前代码，不是推测。

### 2.1 Source 没有 Realm 字段

`internal/store/store.go:26-70` 的 `Source` 只有 `BaseURL`、`RepoHost`、`RegistryCap`、`RegistryPath` 等字段，没有 Realm 或认证端点字段。

`internal/api/api.go:619-625` 新增 Source 时只写 `BaseURL`、名称、`RepoHost` 和能力初值，不接受 Realm 配置。

`internal/store/schema/canonical.sql:31-70` 的 `sources` 表也没有 Realm 列。

### 2.2 Probe 使用全局 Host 白名单

`internal/probe/registryhost.go:31-43` 的 `RegistryHostProbe` 带的是：

```go
// Realms 是 Host → Realm 白名单；为空时用 v2auth.DefaultRealms()。
Realms map[string][]string
```

`internal/probe/registryhost.go:182-186`：

```go
realms := p.Realms
if realms == nil {
    realms = v2auth.DefaultRealms()
}
auth := v2auth.New(newClient(p.Timeout), realms)
```

`internal/runner/hostprobe.go:417-418` 把 Runner 级 `Realms` 原样传给每次探测。也就是说，探活没有 Source 级 Realm 输入。

### 2.3 Gateway 的 Realm 判定也是全局的

`internal/gateway/registryauth.go:181-196`：

```go
var defaultRealmAuth = v2auth.New(nil, nil)

func realmAllowedForHost(host, scheme, raw string) bool {
    ...
    if strings.EqualFold(u.Host, host) && strings.EqualFold(u.Scheme, scheme) {
        return true
    }
    return defaultRealmAuth.RealmAllowed(host, u) == nil
}
```

`internal/gateway/registryauth.go:142-178` 的 `bearerTransport` 对整个上游统一处理 401，没有 Source 参数。

### 2.4 Gateway 的 Token 缓存没有 Source 维度

`internal/gateway/registryauth.go:21-35` 是全局 `tokenCache`。

`internal/gateway/registryauth.go:68-70` 的 key 是：

```go
key := realm + "|" + service + "|" + scope
```

没有 Source ID、凭据代次或 Source base host。两个不同 Source 只要 Realm、Service、Scope 相同，就会共享 Token。

### 2.5 Probe 认证不缓存 Token，Gateway 缓存

`internal/v2auth/auth.go:1-7` 明确写着每次资源请求独立走 401 → Challenge → Realm → Token，不缓存 Token。

`internal/v2auth/auth.go:202-233` 的 `Do` 每次 401 都重新换 Token；`auth.go:279-331` 的 `token` 只负责一次 Token 请求。

Gateway 另有一套 `tokenCache`。因此 3.5.10 不能只改 `v2auth`，否则探活和 Gateway 会出现两套 Realm 语义。

## 3. 设计目标

1. Realm 判定从“Host 全局表”变成“按 Source 计算的策略”。
2. Source 可以显式声明自己的认证端点，但只能由管理员配置。
3. 默认不扩大任何现有权限：旧 Source 的空配置行为与 3.5.9 相同。
4. 探活和 Gateway 使用同一个策略函数，不能出现“探活通过、Gateway 拒绝”或反过来的分叉。
5. Token 缓存按 Source 和凭据代次隔离，Source 禁用、删除或轮换凭据后不能复用旧 Token。
6. 所有 Realm 请求继续经过现有 SSRF/DNS/IP Guard；不允许任意重定向。
7. 失败关闭：策略解析失败、Source 身份不一致、Realm 非 https、带 userinfo、通配符非法时拒绝，不降级为放行。

## 4. 非目标

- 不实现 OAuth、OIDC、云厂商 IAM 或新的凭据类型。
- 不支持在 Challenge 中动态学习 Realm。
- 不支持用户级凭据或把不同用户的 Token 混用。
- 不改变官方 Host 已有的 Realm 行为。
- 不把“八个 Host 都有公共源”作为 3.5.10 的发布条件。
- 不在本阶段接入 CGR 的 401 认证；那是另一项认证能力。

## 5. 方案：Source Realm Policy

### 5.1 策略输入

每个 Source 计算一份 `RealmPolicy`：

```text
SourceID        int64
RepoHost        string
BaseURL         string
RealmExtra      []string   // 管理员显式配置，可为空
CredentialsGen  int64
```

`BaseURL` 必须是规范化后的 https URL；测试环境的 http 只能通过测试夹具注入，生产装配拒绝。

### 5.2 允许集合

对某个 Source，允许的 Realm 是以下集合：

```text
A. Source 自身的 scheme + host
B. 如果 Source 是官方源（BaseURL host == RepoHost），沿用 DefaultRealmsFor(RepoHost)
C. RealmExtra 中显式配置的 scheme + host
```

规则：

- A 是默认能力。一个 Source 的 Challenge 指向自己的认证端点，不应被“Host 全局表”误杀。
- B 只对官方源生效，保持 3.5.9 行为；第三方 Source 不能自动继承官方 Realm。
- C 只允许精确 `https://host[:port]`，不接受通配符、路径、userinfo、查询参数。
- 不允许 `http://`；不允许 IP literal，除非以后单独设计自建源策略。
- 匹配只比较 scheme + host（含端口），路径仍按 Challenge 原样使用，但必须再经过 URL 规范化和 Guard。
- 不允许“Challenge 给什么就信什么”。A/B/C 之外一律 `ErrRealmDenied`。

这样 `m.daocloud.io` 作为 `public.ecr.aws` 的 Source 时：

```text
repo_host = public.ecr.aws
base_url  = https://m.daocloud.io
允许 A    = https://m.daocloud.io
```

不需要把 `m.daocloud.io` 写进 `public.ecr.aws` 的全局表，也不会让其他 Host 的 Source 自动信任它。

### 5.3 为什么不把官方 Realm 自动给第三方 Source

如果第三方 Source 的 Challenge 指向 `https://public.ecr.aws/token`，而请求最终仍发给第三方 Source，官方 Token 会被送到第三方。这不是当前 ECR 场景需要的，也会扩大凭据面。

因此：

- 官方源保留官方 Realm；
- 第三方源默认只信自己的认证端点；
- 确需跨 Host 的第三方源，必须由管理员写 `RealmExtra`，并在审计日志中记录。

### 5.4 Probe 与 Gateway 共用

新增共享函数，例如：

```go
func PolicyForSource(src Source) RealmPolicy
func (p RealmPolicy) Allowed(realm *url.URL) error
```

- `probe.RegistryHostProbe` 从 `Realms map` 改为接收 `RealmPolicy`（或 Source 快照），不再回退到 `DefaultRealms()`。
- `gateway.bearerTransport` 从全局单例改为按 Source 构造，或携带 `SourceID + RealmPolicy` 的 transport 包装。
- `v2auth.Authenticator` 的 `RealmAllowed` 接受策略而不是裸 map；保留 `New(client, nil)` 给官方默认路径，但 Source 路径不得使用全局默认。

## 6. Token 缓存与失效

### 6.1 Key

Gateway Token 缓存的 key 改为：

```text
sourceID | credentialGeneration | realmSchemeHost | service | scope
```

官方源也带 `sourceID=0`（或明确的 official 标识）和 `credentialGeneration`，不能再用裸 `realm|service|scope`。

### 6.2 TTL 与容量

保持现有行为：

- 使用 `expires_in`；
- 无 `expires_in` 时默认 60s；
- 剩余 TTL 大于 45s 时提前 30s 过期；
- 条目上限 256，先清过期，再按到期时间淘汰。

### 6.3 失效

- Source 禁用、删除、`BaseURL`/`RepoHost` 修改、`RealmExtra` 修改、凭据轮换：递增 `CredentialsGen` 或删除该 Source 的缓存条目。
- 不允许通过“清空全局缓存”实现失效，避免影响其他 Source。
- 旧 generation 的 in-flight Token 响应不得写回新 generation；写入前比较 generation。
- 探活不缓存 Token，不受此缓存影响；但它的 Realm 策略必须与 Gateway 相同。

## 7. Schema 与 API

### 7.1 Schema

建议新增一列，避免新表：

```sql
ALTER TABLE sources ADD COLUMN realm_extra TEXT NOT NULL DEFAULT '';
```

存储为换行分隔的精确 Realm 列表，空串表示无额外 Realm。选择单列的理由：

- 绝大多数 Source 为空；
- 不需要按 Realm 查询；
- 避免新增表和 join；
- 迁移和回滚简单。

代价：

- 需要在 Store/API 层解析和校验；
- 不能直接在 SQL 里按 Realm 建索引；
- 列表长度必须限制（例如 8 条、每条 255 字符）。

Canonical Schema 的 hash/version 必须随列变更更新；旧库必须走离线迁移，不在 `store.Open` 时补列。这是 3.5.5 以来的硬约束。

### 7.2 API

- 新增/编辑 Source 时可传 `realm_extra`，只有管理员/受信 API 可写。
- 普通面板若暂无字段，保持只读或不显示；不能默认写入。
- 校验失败返回 400，错误信息只写规则，不回显完整 Challenge 或 Token。
- 修改 `realm_extra` 触发 Source 认证策略失效和一次受控重探；不直接清零 `registry_cap`，避免把“配置变更”伪装成“能力失败”。

## 8. 安全不变量

1. 任何 Realm 不在 A/B/C 集合内 → 拒绝，且不请求该 Realm。
2. `http://`、userinfo、通配符、非精确 host → 拒绝。
3. 第三方 Source 不得自动获得官方 Host 的 Realm 集合。
4. 官方 Source 的默认行为与 3.5.9 一致。
5. Token 请求必须走现有 `safehttp` Guard；重定向不能绕过 Guard。
6. Token 缓存 key 必须包含 Source 和凭据代次；不同 Source 不共享。
7. Source 禁用/删除/凭据轮换后，旧 Token 不能继续命中。
8. 日志只记录 `source_id`、`repo_host`、`realm_host`、状态码；不记录 Token、Authorization、用户名密码或完整查询串。
9. 探活与 Gateway 对同一个 Source 使用同一个策略对象；两侧测试必须能互相复现。
10. 策略解析失败时拒绝，不退回全局白名单。

## 9. 实施阶段

### Phase A：设计冻结

- 本文经独立审查，确认 A/B/C 集合和 token key；
- 确认 `realm_extra` 单列方案；
- 确认不修改官方 Host 默认表；
- 未签字前不写代码。

### Phase B：Schema 与策略

- 新增 `realm_extra` 列、迁移和 schema hash；
- 实现 `RealmPolicy`、URL 校验和错误类型；
- 单元测试覆盖 allow/deny 边界；
- 旧 Source 空配置行为不变。

### Phase C：Gateway

- `bearerTransport` 按 Source 构造；
- Token cache key 加 SourceID + generation；
- 失效路径接入 Source 生命周期；
- 回归测试：官方源、公共源、同 Realm 双 Source、代次变化。

### Phase D：Probe

- `RegistryHostProbe` 接收 Source 策略；
- HostProbe runner 从 Source 读取策略，不再传全局 map；
- 探活和 Gateway 使用同一 allow 判定；
- 失败路径不写 `cap=1`、不解 Guard。

### Phase E：外部验收

- ECR：`m.daocloud.io` Source 探活 cap=1；候选 Blob 命中或回退官方；
- GitLab：先解决官方匿名 401，再验证 Source 与回退；
- PKG：没有同 Host 公共源，只能用官方上游故障边验证回退代码路径，标记“公共源缺失”；
- CGR：官方匿名 401；在认证能力明确前不纳入发布阻塞。

## 10. 验收断言

至少包含：

1. `m.daocloud.io` 作为 `public.ecr.aws` Source：Realm `https://m.daocloud.io` 允许；`https://evil.example` 拒绝。
2. 第三方 Source 的 Challenge 指向官方 `public.ecr.aws`：默认拒绝；写入 `realm_extra` 后才允许。
3. 官方 `gcr.io` Source：原有 `https://gcr.io`、`https://storage.googleapis.com` 仍允许。
4. 官方 `registry.gitlab.com` Source：`https://gitlab.com` 仍允许。
5. 两个 Source 使用相同 realm/service/scope：缓存条目不同；一个 Source 的 Token 不命中另一个。
6. Source 凭据 generation 从 N 到 N+1：旧 key 不命中；旧 in-flight 结果不写入新 generation。
7. Source 禁用/删除：该 Source 的缓存条目不可用；其他 Source 不受影响。
8. Realm 带 userinfo、http、通配符、非法端口：全部拒绝，且不发出 Token 请求。
9. Probe 与 Gateway 对同一组输入给出相同 allow/deny。
10. 所有拒绝路径都不写 `cap=1`、不解 Guard、不把失败伪装成官方成功。

断言必须分别验证 allow 与 deny，不能用“成功请求 200”代替 Realm 拒绝测试。

## 11. 仍开放的问题

这些问题需要独立决策，不能靠实现时临时放行：

1. **GitLab 官方匿名 401**：Realm 策略解决的是 Source 认证端点，不解决官方 `registry.gitlab.com` 匿名拉取被拒。需要确认 GitLab 的匿名 Token 流程或凭据策略。
2. **CGR 官方匿名 401**：是否支持其认证方式，还是明确列为外部依赖限制。
3. **PKG 公共源缺失**：没有同 Host 第三方源；只能验证官方回退代码路径，不能声称公共源覆盖。
4. **`realm_extra` 的管理入口**：是否只在受信 API/CLI 开放，还是面板也开放；无论哪种，都必须审计。
5. **IP literal / 自建源**：本设计默认拒绝；如果自建源需要，另开策略，不与公共源混用。

在上述问题关闭前，3.5.10 设计不能标记为 frozen，也不能开始 Phase B 的实现。
