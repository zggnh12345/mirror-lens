## 0. 任务目标与交付边界

### 0.1 核心目标

在不破坏现有域名 Registry 请求与认证行为、Blob 内容复用能力、凭据数据和数据库结构的前提下，完成自定义 Registry Endpoint 支持。Manifest 存量缓存因 Key 格式变更而发生的一次性逻辑失效属于本版本明确接受并必须披露的升级影响，不得笼统承诺“现有缓存全部复用”：

1. 自定义 Registry 节点支持 `HTTP` 和 `HTTPS`。
2. 支持域名、IPv4、IPv6。
3. 支持显式自定义端口，并正确处理协议默认端口。
4. 对公网 IP 执行显式准入；不得因为地址可解析为 IP 就自动放行。
5. 所有请求继续经过现有 `safehttp` 安全链路，不得新增 SSRF、DNS Rebinding 或重定向检查旁路。
6. RegistryIdentity、RegistryEndpoint、SourceEndpoint、Origin 与 Authority 严格分离，Manifest CacheKey 身份只取规划期 RegistryEndpoint，避免同一 Host 不同协议或端口之间发生 Manifest 缓存串味。
7. 保持现有 Blob 内容寻址缓存和 Cache Epoch 不变；Manifest Key 改为完整 Endpoint 身份后，所有既有域名 Registry 的旧格式 Manifest 缓存条目均不会命中新 Key。每个尚未以新格式重建的 Manifest Key，在升级后首次被请求时都必然 Miss、回源并建立新格式缓存。
8. **不修改数据库 Schema，不迁移数据库，不重建数据库，不转换现有凭据格式。**
9. 提供可回滚的应用版本升级；不把“数据库兼容”误称为“单实例严格零停机”。

### 0.2 本版本必须完成

- Registry Host 对域名、IPv4、IPv6 的规范化与准入处理。
- 自定义 Registry 节点 UI/API/配置链路支持 HTTP、HTTPS、IP 和自定义端口。
- Endpoint、Authority、Origin、RegistryIdentity 的统一语义。
- TLS 探测和证书验证使用正确的 Endpoint 端口及 Host 验证名。
- HTTP/HTTPS 重定向、Token Realm、凭据转发策略。
- Manifest 缓存按完整 Endpoint 隔离，Blob 缓存保持 Digest Key。
- 全链路安全检查、回归测试、真实环境验收和性能对照。
- 文档、测试证据、发布产物和回滚材料归档。

### 0.3 明确不做

- 不修改数据库表结构、索引、约束或 Schema Version。
- 不迁移或重加密现有凭据，不修改 AEAD AAD 格式。
- 不把端口并入 Registry Host 身份，不做端口级凭据隔离或 Host 状态拆分。
- 不扩展专用云凭据 Provider 的 `hostProfiles` 名单。
- 不改变 `DefaultRealmsFor(IP)` 的默认信任行为；IP 不自动获得静态 Realm 信任。
- 不递增 Cache Epoch，不执行全量缓存清理，不清空 Blob 缓存。
- 不重写现有代理协议、下载调度或无关的 Registry 核心架构。
- 不增加 HTTPS 失败后自动降级 HTTP 的能力。
- 不把本功能扩展成任意 URL 抓取或开放代理。
- 不默认放行私网、回环、链路本地、组播或保留地址。

### 1.3 已知风险点必须复核

取证至少验证以下现存行为是否与实际代码一致：

1. `checkHost()` 存在拒绝冒号和 IP 字面量的逻辑；IPv6 不能再由简单的冒号判断误拒绝。
2. 即使删除 IP 拒绝，`Allowed()` 的域名名单仍可能拒绝公网 IP；必须处理第二道准入，不得只改第一处。
3. `safehttp` 已实现 IP 地址检查、实际拨号 IP 检查和重定向检查；本次必须复用，不得旁路。
4. TLS 探测当前若固定使用 443，必须改为使用实际 Endpoint 端口；HTTP Endpoint 不得执行 TLS 握手探测。
5. `verifyChain` 对 IP 必须执行 IP SAN 验证，不能用 DNS SAN 替代。
6. `RedirectPolicy`、`recheckRedirectPolicy`、`registryauth` 等位置若使用 `URL.Host` 直接比较，必须审查其是否错误地把端口混入 Host 身份或漏掉 Origin 差异。
7. `recheckRedirectPolicy` 不得因为跨 Host/Origin 清除认证头后就提前跳过该跳的 Policy 和 `safehttp` 检查。
8. `DefaultRealmsFor(IP)` 保持空结果；`hostProfiles` 保持专用 Provider 现有名单。
9. 必须专门回归 `identity.go` 中当前 HTTPS-only 限制的真实作用域；允许矩阵中的 HTTP Token Realm 不得改变普通 Redirect 的 HTTPS-only 语义。
10. `RegistryHostProbe{BaseURL, Host}` 以及 Adapter 的 `Scheme` 等现有模型应优先复用；不得在没有证据的情况下重建一套平行架构。
11. Manifest Key 当前若含有端口，必须确认修改为规范化 Endpoint Key 后仍完整保留 Scheme、Host 和有效端口；不能误用不含端口的 RegistryIdentity。
12. 必须核实旧格式 Manifest Key 到新格式 Manifest Key 的实际字符串变化、查询入口和命中逻辑，明确既有域名 Registry 的每个旧 Manifest Key 都不会命中新 Key；不能只把该影响归因于新增 IP Registry。

**G0-2：Token Realm 与普通 Redirect 的机制边界（最高安全优先级）**

- 分别追踪 Registry 发起的 Token Realm 请求和 HTTP Client 普通重定向的调用链、策略入口、认证头处理及 `safehttp` 检查。

- 用 2.5 的矩阵逐项映射到实际函数：HTTP Registry + 同 Host HTTP Realm、HTTP Registry + 同 Host HTTPS Realm、HTTPS Registry + 同 Host HTTPS Realm、HTTPS Registry + 同 Host HTTP Realm、跨 Host Realm；普通 Redirect 则按完整 Origin 独立判断。
- 证明允许 HTTP Realm 不会放宽普通 HTTPS→HTTP Redirect，不会让跨 Origin Authorization 泄漏，也不会跳过每跳 Policy 和 `safehttp` 检查。
- 若两套机制在现有实现中无法安全分离，判定 `BLOCKED`，提交最小范围设计，不得通过全局放宽 HTTPS-only 来绕过。

**G0-3：真实 IPv4/IPv6 与公网验收环境清单**

**G0-4：Manifest Key 变更与性能基线口径**

- 从当前代码提取旧版与候选新版 Manifest Key 的真实样例，覆盖域名默认 HTTPS、显式 `:443`、HTTP、非默认端口及 IPv6。
- 确认旧格式 `docker:manifest:registry.example.com/repo:tag|accept=…`（epoch=0）与新格式 `docker:m:1:https://registry.example.com:443/repo:tag|accept=…`（epoch>0）不相等，且当前读路径没有旧 Key 兼容查找；如代码事实不同，必须按实测修订说明。**不存在 `docker:m:0:` 前缀**——epoch=0 走 `docker:manifest:`，`docker:m:<epoch>:` 要求 epoch>0；3.5.24 目标格式前缀冻结为 `epoch<=0 → docker:manifest:`、`epoch>0 → docker:m:<epoch>:`（见 §2.9），只改变 Rest 部分。
- 明确升级后所有既有域名 Registry 的旧格式 Manifest 缓存均无法直接命中新格式 Key；对每个尚未重建的新 Manifest Key，其升级后第一次请求都会回源 Miss 并重建该 Key 记录。不能把影响误写成“每个 Registry 只回源一次”。旧记录不主动清空，按原 TTL/GC 回收。Blob Digest Key 和 Cache Epoch 不变，Blob 热缓存仍可复用。
- 冻结 3.5.23 与 3.5.24 热缓存测试方法：两个版本分别先完成自己的 Manifest 缓存预热，再执行热缓存测量。3.5.24 升级后的首次回源/重建请求单独记录为一次性缓存重建成本，不混入热缓存命中性能样本；预热完成后再测候选热缓存。

## 2. 设计冻结

### 2.1 五个核心概念

必须在代码、测试和文档中统一使用以下概念，不得混为一个 `host` 字符串：

| 概念 | 定义 | 示例 |
|---|---|---|
| `RegistryIdentity` | 逻辑 Registry 身份（规范化 Host），不含协议和端口；用于 repo_host、策略 Host、凭据 Host 和状态关联。**IP 字面量不作为示例**——若配置目标本身是 IP，它表示“连接地址”，不能由此推导出一个独立的逻辑 Registry Host 身份 | `registry.example.com` |
| `RegistryEndpoint` | 请求规划期的逻辑 Registry 目标（scheme://host:port）；Scheme + CanonicalHost + EffectivePort，用于 Manifest CacheKey。来源链见 §4.6 与 §5.6：Scheme 取 `Adapter.Scheme`（当前 HTTPS）、`CanonicalHost = registryhost.Normalize(ParsedPath.Host)`、`EffectivePort` 按 Scheme 推导（HTTPS→443/HTTP→80）；唯一构造点在 `rememberedHost`/Fallback/Source 调度之前。当前不提供逻辑 Registry 显式非默认端口输入能力 | `https://registry.example.com:443` |
| `SourceEndpoint` | 调度选出的实际镜像节点连接地址（原 `Endpoint`）：Scheme + CanonicalHost + EffectivePort，对应 `sources.base_url`，与逻辑身份分开 | `https://mirror.example.com:5443` |
| `Origin` | 实际请求及重定向的来源身份：Scheme + CanonicalHost + EffectivePort，用于凭据转发与完整同源判断 | `https://registry.example.com:443` |
| `Authority` | CanonicalHost + EffectivePort（含必要 IPv6 方括号），是地址序列化的组成部分，不是独立业务身份 | `registry.example.com:443`、`[2001:db8::10]:5000` |

**身份命名统一（与最终版设计冻结稿 §1 对齐）**：设计冻结稿早期的 `Endpoint`/`Authority` 命名在这里统一为——`SourceEndpoint`（=本节 `Endpoint`，调度选出的实际回源连接地址）、`Origin`（=本节 `Origin`）、`Authority`（CanonicalHost+EffectivePort）；`RegistryEndpoint` 为正式核心概念，专指请求规划期确定的逻辑目标地址（scheme://host:port），不代表调度实际连接节点。`RegistryEndpoint` 与 `Origin` 可复用相同字段结构和规范化算法，但不得混用业务来源、比较语义和构造入口——Manifest CacheKey 只能由规划期 `RegistryEndpoint` 构造，不得复用 `Origin` 业务对象或同源比较函数。UI 必须明确区分**逻辑 Registry Host（用户配置的镜像目标）**与**实际连接地址（调度选中的 SourceEndpoint，可能是 IP）**；连接地址是 IP 时，不得自动推导出一个逻辑 Registry Host，也不得据此扩展其凭据/Realm 资格。

> 本节示例中的 `2001:db8::10`/`203.0.113.10` 仅为文档保留地址，用于格式与拒绝测试，不构成 RegistryIdentity 示例，也不代表真实验收。

规则：

- RegistryIdentity 不得包含 Scheme 或端口。
- Endpoint 必须包含有效端口。
- Authority 不含 Scheme。
- Origin 必须同时考虑 Scheme、规范化 Host 和有效端口。
- 任何比较都必须明确使用 Identity、Authority 还是 Origin；禁止使用一个含混的 `sameHost` 语义覆盖全部场景。

### 2.2 统一规范化

必须提供集中、可复用、带单元测试的地址解析和规范化实现。

1. Scheme 转为小写，只接受 `http`、`https`。
2. Host 通过标准库结构化解析；IP 使用 `net/netip`，URL/端口使用 `net/url`、`net.SplitHostPort`、`net.JoinHostPort` 等标准方式。
3. 禁止用 `strings.Split(host, ":")` 等字符串切割处理 IPv6 或 Host/Port。
4. IPv4、IPv6 和 IPv4-mapped IPv6 使用统一规范化语义；IP 比较遵循 `safehttp` 的 `Unmap()` 规则。
5. HTTP 缺省端口为 `80`，HTTPS 缺省端口为 `443`。
6. 显式默认端口和省略端口规范化为同一个 Endpoint：`http://host` 等价于 `http://host:80`，`https://host` 等价于 `https://host:443`。
7. 非默认端口必须保留。
8. IPv6 的 Authority/URL 序列化必须使用方括号。
9. 域名大小写、尾点、IDNA 等处理应沿用项目既有域名规范化规则；如需调整必须通过回归测试证明不改变既有允许/拒绝边界。
10. 非法 Scheme、非法端口、端口越界、缺失 Host、带歧义的裸 IPv6 URL 必须明确报错，不得猜测用户输入。

### 2.3 自定义 Registry 节点 UI/API

新增或编辑自定义 Registry 节点必须具备明确的协议配置能力：

- 协议选择：`HTTPS` / `HTTP`。
- Host 输入：域名、IPv4 或 IPv6。
- 端口输入：可选；留空时按协议使用默认端口。
- 认证配置：继续使用现有凭据配置和存储机制。
- HTTP 明文警告：选择 HTTP 时，在保存前和节点详情中明确提示认证信息与传输内容可能以明文传输。
- 编辑已有节点时，旧配置必须按既有默认行为解释，不能静默改变原有 HTTPS/默认端口语义。

UI 可以使用协议、Host、端口三个明确字段；内部 API/持久化优先复用现有 Endpoint/BaseURL 等字段。必须避免 UI、API、Adapter 各自拼接不同地址。

**两个独立输入必须分离（冻结；属需实现目标，不得表述为现状已支持）**：

- 输入 A — 逻辑 Registry 身份（`RegistryIdentity`）：UI 提供独立的"归属 Registry"选择项（从允许的 Registry Host 中选，如 `ghcr.io`），经 API `host` 字段 → DB `repo_host`，用于 repo_host、策略 Host、凭据 Host，并作为请求规划期 RegistryEndpoint 的逻辑 Host 输入；RegistryIdentity 本身不构成完整 Manifest CacheKey。
- 输入 B — 实际连接地址（`SourceEndpoint`）：由协议 + Host + 端口组成，经 API `url` 字段 → DB `sources.base_url`，仅用于出站连接。
- IP（或其他无法表明逻辑身份的）连接地址不得自动推导出 `RegistryIdentity`；未显式选择 A 时不得静默默认到 `docker.io`（现状 `api.go:642-644` 的默认行为属待修缺陷）。当前 UI POST 仅提交 `url`/`name`（`index.html:1416`）、不提交 `host`，输入 A 的入口与传递必须在实现中补齐，并纳入 §4.3 验收清单。

**HTTPS 应作为新增节点的默认选择。** 用户明确选择 HTTP 才启用明文 Endpoint。HTTP 警告不能只放在帮助文档中，必须出现在实际配置流程。

节点详情应能准确显示规范化后的 Endpoint，例如：

- `https://registry.example.com`
- `http://203.0.113.10:5000`
- `https://[2001:db8::10]:5443`

UI 不得把端口显示成 RegistryIdentity 的一部分；身份与连接地址应有明确区分。

### 2.4 IP 准入与安全边界

1. 保留现有域名 `defaultHosts` 和 `IsArtifactRegistry` 等准入策略。
2. 公网 IP 必须通过管理员明确创建/登记的自定义 Registry 节点进入准入流程；不得因 `net.ParseIP()` 成功而直接 `return nil`。
3. 必须使用现有自定义节点持久化/登记路径作为显式准入依据。若取证发现当前没有可安全复用的登记来源，停止该项实现并提交设计阻塞报告；不得擅自引入新的数据库表、全局配置开关或开放式 IP 放行规则。
4. 私网、回环、链路本地、组播、未指定及保留地址继续由 `safehttp` 拒绝。该版本不通过关闭 `safehttp` 或新增旁路来支持内网 IP。
5. 对 IP 字面量以及 DNS 解析结果，必须在实际 Dial 阶段再次校验目标 IP，防止 DNS Rebinding。
6. 所有 HTTP 请求、TLS 探测、Token Realm、Blob 下载、重定向和重试路径都必须受同一安全边界约束。
7. 不允许通过 URL 用户信息、IPv4-mapped IPv6、异常端口表示、重定向或代理链绕过检查。
8. 自定义节点登记不等于允许任意请求 URL；请求目标仍必须匹配已授权的 Registry Endpoint/Policy。

### 2.5 HTTP/HTTPS 传输策略

本节严格区分三个 Scheme，不得混同：RegistryEndpoint.Scheme 来自 `Adapter.Scheme`（规划期逻辑身份，默认 HTTPS）；SourceEndpoint.Scheme 来自 `sources.base_url`（用户可配 HTTP/HTTPS，实际节点连接）；Origin.Scheme 是实际请求及重定向的来源身份。三者职责分离、互不补位。

#### SourceEndpoint / 实际上游传输策略（用户可配置）

- 管理员为自定义镜像节点明确配置 HTTP，即视为明确选择明文传输；该选择只改变 SourceEndpoint 实际连接协议与节点地址。允许该 Registry 使用其配置的凭据，包括 Basic Auth，但 UI 必须明确警告。
- 管理员未明确配置 HTTP 时，SourceEndpoint 默认 HTTPS。
- HTTPS 请求不得自动降级到 HTTP。
- HTTP 到 HTTPS 可以作为受控升级，但不得自动把原 Origin 的 Authorization 头复制到新 Origin。
- 不得因 HTTP 测试方便而在全局关闭 TLS 证书验证。
- **协议隔离（P1-2）**：用户把 SourceEndpoint 从 HTTPS 切到 HTTP，不得改变 `Adapter.Scheme`、RegistryEndpoint 逻辑身份或 Manifest CacheKey；Authorization 不得跨 Origin 泄漏；Realm 授权与普通 3xx 重定向的完整 Origin 校验仍分别独立有效（见 §4 协议隔离回归测试）。

#### Registry Endpoint（规划期逻辑身份，非用户传输配置）

- RegistryEndpoint.Scheme 取 `Adapter.Scheme`（`registryadapter.New()` 初始化为 HTTPS），不来自用户 SourceEndpoint 的 HTTP/HTTPS 选择，也不来自入站 `r.TLS`/`r.Host`。
- RegistryEndpoint 用于 Manifest CacheKey 逻辑身份；SourceEndpoint 的 HTTP/HTTPS 切换不改变该身份。

#### Token Realm 独立授权矩阵

Token Realm 与普通 HTTP 重定向是两套机制，必须分别实现和测试：

| Registry Endpoint | Token Realm | 结果 |
|---|---|---|
| HTTP | 同 Host、HTTP | 允许，受独立 Policy 和 safehttp 检查 |
| HTTP | 同 Host、HTTPS | 允许安全升级，受独立 Policy 和 safehttp 检查 |
| HTTPS | 同 Host、HTTPS | 允许，受独立 Policy 和 safehttp 检查 |
| HTTPS | 同 Host、HTTP | 拒绝，禁止 HTTPS 降级 |
| HTTP/HTTPS | **显式白名单 HTTPS 跨 Host**（lscr.io→ghcr.io、gcr.io→storage.googleapis.com、registry.gitlab.com→gitlab.com） | **允许（保留既有白名单能力）**，受白名单 Policy 和 safehttp 检查 |
| HTTP/HTTPS | **未配置的跨 Host** | **拒绝** |

**跨 Host 裁定（修复原“一刀切拒绝”）**：Realm 授权与 Token 3xx 重定向是两套独立机制，本节只针对 **Realm 授权**。保留既有显式白名单兼容——`DefaultRealms()`（`auth.go:151-165`）中的 lscr.io/gcr.io/gitlab.com 三组映射必须继续允许，并有 `TestRealmAllowed` / `TestBearerTransportAllowsGitLabRealm` 测试锁定；**不得把白名单允许扩展为任意跨 Host**，未配置跨 Host 一律拒绝。Token 3xx 重定向继续独立执行完整 Origin 限制，不因 Realm 白名单而放宽。

“同 Host”必须使用规范化后的 RegistryIdentity 比较，不能直接比较含端口的 `URL.Host`。

**实现边界：** 不得为了允许 HTTP Registry 的同 Host HTTP Token Realm，直接删除或全局放宽通用 HTTPS-only / Redirect 限制。必须把 Realm 授权判断落在 Realm 专属策略路径，把普通 Redirect 的完整 Origin、HTTPS 降级限制和逐跳安全检查保留在 Redirect 专属路径。若现有 `identity.go` 等共享检查点同时承担两种语义，必须先拆清调用上下文并用独立测试锁定边界，不能用一个全局布尔开关覆盖两种机制。

Realm 的凭据查找与授权判断必须分离：只有 Policy 明确授权的 Realm 才能查找和发送对应凭据。不能因为凭据 Map 中存在同一个 Host 的凭据，就推定任何端口、Scheme 或 Realm 都有权使用它。

本版本仍按 Host 共享现有凭据身份；同一 IP 不同端口不获得端口级凭据隔离。必须在文档和安全测试中明确这个既有模型边界。

#### 普通重定向的凭据策略

- 完整 Origin 相同，才可按现有规则保留认证头。
- Origin 变化（Scheme、Host 或有效端口任一变化）时，清除原 Authorization 等敏感认证头。
- 清除认证头不代表跳过重定向目标校验。
- 每一跳都必须重新执行 RedirectPolicy、目标 Endpoint/Host 准入和 `safehttp` 检查。
- 跨 Host 或跨端口不得因为“Host 看起来一样”而自动转发原认证头。
- Blob CDN 白名单继续沿用，但每个允许的目标仍须通过既有安全检查。

### 2.6 TLS 与证书校验

1. TLS 拨号目标使用 Endpoint 的真实 Host 和 EffectivePort。
2. TLS ServerName 和证书验证身份使用 CanonicalHost。
3. IP Endpoint 必须校验 IP SAN；只有 DNS SAN 的证书不得通过 IP 校验。
4. IP 作为 ServerName 时不得人为构造 DNS SNI；使用 Go TLS/X.509 的 IP 身份校验语义。
5. 自定义非默认 HTTPS 端口必须真实连接该端口，不能固定探测 443。
6. HTTP Endpoint 不执行 TLS 握手或证书探测。
7. TLS 验证失败必须按失败处理，不得静默跳过证书校验。
8. 测试必须覆盖 DNS SAN、IP SAN、错误 IP SAN、非默认端口及握手失败。

### 2.7 凭据与身份兼容

以下现有身份和格式保持不变：

- `source_host_caps(source_id, host)`。
- `source_realm_policy` 的 Host 维度身份。
- `registry_host_gen.host`。
- `registry_host_recovery.scope`。
- 凭据文件 `Hosts` 映射及其 AEAD AAD Host 绑定。
- 现有专用凭据 Provider `hostProfiles` 名单。

不得把端口拼接进以上 Host 身份字段。不得修改凭据加密格式或重写已有凭据。不得因支持 IP 自动给 IP 配置默认 Realm 或专用云凭据 Provider。

**IP 认证边界（冻结）**：

- 匿名 IP SourceEndpoint：仅支持“源即目标、无认证需求”且经管理员显式登记（`sources.base_url`）的回源场景；不得因地址可解析为 IP 自动放行；请求目标仍须匹配已授权 Endpoint/Policy。
- 逻辑 Registry 凭据复用条件：仅当请求身份为显式配置的逻辑 `RegistryIdentity`（非 IP 字面量）且目标匹配其已授权 Endpoint/Policy 时方可复用；IP 字面量身份不得自动继承逻辑 Registry 凭据，同一 IP 不同端口不做端口级凭据隔离。
- IP 字面量 Token Realm：`DefaultRealmsFor(IP)` 保持空结果（`internal/v2auth/auth.go:170-175`）；不支持从 IP 自动推导默认 Realm；`hostProfiles` 专用 Provider 名单不因支持 IP 而扩展。
- 不得自动扩展 IP 的默认 Realm 信任或专用云凭据资格（与 §0.3、§2.4 一致）。

### 2.8 数据库、单轨、单事务与无过渡态升级设计冻结

**本版本是应用程序升级，不是数据库升级。数据库升级路径只有一条：不升级数据库。** 3.5.24 不执行 Schema 迁移，因此不存在旧 Schema/新 Schema 并存、迁移中间态或双轨兼容阶段。

#### 2.8.1 数据库结构冻结

硬性约束：

1. 不增加、删除或修改数据库表、列、索引、约束、触发器及其他 Schema 对象。
2. 不改变 Schema Version，不写入新的迁移版本号或迁移完成标记。
3. 不新增、执行或隐式触发数据库 migration。
4. 不重建数据库、不复制到新数据库、不切换数据库文件、不清空业务数据、不迁移 Host 状态。
5. 不转换凭据格式、不修改 AEAD AAD、不重新加密既有凭据。
6. 自定义 Endpoint 的 Scheme/Port 必须使用取证确认的既有持久化载体；不得为了本次功能擅自增加 SQL 字段。
7. 如果现有持久化模型无法表达 Scheme 或端口，立即停止该功能实施并报告阻塞；不得自行增加 Schema，也不得偷偷把端口拼入 RegistryIdentity 或 Host 身份字段。
8. 升级前后必须生成可比较的 Schema 指纹、Schema Version、表/索引/约束清单和关键业务数据抽样证据。
9. 启动检查不得以“自动修复”为名执行 DDL、数据回填、数据清洗或迁移。
10. 不得通过启动时 `CREATE TABLE IF NOT EXISTS` 等隐式建表方式掩盖 Schema 不匹配；必须区分应用正常运行所需的只读检查与数据库结构变更。

#### 2.8.2 单轨原则

升级和运行期间只允许一条权威路径：

`3.5.23 停止 → 3.5.24 单版本替换 → 只读启动检查 → 3.5.24 正常运行`

禁止：

- 新旧版本同时连接并写入同一个生产数据库。
- 新旧 Schema 双轨、双版本兼容层或临时兼容表。
- 影子表、双写、数据同步、后台渐进迁移。
- 临时数据库/正式数据库双库切换。
- 先写新格式、再回填旧格式，或反向双写。
- 迁移失败后自动切换另一套数据库结构。
- 为兼容旧缓存而保留第二套数据库身份模型。
- 通过 feature flag 同时维护两套互相竞争的 Registry Identity/Endpoint 持久化语义。

不得把单轨误解为允许新旧程序短暂并行。单实例部署必须先停止旧进程，再启动新进程。若部署平台无法保证该顺序，必须先解决部署编排问题，不得带着双写风险继续升级。

#### 2.8.3 单事务原则

由于本版本没有数据库迁移，**不存在数据库迁移事务，也不允许人为制造一个迁移事务来执行无必要的数据改写**。

单事务约束适用于运行期确实需要原子完成的单个业务操作：

1. 一个逻辑业务操作若涉及多条相互依赖的数据库写入，必须在同一个数据库事务中完成。
2. 事务边界必须覆盖该操作的全部数据库变更；不能先提交一部分，再执行剩余写入。
3. 任意一步失败必须整体回滚，不得留下半完成状态。
4. 不得把一个逻辑操作拆成多个独立事务，依靠重试或后台补偿拼接成“最终一致”来替代本项目要求的原子性。
5. 不得在事务提交前向调用方报告成功，也不得在事务回滚后保留已生效的外部成功状态。
6. 不得在事务中执行网络请求、长时间探测或等待外部服务；先完成必要的外部校验，再以短事务提交本地状态，避免长事务锁住 SQLite。
7. 不涉及数据库写入的启动检查必须只读，不应为了“事务完整”而开启空事务或写入无意义标记。
8. 若代码审查发现本次功能必须新增数据库写入才能保存 Endpoint，则视为违反当前冻结边界，停止并重新提交设计裁定；不得自行将其包装成单事务后继续。

**重要边界：** 整个应用替换流程（停止进程、替换镜像、启动进程）不是数据库事务，不能声称由一个 SQL 事务覆盖。这里的“单事务”指单个逻辑数据库业务写入的原子性；本次升级本身没有数据库写入事务。

#### 2.8.4 启动前只读门禁

3.5.24 启动时必须先执行只读兼容性检查，至少包括：

- 数据库文件存在且可按当前部署权限读取。
- Schema Version 与 3.5.23 基线一致。
- 关键表、列、索引和约束与冻结指纹一致。
- 数据库完整性检查通过。
- 既有凭据能够按原格式读取/解密（不得输出秘密内容）。
- 关键 Registry Host 状态记录可读取。
- Cache Epoch 与升级前记录一致。

检查结果处理：

| 检查结果 | 启动行为 |
|---|---|
| 全部符合预期 | 允许正常启动 |
| Schema Version 不一致 | 拒绝启动，保留现场 |
| 关键 Schema 指纹不一致 | 拒绝启动，保留现场 |
| 数据库完整性异常 | 拒绝启动，不自动修复 |
| 凭据无法按旧格式读取 | 拒绝启用相关功能并按既有安全策略处理；不得重写凭据 |
| 数据库不可读或权限异常 | 明确报错，不创建空数据库替代 |
| 检查结果不确定 | 停止启动，不得按通过处理 |

启动检查不得自动执行 DDL、迁移、重建、数据回填、凭据重加密或 Cache Epoch 修改。

#### 2.8.5 可保证与不可保证的升级体验

可保证目标：

- 不需要数据库迁移。
- 不需要重建数据库或替换数据库文件。
- 不需要重新录入或转换现有凭据。
- 不需要清空 Blob 缓存。
- 不需要递增 Cache Epoch。
- 原有域名 Registry 配置按原语义继续工作。
- 数据库结构和既有业务数据不因本次升级而进入中间态。

不承诺事项：

- 单实例容器替换不承诺严格零停机；镜像替换和进程重启可能造成短暂请求中断。
- Manifest 缓存 Key 变化会使旧 Manifest Key 在新版本下自然不命中；第一次请求可能重新回源。
- 不得把“数据库无迁移、无中间态”表述成“所有请求无感、绝无中断”。

### 2.9 缓存 Key 与兼容

#### Manifest

新增唯一的 `ManifestEndpointKey`：

`Scheme + CanonicalHost + EffectivePort`

建议使用与 Origin 相同规范化规则的无歧义序列化格式，但该值只表示规划期 `RegistryEndpoint`；IPv6 Host 必须带方括号。默认端口必须显式规范化为有效端口。**不得**把 `Origin` 业务对象或同源比较函数直接作为 Manifest CacheKey 的构造依据。因此：

- `https://host` 与 `https://host:443` 使用同一个 Manifest Endpoint Key。
- `http://host` 与 `http://host:80` 使用同一个 Manifest Endpoint Key。
- `http://host` 与 `https://host` 必须隔离。
- 同 Host 不同非默认端口必须隔离。
- 不同 Host 必须隔离。

**Key 前缀与格式（冻结，沿用现有解析体系，不新增 `docker:m|manifest:`）**：

| 条件 | 3.5.24 目标格式 |
|---|---|
| `epoch <= 0` | `docker:manifest:<RegistryEndpoint>/<repo>:<ref>\|accept=...` |
| `epoch > 0` | `docker:m:<epoch>:<RegistryEndpoint>/<repo>:<ref>\|accept=...` |

示例（Epoch=1）：`docker:m:1:https://registry.example.com:443/library/alpine:latest|accept=...`；IPv6：`docker:m:1:https://[2001:db8::10]:443/library/alpine:latest|accept=...`。理由：`RegistryCacheKind` 用 `docker:manifest:` / `docker:m:` 识别 Manifest，`RegistryCacheKeyEpoch` 用固定字段解析 Epoch；延续前缀、只改 Rest，避免改动键类型识别、Epoch 解析与清理逻辑。测试预期需同步：旧格式 `docker:manifest:`（epoch=0）、当前 `docker:m:<epoch>:`（Rest 仍裸 host）、3.5.24 目标（Rest 改为完整 Endpoint）；两类前缀的缓存分类与 Epoch 解析测试保持通过，Epoch=0 不得写成 `docker:m:0:`。

**P0-3 设计裁定（已明确，六项设计证据已归档 2026-11-25，来源链闭合）**：RegistryEndpoint 在请求规划期按唯一来源链构造，不得从入站地址或实际镜像节点推导。三种协议必须区分：①入站协议（Docker 客户端访问 Mirror Lens）；②Registry 上游协议（`Adapter.Scheme`）；③SourceEndpoint 协议（`sources.base_url` 的 Scheme）。三者不得互相替代补位。

- **Scheme**：当前生产装配调用 `registryadapter.New()`（`registry.go:138-143`）把 `Adapter.Scheme` 初始化为 `https`，无其他生产赋值路径，故当前为 HTTPS；不得用入站 `r.TLS`/`r.Host` 或 SourceEndpoint Scheme 替代。
- **CanonicalHost**：唯一来源链 `请求路径 → ParsePath → parseRepo → ParsedPath.Host → registryhost.Normalize → RegistryEndpoint.CanonicalHost`。`ParsedPath.Host` 是 Endpoint 构造唯一接收的 Host 输入；显式 Host 前缀请求由路径解析得到，裸仓库名请求由 `parseRepo` 以 `Adapter.Upstream` 作为默认 Host 形成 `ParsedPath.Host`。Docker Hub 别名必须复用 `registryhost.Normalize()`（`registryhost.go:37-47`）规范化：`docker.io`/`registry-1.docker.io`/`index.docker.io` → `docker.io`，不得在 Registry Adapter 内另实现别名转换。`Normalize()` 只用于验证输入与生成 CanonicalHost，**不得把返回值写回配置或 `Adapter.Upstream`**：`registry-1.docker.io`→`docker.io` 仅是逻辑身份，配置与 `Adapter.Upstream` 必须保持原始 `registry-1.docker.io`，否则改变默认上游判断与 GHCR fallback（见 §4 专用测试）。`Adapter.Upstream` 是默认 Host/实际上游路由配置，**不是** CacheKey 构造阶段的第二个 Host 来源，CacheKey 阶段不得再独立读取它或与 CanonicalHost 混用。`CanonicalHost=docker.io`（逻辑身份）与实际回源 Host `registry-1.docker.io`（连接地址）必须区分，这不是身份不一致。
- **EffectivePort**：当前逻辑 Registry 请求模型没有独立端口输入；`config.Registry.Upstream`（`config.go:95`）采用严格纯主机名契约、不含 Scheme/显式端口/IP（当前 `Config.Validate` `config.go:634-642` 仅拒空值与 `://`、`/`，缺口属实施必修项；UI 仅 `internal/api/config.go:149-150` TrimSpace+Hint，不代表已校验）；`sources.base_url` 的端口属 SourceEndpoint。当前 Scheme 为 HTTPS，故 EffectivePort=443。通用规则 HTTPS→443、HTTP→80，但不代表产品已提供逻辑 Registry 的 HTTP 或自定义端口配置能力。P0-3 关闭仅证明现有受支持请求模型来源链完整，不授予新增逻辑 Registry Scheme/Port 输入能力，不得据此扩大产品承诺；非默认端口 Key 隔离测试仅作 Endpoint 值与 Key Builder 语义测试保留，不得据此宣称 `/v2/` 入口已支持用户配置任意逻辑端口。
- **构造时机**：RegistryEndpoint 必须在 `rememberedHost()` 替换实际回源 Host、Fallback、Source 调度之前构造；`rememberedHost`/Fallback/SourceEndpoint 的切换不得改变 RegistryEndpoint 与 CacheKey；Upstream 保持现有 `rememberedHost`/Fallback 行为，不得强行改成 RegistryEndpoint.URL 破坏 GHCR fallback；Origin 仍用于凭据及重定向安全判断，不得复用为 Manifest CacheKey 身份。
- **能力边界**：IPv6 Endpoint/Authority 方括号序列化及 Manifest Key 格式测试继续保留；该序列化能力不代表当前 `/v2/` 路径支持 IP 字面量作为 RegistryIdentity，不得由序列化测试推导新的 IP 身份准入能力。

P0-3 六项设计证据门禁（不要求实施 API/UI/持久化/重启恢复）：P0-3-1 `Adapter.Scheme` 初始化与生产赋值路径唯一；P0-3-2 `ParsePath → parseRepo → ParsedPath.Host → registryhost.Normalize`；P0-3-3 严格纯主机名契约、按 Scheme 推导默认端口；P0-3-4 `rememberedHost`/Fallback/Source 调度之前构造；P0-3-5 CacheKey 只用 RegistryEndpoint，不用 Origin 或 SourceEndpoint；P0-3-6 所有 Manifest 入口统一使用同一个 Key 构造点。六项证据已于 2026-11-25 归档（见 evidence-baseline §P0-3 六项证据归档），P0-3 据此关闭；关闭后 G1 仍保持 `DRAFT_NOT_FROZEN` 直至独立冻结授权。

**registry.upstream 严格纯主机名输入契约（2026-11-25 DECISION_ACCEPTED，与 P0-3-3 关联）**：`registry.upstream` 只允许符合 `registryhost.Normalize()` 现有语法规则的纯主机名；禁止显式端口、IPv4、IPv6 字面量、完整 URL 与路径，不另实现一套 Host 语法。允许：`registry-1.docker.io`/`registry.example.com`、大写（Normalize 规范化）、尾点（去尾点）；禁止：`:5000`、`203.0.113.10`、`[2001:db8::10]:5000`、`https://…`、`/v2` 路径。CanonicalHost 仅作逻辑身份，不得覆盖 `Adapter.Upstream` 实际路由，也不得把 `RegistryEndpoint.CanonicalHost` 直接覆盖到 `Plan.LogicalHost`。

**P0-3-3 冻结措辞**：设计目标契约为 registry.upstream 严格纯主机名、按 Scheme 推导 EffectivePort；不提供逻辑 Registry 显式端口/IP 输入。**现状**：当前 `Config.Validate`（`config.go:634-642`）尚未拒绝端口/IP/Scheme，缺口属实施必修项；本项设计证据 PASS 不代表配置加载/Web 保存 RED/GREEN 测试已通过。其余五项（P0-3-1/2/4/5/6）承前不变。

**三项保护条件（冻结）**：①rememberedHost——CacheKey 用原始请求身份，不得以 CanonicalHost 覆盖 `Plan.LogicalHost`；②IPv6——保留方括号序列化测试，不开放 IPv6 RegistryIdentity/upstream 输入；IPv6 SourceEndpoint 支持是独立实现项，允许独立修正 `normalizeURL()` 解析覆盖 IPv6 方括号、非默认端口、非法 IPv6 URL，但不得套用 registry 纯域名校验规则；③SourceEndpoint——HTTP/HTTPS/域名/IPv4/IPv6/非默认端口仍是 `sources.base_url` 能力，不受本节限制，不得因本契约而收紧这些既有能力。能力边界：自定义节点地址须入 `sources.base_url`，禁止把 `http://192.0.2.10:8080` 写入 `registry.upstream`、把 IP 写入 `repo_host`、或据此构造逻辑 Registry CacheKey；3.5.24 须核实 UI 添加→API 保存→探测器→TLS SAN（不固定 443）→Gateway 拨号→Redirect/认证/SSRF/IP 访问控制→编辑/删除/重启恢复一致，SourceEndpoint 支持 IP 不等于绕过安全策略。

**实施阶段强制要求（非 G1 冻结前置）**：Config.Validate（registry 分支 `config.go:634-642`）启用时须拒绝空值、Scheme/路径/查询/Fragment/Userinfo、端口、IP 字面量并经 Normalize 验证；非法配置必须明确报错，不得静默退回 Docker Hub、不得截掉端口后继续使用、不得因单个配置非法就自动改成默认上游；保留原始 Host 别名不回写 Adapter.Upstream；四入口统一（YAML 加载、Web Setter、写入+读回验证、Validate 失败不得覆盖原配置文件），不能仅靠 UI 提示。两条精确提醒：①用 `Normalize()` 不用 `Check()`（`registryhost.go:169-176` `Check()`=`Normalize()`+`Allowed()` 白名单，误用会把 `registry.example.com` 以 `UnsupportedError` 拒绝）；②校验落点限定 `config.go:634-642` registry 分支，不得误伤 SourceEndpoint：`sources.base_url` 经 `addSource()` 与 `api.go:677-700 normalizeURL` 解析，其 HTTP/HTTPS、IP、非默认端口能力不得收紧；为支持 IPv6 SourceEndpoint 允许独立修正 `normalizeURL()` 的 URL 解析（IPv6 方括号、非默认端口、非法 IPv6 URL），但不得套用 registry 纯域名 `Normalize()` 规则，也不得扩展为全局 URL/Host 限制。阶段边界：不得要求在 G1 关闭前先提交 Go 代码（避免 B2 流程死锁）。

所有 `PlanParsed` 生成的 Manifest（Tag、Digest、latest 等）必须经过同一共同构造点，不能只修一个路径。

`referrers` 是独立解析分支；本次按现有行为不生成 Manifest 缓存 Key。验收要求其身份规范化和安全策略正确，且不绕过 RegistryIdentity。

#### Blob

- Blob Key 继续只使用 Digest。
- 不得给 Blob Key 添加 Host、Scheme、端口或 Endpoint 前缀。
- 同一内容 Digest 的跨 Registry Blob 复用必须保持。

#### Cache Epoch 与旧缓存

- Cache Epoch 完全不变。
- 禁止因为 Manifest Key 格式变化而执行 Epoch bump、Epoch sweep 或全量缓存清理。
- 旧 Manifest Key 自然不再命中新 Key，由现有 TTL/GC 回收。
- 原有 Blob Key 必须继续命中。
- 新增 Manifest Key 不得造成 `RegistryCacheKind`、Epoch 解析或缓存统计逻辑异常。
- 必须验证 Key 中包含 `://`、端口分隔符和 IPv6 方括号时，现有数据库 Key 解析与分类逻辑仍正确。

### 2.10 设计冻结门禁

进入实现前，必须提交并核准：

- `3.5.24-design-freeze.md`。
- Endpoint/Identity/Origin 结构定义。
- UI/API/配置字段映射。
- IP 准入来源及安全数据流。
- HTTP/HTTPS 重定向与 Realm 策略矩阵。
- TLS 连接和验证规则。

**阶段 C：自定义节点 UI/API**

2. 增加域名/IPv4/IPv6 Host 输入和可选端口。

5. 复用现有凭据配置与持久化方式。
6. 老配置加载不得意外改变协议或端口。

**阶段 D：TLS 与 Registry 请求链路**

1. 将 Endpoint 实际端口传入 TLS 探测。

4. HTTP 不触发 TLS 探测。
5. 适配 HTTP/HTTPS Registry 请求、Token Realm 和 Blob 下载。

**阶段 E：重定向与凭据安全**

1. 分离 RegistryIdentity 同 Host 比较和完整 Origin 比较。
2. 普通重定向按 Origin 控制 Authorization 头。
3. Token Realm 按独立矩阵授权。

5. 保留并回归 Blob CDN 白名单。
6. 验证同 Host 不等于跨端口 Origin 相同。

**阶段 F：Manifest/Blob 缓存**

1. 统一构造 ManifestEndpointKey。
2. 所有 Manifest 计划路径使用共同构造点。
3. `referrers` 不创建 Manifest Key。
4. Blob Key 保持纯 Digest。
5. Cache Epoch 不变。
6. 验证旧 Manifest 自然失效、新 Manifest 隔离、Blob 继续复用。

**阶段 G：文档与发布准备**

更新用户文档、配置说明、HTTP 明文风险说明、升级说明、回滚说明和版本变更记录。

## 4. RED-GREEN 测试矩阵

所有测试必须可重复运行，不得依赖不可控的公网随机服务。

### 4.1 地址解析与规范化

| 输入 | 预期 |
|---|---|
| `https://registry.example.com` | HTTPS，默认端口 443 |
| `https://registry.example.com:443` | 与上一项 Endpoint 等价 |
| `http://registry.example.com` | HTTP，默认端口 80 |
| `http://registry.example.com:80` | 与上一项 Endpoint 等价 |
| `https://registry.example.com:5443` | 保留 5443 |
| `https://203.0.113.10` | 识别为 IPv4 Endpoint；格式测试不代表该保留地址可通过准入 |
| `http://203.0.113.10:5000` | 识别为 IPv4 + HTTP + 5000 |
| `https://[2001:db8::10]` | 识别为 IPv6，Authority 方括号正确 |
| `https://[2001:db8::10]:5443` | IPv6 非默认端口正确 |
| 未带方括号的歧义 IPv6 URL | 明确拒绝或按标准 URL 语义报错，不猜测 |
| `ftp://host`、空 Host、非法端口、越界端口 | 明确拒绝 |

**registry.upstream 严格纯主机名契约 RED 用例（配置加载 + Web 保存两条路径均须覆盖）**：

| 输入（`registry.upstream`） | 预期（配置加载与 Web 保存一致） |
|---|---|
| `registry-1.docker.io`、`registry.example.com`、`Registry.Example.COM`、`registry.example.com.` | 允许；原始合法 Host 保留在配置与 `Adapter.Upstream` 中，`Normalize()` 仅用于生成 CanonicalHost，不得覆盖实际路由 Host |
| `registry.example.com:5000` | 明确拒绝，不得截掉端口后继续使用 |
| `203.0.113.10` | 明确拒绝（IPv4 字面量） |
| `[2001:db8::10]`、`[2001:db8::10]:5000` | 明确拒绝（IPv6 字面量） |
| `https://registry.example.com`、`ftp://host` | 明确拒绝（Scheme 非法） |
| `registry.example.com/v2`、`registry.example.com?x=1`、`user@registry.example.com` | 明确拒绝（路径/查询/Userinfo） |

| Validate 失败后重新加载配置文件 | 原配置文件内容不被覆盖 |

不得因单个非法配置自动改成默认上游；校验只作用 `registry.upstream`，`sources.base_url` 的 IPv4/IPv6/HTTP/HTTPS/非默认端口用例（§4.1/§4.2）继续通过、不受影响。

**registry-1.docker.io 路由语义专用测试（P1-1，必须验证行为而非仅验证 Normalize 返回值）**：配置 `registry.upstream = registry-1.docker.io` 时，须同时断言——①配置与 `Adapter.Upstream` 仍为 `registry-1.docker.io`（原始 Host 别名未被写回）；②`registryhost.Normalize()` 返回值/RegistryEndpoint.CanonicalHost 为 `docker.io`（逻辑身份）；③`parseRepo()` 以 `registry-1.docker.io` 为裸仓库名默认 Host、`PlanParsed()` 默认 Registry 判断不变；④`addGhcrFallback()` 在默认上游仍为 `registry-1.docker.io` 时照常添加 GHCR fallback，默认 Docker Hub 实际路由与 fallback 条件无语义变化。

**SourceEndpoint 协议隔离回归测试（P1-2）**：同一 RegistryIdentity、Repo、Ref，把 SourceEndpoint 从 HTTPS 切到 HTTP（或反向），须同时断言——①实际连接协议随节点配置变化（HTTP 节点走明文、HTTPS 节点走 TLS）；②RegistryEndpoint.Scheme 与 Manifest CacheKey 不随 SourceEndpoint 改变；③HTTP/HTTPS 切换不得导致 Authorization 跨 Origin 泄漏（跨 Origin 后 Authorization 清除）；④Token Realm Policy 授权与普通 3xx Redirect 的完整 Origin 校验仍各自独立有效，不因协议切换而放宽或互相替代。

**sources.base_url IPv6 解析测试（P1-3，与 registry 纯域名校验分离）**：覆盖 `https://[2001:db8::10]`（IPv6 方括号）、`https://[2001:db8::10]:5443`（IPv6 非默认端口）、非法 IPv6 URL（未闭合方括号/非法地址）明确拒绝或按标准 URL 语义报错；不得因新增 registry.upstream 纯主机名契约而收紧这些 `sources.base_url` 既有能力，也不得把 registry 的 `Normalize()`/`Check()` 规则套到 SourceEndpoint。

### 4.2 IP 安全与准入

- 管理员登记的可达公网 IPv4 节点可以进入受控准入路径。
- 管理员登记的可达公网 IPv6 节点可以进入受控准入路径。
- 未登记公网 IP 不得因 IP 解析成功而自动放行。
- 私网、回环、链路本地、组播、未指定和保留 IP 继续拒绝。
- IPv4-mapped IPv6 不得绕过 IPv4 私网/保留地址规则。
- DNS 首次解析为公网 IP、随后重绑定到私网 IP 时，实际拨号必须拒绝。
- 重定向到私网 IP 必须拒绝。
- 使用代理、重试、Realm、Blob 等链路不能绕过相同检查。

### 4.3 自定义节点 UI/API

- 新建 HTTPS 域名节点。
- 新建 HTTP 域名节点并显示明文警告。
- 新建 HTTPS IPv4 节点。
- 新建 HTTP IPv4 非默认端口节点。
- 新建 HTTPS IPv6 节点。
- 新建 HTTP IPv6 非默认端口节点。
- 编辑节点后协议、Host、端口和凭据保持一致。
- 刷新页面、重启服务后配置仍然一致。
- 旧版节点配置升级后行为不变。
- 非法端口、非法地址、未支持 Scheme 在前端和后端均被拒绝。

### 4.4 TLS

- DNS Endpoint + 有效 DNS SAN 证书成功。
- IP Endpoint + 有效 IP SAN 证书成功。
- IP Endpoint + 仅 DNS SAN 证书失败。
- IP Endpoint + 错误 IP SAN 证书失败。
- HTTPS 自定义端口连接正确端口。
- HTTP 不进行 TLS 握手。
- TLS 验证失败不得降级到 HTTP。

### 4.5 重定向和 Realm

逐项验证 2.5 的矩阵，包括：

- 同 Host、同 Origin。
- 同 Host、不同端口。
- 同 Host、不同 Scheme。
- 跨 Host、相同 Scheme。
- HTTPS → HTTP 拒绝。
- HTTP → HTTPS 受控升级。
- Token Realm 与普通 Redirect 分别测试。
- 跨 Origin 后 Authorization 清除，但仍执行目标地址检查。
- 同 Host 凭据存在，不代表任意 Realm/端口自动获得授权。

### 4.6 缓存

- 同一 Endpoint 的 Manifest 热缓存命中。
- 不同 Scheme 的 Manifest 不串缓存。
- 同 Host 不同非默认端口的 Manifest 不串缓存。
- 显式默认端口和省略默认端口的 Manifest Key 等价。
- IPv6 Endpoint Key 序列化无歧义。
- 所有 Tag、Digest、latest 等 Manifest 入口一致。
- `referrers` 不生成 Manifest Key。
- 同一 Digest 的 Blob 在不同 Registry/Endpoint 之间仍可复用。
- Blob Key 格式与升级前完全一致。
- Cache Epoch 升级前后完全一致。
- 旧 Manifest Key 不命中新 Key，但旧记录可由原 TTL/GC 机制回收。
- Key 前缀分类与 Epoch 解析：epoch=0 的旧键以 `docker:manifest:` 识别（不得出现 `docker:m:0:`），epoch>0 以 `docker:m:<epoch>:` 识别；升级后两种前缀的 `RegistryCacheKind` 分类与 `RegistryCacheKeyEpoch` 解析均正确，含 `://`/端口/IPv6 方括号的 Rest 不影响分类。
- 升级首次回源：每个尚未重建的新 Key 升级后第一次请求各自 Miss 回源并重建该 Key，记为 `manifest_key_rebuild_first_miss`，按 Key 计数（不是每 Registry 一次），且不计入热缓存命中样本。

### 4.7 数据库兼容、单轨与事务原子性

必须用测试和运行证据证明以下要求，而不能只检查迁移目录中“没有新增文件”：

**Schema 不变测试**
- Schema Version 与 3.5.23 基线完全一致。
- 表、列、索引、约束、触发器等 Schema 对象指纹完全一致。
- 没有执行 DDL、migration、自动建表、数据回填或隐式升级。
- 启动前后数据库完整性检查均通过。
- 既有 Registry Host 状态记录数量及关键字段抽样一致。
- 既有凭据可按原格式解密、读取和完成认证；测试日志不得泄漏凭据明文。
- AEAD AAD 格式不变。
- Cache Epoch 不变。

**单轨测试**
- 升级编排先停止 3.5.23，再启动 3.5.24。
- 不允许两个版本同时对同一数据库进行读写。
- 不出现临时库、影子表、双写、后台迁移或双版本 Schema 兼容。
- 3.5.24 只使用一套 RegistryIdentity/Endpoint 语义。
- 通过进程状态、容器状态和数据库连接/日志证据证明不存在新旧版本并行写入。

**单事务测试**
- 本次升级不存在数据库迁移事务，也不存在分阶段迁移事务。

- 在事务中间人为注入失败，验证全部相关写入回滚，不留下部分记录。

## 7. 真实环境验收

### 7.1 环境要求

使用可控、可复现的 Registry 测试环境。环境资料必须固定并归档：

- Registry 镜像名和不可变 Digest。
- 认证服务镜像名和 Digest（如适用）。
- TLS 证书及 SAN 内容、有效期和签发方式。
- IPv4/IPv6 网络拓扑和实际地址。
- HTTP/HTTPS 端口映射。
- 测试账户权限和凭据注入方式（不得把明文密码写入公开日志）。
- 测试镜像层、Manifest Digest 和预期内容 Hash。
- NAS/宿主机、容器、Go 版本和网络条件。

不得把 RFC 5737 的 `192.0.2.0/24` 或 RFC 3849 的 `2001:db8::/32` 文档保留地址当成真实可连接验收目标。它们只能用于地址解析和拒绝规则测试。真实连接验收必须使用可控、实际可达且满足安全准入规则的地址。

### 7.2 必测环境组合

- 现有域名 HTTPS Registry：升级前后回归。
- 可控公网 IPv4 HTTPS Registry：有效 IP SAN。
- 可控公网 IPv4 HTTP Registry：明确配置及明文警告。
- 可控公网 IPv6 HTTPS Registry：有效 IP SAN。
- 可控公网 IPv6 HTTP Registry：明确配置及明文警告。
- 至少一个自定义非默认端口。
- 认证 Registry + Token Realm。
- HTTPS/HTTP 重定向与 Blob 下载。
- 被拒绝的私网/回环/保留地址目标。

如果测试环境无法提供可路由 IPv6 或真实公网 IP，相关场景标记 `BLOCKED`，不得用本地字符串解析测试冒充真实环境验收。

### 7.3 升级验收：单轨、无数据库过渡态

升级前保存：

- 当前运行镜像 Digest、Commit SHA 和进程/容器状态。
- 数据库备份和完整性结果。
- Schema Version、Schema 指纹、表/索引/约束/触发器清单。
- 关键业务数据抽样和既有 Registry Host 状态记录。
- Cache Epoch。
- 既有 Registry 配置和凭据可用性记录（不得归档明文凭据）。
- 抽样 Manifest Key、Blob Key 和 Blob 文件 Hash。
- 当前数据库连接与进程归属证据。

升级必须按单轨顺序执行：

1. 停止 3.5.23 服务，确认旧进程已退出且不再持有数据库写连接。
2. 确认不存在另一个旧版本实例或后台任务继续写入同一数据库。
3. 替换应用镜像/二进制；不得同时启动新旧版本。
4. 启动 3.5.24，先执行只读 Schema/完整性/兼容性门禁。
5. 门禁通过后才允许进入正常服务状态。
6. 若门禁失败，立即停止 3.5.24，保留数据库和日志现场；不得自动修复、迁移或创建新数据库。
7. 不得在升级期间运行任何 Schema 迁移、数据回填或凭据转换。

升级后验证：

1. 应用正常启动，Ready 状态正常。
2. Schema Version 与升级前完全一致。
3. Schema 指纹、表结构、索引、约束和触发器无变化。
4. 没有 DDL、migration、自动建表、数据回填或迁移标记写入。
5. 升级前后数据库完整性检查均通过。
6. 既有业务数据、Registry Host 状态和凭据可正常读取/使用。
7. 既有 Registry 配置和凭据正常。
8. 旧域名 Registry 的 Pull/Manifest/Blob 行为正常；必须对多个既有 Manifest Key 样本验证：每个未重建的新 Key 第一次请求因旧/新 Key 不等而回源，随后相同 Key 请求命中新缓存。
9. Cache Epoch 不变。
10. 原 Blob Key 和 Blob 内容 Hash 不变，热缓存仍能命中。
11. Manifest 按新 Endpoint Key 工作；每个尚未以新格式重建的 Key，其第一次请求均预期回源，随后相同 Key 的请求必须命中新格式缓存。
12. HTTP 节点显示明文警告，HTTPS 节点验证证书。
13. 失败和拒绝路径的错误码、日志和指标符合预期。
14. 重启服务后自定义节点的协议、Host、端口和凭据仍保持。
15. 进程/容器证据证明不存在新旧版本并行运行或双写。

**无过渡态判定：** 升级全过程只能观察到“旧版本停止、服务暂不可用/替换中、新版本只读检查、新版本正常运行”这些应用部署状态；不得观察到数据库 Schema 逐步变化、旧新结构并存、业务数据分批转换或新旧版本同时写库。

### 7.4 无感升级的验收口径

本版本承诺的是**数据库和业务数据兼容的平滑升级**，不是单实例进程严格零停机。缓存兼容边界必须明确区分 Manifest 与 Blob：

- 不要求用户重新配置已有域名 Registry。
- 不要求用户重新录入凭据。
- 不要求数据库迁移。
- 不要求清空缓存，也不执行 Cache Epoch bump。
- Blob Digest Key 不变，原 Blob 热缓存可以继续复用，不要求手动重建 Blob 缓存。
- **所有既有域名 Registry 的旧格式 Manifest 缓存条目都不会命中新格式 Endpoint Key。对每个尚未以新格式重建的 Manifest Key，其升级后第一次请求都会发生回源 Miss，并建立该 Key 的新格式缓存；这不是“每个 Registry 全局只 Miss 一次”，而是每个不同 Manifest Key 各自首次重建一次。**
- 旧 Manifest 记录不主动删除，继续由既有 TTL/GC 回收；不得为了消除首次 Miss 而清空缓存或改变 Cache Epoch。
- 升级说明必须提前告知用户：每个尚未以新格式重建的 Manifest Key，在升级后第一次被请求时都会回源；该 Key 重建后，后续请求恢复热缓存命中。Blob 层仍可复用原缓存。
- 单实例容器更新若需要重启，必须记录实际中断窗口；不能宣称零停机。

## 8. 性能对照

### 8.1 对照原则

性能测试必须同时验证新功能和旧功能不退化。不能只测 IP Registry，也不能只报告单次峰值。

在性能测试开始前冻结：

- 测试机器、容器资源限制、网络链路和 Registry 位置。
- 测试镜像与内容 Digest。
- 并发数、请求数、文件大小和缓存状态。
- 基线版本与候选版本的镜像 Digest/Commit SHA。
- 每个场景重复次数、统计口径和允许退化阈值。

性能阈值必须基于实测基线、测量噪声和项目可接受 SLA 在测试前确定。禁止在看到结果后临时调整阈值。

### 8.2 必测场景

热缓存测试采用严格的“先预热、后测量”口径：3.5.23 基线必须先用旧 Key 预热后测热缓存；3.5.24 候选必须先用新 Endpoint Key 预热后测热缓存。两个版本的预热请求均不计入热缓存样本。升级后，每个尚未重建的新 Manifest Key 第一次请求所产生的回源单独按 `manifest_key_rebuild_first_miss` 记录，统计受影响 Key 数、回源次数、耗时和 Registry 端请求；这些重建请求不纳入热缓存命中性能样本。

| 场景 | 基线/候选都测 | 目的 |
|---|---|---|
| 现有域名 Registry 冷缓存 | 是 | 发现新增规范化、策略检查带来的回源退化 |
| 现有域名 Registry 热缓存 | 是 | 两个版本各自先预热各自的 Manifest Key，再验证热缓存命中和本地响应性能；不得拿 3.5.23 旧 Key 与 3.5.24 新 Key 的首次 Miss 直接比较热缓存 |
| 现有域名 Registry 并发 Pull | 是 | 验证调度和吞吐无回归 |
| IPv4 HTTPS 冷/热缓存 | 候选必须 | 验证完整 Endpoint 链路 |
| IPv4 HTTP 冷/热缓存 | 候选必须 | 验证明文 Endpoint 链路 |
| IPv6 HTTPS/HTTP | 环境具备时 | 验证 IPv6 真实链路 |
| 同 Host 不同端口/协议 | 候选必须 | 验证 Manifest 隔离正确、Blob 仍复用 |
| 认证与 Token Realm | 候选必须 | 验证认证额外开销和正确性 |

### 8.3 指标与统计

至少记录：

- Manifest TTFB、总耗时。
- Blob TTFB、总耗时、实际吞吐。
- 冷缓存回源耗时、热缓存响应耗时。
- 成功率、失败率、重试次数。
- 缓存 Hit/Miss、Blob 复用命中。
- 并发吞吐、请求延迟分布。
- CPU、内存、网络流量。
- Registry 端负载和客户端实际下载结果。

每个场景至少重复 20 次后再计算 P95；样本不足 20 次时报告中位数、最小值、最大值和样本量，不得给出貌似精确的 P95。测试报告必须同时展示基线和候选原始结果及差值。

### 8.4 性能通过标准

- 先检查正确性和缓存语义，错误缓存命中不能算性能提升。
- 3.5.23 基线与 3.5.24 候选必须分别完成 Manifest 预热后再测热缓存；必须使用各版本真实生效的 Key，不得把候选首次 Miss 当作热缓存数据。
- 3.5.24 升级后，每个尚未重建的新 Manifest Key 的首次回源必须单独报告，作为按 Key 计数的一次性缓存重建成本；它不计入热缓存退化判定，但不得从升级影响报告中隐去。
- 候选版本预热完成后的域名 Manifest 热缓存，以及冷缓存回源、并发场景，仍必须按冻结阈值与基线对照。
- Blob 热缓存复用必须保持；不得因 Endpoint Key 变化导致 Blob 冷重建。
- 不得以 IP 新功能速度高于某个单次峰值作为通过标准。
- 若环境噪声导致结果不确定，标记 `INCONCLUSIVE` 并复测，不得判定通过。

**门禁 G4：** 没有同环境基线、候选对照和预先冻结的阈值，不得给出“性能无回归”结论。

## 10. 发布、升级与回滚

### 10.1 发布前检查

- 最终 Commit 已完成独立复核。
- 最终 Commit 上全量测试通过。
- 真实环境验收通过，或明确列出未能执行的阻塞场景。
- 性能对照达到预先冻结的门槛。
- 数据库 Schema 不变证据齐全。
- 发布镜像与 Commit SHA 对应。
- 升级和回滚命令已在非生产环境验证。

### 10.2 正常升级步骤：单轨发布流程

执行升级前，面向用户的版本说明/维护提示必须明确写明：Manifest Key 格式变更会使既有域名 Registry 的旧 Manifest 缓存条目无法命中新 Key；每个尚未重建的新 Manifest Key 首次访问时会回源，后续该 Key 才恢复热缓存命中。Blob Digest 缓存不受影响，原 Blob 可继续复用。

1. 保存当前运行镜像 Digest、Commit SHA、配置备份和部署参数。
2. 进行数据库备份；备份是安全措施，不代表本次会修改数据库。
3. 记录 Schema Version、Schema 指纹、表/索引/约束/触发器清单、关键数据抽样、Cache Epoch 和缓存抽样信息。
4. 拉取并核对 3.5.24 镜像 Digest，确认镜像对应已验收 Commit。
5. 停止 3.5.23，确认旧进程完全退出、旧数据库写连接关闭。
6. 检查不存在其他旧版本容器、进程、定时任务或后台 worker 继续访问同一数据库。
7. 替换应用镜像；整个过程不执行数据库迁移、DDL、数据回填、凭据转换或缓存 Epoch 变更。
8. 启动唯一的 3.5.24 实例，先运行只读启动门禁。
9. 只读门禁全部通过后，才允许服务进入 Ready。
10. 若门禁失败，停止 3.5.24 并保留现场；不得启动自动修复、数据库重建或降级迁移。
11. 验收旧域名 Registry、既有凭据、Blob 热缓存、新 Endpoint、HTTP/HTTPS 安全策略和关键指标；抽样覆盖多个既有 Manifest Key，逐个验证每个未重建 Key 的首次请求回源重建、后续请求热缓存命中，并将所有首次重建耗时与热缓存性能分开记录。
12. 归档本次升级记录、旧新进程时间线、数据库前后指纹和实际重启/中断时间。

本流程只存在一条应用版本切换路径。不得采用蓝绿双实例同时写同一 SQLite 数据库的方式实现“无感”；若将来部署形态需要蓝绿切换，必须先单独证明数据库连接、锁、写入和版本兼容边界，并重新冻结方案。

### 10.3 回滚原则

回滚目标是恢复旧应用版本，不回滚或重建数据库。

1. 保留升级前镜像 Digest、配置备份和部署参数。
2. 如新版本出现阻断问题，停止继续扩大流量并回退旧镜像。
3. 数据库 Schema 未变，因此不执行数据库降级或恢复旧 Schema。
4. 不删除 Blob 缓存，不清空整个缓存目录，不递增或重置 Cache Epoch。
5. 新版本写入的新 Manifest Endpoint Key 记录可以保留；旧版本不查询这些新 Key，旧 Key 仍按原语义工作。
6. 回退后验证旧域名 Registry、旧 Manifest 缓存和 Blob 缓存。
7. 如果发现数据库结构或凭据格式意外变化，说明违反设计冻结，必须进入事故处理，不得按普通回滚流程掩盖。

### 10.4 发布产物对应性

必须验证：

- Git Tag 指向的 Commit SHA 与最终验收 Commit 一致。
- 发布镜像标签对应正确 Commit。
- 镜像 Digest 已记录。
- SBOM/构建信息（若项目已有）与同一产物对应。
- 发布说明描述与实际代码功能一致。

## 11. 自动化状态机与停止条件

### 11.1 状态机

```text
INIT
  ↓
BASELINE_LOCKED
  ↓
EVIDENCE_COMPLETE
  ↓
G1_DESIGN_REVIEW
  ├─ P0/P1 或 P0-3 未闭合
  │    ↓
  │  DRAFT_NOT_FROZEN
  │    ↓
  │  STOP / WAIT_FOR_DESIGN_RESOLUTION
  │
  └─ 全部门禁通过（P0-3 六项证据已归档、来源链闭合）
       ↓
     WAIT_FOR_DESIGN_FREEZE_AUTHORIZATION（独立冻结授权门禁）
       ↓
     DESIGN_FREEZE_AUTHORIZED（独立授权状态，不得由前序状态自动推导）
       ↓
     DESIGN_FROZEN（仅在 DESIGN_FREEZE_AUTHORIZED 后进入）
       ↓
     WAIT_FOR_IMPLEMENTATION_AUTHORIZATION
       ↓
     IMPLEMENTATION_AUTHORIZED（独立授权状态，不得由前一状态自动推导）
       ↓
     RED_TESTS_CONFIRMED
       ↓
     IMPLEMENTED
  ↓
INDEPENDENT_REVIEW_PASSED
  ↓
FULL_TESTS_PASSED
  ↓
REAL_ENV_ACCEPTED
  ↓
PERFORMANCE_ACCEPTED
  ↓
DOCS_AND_EVIDENCE_ARCHIVED
  ↓
RELEASE_READY
  ↓
DEPLOYED_AND_VERIFIED（仅在具备生产授权时）
```

当前状态说明：`G1_DESIGN_REVIEW`；P0-3 来源链裁定已明确、六项设计证据已于 2026-11-25 归档、P0-3 据此关闭，但尚未获得独立冻结授权，故停在 `WAIT_FOR_DESIGN_FREEZE_AUTHORIZATION`，G1 保持 `DRAFT_NOT_FROZEN`（未进入 `STOP / WAIT_FOR_DESIGN_RESOLUTION`，因 P0-3 已闭合）。P0-3 关闭不等于 `DESIGN_FROZEN`——后者还需独立冻结授权（`DESIGN_FREEZE_AUTHORIZED`），进入实施另需 `IMPLEMENTATION_AUTHORIZED`。

### 11.2 必须停止并上报的情况

- 远程基线不清楚或工作区存在无法安全保留的用户改动。
- 现有自定义节点持久化方式无法表达 Scheme/Port，且必须修改数据库才能实现。
- 找不到安全、可审计的管理员显式 IP 登记来源。
- 必须放宽 `safehttp` 才能使功能工作。
- 发现必须修改凭据 AEAD AAD 或数据库 Host 身份才能完成目标。
- Token Realm 认证可能把 Host 级凭据发送到未授权 Endpoint。
- Manifest 缓存无法做到 Scheme/Host/Port 完整隔离。
- Blob Key 或 Cache Epoch 被迫变更。
- 现有域名 Registry 行为发生未解释的兼容性变化。
- 任何 P0/P1 安全问题未关闭。
- 全量测试、真实环境验收或性能门禁失败。
- 生产部署缺少明确授权。

停止后必须保留已完成证据、当前 Commit 和失败原因；不得删除工作分支或通过伪造 PASS 完成状态。

### 11.3 状态定义

- `PASS`：有可复现证据，满足预先定义的验收标准。
- `FAIL`：执行过且未满足标准。
- `BLOCKED`：因外部条件或设计缺口无法执行。
- `NOT_RUN`：未执行，不得用其他测试结果替代。
- `INCONCLUSIVE`：执行过，但样本或环境不足以得出可靠结论。

## 14. 不可变更的五项最终门禁

1. **远程基线锁定：** 所有结论和测试必须绑定真实 Commit SHA。
2. **RED 测试真实性：** 新增测试必须证明旧实现确实失败，不能只补一条永远通过的测试。
3. **独立复核隔离：** 复核者直接审查最终代码，不以实施者自述代替证据。
4. **最终提交复测：** 发布 Commit 必须重新执行关键测试，不能引用中间状态结果。
5. **发布产物对应性：** Git Tag、Commit、镜像标签和镜像 Digest 必须互相对应。

同时，本版本另有五条不可突破的运行与兼容性底线：

- **数据库不变：** 不改 Schema、不迁移、不改凭据格式、不自动修复或重建数据库。
- **单轨升级：** 旧版本先停止，新版本后启动；禁止双版本并行写库、双轨 Schema、双写、影子表和渐进迁移。
- **单事务原子性：** 本次没有数据库迁移事务；运行期单个多行逻辑写入必须在一个事务内整体提交或整体回滚，禁止部分提交和后台补偿式拼接。
- **Blob 不变：** Blob Digest Key 不变，Cache Epoch 不变，不清空 Blob 缓存。
- **旧功能不退化：** 现有域名 Registry 的请求、配置和认证行为必须通过升级回归；Blob Digest 缓存复用必须保持。每个 Manifest 旧 Key 因格式变更产生的首次回源属于已披露的预期影响；候选版本新 Key 预热后的热缓存性能仍必须通过对照阈值。

**术语边界：** “单轨”描述版本/数据演进只有一条权威路径；“单事务”描述单个逻辑数据库写操作的原子性。应用镜像替换本身不属于 SQL 事务。本次数据库升级事务数量为零，因为数据库不升级。

以上任务书为 3.5.24 无人值守实施与验收的统一基线。若实际代码取证与本文件的已知前提不符，应先记录证据并停止冲突部分，不得擅自扩大范围或改变冻结决策。
