> 状态：v5.2 修订版，在 v5 基础上落实代次隔离：整数 `recovery.gen` + `source_health_scope.gen` 四列主键（P1-4/P1-6）、hard-excluded 重验事务化（P1-5）、探测起点捕获 gen 并在事务内校验（P1-7）。**P1-7 仅设计通过，未实施、未测试，不得标记为已修复。** A2、Phase B、Phase C 均未启动。

## 0. 边界与硬约束

- 不重写传输协议、并发模型、通用调度算法；已大量验证的 Scheduler 不作为持续改造对象。
- 3.5.2 顺序 **A → B → C**，不改变既定架构边界。A1 不实现 Phase B（legacy 退出）与 Phase C（缓存身份隔离）的任何代码。
- 不混入 Host 级 `query_mode`、源级竞速资格（不在 3.5.2 范围）。
- 四模型职责不交叉：
  - `registry_cap`：能力判断唯一权威（`-1` 未知 / `0` 不支持 / `1` 支持 / `2` 内容不一致，`internal/store/host.go:18-23`）。
  - `source_health_scope`：特定 source、特定 Host 的**既有健康探测**结果（`fails` / `last_at` / `ok_at`）。
  - `breaker_state`：具体请求维度的熔断状态（键 `(source_id, kind)`）。
  - **新恢复层 `registry_host_recovery`**：新鲜度、恢复探测时间、下次允许探测时间、恢复退避。**不重复保存 capability 真值，不替代 breaker_state。**

## 1. `registry_host_recovery` 表：最小字段 + 派生规则

### 1.1 表结构

```sql
CREATE TABLE IF NOT EXISTS registry_host_recovery (
  source_id       INTEGER NOT NULL,
  family          TEXT    NOT NULL DEFAULT 'registry',
  scope           TEXT    NOT NULL,            -- registryhost.Check 规范化后的 Host，与 source_health_scope.scope / sources.repo_host 同源
  state           TEXT    NOT NULL,            -- 派生六态（见 1.2），仅作可读投影，不独立决定能力
  last_probe_at   INTEGER NOT NULL DEFAULT 0,
  last_success_at INTEGER NOT NULL DEFAULT 0,  -- 真实成功时间（见 1.3），非 last_at
  next_probe_at   INTEGER NOT NULL DEFAULT 0,  -- 下次允许探测时间（Unix 秒），持久化调度唯一权威
  rec_failures    INTEGER NOT NULL DEFAULT 0,  -- 连续恢复探测失败次数（持久化退避唯一权威）
  last_error      TEXT    NOT NULL DEFAULT '',
  gen             INTEGER NOT NULL DEFAULT 0,  -- 该行证据所属凭据代次，= 提交时 registry_host_gen.gen
  updated_at      INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY(source_id, family, scope),
  FOREIGN KEY(source_id) REFERENCES sources(id) ON DELETE CASCADE
);
```

**归属粒度裁定（C1 前必读）：恢复状态是 source 级，不是 Host 级。**

- 探测粒度是 `Source × Host`：`HostProbeJob{SourceID, Host, BaseURL, Repo, Tag}`（`hostprobe.go:19-25`），Runner 注释明确"把未验证的 Source×Host 探测一次"（`hostprobe.go:52`）。
- 进程内互斥与退避 key 是 `sourceID|host`（`hostprobe.go:58`、`hostprobe.go:293`）。
- 写回是 `SetHostCaps(id, ...)`，`UPDATE sources ... WHERE id=?`（`host.go:158-165`），cap 本身按源存储。
- 因此同一 Host 的多个源必须各有独立 `state / next_probe_at / rec_failures`。若改成 `host` 单主键：源 A 的失败会排除源 B 的候选资格、推迟源 B 的重探，且同 Host 并行探测会争写同一行。
- `registry_host_gen` 仍是 Host 级（凭据按 Host 共享），这不要求 recovery 也按 Host 聚合：代次是输入，恢复是每个源各自的输出。

字段取舍：

- **新增 `gen` 列绑定代次（P1-4）**：值为写入该行证据时的 `registry_host_gen.gen`（整数单调，非时间戳）。`registry_host_gen.gen` 已存在于 `store.go:246-251`（`host PK / gen / cred_digest / updated_at`）。代次判定一律比较整数 `gen`，不比较任何时间字段——秒级时间戳在"凭据变更与探测同秒"时无法区分先后（`>=` 误认旧证据，`>` 误杀同秒新成功）。写序守卫仍不需要独立字段（见 §2.2）。
- **不存 capability 真值**：`state` 是派生投影，能力结论仍以 `registry_cap` 为准。
- **FK CASCADE**：源被删时恢复行随之删除（与 `source_health_scope` 一致）；`breaker_state` 走显式 `ClearBreakerStates`，不强制统一。
- `rec_failures` 是**持久化的恢复退避唯一权威计数器**；现有 runner 内存 `probeState.backoff` 不再承担准入（见 §6）。它与 `source_health_scope.fails` 是**不同维度**：前者是恢复探测连续失败次数，后者是既有 Host 健康结果统计。**不得为让两者数值一致而修改 `NoteProbeScoped` 语义**（见 §2.5）。

### 1.1.1 `source_health_scope` 的代次化（P1-6）

**问题**：`recovery.gen` 只能证明 recovery 行属于新代次，不能证明 `source_health_scope.fails` 属于新代次。凭据变更后 `recovery.gen==currentGen` 成立，而旧 `fails=3` 没有代次字段，会被 §1.2 的 `failed` 派生和 §5 的 `fails<>0` 闸门重新认作当前代次失败。

**采用方案 A（同一张表按代次分区），不新增第二张健康表：**

```sql
CREATE TABLE source_health_scope (
  source_id INTEGER NOT NULL REFERENCES sources(id) ON DELETE CASCADE,
  family    TEXT NOT NULL,
  scope     TEXT NOT NULL DEFAULT '',
  gen       INTEGER NOT NULL DEFAULT 0,   -- 该健康样本所属凭据代次
  fails     INTEGER NOT NULL DEFAULT 0,
  ok_at     INTEGER NOT NULL DEFAULT 0,
  last_at   INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY(source_id, family, scope, gen)
);
```

- **主键扩展为四列**：同一 `(source_id, family, scope)` 在每个代次各有一行；旧代次行保留，供诊断与审计，不再参与当前派生。
- **迁移（P1-7 补充：必须在事务内原子重建）**：SQLite 无法原地改主键，按下列顺序执行，任一步失败整体回滚。
  ```sql
  PRAGMA foreign_keys=OFF;              -- 必须在 BEGIN 之前设置（事务内设置是 no-op）
  BEGIN IMMEDIATE;
  CREATE TABLE source_health_scope_new (
    source_id INTEGER NOT NULL REFERENCES sources(id) ON DELETE CASCADE,
    family TEXT NOT NULL, scope TEXT NOT NULL DEFAULT '',
    gen INTEGER NOT NULL DEFAULT 0,
    fails INTEGER NOT NULL DEFAULT 0,
    ok_at INTEGER NOT NULL DEFAULT 0,
    last_at INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY(source_id, family, scope, gen));
  INSERT INTO source_health_scope_new(source_id,family,scope,gen,fails,ok_at,last_at)
    SELECT source_id,family,scope,0,fails,ok_at,last_at FROM source_health_scope;
  DROP TABLE source_health_scope;
  ALTER TABLE source_health_scope_new RENAME TO source_health_scope;
  -- 旧表若有索引，在此按原定义重建
  PRAGMA foreign_key_check;             -- 有返回行则 ROLLBACK
  COMMIT;
  PRAGMA foreign_keys=ON;
  ```
  - 迁移前后校验：`SELECT COUNT(*)` 一致；`PRAGMA table_info(source_health_scope)` 主键顺序为 `source_id,family,scope,gen`；`PRAGMA foreign_key_check` 为空；运行时实际 `PRAGMA foreign_keys` 值记录到日志（不假设默认开启）。
  - **失败路径**：任何一步出错立即 `ROLLBACK`；`foreign_keys=ON` 的恢复必须放在 `defer` 里，正常路径和失败路径都执行，不能只在 COMMIT 后写一行。
  - **`PRAGMA foreign_key_check` 返回任何行即 ROLLBACK**，不得只记日志继续提交。
  - **索引**：迁移前导出 `sqlite_master` 中 `tbl_name='source_health_scope' AND type='index'` 的原始 DDL，迁移后逐条比对名称与定义；测试要断言索引存在且 `EXPLAIN QUERY PLAN` 走索引，不能只看"重建语句执行成功"。
  - **回滚测试**：人为在新表复制后注入失败（如在 `RENAME` 前返回错误），断言旧表仍在、行数与内容不变、外键关系完好、`foreign_keys` 已恢复为 ON。
  - `gen=0` 语义是"代次未知 / 凭据从未变更"，不是"属于第 0 代凭据"。
- **写路径**：Registry 路径只由 `CommitHostProbe` 写，`gen` 取探测起点的 `snap.Generation`（§2.3，P1-7），事务内校验后才写四列主键行；`NoteProbeScoped` 不再服务 Registry 路径，仅服务 `family<>'registry'` / `scope=''` 的调用方，固定 `gen=0`。禁止任何写入函数在写入时用 `currentGen` 反推归属。
- **读路径**：`ScopedHealthOf` 只返回 `gen=currentGen(scope)` 的行（`scope=''` 取 `gen=0`）；候选 SQL 与派生条件都带 `z.gen=currentGen`。
- **历史归属规则（种子迁移同样适用）**：`gen=0` 的行只在 `currentGen==0` 时算当前代次证据；`currentGen>0` 时一律不算。无法证明归属的历史证据按"无证据"处理，状态落 `initial`，由首次探测重建——fail-closed，不猜。
- **为什么不选方案 B（独立当前代次健康表）**：B 需要双写或让旧表停止更新，前者形成两份可能分叉的状态，后者让诊断数据冻结、比保留更差；A 只有一张表、一套语义，历史行天然成为只读分区。

### 1.2 六态派生（修正三审 P1-1：failed 覆盖 cap=1 恢复失败 + 完整优先级）

**六态定义（按优先级从高到低判定，第一个命中即为该行状态，避免多行同时满足时各自解释）：**

| 优先级 | 派生状态 | 含义 | 进入条件（综合判定） | 候选资格 |
| --- | --- | --- | --- | --- |
| 1 | `hard-excluded` (cap=2) | 内容不一致，硬隔离 | `registry_cap=2` | **永不进候选**；不并入 `unsupported`；仅凭据 / 仓库变更时按内容一致性安全语义重验，不进普通长周期恢复循环 |
| 2 | `unsupported` (cap=0) | 明确不支持 | `registry_cap=0` | 排除候选；普通长周期重验证 |
| 3 | `failed` | **最近一次有效恢复探测失败，且当前尚未恢复成功**（不受 `registry_cap` 是否仍为 1 限制） | `recovery.gen == 当前 gen` 且 `scoped.gen == 当前 gen` 且有探测历史（`scoped.fails>=1` 或 `last_error<>''` / `rec_failures>=1`），且当前未满足 `ok` 的成功 + 新鲜条件 | 排除候选；按退避重探 |
| 4 | `ok` | 最近有效探测成功且在有效期内 | `registry_cap==1` 且 `recovery.gen==当前 gen` 且 `scoped.gen==当前 gen` 且 `scoped.fails==0` 且 `last_success_at>0` 且未超 TTL | **进入候选**（严格，见 §5 TTL 闸门） |
| 5 | `expired` | 曾成功但超过有效期，等待重验 | `registry_cap==1` 且曾有成功（`last_success_at>0`）但 `now - last_success_at > TTL`，且无新的失败探测 | **不进候选**；进入立即重验队列 |
| 6 | `initial` | **当前凭据代次**在该 Host 上尚无有效探测结果（不等于"历史上从未探测过"） | `recovery.gen != 当前 gen`，或（`registry_cap==-1` 且 `last_probe_at=0`） | 不进候选；立即探测 |

**凭据代次的有效性判定（P1-4：整数 gen 绑定，不依赖时间戳）：**

- `currentGen(host) = COALESCE((SELECT gen FROM registry_host_gen WHERE host=?), 0)`；`registry_host_gen.gen` 是整数单调序号，不是时间。
- **当前代次有效探测** = `recovery.gen == currentGen(host) AND last_probe_at > 0`。
- 任何 scoped 证据只有在 `scoped.gen == currentGen` 时才参与；recovery 证据只有在 `recovery.gen == currentGen` 时才参与 `ok` / `failed` / `expired` 派生；`recovery.gen != currentGen` 一律落 `initial`，旧证据只保留、不参与判定。
- 时间戳不承担代次区分职责：`last_success_at` / `last_probe_at` 只用于 TTL 与新鲜度，同一秒内的新旧证据不需要靠 `>` / `>=` 区分。
- `ApplyCredChanges` 在同一事务内取变更后的 `gen` 写入 recovery 行（见 §2.4），因此提交完成即完成隔离，无窗口。
- 该列同时解决"同秒旧成功被误认"与"同秒新成功被误杀"两个方向：判据是整数相等，不是时间先后。

**两个 scoped 阈值的职责区分（R1，用户五审裁定）：**

- `scoped.fails == 0`：**恢复状态 `ok` 的健康条件**，也是候选准入条件。任何一次连续失败都使 `ok` 不成立。
- `scoped.fails >= HealthFails`：**既有健康阈值与隔离条件**，保留原语义（既有熔断 / 诊断 / 事件路径继续使用），但**不再是候选准入的唯一判据**。
- 二者用途不同，不得互相替代：候选 SQL 必须验证 `fails == 0`，不能只验证 `>= HealthFails`。`fails >= HealthFails` 必然 `fails != 0`，因此被零失败条件蕴含，但该既有语义不被删除。

**状态转换（三审 P1-1 明确，作为 A1 核心状态迁移测试）：**

```
initial ──成功──> ok
initial ──失败──> failed

ok ──TTL 到期──> expired
ok ──探测失败──> failed        （新增：cap 仍为 1 但最近探测失败，直接 failed）

expired ──成功──> ok
expired ──失败──> failed

failed ──重试成功──> ok
failed ──重试失败──> failed
```

**`failed` 且 `cap=1` 的语义（三审 P1-1 核心场景）：**

- `registry_cap=1` **保留**为历史能力结论（能力列不被恢复失败覆盖）。
- `recovery.state=failed` **阻止进入候选**——这是"恢复状态控制何时重新准入"的实现点。
- 恢复成功后重新确认能力和路径，再恢复候选资格。
- 这确保 cap=1 的 Host 在 TTL 过期后探测失败，落入 `failed`，**既不继续当 `expired`，也不因 `registry_cap` 仍为 1 而重新进候选**。

**关键边界（来自二审 + 三审）：**

- `cap=2` 与恢复状态正交；候选 SQL 的 `registry_cap==1` 闸已将其排除，但显式声明：`cap=2` 绝不因 `recovery=ok/expired` 进候选，也不继承 `cap=0` 的普通长周期重探策略；重验必须遵循内容一致性检查的安全语义，不能降级成普通能力探测。
- `cap=-1` 不无条件等于 `initial`：新 Host 首次探测超时后 cap 仍为 `-1`，但已有**当前代次**（`gen==currentGen`）失败记录 → 判为 `failed`，不是 `initial`；仅有旧代次失败记录时仍为 `initial`。判定必须综合 `registry_cap` + `source_health_scope.fails` + `ok_at` + 恢复层 freshness。

### 1.3 结果处理表：HostProbe 结果分类 + 写列矩阵（三审 P1-3，已按代码核对）

**代码事实（避免把错误分类当既有语义照抄）：**

- `HostProbe` 产出 `cap ∈ {-1,0,1,2}` + `Reason` + `Transport`（`internal/probe/registryhost.go`）。聚合表 `aggregate()`（registryhost.go:366-381）：任一路径 `CapYes` → 1；两条都 `CapMismatch` → 2；两条都 `CapNo` → 0；**其余一切 → -1**。
- **超时 / DNS / 5xx / 401 / HTML / 双 404 等都不是独立 `cap`**，而是 `CapUnknown=-1` 的子类，靠 `Reason`（`transport_error` / `auth_error` / `incomplete_evidence`）+ `Transport`（`dns`/`timeout`/`connect`/`tls`/`http_5xx`）细分（`classifyErr`:591-635、`outcomeReason`:639-662）。
- 现有 runner 写回（`hostprobe.go:343-361`）：`SetHostCaps(capv, ...)` 对**所有** `cap` 写 `registry_cap`（故 `CapUnknown` 写 `-1`，**不保留既有值**）；`CapYes || CapUnknown` 时调用 `NoteProbeScoped(ok = (cap==1))`（故 `CapUnknown` **会累加 `scoped.fails`**，`CapNo`/`CapMismatch` 不写）；`stale_snapshot` 完全不写。
- **A1 的叠加基线是 3.5.1 已落地行为**（用户四审裁定）：`registry_cap` 的写回策略与 `source_health_scope` 的写回策略是**两件可拆开的事**。普通 `CapUnknown` 继续走既有 `SetHostCaps`（写 `-1`）；瞬时传输失败由 A1 恢复层走新增路径（保留历史 cap），但**两者都仍按既有 `NoteProbeScoped` 语义写 scoped 失败记录**。不得把"保留 cap"与"不写 scoped"绑定成一个不可拆分的分支。

**A1 结果→写列矩阵（冻结语义，`CommitHostProbe` 按此实现）：**

| `HostProbe` 结果 | `registry_cap` | `recovery.state` | `source_health_scope`（既有语义，不改） | `rec_failures`（恢复维度） | `next_probe_at` | 后续调度 |
| --- | --- | --- | --- | --- | --- | --- |
| `CapYes` | 写 `1` | `ok` | 按既有语义记录成功（`NoteProbeScoped(ok=true)`，写当前 `gen` 的新行） | 归 `0` | TTL 到期 | 正常候选；`last_error` 清空 |
| `CapUnknown` — `auth_error` / `incomplete_evidence`（401 / HTML / 双 404） | 写 `-1`（**既有通用路径**） | `failed` | **按既有语义记录失败**（`ok=false`，fails+1） | `+1` | `now + 退避(rec_failures)` | 短退避 |
| `CapUnknown` — `transport_error`（DNS / 超时 / connect / TLS / 5xx） | **保留历史值**（新增路径：**跳过**会把 cap 重置为 `-1` 的通用写回） | `failed` | **按既有语义记录失败**（`ok=false`，fails+1，用同一 `NoteProbeScoped`） | `+1` | `now + 退避(rec_failures)` | 短退避 |
| `CapNo` | 写 `0` | `unsupported` | 不写（既有语义：只写能力，不污染健康） | 不进入短周期失败退避 | `now + 长周期` | 长周期重验 |
| `CapMismatch` | 写 `2` | `hard-excluded` | 不写 | 不进入普通恢复退避 | 不进普通循环 | 仅凭据 / 仓库变更触发内容一致性重验 |
| `stale_snapshot`（凭据代次 / Host 归属变化） | 不写 | 不写 | 不写 | 不变 | 本轮不重排（由 §3 陈旧快照分支处理） | 重新获取快照 |

**硬规则（用户四审定案）：**

1. **普通 `CapUnknown` 与瞬时传输错误的唯一区别是 `registry_cap` 写回策略**：前者写 `-1`（既有路径），后者保留历史值（新增路径）。`source_health_scope` 两者都按既有语义写失败，**不得因保留 cap 而跳过 scoped 写回**。
2. `NoteProbeScoped` 既有语义冻结：`CapYes` / `CapUnknown` 写入（`ok = (cap==1)`），`CapNo` / `CapMismatch` 不写入，`stale_snapshot` 不写入。A1 不修改该函数本身。
3. 瞬时传输错误路径**不得调用会把 `registry_cap` 重置为 `-1` 的通用 `CapUnknown` 写回逻辑**；它只跳过 cap 写回，`source_health_scope` 与 `recovery` 照常写。
4. `rec_failures` 与 `source_health_scope.fails` **独立计数**；同一次探测失败可以同时增加两者，但不得互相代替，也不得为让其中一个不增加而破坏另一个的既有语义。
5. **探测失败绝不因 `registry_cap` 仍为 1 被判成成功**——`ok` 要求 `cap==1 AND scoped.fails==0 AND 本次探测成功 AND 未超 TTL` 同时成立；只要本次是失败结果，`state` 就必须落 `failed`。

### 1.4 派生算法（新鲜度来源修正）

在 `CommitHostProbe` 事务内（见 §2.3）推导并 UPSERT，统一用**真实成功时间**：

1. 取 scoped 行 → `fails`, `last_at`, `ok_at`。
2. 取 `registry_cap`（`sources.registry_cap`）。
3. 按 §1.3 矩阵处理本次探测结果（决定写哪些列 / `rec_failures` 增减 / `next_probe_at`），并在**同一 `tx`** 内按固定顺序写入：
   a. `registry_cap` / `registry_path_mode`（适用时；瞬时传输错误跳过 cap 写回）；
   b. `source_health_scope`（适用时，SQL 语义与既有 `NoteProbeScoped` 逐字等价，见 §2.3）；
   c. `registry_host_recovery`（state / last_probe_at / last_success_at / rec_failures / next_probe_at / last_error）。
   固定顺序的理由：`scoped.fails` 是 §1.2 `failed` 判定的输入之一，state 必须基于**本次 scoped 写入之后**的值派生；三条 UPSERT 必须全部走同一 `tx`。
4. 按 §1.2 优先级表推导 `state`，更新 `last_probe_at=now`；推导前在同一 `tx` 内读 `g = registry_host_gen.gen` 并写入 `recovery.gen=g`；scoped UPSERT 写入 `(scope, gen=g)` 行；派生只读 `scoped.gen==g` 的证据。不比较时间戳。成功 → `last_success_at=now`、`rec_failures=0`、`last_error=''`；失败 → `rec_failures++`、`next_probe_at=now+退避(rec_failures)`、`last_error=本次错误（clipProbeNote 截断）`；`unsupported` → `now+长周期`；`hard-excluded` → 不进普通循环；`expired` → `now`（一次受控重验）。`stale_snapshot` 不改 `last_error`。
5. UPSERT（`INSERT ... ON CONFLICT(source_id,family,scope) DO UPDATE`），`updated_at=now`。

**`last_at` ≠ `last_success_at`**：`last_success_at` 取真实成功时间（`ok_at` / `registry_probe_at` 的成功条件值），`last_at` 仅用于区分"是否发生过探测事件"，**不能单独证明最近成功**（一次失败也会刷新 `last_at`）。

### 1.5 `state` 仅为派生投影（澄清 2）

`registry_host_recovery.state` 是 `(registry_cap, scoped 结果, 成功时间, TTL)` 的持久化投影，**不是独立能力权威**。所有影响派生的写必须保持一致，各入口的同步动作：

- `CommitHostProbe`（Registry 探测唯一入口）：cap + scoped + recovery 三表同事务（§2.3 / §2.3.1）。
- `NoteProbeScoped`（非 Registry 或兼容调用方）：只写 scoped，不写 recovery。A1 要求 **Registry 生产路径不再直接调用它**；若有其它调用方写 registry scope，必须同时更新 recovery，否则投影与 scoped 不一致。
- `ApplyCredChanges`：重置 cap 为 `-1`，recovery 置 `next_probe_at=now`、`rec_failures=0`，保留 `last_success_at` 但不据此判 `ok`（§2.4）。
- `SetRepoHost`：清空 cap / path_mode / probe_at / probe_error（既有 `host.go:95-100`），删除旧 Host 的 recovery 行与旧 scope 行，为新 Host 建 `initial` 行。
- TTL 配置变化：允许 `state` 投影滞后，候选以 SQL 的 `last_success_at >= now-TTL` 闸门为准；不为改配置做批量 UPDATE。
- 种子迁移：只按当前 Host 的归属证据推导（§4 R4）。

候选 SQL 必须同时满足 `registry_cap==1` + 路径有效 + 恢复行 `state=='ok'` + **TTL 实时闸门**（§5），**不能只查 `recovery.state`**。

**投影一致性巡检（A1 验收项，不是运行时组件）：**

- **执行条件**：仅在测试 / 验收、Runner 已停止（无并发写）时执行；或在单个 `BEGIN DEFERRED` 读事务内一次性读取 `sources` + `source_health_scope` + `registry_host_recovery`，保证同一快照。不得在事务外分三次查询拼接。
- **比对**：用 `(registry_cap, scoped.fails, last_success_at, now)` 重算 state，与存储值逐行比较；`NoteProbeScoped` 单独写 scoped 后若未同步 recovery，巡检必须报错——A1 要求 Registry 路径不出现这种调用。
- **合法暂态（不得判为漂移）**：① `cap=1` 且 `last_success_at` 已超 TTL 但仍为 `ok`（投影允许滞后，候选由 SQL 的 TTL 闸门兜底）；② `failed` 且 `next_probe_at > now`（退避中）；③ `cap=-1` + `last_success_at` 非零 + `state in (failed, initial)`（凭据变更后保留历史成功时间）；④ 新源无 recovery 行，或 `initial` + `last_probe_at=0`；⑤ 事务回滚后行不存在。
- **边界**：巡检只读、只报错、不自动修复，不参与候选判定。

## 2. 写回边界、代次守卫与职责边界（v1 §2 拆分 + 二审 Issue 5 + 三审 P2-6）

- **2.1 凭据代次守卫**：`CommitHostProbe` 在 `BEGIN IMMEDIATE` 内**显式读取** `registry_host_gen` 的 `gen/cred_digest` 并与探测快照比对（缺行处理见 §2.3.2），各写语句的 `WHERE` 再带 `gen=? AND cred_digest=?` 作防御性双保险；不符即整事务回退，等价于 `HostCapsStaleSnapshot`。
- **2.2 写序守卫——职责边界收紧（三审 P2-6）**：**不增加独立写序字段**。`HostProbeRunner.claim`（`internal/runner/hostprobe.go:239-252`）只负责**同一 Runner 内探测任务互斥**。数据库写回正确性的**最终边界是 DB 事务内的 `repo_host` + `gen` + `cred_digest` + `status<>'archived'` 校验**（`SetHostCaps` 的 `WHERE`，host.go:158-165），它拒绝配置变化后的陈旧写回；`claim` **不作为数据库写回正确性的唯一保障**。种子 / ensure 只做 `INSERT ... ON CONFLICT DO NOTHING`（绝不覆盖已存在行），与 runner 的 UPDATE 不冲突。
- **2.2.1 写入失败关闭（fail-closed，用户四审要求确认）**：
  - **单事务消除部分成功**：§2.3 的 `CommitHostProbe` 把 `registry_host_recovery` 与 `registry_cap` / `registry_path_mode` / `source_health_scope` 放在**同一事务**，因此"scoped 写成功、recovery 写失败"的组合**不可能出现**——要么三者全部提交，要么全部回滚。
  - **回滚 = 旧的一致状态，必须额外关闭**：事务整体失败时三者回到旧值（可能是 `cap=1` + `fails` 未增 + `recovery=ok`）。这个旧状态虽然一致，但对"最近一次探测失败"是过时的，必须由下面的机制阻止它继续授予候选资格。
  - **Runner 不得静默接受写失败**：`CommitHostProbe` 返回错误时，Runner 把 `(source_id, scope)` 加入进程内 `failClosed` 集合，按退避重试该事务；重试成功前该 Host 一律不进候选。`failClosed` 在事务成功或下一次探测成功时移除。
  - **候选查询取保守交集**：候选判定同时要求 DB 的 `recovery.state='ok'` **且**该 Host 不在进程内 `failClosed` 集合。内存与磁盘分叉时方向必须是"更保守"（内存认为不可用），不允许反向放行。
  - **R3：候选过滤必须有线性化点（五审二轮再收紧）**：
    - `failClosed` 是独立进程内组件（key = `(source_id, family, normalized_scope)`，不含 gen），Runner 写入、候选读取；不是第二套 recovery 状态机，不参与派生、不持久化、不改 `state`。
    - **逐项 `Blocked()` 不足以证明正确性**：检查与返回之间存在 TOCTOU 窗口——A 查到 `false`，B 随后 `Block`，A 仍会返回包含 key 的列表。三条入口都必须走同一个 `Guard.Filter(list)`，不允许一条用快照、另一条逐项检查。
    - `Guard.Filter` 的协议（seqlock 式读—校验—重试）：
      1. `snap, epoch := Guard.Snapshot()`：在 `RLock` 下拷贝 blocked 集合与当前 `epoch`；
      2. `out := filter(list, snap)`；
      3. `Guard.Verify(epoch)`：在 `RLock` 下比较 `epoch` 是否仍相等；
      4. 相等 → 返回 `out`，**Verify 成功的时刻即线性化点**；不等 → 说明期间发生过 `Block`，重新 Snapshot + 过滤，最多重试 3 次；
      5. 重试耗尽 → 返回空集（fail-closed），并打点 `guard_filter_retry_exhausted_total`。
    - 线性化语义（按用户三轮修正表述）：`Block` 在 `Verify` 成功**之前完成** → `epoch` 改变 → 本次必重试并排除该 key；`Block` 在 `Verify` 成功**之后发生** → 本次返回在线性顺序上**先于** `Block`，物理上仍可能包含该 key，但并发历史上 Filter 先于 Block，不违反线性化一致性；后续 Filter 必排除。**不得**把保证表述为"任何在置位之后物理完成的返回都排除该 key"——那比协议实际提供的更强。
    - 三条路径统一调用 `Filter`：
      ① 缓存命中：`CandidatesN` 把 `cached()` 的原始列表交给 `Filter`；
      ② 缓存未命中：Store 查询结果先 `Filter`，**缓存存原始结果**（也可存已过滤结果，但缓存不承担正确性）；
      ③ `Store.registryCandidates` 返回前 `Filter`（覆盖 `api.go:517` 直调）。
    - `Invalidate()` 仍在置位后立即调用，只用于缩短旧缓存寿命；即使不调用或调用失败，`Filter` 的线性化点仍保证正确性。
    - 生命周期：只有 `CommitHostProbe` 成功提交才解除；重试启动、超时、普通探测成功但写库失败均不解除。
    - 清理竞态：Guard 每个 key 记录置位时的 `(gen, seq)`；清理方 `UnblockIfMatch(key, gen, seq)` 只在当前记录匹配时删除，旧代次清理不得误删新代位项。
    - 源删除（FK CASCADE）后同步清 Guard 项；SQLite 自增 ID 不复用，若未来复用则必须把 epoch 加入 key。
  - **重启后关闭到期窗口**：Runner 启动时先执行一次幂等物化 `UPDATE registry_host_recovery SET state='expired', next_probe_at=now WHERE state='ok' AND next_probe_at<=now`（或等价的显式到期判定），再开始探测。这样重启前"已到期但写回失败"的旧 `ok` 不会在首轮探测完成前被放行。
  - **残余窗口显式声明**：仅剩"TTL 未到期 + 写失败 + 进程崩溃"这一组合。此时 DB 的 `ok` 是"最近一次成功探测且在 TTL 内"的合法结论，最坏持续一个 `RecoveryVerifyTTL`，由 TTL 上限约束；同时打点 `recovery_write_fail_total` / `recovery_failclosed_total` 便于观测。不允许把该窗口扩大为"永久放行"。
  - **DB 持续不可用**：候选查询本身失败时按既有策略降级到官方源，而不是放行缓存候选。

- **2.3 统一事务边界（二审必改）**：取消"先 `SetHostCaps` 再单独 UPDATE recovery"的两步写法。新增（或扩展）`CommitHostProbe(id, rawHost, cap, pathMode, reason, transport, at, errText, gen, credDigest)`（实现以 `store.HostProbeCommit` 结构体承载同一组字段，另带 `HasCredential` 与 `TTL`：前者用于缺行三态，后者用于成功结论有效期），在**一个事务**内：`BEGIN IMMEDIATE` → 校验 `repo_host` 仍为探测时 Host、`registry_host_gen.gen/cred_digest` 一致、`status<>'archived'` → 按 §1.3 写列矩阵原子写 `registry_cap` / `registry_path_mode` +（适用时）`source_health_scope` + `registry_host_recovery`（派生 state / 时间 / 退避）。所有写受同一组条件约束，陈旧快照在该事务开启前判定，命中则不写回（见 §3）。

  **P1-7：gen 必须来自探测起点，不得在写入时重新读取。**
  - `gen` 的唯一来源是探测开始时的 `Creds.Snapshot(host).Generation`（`hostprobe.go:297`），随结果对象一路携带到 `CommitHostProbe`；现有 `runOne` 已持有 `snap.Generation`（`hostprobe.go:314/343`），A1 只需把它透传给 scoped 写入。
  - 事务内第一条语句读取 `registry_host_gen` 的 `(gen, cred_digest)`，与传入的 `(gen, credDigest)` 比较；**缺行不得用 `COALESCE` 折算成 0**，必须按 §2.3.2 的三态规则处理；**不等立即 ROLLBACK**，不写 `registry_cap` / `registry_path_mode` / `source_health_scope` / `registry_host_recovery` 任何一列，返回 `HostCapsStaleSnapshot`。
  - `BEGIN IMMEDIATE` 取得写锁，保证「读 gen → 校验 → 写三表 → COMMIT」期间 `ApplyCredChanges` 无法插入提交；因此不存在"校验通过后 gen 又被改"的窗口。
  - **禁止**在 `CommitHostProbe` 内或它调用的任何函数内用 `currentGen(scope)` 反推代次；写入的代次只能是参数 `gen`。
- **2.3.1 R2：scoped 写入必须使用同一 tx（实现边界冻结）**：
  - 现有 `NoteProbeScoped`（`sources.go:110-146`）通过 `s.db.Exec` 直接写库，**不在 `CommitHostProbe` 已开启的事务内**。因此不能"调用 `NoteProbeScoped` 然后声称三表同事务"。
  - 实现方式：`CommitHostProbe` 在 `tx` 内执行带代次的 UPSERT，目标行固定为 `(source_id, 'registry', scope, gen=参数gen)`（成功：`fails=0, ok_at=?, last_at=?`；失败：`fails=fails+1, last_at=?`），`gen` 不由 SQL 子查询推导。`NoteProbeScoped` 函数签名与 fails 语义**不修改**，但 **A1 起 Registry 生产路径不得调用它**（它无法携带探测起点 gen）；它只服务 `family<>'registry'` 或 `scope=''` 的调用方，固定写 `gen=0`。
  - 三组写入全部走 `tx.Exec`，**禁止混用 `s.db` 与 `tx`**；任一失败整事务回滚。
  - 一致性测试：同一输入分别走 `NoteProbeScoped` 与 `CommitHostProbe`，断言 `source_health_scope` 的 `fails / ok_at / last_at` 结果逐字段一致。
- **2.3.2 缺行语义与旁路写入（P1-7 冻结前实施约束）**：
  - **`registry_host_gen` 缺行不得用 `COALESCE` 当成 gen=0 通过校验。** 事务内读取必须区分三种情况：
    ```go
    var gen int64; var digest string
    err := tx.QueryRow(`SELECT gen, COALESCE(cred_digest,'') FROM registry_host_gen WHERE host=?`, host).Scan(&gen, &digest)
    switch {
    case err == sql.ErrNoRows && !probe.HasCredential && probe.Gen == 0:
        // 无凭据公开 Host：按显式规则在事务内建 gen=0 行，再继续
        tx.Exec(`INSERT OR IGNORE INTO registry_host_gen(host,gen,cred_digest,updated_at) VALUES(?,0,'',?)`, host, at)
    case err == sql.ErrNoRows:
        return HostCapsStaleSnapshot          // 有凭据却无代次行 = 未对账，拒绝
    case err != nil:
        return err
    case gen != probe.Gen || digest != probe.Digest:
        return HostCapsStaleSnapshot          // 代次/摘要不符，整事务回滚
    }
    ```
    `probe.HasCredential` / `probe.Gen` / `probe.Digest` 全部来自探测起点的 `Creds.Snapshot`，事务内不得重新推导。
  - **唯一写路径**：`CommitHostProbe` 是 Registry 探测结果写 `registry_cap` / `registry_path_mode` / `registry_probe_at` / `registry_probe_error` / `source_health_scope` / `registry_host_recovery` 的唯一入口。A1 起 `SetHostCaps` 退出生产调用链（保留为内部实现或测试辅助），禁止 `SetHostCaps` 与 `CommitHostProbe` 双写。
  - **全仓审计基线（A1 实施时以此为准，新增调用点必须复核）**：
    | 写入面 | 当前生产调用点 | A1 处置 |
    | --- | --- | --- |
    | `NoteProbeScoped(family='registry')` | `hostprobe.go:358` | 删除，并入 `CommitHostProbe` |
    | `source_health_scope` 表级写 | `sources.go:121/127`（`NoteProbeScoped` 内） | 仅保留非 Registry / `scope=''` 调用 |
    | `registry_probe_at/error` | `host.go:97`（`SetRepoHost` 清空）、`host.go:159`（`SetHostCaps`） | `SetHostCaps` 并入 `CommitHostProbe`；`SetRepoHost` 不受探测 gen 约束 |
    | `SetHostCaps` | `hostprobe.go:343` | 调用点改为 `CommitHostProbe` |
  - **瞬时错误不绕过代次校验**：`cap` 写回可跳过，但事务仍必须做 gen/digest 比对；不符即整体回滚，不因"这次只是传输错误"而放行 scoped / recovery 写入。

- **2.4 凭据变更事务（二审必改 + P1-4 代次绑定）**：`ApplyCredChanges` 在**同一事务**内完成两件事：
  1. 既有语义：对 `repo_host=规范化(c.Host)` 的源置 `registry_cap=-1, registry_path_mode=''`（`host.go:311-317` 的"只清结论、保留诊断"不变）。
  2. 代次绑定：读本事务写入后的 `registry_host_gen.gen`（即 `g`），对该 Host 的 recovery 行执行：
     - `gen=g`：新代次的证据只能由新代次写入；
     - `state='initial'`、`last_probe_at=0`、`last_error=''`；
     - `next_probe_at=now`、`rec_failures=0`；
     - `last_success_at` **保留**为历史事实，但 `recovery.gen != currentGen` 时它不参与 `ok` 判定（§1.2），所以不会误判健康；
     - `updated_at=now`。
  - 行不存在时直接 INSERT（`gen=g, state='initial', next_probe_at=now`），不依赖 §7 的 ensure 时序。
  - **不删 `source_health_scope` 行**：旧行 `gen` 保持旧值，因 `scoped.gen != currentGen` 被 §1.1.1 的读路径整体排除；不需要 UPDATE 旧行，也不需要在事务内清 fails。凭据变更后状态**必然是 `initial`**，首次新代次探测写入 `gen=g` 的新行后，才可能转 `failed` / `ok`。
  - 隔离判据是整数 `gen` 相等，**不比较任何时间戳**，因此不存在"同秒旧成功被继承"或"同秒新成功被误杀"。
  - 不新增 generation **表**；复用 `registry_host_gen.gen`，recovery 行新增 `gen` 列承载绑定（§1.1）。

- **2.5 保持既有 scoped 健康语义（用户四审裁定，必须原文遵守）**：`CommitHostProbe` 不得为让 `source_health_scope.fails` 与恢复退避同步而改变 `NoteProbeScoped` 的既有语义。冻结的既有语义：
  - `CapYes` / `CapUnknown` → 按既有语义写 scoped 健康（`ok = (cap==1)`）。**包括瞬时传输错误**：DNS / 超时 / connect / TLS / 5xx 仍按现有 CapUnknown 语义记录 scoped 失败。
  - `CapNo` → 只写能力状态，**不污染 scoped 健康**。
  - `stale_snapshot` → 完全不写。
  - `rec_failures`（恢复探测连续失败）与 `source_health_scope.fails`（既有 Host 健康统计）是**不同维度**，独立计数；同一次探测失败可同时增加两者，但不得互相代替，也不得为对齐数值修改任一写回路径。
  - **"保留历史 cap"与"写 scoped 失败"必须解耦**：瞬时传输错误只跳过 `registry_cap` 写回，不得连带跳过 scoped 健康写入（写入由 `CommitHostProbe` 事务完成，不再调用 `NoteProbeScoped`）。
- **P1-7 调用边界**：`NoteProbeScoped` 不允许作为 Registry 生产路径的写入函数——它在写入时读 `currentGen`，会把 gen=5 启动的探测结果记到 gen=6 名下。Registry 路径只走 `CommitHostProbe(..., gen=snap.Generation, ...)`。

## 3. 陈旧快照不写回（同 v1）

`runOne` 在 `HostCapsStaleSnapshot` 分支只 `retry=true`，**不写任何恢复状态 / 失败 / `last_success_at`**（`hostprobe.go:362-364` 已有）。恢复写回**仅**放在 `HostCapsCommitted` 分支内（即 §2.3 事务成功提交后）。陈旧快照（凭据代次或 Host 归属变化）天然不会污染恢复状态。

## 4. 全量种子迁移（A1 硬依赖）

- **触发时机**：Store 初始化 / 迁移阶段，在 `registryCandidates` 被查询之前完成（避免"升级即无候选"）。`migrateRecoverySeed()` 幂等。
- **覆盖范围**：与 `hostCaps` 完全一致——`status<>'archived' AND repo_host<>'' AND repo_host<>'ghcr.io'`，**不过滤 `enabled`**（与 §6 Runner 维护集合、§11 Phase B 覆盖集合三者同一定义，见 §6.1）。包含当前 `cap=-1 / 0 / 1 / 2` 的源。
- **初始状态推导（P1-3：严格按 §1.2 优先级，不按列举顺序）**：新鲜度用 `ok_at` / `registry_probe_at` 成功条件（非 `last_at`），新行 `gen = COALESCE((SELECT gen FROM registry_host_gen WHERE host=s.repo_host), 0)`；该值只标记 recovery 行自身所属代次，**不**把历史 scoped 证据归入当前代次——历史归属由下面的 `scoped.gen==currentGen` 规则单独判定，`gen=0` 的旧行在 `currentGen>0` 时不算证据。判定顺序固定为：

  ```
  1. cap == 2                                  -> hard-excluded
  2. cap == 0                                  -> unsupported
  3. 有失败证据（scoped.gen==currentGen && scoped.fails>=1）  -> failed
  4. cap == 1 && scoped.gen==currentGen
     && scoped.ok_at>0 && 未超 TTL              -> ok
  5. cap == 1 && scoped.gen==currentGen
     && scoped.ok_at>0 && 超 TTL                -> expired
  6. 其余（含 cap==1 && fails==0
         但 last_success_at==0）                -> initial
  ```

  关键点：
  - 第 3 步优先于第 4/5 步：`cap=1` 且**超 TTL 又有失败证据**的源必须判 `failed`，不能先匹配 `expired`。
  - `cap==1` 且 `scoped.fails==0` 但 `last_success_at==0`（cap 被手工写成 1、无真实成功记录）**不得判 `ok`**，落 `initial`，等一次真实探测。
  - **历史证据归属（P1-6）**：迁移写入的旧 scoped 行 `gen=0`。第 3/4/5 步只认 `scoped.gen==currentGen` 的行；`currentGen>0` 时 `gen=0` 的历史失败/成功**一律不算**，状态落 `initial`，首次探测重建。
  - `sources.registry_probe_at` / `registry_probe_error` 没有代次字段，**不得**直接当当前代次证据：仅当 `currentGen==0`（凭据从未变更）时才可采信；`currentGen>0` 时忽略，避免升级迁移把上一个凭据的错误归到当前代次。
  - `recovery.rec_failures` 在新表中为空，种子阶段不可能有值，不参与首轮判定。
  - 凭据变更后由 §2.4 重置 recovery 行，不靠种子再判。
  - `cap==-1` 且无当前代次任何证据 → `initial`；旧 family 聚合失败记录**不构成**探测历史。

- **R4：失败历史的归属证据（防止跨 Host 污染）**：
  - 只有能证明属于**当前 `repo_host`** 的证据才能用于 Host 级状态推导：
    - `source_health_scope` 中 `(source_id, family='registry', scope=规范化当前 repo_host)` 的行——按 scope 精确归属，天然隔离。
    - `sources.registry_probe_at` / `registry_probe_error`：仅当 `repo_host` 未变时可归因。已核验全仓写入点只有两处——`SetRepoHost` 清零（`host.go:95-100`）与 `SetHostCaps` 带 `repo_host=?` 守卫写入（`host.go:158-169`）；因此非零值必然属于当前 Host，不存在第三条无守卫写入路径。
  - **旧 `source_health`（family 聚合）不用于当前 Host 推导**：它不区分 Host，可能是该源在其它 Registry 上的历史，直接使用会重新引入跨 Host 污染。
  - 旧 `source_health_scope` 中 scope ≠ 当前 `repo_host` 的行不参与当前 Host 推导（保留但不用，留给 Phase B 清理）。
  - 无归属证据时判 `initial`（立即探测），**不判 `failed`**：保守策略的代价最多是一次探测；一次成功即回 `ok`，不会把其他 Host 的失败长期扣在当前 Host 上。
- **幂等**：`INSERT ... ON CONFLICT(source_id,family,scope) DO NOTHING`——重复启动**不重置** `next_probe_at` / `rec_failures` / `last_success_at`（只插不更新）。
- **验证清单**（写入测试）：
  1. 已有且新鲜的成功结果不被降级（`ok` 保持）。
  2. 已有失败记录不被初始化成健康（`failed` 保持）。
  3. `CapNo(0)` / 内容不一致 `(2)` 不被初始化成 `ok`。
  4. `cap=2` 种子迁移保持硬隔离语义，不变成普通 unsupported。
  5. 重复启动不重置 `next_probe_at` / 退避。
  6. 新增源与 Host 改归属能建立正确初始记录。
  7. **三审新增**：`cap=1` 但有失败历史的源，种子迁移判为 `failed`，不判 `ok` / `expired`。

## 5. `registryCandidates` 过渡判定（二审 #2 + #3 + 三审 P1-2 TTL 闸门）

- **删除 legacy OR 分支**：`sources.go:282-285` 的 `(NOT EXISTS scoped) AND (EXISTS legacy fails>=阈值)` 在 A1 从候选查询中移除。旧 `source_health` family='registry' 数据**保留**（不删、不归档，留给 Phase B 做数据退出与回滚）。
- **候选条件（A1 终版，含 TTL 实时闸门）**：

  ```sql
  SELECT ... FROM sources s
  WHERE s.enabled = 1 AND s.status IN ('usable','degraded')
    AND s.registry_cap = 1 AND s.repo_host = ?
    AND s.registry_path_mode IN ('native','host_prefix')
    -- R1：零连续失败，与 §1.2 的 ok 定义逐字一致。
    -- 既有 HealthFails 阈值语义保留在既有健康/诊断路径，不作候选准入唯一判据；
    -- fails >= HealthFails 必然 fails <> 0，已被本条件涵盖。
    AND NOT EXISTS (SELECT 1 FROM source_health_scope z
                    WHERE z.source_id=s.id AND z.family='registry'
                      AND z.scope=? AND z.fails <> 0
                      -- P1-6：只认当前凭据代次的健康样本
                      AND z.gen = COALESCE((SELECT g.gen FROM registry_host_gen g
                                            WHERE g.host=s.repo_host), 0))
    AND EXISTS (SELECT 1 FROM registry_host_recovery r
                WHERE r.source_id=s.id AND r.family='registry'
                  AND r.scope=? AND r.state='ok'
                  -- P1-4：recovery 证据必须属于当前凭据代次（整数比较，非时间）
                  AND r.gen = COALESCE((SELECT g.gen FROM registry_host_gen g
                                        WHERE g.host=s.repo_host), 0)
                  AND r.last_success_at > 0
                  AND r.last_success_at >= ?)                     -- TTL 实时闸门：now - RecoveryVerifyTTL
  ```

- **TTL 实时闸门（三审 P1-2，必须）**：`state` 是 DB 投影，不会随时间自动变化。仅靠 Runner 写回 `expired` 无法保证 TTL 生效（T0 `ok`，T0+24h 未跑 Runner 时仍放行）。因此候选 SQL 直接带 `last_success_at >= now - TTL` 闸门，**即使 Runner 尚未运行，过期 Host 也不进候选**。TTL 动态修改时该查询闸门始终成立，**不只依赖配置变更后批量 UPDATE**。
- **保留 Runner 状态物化**：到期任务进入恢复队列；探测成功更新 `ok`；失败更新 `failed`。这不是第二套状态模型，只是防止投影更新延迟导致过期资格继续生效。
- **`expired` / `failed` 不进候选（三审 P1-1 + 二审 #3）**：只有 `state=='ok'` 且 TTL 闸门通过才准入；`expired` 由 Runner 立即重验，成功后回 `ok`、失败转 `failed`；`failed` 按退避重验，成功后回 `ok`。**不引入 stale-while-revalidate**。没有可用加速候选时，现有架构仍回退官方源——损失的是加速收益，不是信任过期 / 失败的能力结论。
- **候选资格五重约束（用户四审明确，五审 R1 收紧，P1-4 加代次）**：`registry_cap==1` + `scoped.fails==0`（零连续失败，与 §1.2 `ok` 一致）+ `recovery.state=='ok'` + `recovery.gen==currentGen` + TTL 实时闸门，五者同时成立才准入；任一不满足即排除。
- **三条独立闸门不得互相替代（P1-7 复核）**：① `z.scope` 与 `s.repo_host` 必须来自同一个 Go 变量（同一次 `registryhost.Check` 结果），禁止一处 rawHost、一处规范化值；② `recovery.gen==currentGen` 与 `scoped.gen==currentGen` 分别保留，缺一不可；③ `scoped.fails==0` 与 `recovery.state='ok'` 是两个独立条件——前者是历史连续失败闸门，后者是当前恢复投影闸门，不能用一个代替另一个。
- **缺失 recovery 行 = 不进候选**，且由 §6 的 Runner 重发现（不会既不能候选也不被探测）。
- **C5 落地注（实现事实）**：
  - Store 拆成 `registryCandidatesRaw(host)`（只执行 SQL，返回原始候选并带 `last_success_at`）与 `registryCandidates(host)`（raw + `FilterByGuard`）。API 直调走后者；调度缓存只能走前者（`RegistryCandidatesRaw`），命中缓存时用**当前** `now` 重算 `last_success_at >= now-TTL` 再 `FilterByGuard`——否则 SQL 的时间条件会被缓存绕过。
  - `FilterByGuard[T]` 返回独立 slice，不修改输入及其底层数组（缓存保留原始列表，解除屏蔽后可恢复）；协议为 snapshot → filter → verify，epoch 变化整体重试 3 次，耗尽返回空集并累加 `guard_filter_retry_exhausted_total`，禁止退化为未过滤列表。
  - Runner：`CommitHostProbe` 返回 error → `Block(key, gen)` 后 `Invalidate()`；返回 `HostCapsCommitted` → `Invalidate()` 后 `UnblockIfMatch(key, token)`。token 由 Block 产生并存于 Runner 进程内 map（与 Guard 同生命周期，重启一起清空）。`stale / sourceChanged / unavailable` 三类枚举不 Block 也不 Unblock。
  - TTL 只有一个来源：`Store.RecoveryTTL()`（`ML_RECOVERY_TTL`，默认 24h），候选 SQL、缓存重检、Runner 写入共用，避免口径分裂。
  - Guard/缓存/调度入口的键统一为 `(source_id, 'registry', 规范化 host)`；Scheduler 只对 `registry:` 类目过滤，其他类目原样返回。
  - **TTL 时间精度**：cutoff 一律为 `now.Unix() - int64(TTL/time.Second)`，秒级、向下取整，SQL 与 Scheduler 使用同一语义与同一个 `>=` 边界。`ML_RECOVERY_TTL` 最小 1s，小于 1s 的配置被拒绝并回落默认值（否则截断成 0 等价于「全部失效」）。Store 的 `nowTime()` 与 Scheduler 的 `s.now()` 是两个时钟注入点：生产都是系统时间，测试必须各自注入；未命中路径的二次检查用更晚的时间，只会更严格。
  - **`Block` 的 seq 与状态同临界区**：seq 在 `mu.Lock()` 内分配，保证「后写入的条目 seq 更大」，不依赖调用方串行。
- **绝不只查 `recovery.state`**：必须同时 `registry_cap==1` + 路径有效 + TTL 闸门（澄清 2 + 三审 P1-2）。
- 关键点：**保留 legacy 数据可以，保留 legacy 对运行时候选资格的否决权不可以。** 这不等于提前完成 Phase B——A1 只停止旧数据参与决策，B 仍独立负责数据退出。

## 6. Runner 调度（二审 #4 + 三审 P2-5）

- **`recovery` 表为持久化调度唯一权威**；`claim` 仅保留同 `(source, host)` 运行中互斥；现有内存 `probeState.next` / `probeState.backoff` 不再决定准入（deprecate for admission）。
- **6.1 源集合定义统一（三审 P2-5，Runner / 种子 / 候选三者边界写死）：**

  | 集合 | 定义 | 用途 |
  | --- | --- | --- |
  | **恢复状态维护集合**（= §4 种子 + §6 Runner 任务） | `status<>'archived' AND repo_host<>'' AND repo_host<>'ghcr.io'`，**不过滤 `enabled`**，与现有 `hostCaps`/`ListHostCaps` 一致 | 需要维持 recovery 行的所有源，含 disabled；disabled 也保留 Host 状态 |
  | **实际允许参与候选集合** | `enabled=1 AND status IN('usable','degraded')` + §5 全部资格检查 | 真正可进候选的源 |
  | **Runner 是否探测 disabled 源** | **必须单独说明**：disabled 源的 recovery 行存在但**不因该行进入周期性恢复循环**（避免禁用源占探测配额）；其恢复状态维持为"冻结"，待源被重新 enable 时按 §7 唤醒路径立即重探。Runner 的"待探测"查询对 disabled 源返回 false（即使 `next_probe_at<=now`），除非被显式唤醒 | 防止"禁用源有 recovery 行就被无条件周期探测" |

- **待探测选择改为 recovery 驱动**（替换 `ListPendingHostCaps` 的 `registry_cap<>1`）：

  ```sql
  SELECT ... FROM sources s
  WHERE s.status<>'archived' AND s.repo_host<>'' AND s.repo_host<>'ghcr.io'
    AND s.enabled = 1                                   -- §6.1：disabled 源不进周期探测
    AND s.registry_cap <> 2                             -- P1-1：hard-excluded 不进普通循环
    AND NOT EXISTS (SELECT 1 FROM registry_host_recovery r
                    WHERE r.source_id=s.id AND r.family='registry'
                      AND r.scope=s.repo_host AND r.state='hard-excluded')
    AND ( NOT EXISTS (SELECT 1 FROM registry_host_recovery r
                      WHERE r.source_id=s.id AND r.family='registry' AND r.scope=s.repo_host)
       OR EXISTS (SELECT 1 FROM registry_host_recovery r
                  WHERE r.source_id=s.id AND r.family='registry'
                    AND r.scope=s.repo_host AND r.next_probe_at <= ?) )
  ```

  这样 `cap=1` 但 recovery 行缺失 / 到期的源既**不进候选**又**会被 Runner 重探测**；disabled 源既不进候选也不进周期探测，但保留 recovery 行。
- **P1-1：`hard-excluded` 显式排除**：`registry_cap<>2` 与 `state<>'hard-excluded'` 双重条件缺一不可——前者防 cap 未写回时被时间条件捞起，后者防 cap 已变更但 recovery 投影仍为 `hard-excluded`。断言 33 覆盖：`cap=2` 且 `next_probe_at=0` / 已到期两种取值下，周期查询均不返回该源。
- **P1-5：重验入口的可靠性**：`cap=2` 的重验**不依赖内存队列**。`ApplyCredChanges` / `SetRepoHost` 在同一事务内把该 Host 的 recovery 行改写为 `state='initial', gen=新 gen, next_probe_at=now, last_probe_at=0`；提交完成后该行已满足上面的 `next_probe_at<=?` 分支，下一轮周期查询必然捞到（因为 `registry_cap` 同事务被清为 `-1`，不再被 `cap<>2` 排除）。因此**事务内的状态重置是必要且充分的入口**；`WakeHostRecheck` 只是降低延迟的通知，进程退出 / 队列满 / 合并丢失只影响时延，不影响最终重验。
- **调度唤醒与延迟上界（P1-5 补充）**：每轮探测后按最早 `next_probe_at` 设一个 Timer 唤醒（**不新建 Runner**）；保留 6h ticker 做常规扫描 / 对账；**Runner 启动时立即扫一轮**，不等 ticker；`WakeHostRecheck` 丢失时，事务提交的 `next_probe_at=now` 最迟在一个扫描周期（默认 6h，可配置 `RecoveryScanInterval`）内被发现，这是明确的延迟上界，不是数据丢失。多次凭据变更只覆盖同一 recovery 行的 `gen/next_probe_at`，旧通知即使到达也只会触发一次按当前 DB 状态的重扫，不会消费旧代次；非阻塞唤醒信号覆盖新增源 / 改 host / 源被 enable（即时 `Once()`）。短退避（15s → 10m，复用 `maxHostProbeBackoff`）由 `next_probe_at` 表达，**不再等 6h**。
- **非探测失败**（`stale_snapshot` / `cred_pending`）单独临时重排，**不增** `rec_failures`。

**R5：单 Runner 探测互斥前提（必须冻结）：**

- 前提：同一 `(source_id, family, scope, gen)` 在任意时刻**最多一个有效探测提交者**。
- 保证机制：单进程单 `HostProbeRunner` + `claim`（`hostprobe.go:239-252`，`r.mu` 保护的进程内 map；`claim` 对同一 key 先占位、跑完 `finish`）。
- `gen` / `cred_digest` / `repo_host` 守卫只解决"配置变化后的陈旧写回"，**不解决同代次内两个探测的先后覆盖**：A 先启动但慢、B 后启动但快时，B 成功写 `ok` 后 A 仍可凭相同 gen 提交 `failed`。
- 因此 A1 **明确不支持多 Runner 实例**；若未来允许多实例，必须增加 DB 级 claim 或探测序列号（monotonic seq）守卫，不能仅靠当前 `gen`。
- `claim` 的互斥只有**进程内**语义：`probeState.running` + 进程内 map，只保证同一进程的两轮扫描不重复启动同一 key；**不提供跨进程 / 跨实例互斥**。单 `HostProbeRunner` 实例是硬约束，不能把当前 `claim` 当分布式锁用。`next_probe_at` 负责持久化调度，`running` 负责进程内执行互斥，两者不混用。
- **claim 生命周期必须覆盖"探测开始 → 事务提交完成"**：`claim` 在 `runOne` 入口获取，在 `finish`（成功 / 失败 / 超时 / 取消 / 写库失败）统一释放；所有返回路径（含 panic 恢复）都用 `defer` 释放，不能在探测请求返回时提前释放。
- 进程内必须确实只有一个 `HostProbeRunner` 实例；`claim` 的 key 必须包含 `(source_id, family, scope)`，与 Guard、候选 SQL 的 scope 同源。
- 断言：注入超时、取消、`CommitHostProbe` 返回错误三条退出路径，均能在下一轮立即重新 `claim`，不出现永久占位；claim 覆盖期间 Guard 的 Block 不得被提前解除。

## 7. 运行时 recovery 行建立（澄清 3）

- 全量种子只解决启动数据；运行时 `AddSource`（直接带 `repo_host`，`store.go:732-745`）/ `SetRepoHost` 改归属，必须在**同一事务内**建 `initial` recovery 行（或 ensure），`SetRepoHost` 同事务清理旧 Host 的 recovery 行；**成功提交后才发唤醒**，不寄望 6h 周期重建。
- 源的 `enabled` 从 0 变 1 时：恢复行若已存在则不动，**发一次非阻塞唤醒**让其立即重探（§6.1）。
- **`hard-excluded` 的重验生命周期（P1-5）**：事实来源是 recovery 行的持久化状态，不是通知。`ApplyCredChanges` / `SetRepoHost` 在**同一事务**内完成：`registry_cap=-1`、`state='initial'`、`gen=变更后的 registry_host_gen.gen`、`last_probe_at=0`、`next_probe_at=now`。事务提交即形成可被 §6 查询发现的重验任务，不依赖任何进程内队列。
- `WakeHostRecheck(sourceID)` 仅作为**延迟优化**：非阻塞通知 Runner 立即扫一轮；队列满 / 未启动 / 进程退出时直接丢弃，正确性不受影响。不得把它写成唯一入口，也不得用它表达状态转换。
- **C4 落地（2026-11-12）**：不实现 `WakeHostRecheck` 内存队列。`registry_host_recovery.next_probe_at` 是调度唯一权威，Runner 主循环按 `ScanInterval`（默认 30s，`ML_HOSTPROBE_SCAN`）调用 `store.ListDueHostProbes(now)`；`Interval`（默认 6h）只负责 `reconcileRepos` 全量对账。恢复延迟因此是 30s 量级，且不存在「通知丢失 / 队列满 / 进程重启」路径。注意 `Once` 是串行的（内部 `wg.Wait`），一轮里最慢的探测会顺延下一轮扫描，所以 30s 只是扫描节拍，不是严格上界；最坏延迟 ≈ 30s + 本轮整批探测耗时。`enabled` 由 0 改 1 时，`UpdateSource` 在同一次写入里把该源的 `next_probe_at` 拉到 now，不必等完失败退避。
- `enabled` 0→1 **不解除** `hard-excluded`（`registry_cap=2` 或 `state='hard-excluded'` 仍被 `ListDueHostProbes` 排除）。重新启用来源与重新验证一个已被判定为 hard-excluded 的 Registry 是两种操作，后者只能由凭据变更、Host 变更或显式重验触发。
- `ListDueHostProbes` 的边界：`status<>'archived'`、`repo_host` 非空且非 `ghcr.io`、`enabled=1`、`registry_cap<>2`、无 `state='hard-excluded'`，且（recovery 行缺失 或 `next_probe_at<=now`）。recovery 行缺失不等于健康——`cap=1` 但缺行也入队。
- 若未来确实需要"持久化待重验标记"（例如按 Host 单独重验而不改 cap），必须落在 recovery 行（如 `recheck_requested` 列），并在探测提交的同一事务内清除；A1 不需要该列，因为 `state/gen/next_probe_at` 已足以表达。
- `AddSource`：source 行与 recovery 行必须在**同一事务**内创建（`gen=currentGen, state='initial', next_probe_at=now`）；事务提交成功后才发唤醒，失败不发。
- `SetRepoHost`：同一事务内删除旧 Host 的 `source_health_scope`（`family='registry', scope=旧Host`）与旧 recovery 行，插入新 Host 的 recovery 行（`gen=currentGen`，`scope=registryhost.Check(新Host)`）；旧 Host 的其它源不受影响；提交成功后才发唤醒。
- 唤醒任务只携带 `source_id`：消费时以 DB 当前行为准（`repo_host` / `scope` / `gen` 均现读），因此同一 source 连续改 Host 时，旧任务即使存活也只会触发一次"按当前配置重扫"，不会用旧 Host 覆盖新状态。

## 8. 恢复状态 TTL（采纳二审 #10）

- 定义 `RecoveryVerifyTTL`（建议默认 24h，可配置）：`registry_cap==1` 的 Host，若 `now - last_success_at > TTL` → 判为 `expired`，进入一次受控重验。
- 重验仍 `cap==1` → 回到 `ok`，不抖动；重验失败 → `failed` + 退避。
- TTL 不替代 `reconcileRepos` / `ApplyCredChanges`（凭据 / 仓库变更立即重置），仅处理"cap 仍 1 但结果过旧"的情况。
- TTL 修改后**无需批量 UPDATE**：§5 候选查询闸门在每次查询时按当前 TTL 实时判断（三审 P1-2）。
- **边界统一（P2 补充）**：状态判定用 `now - last_success_at > TTL`，候选 SQL 用 `last_success_at >= now - TTL`，两者是同一不等式的补集，实现必须共用同一个 `now` 与同一个 TTL 值，禁止一处用 `>=`、另一处用 `>`。
- **缩短 TTL**：候选 SQL 立即生效（实时计算），不需要等 Runner；Runner 在下一轮 `next_probe_at` 或 6h ticker 时把行物化为 `expired` 并重验。候选资格先于投影更新被收紧，方向安全。
- **延长 TTL**：不自动把已 `expired` 的行放回候选。候选要求 `state='ok'`，`expired` 行仍被拒；必须重验成功写回 `ok` 才恢复。避免"改配置即放行未经重验的旧成功"。
- **Runner 及时性**：TTL 缩短后，已在 `next_probe_at` 远期的 `ok` 行不会被立即重探，但已因 SQL 闸门失去候选资格；不构成"继续使用过期能力"。若需要更快恢复加速，触发一次非阻塞唤醒扫轮，不改变正确性。

## 9. 真实 Runner 测试的最小 DI 边界（采纳二审 #11，已查代码定论）

- **结论：不需要抽象 `Creds` 接口**。经查 `internal/secret/creds.go`：`NewCredStore(path, key, db)` 仅需临时目录 + 内存随机 32 字节 key + 测试用 `store.DB`；空凭据文档 + `Reconcile()` 后 `Snapshot(host)` 对**无凭据的公开 Host** 返回 `{Generation:0, Digest:"", HasCredential:false}`（不报错，`creds.go:284-289`），对有凭据 Host 可 `Put` 测试用户名 / 密码（内存 key 加密到临时文件，无外部依赖）。
- 因此真实 Runner 测试走**真实调用链**：注入 `o.Probe`（可控 registry 响应）、`o.Now`、`o.Repos`、临时 DB、`o.Creds`（真实测试构造的 Store）+ 可控 DNS resolver，覆盖 `CapYes` / `CapUnknown(transport)` / `CapUnknown(auth)` / `CapNo` / `CapMismatch` / 超时 / DNS / 陈旧快照。无需抽出 `Creds` 接口。
- 若后续发现真实 Store 在测试中存在文件锁 / 跨进程副作用等不可控因素，再评估最小接口——但当前证据支持直接用。
- **failClosed 的注入边界（R3）**：`failClosed` 必须是**一个**进程内实例，被 Runner（写）、`Store.registryCandidates`（读）、`Scheduler.CandidatesN`（读缓存）共享。最小实现（P1-4 接口闭合）：
  ```go
  type GuardKey struct{ SourceID int64; Family, Scope string }
  type GuardToken struct{ Gen int64; Seq uint64 }

  func NewRecoveryGuard() *RecoveryGuard
  func (g *RecoveryGuard) Block(k GuardKey, gen int64) GuardToken
  func (g *RecoveryGuard) UnblockIfMatch(k GuardKey, t GuardToken) bool
  func FilterByGuard[T any](g *RecoveryGuard, list []T, key func(T) GuardKey) []T
  ```
  `Block` 返回本次置位的 token（`seq` 为进程级全局单调），`UnblockIfMatch` 用 `(gen,seq)` 全等比较；快照条目同时携带 `Gen/Seq`，否则 Filter 无法表达置位身份。用泛型函数而非接口：Store 的 `SourceStat` 与 Scheduler 的 `Candidate` 都能在调用点提供键函数，不需要把 Guard 下沉成包依赖。
  **同步契约（P2-3）**：`Block` 与 `UnblockIfMatch` 必须在**同一把写锁**内修改 blocked map 并 `epoch++`（`UnblockIfMatch` 即使未实际删除也要递增，防止"Block→Unblock→集合复原"逃过 Verify）；`Snapshot` / `Verify` 在同一把读锁临界区内完成拷贝与比较；`epoch` 用 `atomic.Uint64` 单调递增，进程生命周期内不回绕、不复用；返回的 `seq` 取自**进程级** `atomic.Uint64` 全局单调计数器，不是 per-key 计数器——同一 key 删除后重新 Block 也绝不会复用旧 `seq`，`UnblockIfMatch` 的 `(gen,seq)` 全等比较因此无 ABA。`Filter` 是唯一过滤出口，内部完成 snapshot → filter → verify → retry（3 次后 fail-closed 空集）。
  **Runner token map 的并发边界**：`unblockRoute` 解除的是「该 key 在 map 中的最新 token」，不是本次任务独占的 token。这个语义只在**同一 `host|sourceID` 的探测任务串行**时成立——A1 由 claim 的 `running` 保证（持有到 `CommitHostProbe` 完成），且只支持单 Runner。多 Runner / 多实例不在 A1 支持范围（Guard 与 claim 都是进程内状态）；将来放宽并发约束时必须重新设计 token 所有权（例如探测开始记录 seq 基线，成功只解除基线之前的条目），不能沿用当前语义。

**生产实例唯一性（P2-4 补充）**：`guard` 只能在进程装配点创建一次（`main.go`），经 `Store.SetRecoveryGuard` 注入（nil 返回 error），Scheduler 与 API 直调都从 `Store.RecoveryGuard()` 读同一指针，Runner 由 `HostProbeOptions.Guard` 接收同一实例；`main` 启动时显式断言 `st.RecoveryGuard() == guard`，否则 `log.Fatalf`。`nil` 只允许出现在单元测试构造中（`FilterByGuard` 对 nil 原样返回），生产装配失败即终止启动，不允许"静默不过滤"。断言 36 覆盖。当前工作树**不存在** `RecoveryGuard`（现有 `guard` 均为 `safehttp` / HTTP 中间件，与恢复准入无关）；A1 新增，唯一创建点在 `main.go`（现有唯一 Runner 构造点为 `main.go:319`），`NewHostProbeRunner` / Scheduler / Store 的构造参数把 `RecoveryGuard` 设为**必填**而非可选，从签名上排除漏注入。不新增包、不新增外部依赖、不持久化。

### 10.1 A 阶段强制断言（共 37 条）

**原有 9 条**：
1. 恢复成功不修改 `breaker_state`。
2. Host A 恢复不改变 Host B 的候选资格。
3. `CapNo(0)` 不进入短周期恢复探测。
4. `CapUnknown(-1)` 不自动升级为 `CapYes(1)`。
5. 旧凭据代次的探测结果不能写入恢复状态。
6. 陈旧快照不更新恢复状态和退避时间。
7. 首次启动和运行时新增 Host 都能及时进入探测队列。
8. 已有失败记录不能因种子迁移被初始化成健康。
9. 恢复状态缺失不能被解释为健康，也不能无限期依赖 legacy fallback。

**二审补充 8 条**：
10. `cap=2` 种子迁移保持硬隔离语义，不变成普通 unsupported。
11. `expired` 候选资格按冻结后的明确策略（不进候选），无隐式 stale-while-revalidate。
12. legacy 跨 Host 污染：Host A 有 recovery 行时，不得被 Host B 的 legacy 失败排除。
13. 写回中途凭据变更：不能出现新 cap 与旧 recovery 状态组合。
14. 短退避唤醒：15s 到期后无需等 6h ticker。
15. `cap=1` 但 recovery 缺失：不进候选，且能被 Runner 重发现。
16. 凭据变更：旧代次退避不阻止新凭据立即重探。
17. 修改 Host 归属：旧 recovery 行清除、新 recovery 行建立、其他 Host 不受影响。

**三审补充 5 条**：
18. **（核心）** `cap=1` 的 Host TTL 过期后重探失败 → `state=failed`，不进候选，不因 `registry_cap==1` 重新准入；恢复成功后才回 `ok`。（三审 P1-1）
19. TTL 闸门实时生效：Runner 未运行时，超过 `RecoveryVerifyTTL` 的 `state=ok` 行**也不进候选**（候选 SQL 的 `last_success_at >= now-TTL`）。（三审 P1-2）
20. `CapUnknown` 两个子类（transport / auth+incomplete）均落 `state=failed`、`rec_failures+1`、**按既有语义累加当前 `gen` 行的 `scoped.fails`**；区别仅在 `registry_cap`：auth+incomplete 写 `-1`（既有路径），transport 保留历史值（新增路径，不调用重置为 `-1` 的通用写回）。`CapNo`/`CapMismatch`/`stale_snapshot` 不写 `scoped.fails`。（用户四审裁定）
21. 源集合一致性：种子（§4）、Runner 任务（§6.1）、Phase B 覆盖（§11）三者对 archived / 空 Host / ghcr.io / disabled 的取舍完全一致；disabled 源保留 recovery 行但不进周期探测。（三审 P2-5）
22. claim 仅探测互斥；陈旧写回被 DB 事务的 `repo_host/gen/cred_digest/status` 守卫拒绝，而非仅靠内存 `claim`。（三审 P2-6）

23. **（用户四审指定核心测试）** `cap=1` 的 Host 遇 DNS / timeout：`registry_cap` 仍为 `1`、`source_health_scope.fails` 增加、`recovery.state=failed`、候选被拒绝；恢复成功后重新确认能力与路径，再恢复候选资格。
    - **必须单独证明隔离机制（R1 收紧后要用 fixture 拆开两个闸门）**：R1 把候选 SQL 收紧为 `fails==0` 后，单次 DNS 失败会同时被 `fails!=0` 与 `state!=ok` 拒绝，端到端场景已无法单独归因。因此分三条验证：
      (a) fixture：`cap=1`、`scoped.fails=0`、`recovery.state='failed'`、TTL 有效 → 断言候选**被拒**（单独证明 recovery 闸门）；
      (b) fixture：`cap=1`、`scoped.fails=1`、`recovery.state='ok'`、TTL 有效 → 断言候选**被拒**（单独证明 R1 零失败闸门，即断言 25）；
      (c) 端到端 DNS/timeout：只断言最终不进候选、cap 保留、scoped fails+1、recovery failed；不再用它单独归因某一个闸门。
24. **（用户四审要求）** 注入 `CommitHostProbe` 写失败：候选立即被拒（`failClosed` 内存层），重试成功后 DB 中 `recovery.state=failed`；重启场景下，启动物化把 `state='ok' AND next_probe_at<=now` 置为 `expired`，首轮探测完成前不放行。
**五审补充 8 条（R1–R5 + 二轮并发）：**

25. **R1 一致性**：构造 `cap=1`、`scoped.fails=1`、`HealthFails=3`、人为让 `recovery.state='ok'` 且 `last_success_at` 仍在 TTL 内，断言候选**被拒**；并断言既有 `fails >= HealthFails` 的隔离/诊断语义未被删除。

**五审二轮补充 3 条（R3 并发 + R5 生命周期）：**

30. **R3 线性化（交错时序）**：① 在 `Filter` 的 `Snapshot` 与 `Verify` 之间注入 `Block`，断言本次返回**排除**该 key（epoch 变 → 重试）；② 在 `Verify` 成功之后、返回之前注入 `Block`，断言本次返回**包含**该 key（线性化在前）、且**下一次**返回排除；③ 缓存命中 / 未命中 / Store 直调三条路径各跑一遍；④ 连续注入 4 次 `Block` 使重试耗尽，断言返回空集并打点 `guard_filter_retry_exhausted_total`；⑤ 断言 `Block` 与 `UnblockIfMatch` 均递增 `epoch`，且 `Verify` 观察到 `UnblockIfMatch` 造成的版本变化。
31. **R3 清理竞态与 ABA**：持有旧 `gen/seq` 的 `UnblockIfMatch` 不得删除新代次已置位的项；同一 key 执行 `Block(seq=10) → UnblockIfMatch(seq=10) → Block` 后新项 `seq` 必须 ≠10（全局单调），旧清理不得误删；并发 `Block` / `UnblockIfMatch` 在 `-race` 下无竞态、无丢失置位。
32. **R5 claim 生命周期**：注入超时、取消、`CommitHostProbe` 返回错误三条退出路径，claim 均被释放且下一轮可立即重新获取；claim 覆盖期间 Guard 的 Block 不被提前解除。

**五审三轮补充 3 条（P1 缺陷 + 交叉核验）：**

33. **P1-1 hard-excluded 隔离**：`cap=2` 且 `state='hard-excluded'` 的源，在 `next_probe_at=0` 与 `next_probe_at<=now` 两种取值下，§6 周期查询均不返回；`WakeHostRecheck(id)` 能使其被一次性重验，重验后仍不进入普通循环。
34. **P1-2/P1-4/P1-6 凭据代次闭合（含 scoped）**：构造 `scoped(gen=5, fails=3)`、`scoped(gen=5, ok_at>0)`、`recovery.gen=5`、`registry_host_gen.gen=6`，执行 `ApplyCredChanges` 后：① `state='initial'`，不是 `failed`、不是 `ok`；② §5 候选 SQL 拒绝该源，且不是被 `fails<>0` 单独拒绝（用 `scoped(gen=6, fails=0)` 对照证明 gen 条件生效）；③ 新代次首次探测失败写入 `scoped(gen=6, fails=1)` → `failed`，首次成功写入 `scoped(gen=6, fails=0)` → `ok`；④ 迁移旧行 `gen=0` 且 `currentGen>0` → `initial`；`currentGen=0` 时 `gen=0` 历史可用；⑤ `gen` 相等、差 1、凭据变更与探测同秒三个用例结果一致（判据是整数，不受秒级精度影响）；
  ⑥ **并发竞态（P1-7）**：探测以 `snap.Generation=5` 启动，其间 `ApplyCredChanges` 把当前 gen 推进到 6 并提交；旧探测随后调用 `CommitHostProbe(..., gen=5, credDigest=旧摘要)` → 事务内比对失败、整体回滚，返回 `HostCapsStaleSnapshot`。断言提交前后**全状态快照逐字段相等**：
  - `source_health_scope`：不出现 `gen=6` 行，且 `gen=5` 旧行的 `fails/ok_at/last_at` 均未被更新；
  - `sources`：`registry_cap`、`registry_path_mode`、`registry_probe_at`、`registry_probe_error` 全部不变；
  - `registry_host_recovery`：行不存在时仍不存在，存在时 `state/gen/last_probe_at/next_probe_at/rec_failures/last_error/last_success_at` 全部不变。
  用可控的 `Creds.Snapshot` / `Probe` 钩子 + channel/barrier 建立确定性时序，不用 sleep。
35. **P1-3 / P2 交叉**：① 种子迁移中 `cap=1` + 超 TTL + 当前代次失败证据 → `failed`（不是 `expired`）；② `cap=1` + `fails=0` + `last_success_at=0` → `initial`；③ 成功提交清空 `last_error`、失败写入、`stale_snapshot` 不修改；④ 同一 Host 以 `LSCR.IO.` / `lscr.io:443` / 混合大小写输入时，`sources.repo_host`、`source_health_scope.scope`、`recovery.scope`、Runner claim、Guard key、SQL 参数取到同一规范化字符串。

**六审补充 2 条（P1-4/P1-5 + 构造链）：**

36. **Guard 生产实例唯一**：进程装配后断言 `Store.guard`、`Scheduler.guard`、`Runner.guard` 为同一非 nil 指针；任一构造路径传入 nil 时生产构造失败（不允许静默不过滤）；三入口在 `Block` 后同时不返回该源。
37. **TTL 边界与调度一致性**：① 缩短 TTL 后，未重探的 `ok` 行立即被候选 SQL 拒绝；② 延长 TTL 后，已 `expired` 的行不自动回候选，必须重探成功写回 `ok`；③ 状态判定与候选 SQL 使用同一个 `now` 与 TTL，边界值 `now-last_success_at == TTL` 两侧结果互补、无重叠空洞。
