## 一、要解决的问题（承接 3.5.22 §4.8）

200-only 候选失败路径：当前源正常时，某个 HTTP 200 且不支持 Range 的源凭历史高样本通过 `replayCostOK`，被选为候选后 5s 只回放一部分，旧源已关闭且无回退 → 客户端下载失败。生产实测中 638 触发过一次（期望 64,396,988，实得 3,714,854）。

3.5.22 未修此路径，仅定位并记录；3.5.23 以方案 A 修。

---

## 二、已知边界（纳入背景，不扩大实施范围）

以下四条为已定位事实实施的边界，纳入本文作为背景与约束，不改变 F1–F4 范围：

1. **200-only 失败路径的暴露面低但无代码硬保证。** docker `sched_order=[54,88]`，638 不在 docker 候选；88 近 5 条中位约 0.75MB/s，10MB 前缀估算约 13s > 5s，会被 `replay_over_budget` 拒绝。但一旦把 638 加进 docker 顺序，或 88 出现高样本后实际骤降，仍可触发。**操作约束：3.5.23 方案 A 落地前维持 `[54,88]`，不要把 638 加入 docker 候选。**该约束属生产配置变更，须单独授权，不在无人值守范围内。
2. **自然状态换源未长期验证。** 生产成功接管只做过 1 次，且是临时改 `sched_order` + 给 638 打星标 + 写 3 条新鲜样本构造出的受控条件。真实自然条件下「星标源 ≥2 + 新鲜样本 ≥3 + 当前源确实慢」三者同时满足概率很低，不要期待常态生效。
3. **`C×1.2` 抖动样本不足。** 只有一次真实接管（c_bps=339,968、threshold=1,451,538），不宣称长期稳定。
4. **`P_i/1.3` 偏严为观察项。** 两源同时可用时 88 ghcr(3867KB/s) 因同伴 638(12914KB/s) 被拒（T=9934）；638 不可用时 peer=0，88 才可能被接受。是否过严尚未真实环境确认，列为观察项；3.5.23 不为此调整门槛系数。

## 三、3.5.22 与 3.5.23 的修复逻辑区别（关键）

两版都在改"换源候选/门槛"，但**作用对象和阶段不同**，不可混为一谈：

| 维度 | 3.5.22（已部署） | 3.5.23（本版冻结） |
|---|---|---|
| 修复目标 | 慢源换不动：门槛太高、候选够不着 | 200-only 候选回放超时且无回退 → 客户端失败 |
| 逻辑层面 | **门槛数值 + 进度闸门**：降门槛 `T_i=max(F, P_i/1.3, C×1.2)`、`switch_floor` 8→1、`sent≤min(上限,0.8×total)`、HTTP 200 回放预算 5s、206 头部门禁、回放可取消 | **候选资格（fail-closed）**：中途接管候选必须 `RangeCap==1`；测速与接管共用同一合格集合；`switchAcceptable` 兜底拒 HTTP 200 |
| 对 200-only 源 | 允许其进入候选，靠 `replayCostOK` 估算成本（历史样本可严重偏离 → 失败根因） | 直接排除出中途接管候选集合；200-only 仍可做初始源/回退源，只是不参与中途接管 |
| `P_i/1.3` / `C×1.2` 系数 | 引入并依赖这些系数算门槛 | **不改系数**；仅改变"哪些源进入 peerMedianBps 的分母/集合" |
| 失败路径 | 回放超时 → `savePartial(); finished=true; return`，无回退 | 不合格源根本不进入接管 → 该失败路径被移除 |
| 代码影响面 | config/migrate、watch.go 门槛与回放、stream.go Body 校验 | `watch.go` 的 `switchCandidates` 集中过滤 + `switchAcceptable` 200 兜底 + 测试夹具/回归；不改 stream.go 核心状态机 |

一句话：**3.5.22 调的是"门槛和回放规则"，仍让 200-only 源有机会当候选；3.5.23 调的是"候选准入"——先把不合格源挡在门外，门槛只对合格候选生效。** 3.5.22 的 5s 预算等机制保留，但不再被 200-only 源触发。

## 四、冻结范围：F1–F4

### F1 中途接管候选资格（fail-closed）
- 资格门统一为 `RangeCap == 1`；`RangeCap != 1`（含 0 与 -1）一律不得参与中途接管。
- 不区分"不支持(0)"与"未检测(-1)"；生产数据模型 `-1=未检测`（`sources.go:66` 注释、`canonical.sql:51 DEFAULT -1`），但本版统一 fail-closed。

### F2 速度中位数与实际接管共用候选集
- `peerMedianBps` 与 `trySwitchWithSpeed` 使用同一套过滤后的合格候选。
- 候选失败/被排除后，动态门槛基于剩余合格候选重新计算。

### F3 中途接管拒绝候选 HTTP 200
- `switchAcceptable` 兜底：候选以 HTTP 200 响应时拒绝接管；当前源 HTTP 200、候选 HTTP 206 的正常接管保留。
- 初始源/普通故障转移的 HTTP 200 不受影响。

### F4 测试夹具迁移与回归验证

#### F4.1 现有测试夹具清查与迁移
- 清查范围：6 个测试文件、15 处 `Preferred` 候选构造。
- 逐一确认每处测试真实意图：预期具备中途 Range 接管能力且断言接管成功者显式设 `RangeCap: 1`；不支持 Range 场景保留 0；未测能力场景保留 -1。
- **禁止机械地把全部 15 处统一改成 `RangeCap: 1`。**
- **不得**通过放宽生产过滤条件、把 `RangeCap == 0` 视为合格、或增加测试专用绕过逻辑来解决测试失败。

#### F4.2 原有测试修订
- `watch_switch_test.go` 中"200 长度一致"用例：`wantOK` 由 true 改为拒绝。
- 保留当前源 HTTP 200、候选 HTTP 206 的正常接管场景。
- 排查其他依赖候选 HTTP 200 接管的旧断言，全部调整为符合新规则预期。
- 保留初始源 HTTP 200 的正常下载测试，不得把中途接管限制扩大到初始下载路径。

#### F4.3 新增回归测试（T1–T9）
| 编号 | 测试场景 | 预期结果 |
|---|---|---|
| T1 | 候选 `RangeCap=0` | 不参与中途接管 |
| T2 | 候选 `RangeCap=-1` | 不参与中途接管 |
| T3 | 不合格候选历史速度较高 | 不得进入 `peerMedianBps`，不得抬高速度门槛 |
| T4 | 排除不合格候选后，合格候选达门槛 | 正常接管 |
| T5 | 候选返回 HTTP 200 且 Content-Length 等于 total | 拒绝接管 |
| T6 | 当前源 HTTP 200，候选 HTTP 206 | 允许正常接管 |
| T7 | 所有候选均不满足 `RangeCap==1` | 返回 `ok=false`，当前流继续 |
| T8 | 候选 `RangeCap=1`，返回合法 HTTP 206 | 正常接管 |
| T9 | 候选 A 失败、候选 B 合格 | 基于剩余合格候选重新计算动态门槛 |

#### F4.4 候选集合一致性（本轮原裁定，逐字纳入）

`switchCandidates` 是统一资格过滤的唯一实施落点。

必须确保：
* `peerMedianBps` 使用过滤后的合格候选。
* `trySwitchWithSpeed` 的实际接管循环使用同一资格规则。
* 候选失败或被排除后，动态速度门槛仍只基于剩余合格候选计算。
* 不允许出现测速计算使用一套候选、实际接管使用另一套候选的情况。

**过滤落点约束（防止误伤与错误修复）：**
* `RangeCap != 1` 过滤必须且只能写在 `switchCandidates()` 函数体内，置于返回候选之前。**不得下沉**到 `targets()`、`parTargets` 注入函数、`fetchTarget` 构造层或调度器 `Candidates()` 中。
* 依据：`g.parTargets` 是三路共享注入点——`watch.go:309`（本路径，`switchCandidates`）、`parallel.go:65`（并行填充）、`midparallel.go:86`（中途并行）。若把过滤下沉到这些共享层，会连带影响并行路径的候选。并行路径已有自己的 `rangeKnownOff` 门槛（`parallel.go:793-799`），其测试夹具（`parallel_test.go` 等十余处）不设 RangeCap 是合理的，不应被本次修复波及。
* 因此禁止给并行/中途并行夹具机械补 `RangeCap: 1`，那会引入与本次修复无关的改动，且违反 F4.1 的语义决定原则。

**夹具清查口径（配合 F4.1/F4.5）：**
* 全量清查范围：6 个测试文件、15 处 `Preferred` 候选构造，作为覆盖上限登记。
* 其中真正经过 `switchCandidates` 过滤的是 12 处：`firstbyte_test.go` 6 处、`switch_dynamic_test.go` 5 处、`switch_flow_test.go` 1 处。这 12 处须按各自测试语义决定是否设 `RangeCap: 1`。
* 另 3 处（`exp_switch_gate_test.go`、`single_source_test.go`、`stream_switch_test.go`）虽注入 `parTargets`，但测试体内未直接调用换源函数；确认其不受过滤影响后登记为"无需迁移"，不无差别修改。

#### F4.5 门禁
- 15 处构造全审；正向夹具正确声明 1；0/-1 负向仍验 fail-closed。
- 候选集合为空时须有测试确认 `trySwitch` 返回 `ok=false` 且当前下载流不中断。
- 全部测试通过；**禁止**放宽资格条件或删除有效断言来消除测试失败。

## 五、明确不纳入 3.5.23

- `stream.go` 核心状态机重构。
- 扩大 5 秒回放预算。
- 旧源 Body 回退机制。
- 初始源与普通故障转移逻辑改造。
- 3.5.22 性能算法（`T_i=max(F,P_i/1.3,C×1.2)` 等）重写。
- `P_i/1.3` 门槛系数调整（仅列观察项）。
- 生产配置变更（如 docker `sched_order`）、生产部署。
