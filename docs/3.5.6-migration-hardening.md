# 3.5.6 迁移加固冻结规格与验收矩阵

状态：**冻结**。本文件定义 3.5.6 的迁移正确性边界；实现不得越过本文件扩大
改造范围（不重构 Store、健康模型、Registry 候选池或代理链路）。

## 1. 单一 Canonical Schema

3.4.6、3.5.4 只作为**离线迁移输入**；3.5.6 运行时只接受一套 Canonical Schema。
迁移是一次性、不可逆的单向升级，不保留旧二进制回滚兼容层。

固定输入 Schema 指纹（由 `schema.Hash` 计算，排除行数据）：

| baseline | sha256 |
|---|---|
| 3.4.6 | `972db548d1eac569aec7ae11d859cdfbcd9114a0ee2dd1217ca085ca5a4d835f` |
| 3.5.4 | `4af3f62e273685b10493cafdeb7c6745b8d98d87e017dc1445b42ca66308cffb` |

Canonical 输出结构 hash：

`7b984881e7875f712b9a71162cc9d3615690efe42a6f5db1185c1e5138e8f51e`

新库（`init`/`EnsureFresh`）与两条真实迁移路径必须得到同一 hash。

## 2. M7 冻结：历史迁移只保留审计事实

- 3.5.4 输入中的三条 `schema_migrations` 记录，原样搬到 Canonical 的
  `schema_migrations_audit`：`name`、`applied_at`、`checksum`、`checksum_origin`
  逐列复制，不重算、不修正、不“修复”历史 checksum。
- 新库的 `schema_migrations_audit` 是**空表**；空库不得伪造任何旧版本记录。
- 运行时和迁移工具都不读取审计表来执行迁移；不调用旧 `runStep`，不执行历史
  checksum 校验链，不把审计表当作锁或完成标记。
- 旧的 `schema_migrations` 表名不再进入 Canonical；旧源码中的历史 SQL/checksum
  常量只作为历史证据保留，`Open` 不调用 `migrate()`。
- 语义一句话：**保留历史事实，不保留历史执行机制。**

## 3. M8 冻结：单记录元数据与原子初始化

- `schema_meta` 是单记录模型：`id INTEGER PRIMARY KEY CHECK (id = 1)`；
  `schema_version`、`schema_hash`、`baseline_version`、`applied_at` 属于同一行。
- `EnsureFresh` 在**同一事务**内执行完整 Canonical DDL、在事务内计算结构 hash、
  插入唯一 `schema_meta` 行；任何一步失败回滚，不留下半成品表。
- `ReadMeta` 先 `count(*)`：恰好 1 行才继续；0 行或多行都拒绝启动，不能“取第一行”。
- `Verify` 要求 `schema_meta.schema_version` 等于当前版本，并重算实际结构 hash
  与 `schema_meta.schema_hash` 完全一致。
- 升级脚本用**不可变镜像身份**校验容器：优先比对容器 `.Image` 与
  `--expect-image-id sha256:...`；只给 tag 时必须解析 tag 得到实际 image ID 再比对。
  可变 tag 相同不能证明镜像身份。
- `schema_meta` 单记录是 DDL 硬约束；`ReadMeta` 的行数检查是第二道防线，
  不互相替代。

## 4. M1–M6 冻结行为

| 项 | 冻结行为 |
|---|---|
| M1 | 3.5.4 有 `repo_host`：原样复制，**55 条空 Host 保持空串**；3.4.6 无该列：按能力显式映射（`docker_cap=1` → `docker.io`，仅 `ghcr_cap=1` → `ghcr.io`，其余空串），不统一写空串 |
| M2 | 迁移前计算输入结构指纹并与冻结值比较；未知结构直接拒绝；`--force-baseline` 保留为废弃参数，但**不能绕过**指纹/结构校验；3.5.3 明确拒绝 |
| M3 | 复制后逐表比对行数 + 公共列按主键排序的内容 SHA-256；缺列必须有明确映射，否则拒绝；不能只报行数 |
| M4 | `sources.repo_host` 非空值逐个调用 `registryhost.Check`；空串合法；未知/非法 Host 在创建输出前拒绝；合法别名（如 `registry-1.docker.io`）复制时显式规范化为 `docker.io` |
| M5 | 先把新库写到同目录临时文件并校验，再**单次 `mv`** 替换正式库；旧 WAL/SHM 先移到工作目录，不先 `rm` 正式库；staging 旧库和新库都 checkpoint/关闭并断言无残留 sidecar；崩溃注入有 journal 恢复 |
| M6 | 容器停止校验之外，先拿 `.mirror-lens.lock` 再扫描 FD，切换前再次扫描；其他 UID 的 FD 不可读时 **fail-closed**，不能带着未知写入者切换 |

## 6. 已执行的证据

- `go test ./...`、`go vet ./...`、`go test -race ./...` 和 `go build -buildvcs=false`：通过。
- 真实 3.4.6：Canonical 25 表、164,369 checks、91 sources；3.4.6 源端缺少的 7 个表中 6 张数据表为空、schema_meta 单行；`repo_host` 按能力映射为 34 个 `docker.io`、2 个 `ghcr.io`、55 个空串；输出 `schema_hash=7b984...`。
- 真实 3.5.4：Canonical 25 表、190,670 checks、91 sources、55 空 Host、36 非空 Host；
  `schema_migrations_audit` 3 行；输出同一 hash。
- 独立比对脚本按主键序、列类型标签编码重算源/目标内容哈希：3.4.6 和 3.5.4
  各 24 张数据表 `common_sha_equal=true`（schema_meta 单行另验），无行数差。
- `scripts/upgrade_test.sh` 覆盖正常升级、WAL/SHM manifest、db 篡改、manifest
  缺失/越界、6 个崩溃点（含 rename 后 fsync 前、rename 后）、journal 幂等；全部通过
  （`PASS=29 FAIL=0 SKIP=0`，脚本要求真实 3.4.6 副本）。
- M6 另外以 uid 10000 运行脚本、用 root 伪造一个不可读的 `/proc/<pid>/fd`
  目录：脚本以 “其他 UID 的进程 fd 不可读” 拒绝升级，未触碰正式库。
- 生产切换仍按高危流程执行：先备份 DB/key、校验 manifest、停容器、离线迁移、
  `verify`、切换镜像；不在本文件中预授权生产操作。
