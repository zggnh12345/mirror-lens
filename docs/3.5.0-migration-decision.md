# 3.5.0 数据库迁移路线决策记录（追认）

> 状态：**追认文档**。记录既成事实与可验证依据，不是当初的事前决策记录。
> 事实基线：`v3.4.6`、`v3.5.0` 源码，`42f100c` 提交说明，当前 HEAD `a32f5f1`。
> 写作原因：版本迭代后只剩口头记忆，需要把「增量路线 / 没有单事务 / 哪些不可回退」落到仓库里。

## 1. 结论

- 3.5.0 走的是**增量、可重复执行、旧版本仍可启动**的迁移路线：只加列、加表、加索引、幂等回填，不重建 `sources`。
- **不存在「3.5.0 选了 A、之后没有回到单事务」这段历史。** 逐条 `Exec`、每条隐式提交的写法在 3.4.6 就已经是那样，3.5.0 只是继续往上加步骤。仓库里没有任何提交或文档讨论过「放弃单事务」。
- 现状必须如实描述为：**启动迁移不是原子的**，靠幂等（`IF NOT EXISTS`、列探测、幂等回填）收敛，中断后可续跑，但没有进度记录。

## 3. 为什么走增量路线（可验证的技术理由）

1. **旧二进制兼容**：只加列/加表，旧查询不会 `no such column`；重建表则旧版本可能直接读不了。3.5.0 的目标是升级窗口内新旧镜像都能跑，这是硬约束。
2. **加列是常数时间**：SQLite 的 `ALTER TABLE ADD COLUMN` 只改 schema，不重写数据行。生产库 93 条源的迁移是毫秒级，不需要停机窗口。
3. **索引必须延后**：V1 库的 `sources` 没有 `repo_host`，把 `CREATE INDEX ... ON sources(repo_host)` 放进建表脚本会让老库启动即 `no such column`。这是 `42f100c` 明确记录过的坑。
4. **回填必须幂等**：GHCR 回填只命中「纯 ghcr」源（`ghcr_cap=1` 且 `docker_cap<>1`），重复执行结果不变；否则每次启动都会改归属、丢候选。

## 4. 为什么没有单事务（诚实结论）

- 没有任何「讨论并放弃单事务」的记录。单事务在 3.5.0 之前就没有实现过，所以谈不上「没有回到」。
- 现在若要收成单事务，成本与代价是具体的：
  - `ensureColumns` 依赖事务外的列探测（`PRAGMA table_info`），要改成事务内探测；
  - `upgradeFromV1` 在事务外先建 `_v1kind` 临时表，需要一并挪进事务；
  - `migrateScopedGen` 自带 `BEGIN IMMEDIATE`，嵌套会直接报错，必须拆掉或合并；
  - 失败时只剩一条错误，没有「已完成到第几步」的信息，诊断反而更难。
- 收益只是「全有或全无」。而现有每一步都是幂等的，续跑已经覆盖了同一个目标，所以 3.5.3 的选择是**补步骤登记，而不是包装长事务**。

## 5. 可回退边界（升级前必须知道）

| 迁移 | 引入版本 | 事务 | 提交后旧二进制 | 数据可恢复性 |
| --- | --- | --- | --- | --- |
| 加列 / 加表 / 延后建索引 / GHCR 回填 | 3.5.0 | 无（逐条隐式提交） | 可运行（旧二进制忽略新列） | 可恢复：回填值可由 `ghcr_cap`/`docker_cap` 重算 |
| `upgradeFromV1` 重建 `sources` | 1.x 时代 | 有（重建段） | 不可回 1.x | 不可逆：旧表结构被替换 |
| `source_health_scope` 四列主键重建 | 3.5.2 `bfc296a` | 有（`BEGIN IMMEDIATE`） | 回 3.5.1 **未验证**（旧写入按旧主键假设） | 不可逆；重建前副本是唯一退路 |
| Phase B 归档并删除 `source_health` 的 registry 行 | 3.5.3 | 有（`BEGIN IMMEDIATE`，3.5.3 修正后） | 旧二进制会把 registry 行当候选依据 | 可恢复：`source_health_archive` + `UnarchiveLegacyRegistry`，但必须先撤销迁移标记才能重新迁移（语义待 3.5.3 裁定） |
| 半迁移状态（中断） | 全部 | 无 | 一般可启动 | 续跑即可；无步骤记录，只能靠错误文本推断停在哪 |

## 6. 对 3.5.3 及以后的约束

- 不把整串启动迁移包成一个长事务（理由见 §4）。
- 每一步的业务写入与「步骤完成」标记必须同一事务提交；步骤之间可恢复，靠标记跳过已完成步骤。
- Phase B 的归档/删除/标记必须在同一个 `BEGIN IMMEDIATE` 事务内，且全程使用同一个 `*sql.Conn`（`sql.Tx` 无法指定 IMMEDIATE）。
- `busy_timeout=5000` 是锁竞争的唯一等待来源：`BEGIN IMMEDIATE` 遇到写锁最多等 5s，之后返回 `SQLITE_BUSY`；不会无限排队。
- 新增**重建表**类迁移必须单独写回退方案，不得沿用「幂等续跑」的说法掩盖不可逆性。

## 7. 未决项

- 是否引入 `PRAGMA user_version` 作为快速判据：与 `schema_migrations` 并存会形成双源，暂不做。
- 3.5.0 之前创建的非 Hub 源 `repo_host=''` 仍被当作 Docker Hub，未归一化（3.5.2 roadmap 已登记为遗留）。
- `UnarchiveLegacyRegistry` 是否撤销迁移标记（真回滚 vs 人工数据恢复），3.5.3 需先裁定再进 S4 演练。
