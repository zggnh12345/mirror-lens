# 18a 设计冻结报告：B 配置模型与迁移

版本：3.5.18 / 阶段 18a
日期：2026-11-20 (CST)
依据：冻结任务书 §2.1–§2.5、§18a；1.6 §2811（settings 载体，不新建 store）

## 1. 新配置模型（§2.1）

B 的三个字段彼此独立，全部存 settings 表：

| settings 键 | 取值 | 职责 | 默认 |
|---|---|---|---|
| `cross_registry_enabled` | `true`/`false` | B 总开关 | `true`（默认 ON） |
| `cross_registry_mode` | `sequential`/`race` | B 派发模式 | `sequential` |
| `cross_registry_sort_mode` | `fixed`/`dynamic` | B 候选排序 | `fixed` |

- 旧 `cross_registry_mode` 取值含 `off`；新模型把 `off` 的功能迁移到 `enabled=false`，新 `mode` 不再接受 `off`。为兼容，读取时仍容忍历史 `off` 值（见迁移）。
- 跨站参选集合 `cross_registry_selected_sources` 不变（已有 settings 键）。
- **不新增表、不改 Schema**：与 1.6 §2811 一致，运行时源码与 Schema 版本保持 3.5.17；3.5.18 的程序版本号另行按发布流程设置，本次实施阶段不改（发布/版本号属独立授权事项之外——实际按任务书代码修改授权，版本号改动留到收尾阶段统一处理）。

## 2. 新旧字段冲突优先级（§2.4 冻结裁定）

任务书 §2.4 要求 18a 明确定义并用独立复核确认。冻结如下（**单一规则，所有代码路径共用**）：

1. **新字段优先**：`cross_registry_enabled` 存在时，以它为准决定 enabled；旧 `off` 不再单独决定关闭。
2. **mode 解析优先级**：若 `cross_registry_mode` 为新值 `sequential`/`race`，直接采用；若为历史 `off`，映射为 `enabled=false` + `mode=sequential`（仅当新 `enabled` 字段不存在）；若为其它非法值，回退 `sequential` 并记审计。
3. **sort_mode 独立**：`cross_registry_sort_mode` 只影响排序，不参与 enabled/mode 判定；缺省 `fixed`。
4. **新旧同时存在且冲突**：以新字段为准，记录一条 `audit(kind=config_migration, action=conflict_resolved)` 审计，写明新值、旧值、采纳值。
5. **缺省**：三键都不存在 → `enabled=true, mode=sequential, sort_mode=fixed`（默认 ON）。
6. **部署期配置 `registry.replica_mode`**：作为最底层基线，仅在 settings 三键全部缺省时使用；`off`→enabled=false，`sequential`/`race`→对应模式；空/无法识别→enabled=true+sequential。

## 3. 迁移矩阵（§2.3，与冻结稿一致）

| 旧配置状态 | 新 enabled | 新 mode | 说明 |
|---|---|---|---|
| 显式 off | false | sequential | B 关闭 |
| 显式 sequential | true | sequential | B 开启顺序回退 |
| 显式 race | true | race | B 开启跨站竞速 |
| 旧字段缺省 | true | sequential | 保持运行时缺省行为 |
| 生产双缺省 | true | sequential | 归为默认 ON |

迁移必须：备份配置和 DB；区分显式与缺省；幂等；失败不改 B 启停状态；回滚不删用户已有配置；完成后 API/运行时/Web 三者一致。
