# 200-only 候选失败路径分析（638 春川，2026-11-24）

## 现象

生产受控实测中，临时把 638 春川放进 docker 换源候选后：

1. 638 凭历史约 7.8MB/s 的样本通过 `replayCostOK`，同时把候选组中位速度抬高；
2. 当前源 sparkcr（54，206、约 5MB/s）被 `speed_rejected`；
3. 638（HTTP 200、`range_cap=0`、不支持 Range）被选中；
4. 5s 回放预算内只回放约 3.7MB，触发“长度不符，丢弃：期望 64396988 实得 3714854”；
5. 客户端下载失败。

这是**客户端可见的失败**，不是“换源慢一点”或“自动继续旧源”。

## 根因

### 1. 候选选择依赖历史速度，样本可能严重偏离当前实际

`trySwitchWithSpeed` 取最近 5 条 `proxy_speed` 的中位数作为候选速度 `sBps`，
并用候选组中位速度计算动态门槛（`internal/gateway/watch.go:400-413`）。
638 的历史高样本既让自身通过门槛，也抬高了同伴门槛，导致当前正常的 54 被拒。

### 2. 200-only 候选的回放预算是“估算”，不是实际保证

`replayCostOK` 用 `sent / sBps` 估算回放时间，只有估算 ≤5s 才放行
（`internal/gateway/watch.go:522-529`、`watch.go:655-669`）。
样本 7.8MB/s 时，10MB 前缀估算约 1.3s，放行；实际 638 约 0.74MB/s，
需要约 14.5s，5s 内只回放 3.7MB。

### 3. 旧源已关闭，回放失败没有回退

换源成功后先关闭旧响应体（`internal/gateway/stream.go:716`），
再做 200 回放；回放超时走 `discardWithDeadline` 失败分支，
只执行 `savePartial(); finished=true; return`（`stream.go:748-752`），
不会退回旧源，也不会尝试下一个候选。

### 4. 单流换源路径缺少并行路径已有的 Range 门槛

并行路径用 `rangeKnownOff` 排除已知不支持 Range 的源（`internal/gateway/parallel.go:793-799`）；
单流换源路径没有等价的 `range_cap` 过滤，因此 200-only 源仍可进入候选。

## 当前生产暴露面

生产只读核对（2026-11-24）：

- `sources.range_cap`：54 `docker.sparkcr.cn` = 1；88 `凤凰城` = 0；638 `春川` = 0。
- `settings.sched_order`：`manual`，docker `[54,88]`，github `[638,88]`。
- 638 不在 docker 候选中；88 虽是 200-only，但最近 5 条 docker 样本中位约 0.75MB/s，
  10MB 前缀回放估算约 13s > 5s，会被 `replay_over_budget` 拒绝。

因此**当前正常流量短期不会复现这次 638 失败**。但这是靠历史样本碰巧挡住，不是代码保证：
一旦把 638 加进 docker 顺序，或 88 出现高样本、实际速度骤降，失败路径仍可触发。

## 建议

### 方案 A（推荐，最小改动）

换源候选只保留 `range_cap=1`，并且在计算候选组中位速度之前过滤；
`switchAcceptable` 再拒绝 HTTP 200 作为兜底。200-only 源仍可做初始源和回退源，
只是不参与中途接管。

- 收益：彻底移除“200 回放超时且无回退”的客户端失败路径；200-only 源不再污染
  `peerMedianBps`，不会把正常的 206 源挤掉。
- 代价：88/638 不再参与接管；54（206）仍可；没有 206 候选时继续当前源，不换。
- 测试：候选 `range_cap=0` 不进入候选；同伴中位不包含 200-only；200 响应不被接受。

### 方案 B（保留 200-only 接管，改动大）

把回放动作移到关闭旧源之前；回放失败可退回旧源或试下一个候选。
需要改核心 stream 换源路径，风险和测试量都大，不建议现在做。

### 不建议

只调大 5s 回放预算。历史样本可能任意偏离，旧源又已关闭，实际更慢时仍会失败；
而且会把“换源慢”拖成更长的客户端等待。
