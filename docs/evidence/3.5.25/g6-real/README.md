# G6 真实环境性能对照（3.5.24 基线 vs 3.5.25 候选）

## 环境

- 两版均为从冻结源码现场构建的镜像，运行于同宿主（i3-12300T）、同 Docker 网络（traefik 172.18.0.0/24）、同真实 IP DNS（`10.1.1.4` + `223.5.5.5`），关闭应用限流（`config.yaml limits.enabled=false`，两版一致）。
- 基线 `mirror-lens:3.5.24-g6` = commit `84b013d23f0c11eaf86de9d5e776789467cb4192`；候选 `mirror-lens:3.5.25-verify` = commit `a30d2893a7fa31a8651d91a387a3174882b4abb1`。`mirror-lens --version` 输出逐轮记录于 `hot-paired-console.log`。
- **配对纪律**：三个场景（热缓存、冷缓存、并发）全部在**同一 IP 槽位 172.18.0.28** 上先后换镜像采集，消除容器网络位置/调度亲和差异。每轮换镜像后重新预热到稳定 `X-ML-Cache: HIT`。
- 代理路径固定 `/raw/octocat/Hello-World/762941318ee16e59dabbacb1b4049eec22f0d303/README`（13 字节），真实回源 raw.githubusercontent.com，未关闭 TLS 验证、未放宽 SSRF 策略。

## 口径（任务书 §17.1 / 冻结门槛 §17.2 / 回归门槛 §17.3）

- 热缓存：3 轮独立测量，每轮 500 次请求尝试（5 批 × 100 并发内单次），全部 HIT、成功率 100%；P50/P95 基于 3 轮合并的 1500 个样本计算，**不对 3 轮的 P95 再算 P95**。
- 冷缓存：每轮先 `POST /api/accel/purge {"scope":"all"}` 清缓存，再发首次请求制造 MISS；前 3 轮作暖机丢弃（排除刚 purge 后源站探测未就绪的 20s 冷启动假阴性），正式采集 25 轮（≥ 样本下限 20），全部 MISS。
- 并发 Pull：100 并发 × 5 批 = 500 次尝试，成功率与 P95 按全部尝试计算。
- 失败请求按实际到错误/超时的耗时纳入；每场景另统计成功率、错误类型、cache 头。

## 根因分析：为什么单次采样的“候选慢 40-60%”不成立

初测（两容器分别跑两版）曾出现候选 P50 +62% / P95 +40% 的表观退化。按 §17.3 要求进入根因分析，做了三层取证：

1. **A/A 同镜像对照**：同一镜像（3.5.25）跑在两个槽位、同负载下，P50 差异 8–35%、P95 差异 30–100%；同槽位跨轮自身 P95 波动达 100%。即**微秒级单点 HTTP 请求的环境噪声地板远高于 10%/15% 门槛**，任何单次相对差异都不可归因到代码。
2. **交叉互换镜像**：把两版镜像对调槽位后，“慢的总是原槽位而非某版本”——初测的表观退化随槽位走，不随版本走。
3. **同槽位交替换镜像 3 轮**：单轮 ΔP50 在 -35%~+28%、ΔP95 在 -29%~+61% 间随机摆动，方向不一致；合并 1500 样本后 ΔP50 -7.3%、ΔP95 +4.9%，均落入门槛。

结论：不存在可归因到 3.5.25 代码的性能退化；表观退化是单点微基准被客户端建连/容器调度噪声支配的假象。按 §17.1“不用单次峰值做结论”，以多轮合并样本为准。未通过关闭 TLS 验证、缩短安全检查或减少内容验证换取速度。

## 边界与诚实声明

- 本组数据是**隔离验收实例 + 真实公网源站回源**（raw.githubusercontent.com），不是生产实例压测；生产未触碰、未切换。
- 热缓存场景为代理路径固定小文件 HIT；未覆盖 §17.4 全部指标（Source API、数据库事务、Host 探测、TLS 握手、UI 加载）的逐项延迟分解——这些在 G4 全量测试与 g4-performance 证据中覆盖，本轮聚焦缓存路径的旧/新门槛。
- 冷缓存 P95 按任务书要求重采（非沿用 3.5.24 的中位数口径），且以 3 轮暖机排除冷启动假阴性——暖机轮不纳入样本，已在 result.json 的 `cold_cache.warmup` 标注。
- Source API / 数据库事务 / Host 探测的性能由本地 benchmark（g6-comparison.md）覆盖；两版源码差异仅在这些路径，缓存热路径代码无变化。
