## 1. 设计冻结：A/B 架构

### 1.1 A/B 定义

- **A：Registry 内部 Source 竞速。** 解决同一个逻辑 Registry 内部多个加速 Source 的选择问题。
- **B：跨 Registry 可信副本调度。** 解决不同逻辑 Registry 之间可信副本的顺序回退或并发竞速问题。
- A 和 B 是两个独立调度能力，不是固定串行的两个阶段。
- B 负责选择 Registry；每个 Registry 内部是否启用 A，由该 Host 自身的 A 开关、Source 星标资格、能力状态、健康状态和预算决定。
- A 的多个 Source 不得被算作多个 Registry 副本，也不得被计算成多张跨站投票。

### 1.2 六种组合状态

| A 站内竞速 | B 总开关 | B 派发模式 | 实际行为 |
|---|---|---|---|
| OFF | OFF | 任意 | 原有单站处理 |
| ON | OFF | 任意 | 当前 Registry 内部 A 竞速 |
| OFF | ON | sequential | B 顺序选择 Registry，各站内部顺序选 Source |
| ON | ON | sequential | B 顺序选择 Registry，各站内部可使用 A |
| OFF | ON | race | B 跨 Registry 竞速，各站内部顺序选 Source |
| ON | ON | race | B 跨 Registry 竞速，各站内部可使用 A |

要求：
- B OFF 时，不得因为存在可信映射而进入 B 调度。
- A OFF 时，不得因为 B 开启而绕过 A 的关闭状态。
- A、B 同时开启时，必须遵守各自的资格、并发、预算和取消规则。
- 六行组合矩阵是 3.5.18 独立 B 总开关模型，不得称为 1.6 原有矩阵。

### 1.3 B 介入条件

B 介入的通用前置条件：B 总开关开启；请求属于 B 支持的 Manifest 请求范围；逻辑 Registry 和 Repository 身份明确；存在有效可信副本映射；本次请求预算、Lease 和全局容量允许；请求类型符合当前 B 派发模式的准入条件。

有前缀和无前缀请求均进行可信映射判断。显式前缀只改变首选 Registry，不自动赋予其他 Registry 可信副本资格。B 不得绕过私有认证、身份校验失败、安全策略拒绝或其他 fail-closed 条件。

**候选资格按派发模式分别定义（本轮修订 P1-1）：** 不得用单一“候选 Source 满足跨站参选资格”统摄所有 B 候选——该表述只适用于 race，套到 sequential 会与 §1.6 候选来源模型冲突。

| B 派发模式 | 候选来源 | 派发前资格要求 |
|---|---|---|
| sequential | 有效可信映射中的 Registry | 不要求跨站参选勾选；派发前须满足：仓库身份来自可信映射（B.3 第一层）、B19 私站排除、安全策略/请求类型/运行时准入等前置安全条件 |
| race | 有效可信映射中满足竞速资格的 Registry/Source | 除上述全部派发前门禁外，还须满足 Source 星标、跨站参选集合、能力状态、健康状态 |

**B.3 验证分层（本轮修订 P1-1，全文统一，按 1.6 第 2704–2713 行）：** §1.3、§1.6、§4.3 统一采用两层门禁，不得写成“所有 B.3 检查都在派发前完成”：
- **派发前**：只检查仓库身份（必须来自可信映射，不靠同名/404 猜测）、私站排除、请求范围和其他前置安全条件。
- **请求返回后**：执行 Manifest 身份（三方 Digest 校验）、响应有效性验证。顺序模式也不能因前置身份检查通过就跳过响应后 B.3 验证。

race 模式若参选集合为空，或经派发前候选资格筛选后无合格竞速候选，均按 §1.6 的降级规则退化为 sequential（运行时降级，不是双模式并行，也不降低任何安全门禁）。

### 1.4 A 的资格边界

A 站内竞速必须满足：Host 的 `star_race=true`；Source 人工星标 `Preferred=true`；Source 对该 Host 的能力状态为 `Supported`；探测结果有效；健康、熔断和调度准入通过；请求属于 A 支持的 Manifest GET 范围；至少两个合格 Source；本次预算允许。

不满足条件时，A 不启动，继续原有站内 Source 选择流程。A 的竞速范围遵循 1.6 冻结规则，不得擅自把 Tag 竞速扩展为 Digest 竞速以外的新语义。

### 1.5 B 跨站 Source 资格

- `cross_registry_selected_sources` 默认空列表。
- 跨站参选集合必须是已星标 Source 的子集；读取时与当前星标集合求交。
- 星标撤销后，陈旧勾选不得继续授予资格。
- 星标是基础竞速资格；跨站参选勾选是从星标集合中进一步选出的用途子集。
- 配置勾选不等于实际请求授权；Source 必须由调度器实际选中并通过运行时准入后才能发出请求。
- **Source 级求交（本轮裁定 · 方案二）：** 依据 1.6 第 2689 行，B 竞速的实际请求 Source 取「调度器已选中 ∩ 星标 ∩ 跨站参选勾选」三者交集。参选 Source 不仅决定所属 Registry 是否具备 B 竞速资格，也**直接约束实际请求使用哪个 Source**（尤其 A OFF + B race 时，见 §1.6）。

### 1.6 A/B 接管关系（补充裁定新增）

**候选对象层级（本轮修订）：** B 的竞速候选始终是**逻辑 Registry**，不是 Source。B 先选择逻辑 Registry；每个 Registry 内部再由 A（开启时）或原有单站 Source 逻辑（A 关闭时）选择/约束实际请求 Source。跨站参选集合筛选的是允许参与 B 竞速的 Source，不得把同一 Registry 的多个 Source 当成多个 Registry 副本或多张投票；同一 Registry 下有多个符合交集条件的 Source，仍只算一个 B 候选、一个 Registry 投票主体。B 的 Registry 并发与 A 的 Source 并发是两层，不得混为一谈。

**参选 Source 与实际请求的关系（本轮裁定 · 方案二，按 1.6 第 2689 行 Source 级求交）：** A 是否开启只决定 Registry 内部的 Source 调度方式，**不放宽 B 对参选 Source 的约束**。A OFF 不代表可以让原有单站调度器随意选未勾选的 Source。冻结如下：

| 场景 | 实际行为 |
|---|---|
| A ON + B race | B 选择 Registry；站内 A 在 B 允许的 Source 集合内按星标和能力规则竞速 |
| A OFF + B race | B 选择 Registry；实际请求 Source 必须满足调度器选中 ∩ 星标 ∩ 跨站参选三者交集，参选 Source 直接决定实际请求用哪个 Source |
| A ON + B sequential | B 按可信映射顺序回退；Registry 内部由 A 调度 |
| A OFF + B sequential | B 按可信映射顺序回退；Registry 内部使用原有单站 Source 逻辑（顺序回退不受参选集合限制） |
| B race 参选集合为空 | 退化为 sequential，不启动跨站竞速 |

**B-race 允许 Source 集合公式（本轮修订 P2-1，方案二的精确化）：**

```
S(B-race) = S(scheduler-selected) ∩ S(starred) ∩ S(cross-selected) ∩ S(supported) ∩ S(healthy)
```

其中前三项是方案二确定的**身份交集**（调度器已选中 ∩ 星标 ∩ 跨站参选勾选，1.6 第 2689 行），后两项（supported、healthy）是 §1.4 已冻结的 A 能力状态与健康资格，并非对方案二的新改动，而是把两层资格显式合并。A ON 时 A 只能在 `S(B-race)` 内执行站内竞速，不得把未勾选的星标 Source 加入 B race 请求；A OFF 时原有单站选择逻辑也只能从 `S(B-race)` 中选实际请求 Source。这保证 §1.2"每站内部选择 Source"与本节 Source 级约束不实现成两套规则。同一 Registry 内 `S(B-race)` 有多个 Source 时仍只算一个 B 候选、一个 Registry 投票主体。

**B 的接管触发条件（本轮修订 P1-2，与六行组合矩阵自洽）：** 必须区分当前 Registry 的 A 是否开启——

| 当前 Registry 状态 | B 的接管条件（当前 Registry 才向 B 报告整体失败） |
|---|---|
| A ON | A 完成站内补位及规定的一次重试，仍无有效 Manifest |
| A OFF | 原有单站 Source 处理及规定的一次重试，仍无有效 Manifest |

无论 A 开启与否：B 都不能因 A 关闭而无法启动，也不能绕过当前 Registry 的正常处理与规定重试直接跨站；单个 Source 失败不得直接触发 B。

- B 顺序模式不受跨站参选集合限制；B 竞速模式才要求候选通过星标、参选集合、身份验证及运行时准入。
- 不能要求用户把 A 的所有 Source 手动加入跨站参选集合，才能使 B 具备接管能力。
- B 开启后才允许编辑跨站参选集合；B 关闭时保留已有映射和参选配置，不自动清空，重新开启后恢复。

冻结后的候选来源模型：

| B 派发模式 | 候选来源 | 是否受参选集合限制 | 降级规则 |
|---|---|---|---|
| sequential | 可信映射中的有效 Registry | 否 | 不适用 |
| race | 可信映射中符合跨站竞速资格的 Registry/Source | 是 | 参选集合为空 → 退化为 sequential；见下方降级规则 |

**race 过滤后无合格候选的降级（本轮修订 P1-4）：** race 模式下，若参选集合为空，或经**派发前候选资格筛选**（星标有效性、Source 能力状态、健康状态、调度器选中、跨站参选勾选）后没有任何合格竞速候选，则**退化为 sequential**，按有效可信映射顺序回退；退化后的顺序回退仍必须执行全部安全门禁。**不得为了凑足竞速候选而降低准入条件，也不得因过滤后无候选而让 B 直接失败。** 该运行时降级不是双模式并行——派发模式配置始终只有 sequential / race 两种取值，固定/动态排序是独立维度（见 §3.4）。

**降级触发范围限定（本轮修订 P1-4）：** 退化条件**仅限候选资格问题**，不得把资源分配失败伪装成"无合格候选"：
- 星标/参选/能力/健康过滤后无候选，或所有候选均因 Source 自身熔断而不合格 → 退化 sequential。
- 请求级预算不足（`RBudget` 耗尽、`ReserveR`/`ReserveP` 失败）→ 不得借降级绕过预算门禁。
- 全局并发 Lease 获取失败（`scheduler.Lease`）、全局容量耗尽（`GlobalCapacity`）→ 按容量准入规则处理，不得无条件降级。
- 响应后 B.3 身份失败 → Fail Closed，不得降级（见下方分层表与 §4.3）。

若需在全局容量不足时允许 race 降级为 sequential，必须另行冻结：降级后如何重新申请 `scheduler.Lease`、如何计入 `RBudget`、是否允许占用新预算。当前冻结稿不包含该行为。

**B.3 身份验证的阶段划分（本轮修订，按 1.6 第 2704–2713 行）：** 1.6 定义三层验证内容（仓库身份、Manifest 身份、响应有效性），按**执行时点归入两个门禁阶段**。全文（§1.3、§1.6、§4.3）统一采用此时点划分，不得写成"所有 B.3 检查都在派发前完成"：

| 执行阶段 | 覆盖的 1.6 验证层 | 检查内容 | 失败处理 |
|---|---|---|---|
| 派发前 | 仓库身份（第 1 层） | 仓库身份必须来自可信映射，不靠同名/404 猜测 | 不满足则不生成候选，按派发前资格处理 |
| 响应后 | Manifest 身份（第 2 层）、响应有效性（第 3 层） | Manifest 三方 Digest 校验、响应有效性、跨站身份投票/Authority 软比对 | 按身份安全失败处理（见 §4.3 B.3 资源身份验证失败行） |

**身份失败不得通过降级顺序模式绕过。** 降级条件**仅包含派发前资格筛选后无合格竞速候选**；响应后的 B.3 身份验证、三方 Digest 不一致、内容校验失败必须进入 §4.3 对应失败分类——三方身份 Digest 不一致按"B.3 资源身份验证失败"行 Fail Closed、不重试、不回退（普通 Manifest 格式/正文无效仍按普通候选失败可回退，见该表分类边界），**不得混入候选过滤降级**。

**P1-2 顺序回退资格边界：** 顺序回退不受 `cross_registry_selected_sources` 勾选限制，但仍须满足派发前门禁（仓库身份来自可信映射、B19 私站排除、存在有效可信映射、通过安全策略/请求类型/运行时准入），并在请求返回后执行 B.3 响应后验证（Manifest 三方 Digest + 响应有效性，见本节分层表）；未验证、身份不匹配、安全拒绝的副本不得进入候选，也不得因前置检查通过而跳过响应后验证。“不受限制”**仅针对参选集合这一项**，不代表取消其他任何资格门禁。

**P1-1 B20 定性（修正此前错误定性）：** 3.5.18 **落实 1.6 B20 的原有语义，修正 3.5.17 将跨站参选集合为空直接实现为无候选的行为偏差**（`internal/gateway/replica.go:166-169`：`if len(selected)==0 { return nil,0,nil }`）。**不修改 1.6，不声称覆盖或推翻 B20。** 1.6 第 2839 行 B20 字面“空列表退化为顺序回退”，第 2811/2845/2847 行一致，支持本裁定；真正偏差在 3.5.17 实现。

## 2. B 配置模型与迁移冻结

### 2.1 新配置结构

新配置模型统一使用：

```yaml
cross_registry_enabled: true
cross_registry_mode: sequential
cross_registry_sort_mode: fixed
```

三个字段职责独立：

| 字段 | 取值 | 职责 |
|---|---|---|
| `cross_registry_enabled` | true/false | B 总开关 |
| `cross_registry_mode` | sequential/race | B 派发模式 |
| `cross_registry_sort_mode` | fixed/dynamic | B 候选排序模式 |

**默认值（补充裁定确认）：**

| 配置项 | 默认值 |
|---|---|
| B 总开关 `cross_registry_enabled` | ON (`true`) |
| B 派发模式 `cross_registry_mode` | `sequential` |
| B 排序模式 `cross_registry_sort_mode` | `fixed` |
| 可信映射 | 空 |
| 跨站参选集合 `cross_registry_selected_sources` | 空 |

B 竞速默认不启用；动态排序默认不启用。B 总开关默认 ON 是为了保持 1.6 运行时缺省行为，不代表默认安装会自动产生跨站请求。跨站参选集合仍默认空列表。

具体行为（补充裁定确认）：B ON + sequential → 按可信映射顺序回退，不受参选集合是否为空影响；B ON + race + 空集合 → 不启动跨站竞速，退化为顺序回退；B ON + race + 非空集合 → 仅合格候选参与跨站竞速；B OFF → 完全禁止跨 Registry 调度，保留已有映射与参选配置，重新开启后恢复，新安装参选集合为空。

### 2.2 旧配置的实际矛盾

执行前必须重新核实：`replica.go` 运行时缺省 `""` 是否解析为 `sequential`；`config.go` 的默认值注释；`config.example.yaml` 的旧 `replica_mode: "off"`；`settings` 表中旧字段的真实存储状态；生产配置文件中旧字段的真实存在情况。**生产当前双缺省状态不能以示例配置的 off 推断。** 生产状态必须以真实环境取证为准，不能继续把 1.6 中的历史状态（如第 3207 行“未推送/未打 Tag/生产迁移 NOT_EXECUTED”，已过时）当成当前生产状态。

### 2.3 旧配置迁移矩阵

| 旧配置状态 | 新 enabled | 新 mode | 迁移含义 |
|---|---|---|---|
| 显式 off | false | sequential | B 关闭 |
| 显式 sequential | true | sequential | B 开启，顺序回退 |

## 3. 固定排序与动态排序

### 3.1 固定排序

固定排序是默认排序模式。要求：使用持久化优先级；Web 可查看、调整和保存优先级；保存后有明确的 Generation 变化；同一配置在相同候选集合下产生稳定排序；不得被动态评分覆盖；排序变更必须有审计记录；并发修改必须有一致性保护，避免旧页面覆盖新配置；读取和保存必须与可信映射、跨站参选资格保持一致；固定排序不得改变候选资格和身份验证规则。

### 3.2 动态排序

动态排序是 18c 的新建能力。1.6 已冻结评分定义和样本规则，但当前代码没有完整的 `SuccessRate`、`LatencyScore`、`sort_mode` 实现。因此必须从零完成：样本采集、样本有效性判定、滚动样本窗口、有效样本数量统计、成功率统计、延迟统计、评分计算、排名计算、持久化、排名快照、快照版本和时间、Web 查询展示、运行时调度应用、动态排序关闭后的固定排序恢复。不得只实现评分函数而缺少数据来源和持久化。

### 3.3 动态排序冻结规则

本章是 18c 实施的**唯一精确依据**，实施阶段不得依赖归档文件。三个来源的职责严格区分：

| 来源 | 权威范围 | 本次作用 |
|---|---|---|
| `docs/registry-roadmap-v1.6.md` | 架构与跨站调度规则的权威 | 公式骨架、50 样本门槛、映射独立计数、动态只重排 M 内候选（第 2735 行） |
| 3.5.17 归档冻结清单 G3/W1/F02/F03（`docs/archive/3.5.17-pre-freeze-drafts/`） | 动态排序细化裁定的历史记录 | 补充精确公式、有效样本定义、TTFB 评分规则；**不升格为高于 1.6 的新权威文档** |

归档清单顶部声明其为"设计冻结清单审查基线候选版本"而非正式冻结宣告，但其 §3 明确把 G3/W1/F02/F03 标为"已冻结"，配套 `3.5.17-optimized-plan.draft.md` 称 W2 公式已冻结。因此不凭文件名/归档位置否定其细化裁定；**正确做法是恢复其中明确标注已冻结的动态排序细则，并要求与 1.6 规则一致**。若本章与 1.6 冲突，以 1.6 为准并停止受影响阶段报告。

**公式版本固定为 `B-DYNAMIC-SCORE-FORMULA`。**不得单独用 `F02` 指代评分公式（1.6 中 F02 编号复用：既是 3.5.15 私有直接 Basic Manifest 测试项，又是动态评分公式；测试项统一用 `TEST-3.5.15-PRIVATE-BASIC-MANIFEST`）。

**评分公式（冻结，不再开放讨论）：**

```
Score = 0.6 × SuccessRate + 0.4 × LatencyScore
SuccessRate = 成功样本数 / 有效样本总数
LatencyScore = 1 / (1 + P50(TTFB) / 800ms)
```

- 权重：成功率 60%、响应延迟 40%、调用频率 **0%**（仅用于样本积累，不参与评分，避免高频映射形成反馈循环）。
- 不额外使用时间衰减（50 样本滚动淘汰即自然老化）。
- 无可测量 TTFB 时 `LatencyScore = 0`；只有可测量的 TTFB 参与 P50 中位数。
- 成功率与延迟必须统计自**同一条映射**的同一批样本。
- 并列按可信映射配置中的固定顺序处理，不允许随机打破并列。
- 评分计算失败时的行为：按固定排序兜底并记录原因，不得用过期排序或虚构分数。

**样本窗口 W1（冻结）：**

- 每条可信映射独立维护最近 **50 个有效映射回源样本**；不同映射不得合并统计。
- 新样本进入、最旧移出（滚动窗口）。
- 不足 50 个有效样本时使用固定排序；达到 50 个后允许动态排序。
- 映射身份或可信关系发生变化时，该映射旧窗口清零。

**有效样本 F03（冻结）：**

计入：
- 每次真实回源尝试最多为对应映射贡献一个样本。
- 首站直接命中也计入（不要求先发生跨站跳转）。
- 成功样本必须通过 Manifest 身份验证。
- 真实回源失败计入失败样本。

排除：
- 缓存命中且没有真实回源。
- 用户取消、客户端断开。
- 策略拒绝、认证拒绝。
- 本地准入失败。
- 尚未实际发出的尝试。
- 因其他候选胜出而取消的尝试。

同一请求经过多条映射时，每条实际参与的映射分别最多计一次。

**TTFB 测量口径（本次补充为唯一可测试定义，属测量边界补充、不改权重与算法）：**

- 起点：**实际向上游发出请求的时刻**（即 openUpstream 派发那一刻），不是进入上游调度、Lease 等待或本地排队的时刻。
- 终点：**收到上游响应头的时刻**（`openUpstreamAs` 返回且 `resp != nil`），不是读取到第一个响应正文字节的时刻。
- 本地排队、Lease 等待、缓存处理、Body 读取耗时一律不计入 TTFB。
- 失败样本只要确实取得可测量的响应 TTFB（收到了响应头，如 404/429/5xx/无效 Manifest），其 TTFB 也参与延迟 P50 统计；该样本同时按 F03 计入成功率分母。
- 超时但没有收到响应头的样本：只进入成功率分母（失败样本），**不虚构 TTFB、不参与延迟统计**。
- 被 F03 排除的样本（缓存命中/取消/策略拒绝/认证拒绝/本地准入失败/未发出/因他人胜出取消）：既不计入成功率，也不计入延迟。

**公式级测试（冻结，18c 必须提供）：** 0 / 1 / 49 / 50 个样本；成功率边界（0%、100%、临界）；无可测量 TTFB；超时无响应头；429 / 5xx / 无效 Manifest（有响应头的失败样本 TTFB 参与）；同分稳定排序；并列按固定顺序兜底不随机；样本窗口容量与滚动淘汰；映射身份/可信关系变化清零；动态关闭后恢复固定排序；公式版本常量断言。

严格核对 1.6 原文并逐项落实：样本窗口容量及统计范围；50 个有效样本门槛；有效样本的精确定义；失败、超时、取消、429、5xx、无效响应是否计入样本；成功率分母和分子；延迟采样起止点；缺失数据处理；评分公式及归一化方式；同分处理；不足 50 个样本时的回退规则；排名快照更新时机；评分计算失败时的行为。

动态排序只能重排 M 范围内已经合格的候选，不能：增加 M；改变可信映射；改变跨站参选资格；改变 Source 星标要求；绕过健康和熔断；改变 C/A 并发；改变 Authority 和投票规则。

### 3.4 派发模式与排序模式的作用关系（本轮修订 P1-4）

两组二选一是**独立维度**：派发模式 `sequential` / `race` 决定“如何派发候选”；排序模式 `fixed` / `dynamic` 决定“候选的先后顺序”，两者不得合并成一个多档按钮，也不得相互替代。

| 派发模式 | 排序模式的作用 |
|---|---|
| sequential | 决定可信映射的尝试先后顺序（按固定优先级或动态评分排序） |
| race | 决定合格竞速候选的调度优先级或启动顺序；不改变并发上限和资格 |

排序模式（无论 fixed 还是 dynamic）**只改变候选顺序**，不得改变：M / C / A 并发上限、可信映射、跨站参选资格、Source 星标资格、安全门禁、失败立即补位规则。否则会把排序误实现成“动态选择候选”或“动态增加并发”。派发模式配置始终只有 sequential / race 两种取值；race 因无合格竞速候选而退化时是运行时降级（见 §1.6 P1-3），不是派发模式同时选择两个选项。

## 4. 竞速、失败补位与嵌套调度

### 4.1 继承 1.6 的失败立即补位语义

1.6 已定义竞速失败后对剩余合格候选补位。3.5.18 不得重新引入批次屏障，不得等待首批全部失败后才开始补位。3.5.18 新增问题是 A+B 嵌套后，两层并发槽位如何联动。

### 4.2 分层并发

冻结参数：M=4（跨站可信副本候选上限）；C=2（B 层 Registry 并发上限）；A=2（每 Registry 内部 Source 并发上限）。

A、B 同时开启且均为竞速、候选充足时，首轮理论最多 `C×A = 2×2 = 4` 个 B/A 层物理上游请求（不含 fb 链；fb 链另计，竞速模式单请求物理峰值 `C×A+F=5`）。Authority 不计入 M，不占 C 并发槽位和补位名额。

**适用前提（本轮修订 P2-2）：** `C×A=4` 与 `C×A+F=5` 是 **A、B 两层都实际启用竞速且候选充足**时的首轮理论并发上限，不是任意组合的固定值。理论首轮主链并发（候选充足、预算允许、不含 fb 链）按下表：

| 模式 | 理论首轮主链并发 |
|---|---|
| A OFF + B sequential | 1 |
| A ON + B sequential | A，即 2 |
| A OFF + B race | C，即 2 |
| A ON + B race | C×A，即 4 |

- B sequential 时 B 层任一时刻只派发一个 Registry（主链起点为 1），但该 Registry 内部若 A 开启仍可并发 A 个 Source，故 A ON + B sequential 主链并发为 A=2，不能直接套用 B race 的 `C×A`，也不能误认为 sequential 一定只有一个物理上游请求。
- `C×A+F=5` 是特定竞速预算场景的物理请求峰值，不代表任意组合都能产生 5 个请求。
性能测试与预算验收不得把理论峰值误当成所有模式的固定并发。

### 4.3 补位规则

必须实现：B 层每个 Registry 占用一个 B 槽位，Registry 内部 A 层最多同时占用 A 个 Source 槽位；A 层任意候选失败立即释放 Source 槽位，有剩余合格 Source 时立即补位；A 层候选全部达到整体失败条件后，Registry 才向 B 层报告整体失败；B 层收到 Registry 整体失败后立即释放该 Registry 槽位，有剩余合格 Registry 时立即补位；A 层 Source 失败不得导致 B 层重复派发同一个 Registry；补位必须重新经过资格、预算、Lease、健康、熔断和安全门禁，不得绕过已执行的认证和身份校验要求；任意有效结果胜出后取消其他未完成候选，所有被取消的请求必须释放 Lease、并发槽位和相关资源。

**【补充裁定合并 · Registry 整体失败定义】**

Registry 整体失败 = 当前 Registry 已完成本轮允许的站内调度和规定重试，仍无法提供经过验证的有效 Manifest。判定过程：①当前 Registry 按自身 A 配置（或 A OFF 时的原有单站逻辑）执行 Source 调度；②某 Source 失败立即从剩余合格候选补位；③**当前 Registry 的失败结果必须先按 1.6 B16 分类——只有符合可重试条件（可重试网络故障）的失败才允许消耗本站唯一一次 `RegistryRetryToken` 执行串行 Attempt；不符合重试条件的失败（429/5xx、404、无效 Manifest、Digest 不一致、身份/安全失败等）直接按其分类处理，不消耗重试额度**；④重试是单个串行 Attempt，不得重新启动完整 A 竞速；⑤所有规定的站内处理结束后仍无有效 Manifest，判整体失败；⑥**按失败类型分流**：可回退的普通失败（网络、404、429/5xx、普通 Manifest 无效）才释放该 Registry 的 B 层槽位、按派发模式继续处理其他 Registry；**不可回退的安全失败（B.3 身份未通过、私有认证/安全策略拒绝、Authority 身份失败）为整个请求的终止条件——立即 Fail Closed，不得释放槽位继续尝试其他 Registry，也不得触发 race 降级**。Fail Closed 不是"整体失败的一种可补位状态"。单个 Source 失败不得直接触发 B；**不得把本条误读成每个 Registry 无论失败原因都要再重试一次，也不得误读成只要没有有效 Manifest 就无脑补位**。

**P2-1 本站重试与跨站回退：** 可回退 ≠ 必须重试本站。429/5xx 按 1.6 B16 不触发本站网络重试，但可按规则回退下一 Registry。仅可重试网络故障执行一次串行 Attempt（`RegistryRetryToken`），不重跑完整 A 竞速、不为每 Source 分别给重试额度。

**P2-2 整体失败三分法：** 可重试失败经一次重试仍失败 → 判整体失败；不可重试失败（404/manifest unknown/无效 Manifest/Digest 不一致等）→ 直接判整体失败，不经过“重试后”步骤；安全拒绝 → Fail Closed，不进入跨站回退。

失败类型边界（以 1.6 B.4 为准）：

| 失败类型 | 允许 B 继续回退 | 处理原则 |
|---|---|---|
| 网络连接失败 / 超时 | 是 | 按规定重试后回退 |
| 429 / 5xx | 是 | 遵循退避与错误分类，不重试本站，回退下一 Registry |
| 404 / manifest unknown | 是 | 不重试，进入下一候选 |
| 无效 Manifest / 正文不完整 / 普通响应有效性检查失败（非三方身份 Digest） | 是 | 不重试，拒绝该候选并回退（1.6 B.4 L2754；下一站可能有正确内容，该候选不进投票与提交） |
| B.3 资源身份验证失败（请求期望 Digest、响应头 Digest、正文计算 Digest 三方不一致，即身份 Digest 不一致） | 否 | 不重试、不回退、Fail Closed；不得降级为顺序模式绕过（1.6 B.3 L2709 + B.4 L2755） |
| 公开资源的 401/403 | 按 1.6 规则 | 不重试，不得绕过私有认证限制 |
| 私有认证失败 / 安全策略拒绝 | 否 | Fail Closed，不得通过跨站回退绕过 |
| Authority 身份校验失败 / 内容不一致 | 否 | 按安全失败处理，不得降级绕过 |

**Digest 失败分类边界（本轮修订 P1-2，避免同一事件两种结局）：** B.3 包含三方 Digest 校验，因此必须严格区分——①Manifest 格式错误、正文不完整、普通结构或响应有效性检查失败，按上表"无效 Manifest"行普通候选失败处理，允许回退（1.6 B.4 L2754）；②三方 Digest（请求期望 / 响应头声明 / 正文计算）不一致，属于 B.3 资源身份未证明，按上表"B.3 资源身份验证失败"行 Fail Closed、不回退（1.6 B.3 L2709 + B.4 L2755）。实现者不得把所有 Digest 错误合并成一类，也不得把三方不一致误当普通 Manifest 无效而回退。

关键：B 不能把安全拒绝伪装成普通可用性故障。

### 4.4 胜者判定

HTTP 200 不等于有效胜者。候选必须经过对应的：正文完整读取、Manifest 结构验证、Digest 验证、身份验证、投票条件、Authority 比对条件。只有符合请求类型和 1.6 冻结规则的候选才能成为有效胜者。

### 4.5 取消和资源释放

必须验证：胜者确定后取消未完成分支；每个分支使用独立 Context；取消落败分支后关闭未选中 Body；不得因一个分支取消导致其他分支提前中断；不得留下后台请求、Body 泄漏、Lease 泄漏或并发槽位泄漏；超时、客户端断开、服务关闭、请求取消均能正确清理；取消和补位同时发生时不得重复派发同一候选；结果通道关闭、重复结果和迟到结果不得导致死锁或错误胜者；必须增加针对取消竞态和补位竞态的 Race 测试。

## 5. Authority、身份验证、投票与缓存

### 5.1 Authority 独立规则

Authority Registry 不计入 M，不占 C 并发槽位和补位名额；每个逻辑请求、每个权威 Manifest Identity 最多一次 AuthorityAttempt；软比对和最终兜底共用唯一 Attempt，不得因为 A+B 嵌套重复发起 Authority 请求；Authority 派发、成功、失败和复用状态必须可审计。

**【补充裁定合并 · P2-3 Authority 失败分类】**
- Authority 网络临时不可用 / 超时：遵循 1.6 既有软比对和唯一兜底机制（2709 / 2860 行）。
- Authority 身份验证失败 / 内容不一致：安全失败，不得绕过。
- Authority 不参加普通副本重试。
- AuthorityAttempt 每逻辑请求最多一次，软比对与最终兜底共用，不重复派发。

### 5.2 Digest 投票

继承 1.6：默认 200ms 投票窗口，从首个正文完整读取且 Digest 校验成功的候选开始计时；至少两个不同逻辑 Registry、不同 source_id 的候选通过三方 Digest 校验且彼此一致，才能满足多副本一致性条件；同一 Registry 内两个 Source 不算两票；单一候选按 Authority Digest 软比对规则处理；超时或窗口外候选不得参与当前投票；全候选不一致时按冻结规则回退 Authority。

### 5.3 Tag 和缓存提交

Tag 请求必须等 Authority Digest 一致后才能缓存；副本先返回 200 不能提前写缓存；A 的站内竞速不得在 B 身份或 Digest 验证之前提前提交缓存；B 的副本路径不得绕过请求级最终验证；CachePut 必须统一到请求级最终验证之后；失败、身份不一致、Digest 不一致和 Authority 失败不得错误写入缓存；不得将部分正文或未验证正文提交为有效缓存。

默认缓存键策略为 `digest_only`（1.6 冻结）。B 的可变 Tag 竞速必须由 B 自身可信映射与版本一致性策略控制，不得借调用 A 的 Digest Race 入口绕过 A 的资格限制。

### 5.4 安全回归

必须覆盖：错误 Registry / Repository 身份、错误 Manifest Digest、Tag 指向不同内容、私有认证失败、候选认证泄漏、401/403 语义、429/5xx 退避、404/manifest unknown、重定向后的身份和目标地址校验、不可信 Realm、DNS 重绑定和实际 Dial IP 检查、非法 Manifest、Authority 不可用、投票不一致、投票超时、客户端取消。不得为提高命中率放宽安全边界。

## 6. 预算、Lease 与全局容量

### 6.1 预算冻结

严格继承 1.6 的 R/P/G 预算定义。

**R 预算：**
- 顺序模式：`R_default = M(A+1) + R_fb + R_authority = 4(2+1) + 3 + 1 = 16`
- 竞速模式：首轮 `C×A=4`，补位 `(M−C)(A+1)=6`，`R = 4+6+3+1 = 14`

**G 预算：** `G = N × max(W+1, C×A, 2) + 4`；N=200, W=4, C=2, A=2 → G=1004（W=2 → 804；W=16 → 3404）；`limits.enabled=false` 不得关闭硬上限（只关外部 HTTP 入口限流，内部 RequestScope 仍用 `GlobalConcurrency=N`）。

冻结数值 1.6 依据：顺序 R=16（3065 行）、竞速 R=14（3066 行）、`C×A=4`（3066/2860 行）、`C×A+F=5`（3104 行）、G=1004/804/3404（3127 行 D-04）。任何预算扩大必须单独提出设计变更，不属于 3.5.18 自动实施授权。

### 6.2 预算实施要求

必须核实真实代码路径和实际符号，不得虚构架构对象。当前代码中已知相关对象：`RequestScope`、`Chain`、`Claim`、`RegistryRetryToken`、`RBudget`、`PBudget`、`ReserveR`、`ReserveP`、`scheduler.Lease`、`unified.Pool`、`GlobalCapacity`。不得假定存在 `GlobalLeasePool`、`ExecuteRegistryManifest` 或 `RegistryResult` 等不存在的实现。

18d/18e 必须证明：A+B 嵌套是否复用同一请求预算；Registry 重试是否正确使用 `RegistryRetryToken`；顺序 Registry 首轮最多使用 A 个 Source Attempt；Registry retry 是单个串行 Attempt，不得重新启动完整 A race；Authority Attempt 不重复消耗；P 预算覆盖所有实际物理派发；Hedge、Midfill、Probe、Range chunk 等实际请求路径均受预算约束；重定向重新经过门控；Transport 内部重试边界明确；Reserve、Commit 和失败释放一致；所有 Lease 均有释放路径；请求取消不会造成容量永久占用。

**最终状态采用多维独立记录（本轮修订），不得用单一字符串同时表达所有门禁：**

| 维度 | 状态 |
|---|---|
| 代码与测试 | PASS / FAIL |
| 真实 Registry 功能验收 | PASS / BLOCKED / NOT_EXECUTED |
| 性能对照 | PASS / PERFORMANCE_EXTERNAL_BLOCKED / NOT_EXECUTED |
| 生产验收 | PASS / WAITING_FOR_USER_DECISION / NOT_EXECUTED |
| 最终发布资格 | 由上述门禁综合判定 |

综合判定规则：代码与测试必须 PASS；真实功能验收若为 BLOCKED 则不得宣称完整交付；性能对照若为 `PERFORMANCE_EXTERNAL_BLOCKED` 则最终报告必须附带该状态、不得宣称性能 PASS；生产验收为 `WAITING_FOR_USER_DECISION` 时最终状态为 `READY_FOR_USER_PRODUCTION_AUTHORIZATION`。若性能外部阻塞且生产未授权，最终报告为上述多维状态的组合（代码 PASS + 功能 PASS + 性能 BLOCKED + 生产 WAITING），不得压缩成单一 PASS。
