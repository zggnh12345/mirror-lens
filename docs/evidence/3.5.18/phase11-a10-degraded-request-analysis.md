# 并发 8 budget_skipped 降级请求分析（解释性，不改代码/不改冻结参数）

日期：2026-11-21
数据来源：`a10iso-pair-iso-c8/c3/c1.json`（最终镜像隔离环境正式 A10）
性质：用于解释已通过的性能验收结果，判断未来是否值得优化 A 层资源调度；不改变 3.5.18 冻结参数。

## 一、分析边界（必须先声明，避免自造口径）

用户建议"通过请求 ID 精确筛选 20 个降级请求并逐条关联"。**现有数据无法做到**：
- 每条样本字段仅 `ttfb_ms/src/dig/want/bytes/status/round/slot/digest_hit`，**无请求 ID、无逐请求 budget_skipped 标记**。
- metrics 的 `budget_skipped_total=20` 是聚合值，无法反推到具体 20 条样本。
- 响应头 `X-ML-Source = plan.Source`（gateway.go:419），样本 `src` 记的是最终服务 Source，
  与 metric 的"候选名次 wins_rank"不是一一对应：样本 src-fast 30 / src-slow 50，
  但 wins_rank1=54 / wins_rank2=6，两者对不上。强行按 src 归类降级请求会得到错误结论。

故不采用"按 src 精确摘出 20 条"的口径。以下只给可从现有数据可靠得出的统计推断。

## 二、资源竞争（用户第 1 点，成立）

- max_per_source=4（冻结），每请求需 fast、slow 各一个 Lease。
- `TryAcquireLease` 非阻塞：名额满立即返回 nil，不排队不等待（scheduler.go:868）。
- 并发 8：budget_skipped=20 / fallback=20 / started=80 → 20/80 (25%) 请求未形成双路，立即降级顺序路径。
- 并发 3/1：budget_skipped=0，全部形成双路。
- 结论：并发越高，双路竞速资格因资源名额不足而立即降级越多——用户此点正确。
  注意措辞：是"立即降级"，不是"Lease 等待导致 TTFB 变慢"（该维度不存在，用户已认可撤回）。

## 三、尾延迟规避率（关键实测，纠正了此前的一个说法）

| 并发 | 基线 >250ms 命中 | 竞速组 >250ms 命中 | 竞速组最高 TTFB | 竞速组 P95 |
|---|---|---|---|---|
| 8 | 12/80 (15%) | 1/80 (1.25%) | 393ms | 201.6ms |
| 3 | 9/30 (30%) | 0/30 | 110ms | 89.2ms |
| 1 | 2/10 (20%) | 0/10 | 97ms | 74.1ms |

- 竞速把长尾命中率从 15-30% 压到 0-1.25%——规避效果确实存在。
- **纠正此前说法**：之前称"20 个降级请求吃不到尾延迟规避、把竞速组 P95 抬高"，
  现有数据不支持——竞速组 80 条仅 1 条命中长尾，降级请求并未大面积暴露于 fast 长尾。

## 四、并发8 竞速组 P95=201.6ms 的真实来源

逐条 TTFB（按降序）显示：除 1 条 393ms 长尾外，其余最高一批是 195-206ms 的 **src=slow** 响应
（r1/slot8 206.5、r8/slot2 204.4、r6/slot7 201.9、r5/slot8 201.6、r2/slot2 200.8、r3/slot4 195.7），
其余 src=slow 大量集中在 103-114ms；src=fast 集中在 85-136ms。

对照并发1/3：src=slow 的 p50 分别约 45ms / 63ms；并发8 src=slow 大量在 105-114ms。

推断：并发8 下 slow 源（稳定 20ms 基础）响应被放大到 100-206ms，原因是高并发争抢 slow 源 Lease/连接，
而非 fast 长尾未规避。这批 slow 响应把竞速组 P95 撑到 ~201ms。
即：并发8 改善率偏低（50.43%）的主因是 **slow 源基础延迟在高并发下被放大**，
而不是"预算降级导致长尾规避失效"。两者叠加，但主导项是前者。

## 五、对用户第 3、4、5 点的回应

- 用户"竞速 P95 随并发从 1→8 由 74→201ms 说明对资源竞争敏感"：成立，且根因定位到 slow 源延迟放大。
- 用户"区分问题 A（竞速算法效率）与问题 B（高并发资源调度效率）"：合理。
  - A：预算充足时（并发1/3）双路竞速把长尾命中率压到 0，算法效率已验证。
  - B：并发8 的 slow 源延迟放大 + 25% 立即降级，是资源调度问题。
    但按用户边界，max_per_source=4 是资源保护约束，不擅断为调度器缺陷，也不在本次改。
- 用户"缺失 Lease 等待时间指标"：已撤回（TryAcquireLease 非阻塞，等待恒为 0）。
  若未来要优化 B，应看的是 Lease 分配时序/slow 源并发放大，而非等待时间。

## 六、结论

- 分析用于解释已通过的 A10 结果：竞速机制有效（长尾几乎全规避），并发8 改善率受限于高并发下 slow 源延迟放大 + 25% 立即降级。
- 不改变本次冻结参数、不改代码、不改性能状态（并发8 PASS 50.43% 已归档）。
- 未来若要提升高并发收益，方向是 A 层资源调度（Lease 分配、slow 源并发放大），需独立评估与授权。
