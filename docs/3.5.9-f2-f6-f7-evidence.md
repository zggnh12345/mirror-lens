## F2：坏 Source Blob 不污染缓存

测试条件：

- 实际 `mirror-lens` 二进制，端口 `18196`。
- 受控 Source：`http://127.0.0.1:18201`，`repo_host=gcr.io`，`registry_cap=1`，`registry_path_mode=native`。
- 请求：`GET /v2/gcr.io/distroless/static/blobs/sha256:87070ab6c3868ee9eec265f4192805989e9e2bed7181f19a025893f77b19789c`
- Source 故意返回 2922 字节错误内容；官方 `gcr.io` 返回正确内容。

第一次请求（Source 命中）：

```text
HTTP/1.1 200 OK
Content-Length: 2922
X-ML-Cache: MISS
X-ML-Source: bad-gcr

body sha256 = d21420baae69ac2d976263f93273d5a1e5176a152276ba46a86184d0cd0da915
```

应用日志：

```text
内容校验失败，不入缓存：期望 87070ab6...789c 实得 d21420ba...a915
```

第一次请求后数据库：

```text
cache_entries: 0
blobs: 0
pending_blobs: 0
blob_integrity_failures: 1
  expected=87070ab6...789c
  actual=d21420ba...a915
  source=bad-gcr
  error_code=digest_mismatch
```

然后禁用该 Source，再请求同一 Digest：

```text
第二次：HTTP 200，X-ML-Cache: MISS，body sha256=87070ab6...789c
第三次：HTTP 200，X-ML-Cache: HIT，body sha256=87070ab6...789c
```

结论：

- 错误 Source 的字节没有被写入缓存；
- 校验失败有独立记录；
- 官方成功后才建立缓存；
- 第三次命中是正确的官方内容；
- 第一次请求客户端确实可能先收到未校验字节，这是已知边界，不宣称客户端完整预校验。
