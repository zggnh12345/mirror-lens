## 〇、2026-11-13 重定版（当前有效）

本节推翻原冻结文档中与新要求冲突的部分，尤其是「无法判定身份就保持 unclassified」
对**新增源**的适用性。原 S1 只读分类（34/9/46）仍作为存量数据基线保留，不做回溯改写。

### 0.1 两套基线必须分开引用

| 指标 | 原 S1 冻结 | 2026-11-13 只读快照 |
| --- | --- | --- |
| 源总数 | 91 | 91 |
| `status='dead'` | 55 | 25 |
| `status='pending'` | 6 | 37 |
| `status='usable'` | 29 | 29 |
| 非 usable 合计 | 62（55 dead + 6 pending + 1 degraded） | 62（25 dead + 37 pending） |
| `repo_host=''` | 89 | 55（46 unclassified + 9 not_applicable） |
| `repo_host='docker.io'` | 0（显式值） | 34 |

差异不是代码回归：`status_at` 显示 25 条 dead 中 21 条自 2026-11-03 起就是 dead，
其余 4 条分别在 11-04、11-10、11-11、11-13 转入；55→25 是这段时间探测恢复的结果，
不是迁移造成。S1 的 55 dead 是历史时点事实，当前候选池必须按新快照重算。

### 0.2 「61/62 条 dead」不是 dead

原文档自己写明：62 = 55 dead + 6 pending + 1 degraded，是**非 usable 合计**。
后来出现的 61 与 62 都是同一口径在不同时点的值，不是 dead 单独计数。
当前同口径为 25 + 37 = 62，恰好又回到 62。任何迁移范围只能按 `status='dead'`
的实际 25 条 ID 计算，不能把 61/62 当成 dead 条数，也不能把 dead、Docker、
GitHub、pending 四类数字直接相加（它们互相重叠：25 dead 中 10 条 `docker_cap=1`、
6 条 `github_cap=1`、0 条 `ghcr_cap=1`）。

### 0.3 新增源身份语义（覆盖旧规则）

- 未传 Host 的新增源：`repo_host='docker.io'`、`registry_identity_state='identified'`。
- 显式 Host：按 Host 归一化后写 `identified`；`docker.io` 保留显式值，不再折叠为空串。
- 仅 GHCR 能力（`ghcr_cap=1` 且 `docker_cap<>1`）：`ghcr.io` + `identified`。
- 仅 GitHub 能力（`github_cap=1` 且 `docker_cap<>1`）：空 Host + `not_applicable`。
- 入口一致性：`store.AddSource` 统一判定；`api.go` 手工新增与 `discover.go`
  自动发现都走同一函数，不允许各自推断。空 Host 不再是新增源的合法结果。

存量 46 条 `unclassified` 不受此规则回溯改写：它们是 3.5.3 之前写入的历史行，
继续保留空 Host，直到有可审计的身份确认。新规则约束的是**写入**，不是把存量猜成 Hub。

- GHCR：迁移前 8 = 迁移后 8。ID：54、69、71、86、88、114、115、638。
- foreign Registry：迁移前 0 = 迁移后 0；`registry:docker.io` 与 `registry:ghcr.io`
  在人为构造 `registry_cap=1` 的情况下仍为 0。
- 114/115：`repo_host='ghcr.io'`、`ghcr_cap=1`、`ghcr_prefix=0`、`registry_cap=1`、

### 0.5 恢复协议重入

`rollback()` 遇到已存在的非空 `.restore-failed-<tx>` 时，必须新建 `.restore-failed-<tx>.N`，
不得用 `mv -f` 覆盖旧现场。`scripts/restore_test.sh` 增加「回滚中途 SIGKILL → 二次
--recover」场景，验证旧现场保留、旧配对恢复、journal 清除。

## 一、事实基线（原 S1 快照，仅作历史）

生产库实测：

| 项 | 值 |
| --- | --- |
| 源总数 | 91 |
| `repo_host=''` | 89（全部 `enabled=1`，无 archived） |
| 其中 `status='dead'` | 55 |
| 非 `usable` 合计（dead 55 + pending 6 + degraded 1） | 62 |
| `repo_host='ghcr.io'` | 2（id 114 `ghcr.dockerproxy.com`、id 115 `南京大学 GHCR`，均 `ghcr_cap=1`、`ghcr_prefix=0`、`usable`） |
| 旧 GHCR 候选 | 8 条：54、69、71、86、88、638、114、115 |

口径说明：此前记录中的 6/11/72 是 **`ghcr_cap`** 分布（1:6、0:11、-1:72），不是 `docker_cap`；
`docker_cap` 为 34/10/45。两者交叉表见 `docs/3.5.4-impact-inventory.md`，同一库、同一时点、合计均为 89。

> 上表是 **S1 历史快照**，不是当前生产状态。2026-11-13 重定版后的数字与差异见 §0.1/§0.2；
> 其中 62 是「非 usable 合计」，不是 dead 条数。

身份语义：

- `unclassified`：身份未确认，不等于 Docker Hub；不进 Hub 专属探测，不进 foreign 候选，不得由默认值或启动期 backfill 自动转正。**该禁令约束存量行与读路径；新增源按 §0.3 直接写 identified + docker.io，不从 unclassified 过渡。**
- `not_applicable`：必须有来源类型证据（当前仅 `github_cap=1`）；`docker_cap=-1` 不是证据（45 条中 36 条为 docker 类主机）。

分类冻结（S1 口径通过，未进 S2）：

| 分类 | 数量 | 本次处理 |
| --- | --- | --- |
| identified + `docker.io` | 34 | 明确标识为 Hub（含 6 条双用途） |
| not_applicable | 9 | `github_cap=1` 类型证据 |
| unclassified | 46 | 保留未知，不推断、不自动归类 |

46 条只保留原字段：不改能力字段、不猜 Host、不进 foreign Probe 与 `registry:<host>` 候选。
这是延后识别，不是认定它们不属于 Hub/Registry，也不是永久归档；后续转 `identified` 须走可审计的身份确认，并完成 `SetRepoHost` 的旧 scope 清理与新 Host 恢复初始化。

两条关键推论：

1. `ListDueHostProbes` 只排除 archived，不排除 dead。89 条若统一写为 `docker.io`，
   会全部满足当前查询准入；55 条 dead（非 usable 合计 62）也会进入探测流程。**迁移前必须用 SQL 固化实际任务数，不能用源总数替代查询结果。**
2. `SourceCandidates("ghcr")` 不检查 `repo_host`，只按 `ghcr_cap`、`enabled`、`status`、健康状态筛选。
   归档 114/115 会使候选池 8→6，违反 GHCR 不回归。**3.5.4 保留，不改能力，不归档，不删除。**

## 二、代码冻结要求

### 2.1 老候选池查询保持原样

- `SourceCandidates("docker")`：不修改。
- `SourceCandidates("ghcr")`：不修改。
- 不在上述查询中增加 `registry_identity_state` 过滤，不通过身份字段改变旧池准入语义。
- 目的：把数据迁移与运行时行为变化隔离，老池迁移前后必须完全一致。

身份过滤只允许放在三处：

1. `ListDueHostProbes`：仅允许 `registry_identity_state='identified'` 且 `repo_host NOT IN ('docker.io','ghcr.io')` 的源进入新 Host Probe；
   空 Host、`unclassified`、`not_applicable` 一律排除（不能只排除两个 Host 名）。
2. 新 Registry 通道入口：校验身份与 Host 分类，禁止 Hub/GHCR 进入 foreign 通道。
3. `recovery_seed.go:59-63`：当前只按 `repo_host<>''` 建恢复行，必须加同一身份门禁。

`registryCandidatesRaw` 已有 `registry_cap=1` + recovery 双条件；若身份准入已在新通道入口统一完成，
不重复增加身份判断。**除非代码审查发现存在绕过该入口的调用路径。**

### 2.2 新增入口必须同版归一

全仓新增写入点核对结果：唯一直接 INSERT 为 `AddSource`（`internal/store/store.go:840`），
调用方为 `internal/api/api.go:594`、`internal/discover/discover.go:69`、`internal/discover/seed.go:68`；
`store.go:556` 的 `sources_v2` 为迁移内部重建，不属于新增路径。

因此同版修改 `AddSource` 即覆盖新增、导入、种子三条路径。策略：

- 未传 Host 时，**仅对 Docker Registry 来源**显式映射 Docker Hub：`repo_host='docker.io'` + `registry_identity_state='identified'`。
- 非 Registry 来源按来源类型写 `not_applicable`；无法判定类型时拒绝创建或写 `unclassified`，不得默认映射到 Hub。
- 这不是让空串继续隐含 Hub，而是让新增操作明确产生 Hub 身份。
- 未来若支持“未分类 Registry”，必须由调用方显式传 `unclassified`，空串不再是默认身份。

验收：

```sql
SELECT COUNT(*) FROM sources WHERE repo_host = '';
```

新增源测试必须覆盖，不能只验迁移后的存量；同时复查是否有绕过 `AddSource` 的直接写入（含工具与测试辅助）。

## 三、六条双用途源身份定义

统一为：

- `registry_identity_state = 'identified'`
- `repo_host = 'docker.io'`
- `docker_cap = 1`、`ghcr_cap = 1`
- `ghcr_prefix` **保留各源现有值**，不为统一而强制改为 1

语义（必须写入文档）：

- `registry_identity_state` 表示源的**主 Registry Host**，不表示该源只能服务一个协议或一个 Registry。
- 六条源主 Host 是 `docker.io`，GHCR 能力仍由 `ghcr_cap` / `ghcr_prefix` 独立表达。
- 不得用主 Host 身份覆盖旧 GHCR 能力字段，也不得把 `registry_identity_state` 解释为协议能力集合。
- 一源多 Host 仍是后续架构缺口。

## 五、发布验收门槛（七项）

1. **迁移安全**：M1、M2、D0 完成；M3 checksum 在任何正式迁移前完成；真实库副本升级 Gate 通过。
2. **Probe 隔离**：`ListDueHostProbes` 不将 `docker.io`、`ghcr.io` 送入新探测流程；其他新 Registry 入口遵守同一身份边界。
3. **Hub 不回归**：直接调用 `SourceCandidates("docker")`，迁移前后结果一致。
4. **GHCR 不回归**：直接调用 `SourceCandidates("ghcr")`，迁移前后结果一致，8 条候选全部保留。
5. **双用途不退化**：六条源 Hub 与 GHCR 能力均保留，主 Host 统一为 `docker.io`。
6. **新增源不复活隐式语义**：不传 Host 的新增操作写入 `docker.io` + `identified`；不存在落入 `repo_host=''` 的路径。
7. **新通道隔离**：`SourceCandidates("registry:docker.io")` 为空；foreign Registry 候选正常，diff 符合预期。

索引验收保留：调整索引后用 `EXPLAIN QUERY PLAN` 确认查询计划，不以“索引存在”作为完成依据。

## 六、完成定义

3.5.4 完成的是 **Registry 身份隐式语义收敛**，不是 Registry 能力模型统一。

完成后必须满足：

- 空 `repo_host` 不再隐含 Docker Hub。
- 所有新增源都有明确身份。
- Hub/GHCR 老候选路径保持原样。
- Foreign Registry 使用明确的新身份模型。
- Hub/GHCR 不会误入新 Host Probe。
- 六条双用途源能力完整保留。
- 两条显式 GHCR 源继续留在旧 GHCR 候选池（8 条不变）。
- 所有保留的旧机制均有 owner、保留理由、退出条件和验收证据。

双模型并存与一源多 Host 不作为 3.5.4 未完成项，作为后续架构债登记。
