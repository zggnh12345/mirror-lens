# 3.5.11b 验收清单：source_realm_policy、单事务、单轨

> 状态：**代码实现完成，生产仍运行 `3.5.11a` / Schema `3.5.7`；尚未切换生产**。
> 当前代码：`3.5.11`，Canonical hash `e39e119719633ea8565bfba60f03f34e525259aa177235f97145bca9569f2611`。
> 本文所有必过项都要有可复现证据；本地 `go test ./...`、真实 3.5.7 备份迁移和运行时冒烟已执行，切换前仍需按第 2.2 节重新跑一遍。

## 1. 先固定三个词

### 过渡态干净

- 迁移时旧库只读，目标库只在临时位置；失败不发布目标文件。
- 迁移期间旧二进制不能接触目标库。
- 运行时策略修改要么全部提交，要么全部回滚，不能出现半条策略、半个 generation 或孤儿事件。
- 旧 Token 只要求**不可达**，不要求进程内存里的旧条目立即物理消失。
- 回滚使用备份库 + 旧 `secret.key`，不是“旧二进制直接打开新库”。

### 单事务

只承诺运行时数据库写入：

- `sources`
- `source_realm_policy`
- `policy_gen`
- `source_events`

必须在同一事务中完成。Token Cache 是进程内存，离线 Schema 迁移是另一条流程，二者不纳入数据库事务承诺。

### 单轨

运行时只允许：

- `source_realm_policy`（`source_id > 0`）
- `OfficialPolicy`（`source_id = 0`）

不允许旧 Host 白名单 fallback、dual-read、feature flag，以及“查不到策略就按 Host 猜”的默认值。

## 2. Schema 与迁移过渡态

### 2.1 结构检查

```sql
SELECT name FROM sqlite_master
WHERE type='table' AND name IN ('source_realm_policy','source_realm_policy_meta');

PRAGMA table_info(source_realm_policy);
PRAGMA foreign_key_list(source_realm_policy);
PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

必须满足：

- 只存在 `source_realm_policy`，不存在旧的 Realm 表或 `source_realm_policy_meta`。
- 主键是 `(source_id, host)`。
- `source_id` 外键指向 `sources(id)`，并有 `ON DELETE CASCADE`。
- `primary_realm` 只存 scheme + host，不允许 path/query/fragment/userinfo。
- `extra_realms` 是合法 JSON 数组，最多 3 个对象；`enabled=0` 也占位。
- `policy_gen > 0`。
- `PRAGMA integrity_check` 返回 `ok`，`PRAGMA foreign_key_check` 无行。

### 2.2 迁移前后检查

以真实 3.5.7 备份为输入：

```bash
sha256sum <源库> > before.sha
db-migrate migrate --in <源库> --out <目标库> --baseline 3.5.7
sha256sum <源库> > after.sha
diff before.sha after.sha          # 必须为空
```

目标库检查：

- `schema.Verify` 通过，`schema_version=3.5.11`。
- 没有 `-wal`、`-shm`、`*.tmp-*`。
- 源库 `schema_meta`、业务数据、文件字节都不变。
- 旧二进制打开目标库必须拒绝启动。
- 新二进制打开 3.5.7 旧库必须拒绝启动，不能运行时建表。

覆盖等式：

```text
repo_host 非空的源数
  = 有 (source_id, host) 策略行的源数
  + 迁移报告中列出的缺失策略源数
```

每个缺失源都必须能在报告中找到 `source_id | host | 原因 | 建议动作`。不允许“少了一行但没人知道”。

### 2.3 种子覆盖

至少检查：

- 已知 Host：`quay.io`、`gcr.io`、`registry.k8s.io`、`public.ecr.aws`、`cgr.dev`、`docker.io`。
- `lscr.io` 最终策略包含 `https://ghcr.io`，跨 Host 是显式条目。
- Artifact Registry 使用自身 Host。
- `m.daocloud.io` 作为 `public.ecr.aws` 的 Source，必须能通过探活；不能只按 `repo_host` 种子化后把自身 BaseURL Realm 漏掉。
- 已知 Host + 自定义 BaseURL（如 `ghcr.dockerproxy.com` -> `ghcr.io`）：BaseURL origin 为主，内置官方 Realm 放入 extra；这是「已知 Host + 显式 BaseURL」规则，不是按未知 Host 猜测。
- 自定义且无默认 Realm 的旧 Source：按 1.6 口径进入报告、运行时 fail closed，不能被静默补成官方 Realm。
- `ghcr.io` 必须在内置官方 Realm 表中，否则 `ghcr.io` 镜像源会被误报为 gap。

### 2.4 故障注入

迁移至少覆盖四个失败点：

1. copy 完成后、backfill 前失败。
2. backfill 写入一半失败。
3. `finalizeTargetMeta` 前失败。
4. `publishNoClobber` 失败。

每个失败都必须断言：

- 没有目标文件。
- 没有临时文件或 `-wal` / `-shm`。
- 源库 SHA 不变。
- 旧库仍可正常打开。

## 3. 单事务核对

### 3.1 事务矩阵

| 操作 | 同事务必须包含 | 回滚断言 |
|---|---|---|
| `AddSource` | `sources`、策略行、`source_events` | 策略插入失败时源不存在 |
| `SetRepoHost` | 删旧策略、建新策略、`repo_host`、`policy_gen++`、健康/恢复清理、事件 | 失败时旧 Host 策略和旧 Host 全部保持 |
| 禁用/启用 | `status`、`policy_gen++`、事件 | 失败时状态和 generation 不变 |
| 归档 | `status`、`policy_gen++`、事件 | 失败时仍可用/状态不变 |
| 删除 Source | 源、策略、相关记录、事件 | 失败时源和策略都还在 |
| 修改主 Realm | 策略行、`policy_gen++`、事件 | 失败时旧主 Realm、extra、generation 不变 |
| 修改 extra Realm | 策略行、`policy_gen++`、事件 | 超过 3 个时整体拒绝 |
| 凭据轮换 | 凭据 generation、策略失效依据 | 旧 Token 不可达 |

### 3.2 静态检查

重点入口：

- `internal/store/store.go:443` `AddSource`
- `internal/store/host.go:77` `SetRepoHost`
- `internal/store/store.go:737` `DeleteSource`
- 禁用、归档、状态变更的写入路径
- 新增的策略修改入口

逐项确认：

- 策略写操作只拿 `tx`，不拿 `s.db`。
- `policy_gen++` 和策略行、业务行、事件在同一事务。
- 额外 Realm 上限 3 在同一事务里校验。
- `source_events` 不是提交后异步补写。
- `DeleteSource` 显式删策略，不只依赖 `ON DELETE CASCADE`。
- `SetRepoHost` 的旧策略删除、新策略建立、generation 增加不能分成三次提交。

`db.SetMaxOpenConns(1)` 只能证明连接串行化，不能证明事务边界正确，不能作为单事务证据。

### 3.3 失败注入测试

在隔离测试库里用 SQLite trigger 注入失败，不进入生产路径：

```sql
CREATE TRIGGER fail_policy_insert
BEFORE INSERT ON source_realm_policy
BEGIN
  SELECT RAISE(ABORT, 'inject policy insert failure');
END;
```

至少验证：

- `AddSource` 失败后 `sources` 没有半条记录。
- `SetRepoHost` 失败后旧策略、旧 `repo_host`、旧 generation 原样保留。
- 禁用/归档失败后状态和 `policy_gen` 都不变。
- 策略修改失败后主 Realm、extra、generation、事件全部回滚。
- `DeleteSource` 失败后源和策略都还在。

### 3.4 并发

两个 goroutine 同时修改同一 `(source_id, host)`：

- 只能有一个成功提交，或两个按顺序成功提交。
- `policy_gen` 单调递增，不能回退。
- 不能丢失后一次修改。
- 不能产生重复主键或两条主 Realm。

## 4. 单轨核对

### 4.1 静态扫描

11b 完成后，生产代码应基本搜不到旧运行时符号：

```bash
rg -n 'LegacyHostPolicy|realmAllowedForHost|parseBearer|DefaultRealmsFor|RegistryHostProbe\.Realms|runner\.Options\.Realms' internal --glob '*.go'
```

允许保留的只有：

- `OfficialPolicy` 的种子。
- 迁移工具的只读旧种子。
- 测试显式注入。

`DefaultRealmsFor` 不能再作为 `sourceID > 0` 的 fallback。

### 4.2 运行时行为

必须逐项实测：

- `sourceID = 0`：走 `OfficialPolicy`，官方认证正常。
- `sourceID > 0` 且有策略：正常认证。
- `sourceID > 0` 且无策略：返回 `503` + `auth_policy_missing`，不是 401。
- 第三方 Source 拿到官方 Realm：拒绝。
- 官方 Source 拿到第三方 Realm：拒绝。
- 自定义 Source 只允许策略明确的 Realm。
- `lscr.io -> ghcr.io` 可用。
- `m.daocloud.io` 作为 `public.ecr.aws` Source 可用。
- 策略中的 Realm 带 userinfo、`http://`、通配符、IP 字面量时必须拒绝。

### 4.3 Probe 与 Gateway 同轨

对同一个 `(source_id, host)`：

- `StorePolicy.Resolve`
- Gateway 实际请求
- Probe 实际探活

三者拿到的 `LogicalHost`、`Realms`、`PolicyGen` 必须一致。不能 Probe 用一套、Gateway 用另一套；不能只测最终 200，必须同时测 allow 和 deny。

### 4.4 Token Cache

构造同一 Realm / Service / Scope，但不同 `SourceID`、不同 `Host`、不同 `PolicyGen` 的请求：

- 必须得到不同 key。
- 修改策略后 `policy_gen++`，旧 Token 不能再命中。
- 旧条目留在内存中可以，但必须不可达。
- 并发刷新同一个完整 key 只能打一次 Token 端点。

## 5. 迁移报告

报告至少包含：

```text
source_id | host | 原因 | 建议动作
```

完成条件：

- 报告为空，或每个缺失源都有处理记录。
- 报告不能把自定义 Host 写成“已自动修复”。
- 报告不能把“无策略”写成“官方 Realm 回退”。
- 报告数据不包含 Token、Authorization、查询参数或用户凭据。
