## 原缺陷

`time.AfterFunc(3s, cancel)` 与 `resp.Body.Read` 并发，`Stop()` 返回 false 只说明
回调已启动，不保证它没在读到首字节后取消 ctx，导致已接管的 body 中途断开。

## 裁决语义（准确表述）

`select` 在多分支同时就绪时不保证优先级。本实现不依赖这一点：

- 超时回调只向 cap-1 通道非阻塞投递信号，不 cancel、不关 body。
- 外层 `select` 选中数据 → 数据胜出。
- 外层 `select` 选中超时 → 调用 `afterTimeout(ch)` 再做一次非阻塞接收；
  有值则数据胜出，空则超时胜出并执行 `onTimeout`。

线性化点是 `afterTimeout` 的内层 `default` 被执行的那一刻：此刻 channel 有值
即数据胜，否则超时胜。**不是**“同时就绪必然数据优先”的全局保证。

## Body 与 Lease 生命周期

请求 context 在创建后立即 `l.BindCancel(cancel)`，这样 `Lease.Reclaim("stall")`
能先取消请求、让阻塞的 Read 退出，再关底层 Body；否则 90 秒看门狗会卡在
`leaseBody.Close` 里，名额永远不释放。失败出口的顺序固定为 `cancel()` → `unbind()` → `Body.Close()` → `releaseLease`：
先取消让底层 Read 退出，否则 Close 可能阻塞，而 Reclaim 此时已找不到
取消函数。成功路径把 unbind 交给 `cancelOnClose`。

关闭顺序按场景区分：

- 正常读完/调用方 Close：`Body.Close`（释放 lease、复用连接）→ `unbind` → `cancel`。
- Reclaim/停滞/超时：`cancel`（由 Reclaim 触发）→ 底层 Read 退出 → `Body.Close`。

首读错误传播：`Read` 允许同时返回 `n>0` 和非 nil error。首字节作为 `first`
交付后，该错误由 `pendingErrBody` 在下一次 `Read` 返回，不能被当成正常 EOF；
零长度 `Read` 直接返回 `(0,nil)`，不消费待交付错误。

看门狗必须在 `pendingErrBody` 包装之前启动，否则 `resp.Body.(*leaseBody)`
断言拿到的是 `*pendingErrBody`，90 秒看门狗不会启动。

换源接管走读循环直用路径，不经过 `stream.go` 的 `*leaseBody` 断言，因此
`trySwitch` 自己启动 90 秒空闲看门狗。
